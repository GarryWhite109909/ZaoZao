## 7.1  三个最常用的任务（5 分钟上手）

### 7.1.1  任务 A：扫描一段代码或一个文件

1. 打开 `http://localhost:8765` → 进入**扫描工作台**；
2. 「粘贴代码」标签 → 选语言 → 粘贴代码 → 点「开始分析」；
   或者「上传文件」标签 → 拖入一个或多个代码文件；
3. 等待十几秒（单文件典型 5~15 秒，长文件更久），结果区给出：是否漏洞、CWE 类型、风险等级、漏洞原理说明、修复建议。

> ![图 7-2 扫描结果详情](assets/ui_scan_result.png)

### 7.1.2  任务 B：批量扫描一个项目并导出报告

1. 扫描工作台 →「上传文件」→ 一次拖入整个模块的代码文件（最多 200 个）；
2. 点「开始分析」，页面实时显示进度（扫完一个出一个）；
3. 完成后点「**下载报告**」，得到一份 Markdown 报告：漏洞汇总表 + 每个文件的详细结果 + 修复建议。

### 7.1.3  任务 C：扫描 GitHub 仓库或网页

- 「GitHub」标签 → 粘贴仓库地址 → 设置最多扫描文件数（网页端默认 20，大仓库建议自己限定）→ 开始。系统浅克隆仓库（只读、120 秒超时、扫完即删，不会在用户机器上留下仓库副本）；
- 「URL」标签 → 输入网页地址 → 系统抓取页面里的脚本代码逐个分析。

## 7.2  读懂扫描结果

### 7.2.1  四种判定，各有含义

| 判定 | 含义 | 应当做什么 |
|---|---|---|
| **发现漏洞** | 系统确信存在漏洞（模型多次采样一致 + 通过证据校验） | 按修复建议处理 |
| **安全** | 已实际复核且未发现问题（工具没召回可疑点，且该文件确实进入了复核） | 常规流程即可 |
| **需人工复核** | 系统有怀疑但证据不足，**故意不替用户下结论** | 花一分钟看一眼标注位置 |
| **未复核** | 工具零召回、且本轮注意力预算**没有覆盖到**该文件（LLM 从未被调用） | 按需人工查看；**不要把它当作“已确认安全”** |

> **「需人工复核」不是出错，是设计**：本系统的原则是“宁可多一道人工复核，也不漏报真漏洞、不错杀不确定的判定”。复核结果会单列，不计入安全评分。
>
> **「未复核」同理**：该文件本轮未被分配分析预算、从未进入分析——保留“未复核”这一状态，正是为了让“没有看过”如实可见，而不是被界面渲染成“安全”。

### 7.2.2  每条结果包含什么

- **CWE 类型**：漏洞编号与名称（如 CWE-89 SQL 注入）；
- **风险等级**：Critical / High / Medium / Low（影响安全评分扣分）；
- **Source & Sink**：污点数据的来源行与触发行（有数据流的漏洞才显示），配合编辑器插件可直达代码行；
- **漏洞说明**：自然语言解释“为什么这是漏洞”；
- **修复建议**：行号锚定的局部修复建议；
- **信任层明细**：裁决档位、一致性置信度、共形预测、反事实验证与证据门；低置信候选列入人工复核清单；
- **模型原始输出**：可折叠查看，用于核对。

### 7.2.3  安全评分

系统按 Critical 每项 -8 / High -8 / Medium -4 / Low -2 / Info -0.5 累计扣分给出安全评分；“需人工复核”与“未复核”两类样本均**单列展示、均不参与扣分**（与第二篇 §2.3.3 同口径）。

### 7.2.4  为什么结果可能和 Bandit / Semgrep 不一样

三个常见原因，都属正常：

1. **它把“安全写法”放行了**：参数化查询、`subprocess` 列表参数、`shlex.quote` 等有效防御会被识别，不再像规则工具那样照报误报；
2. **它报了规则工具不报的**：需要理解数据流 / 业务语义的漏洞（认证缺失、信任边界绕过等），规则工具天然覆盖不到；
3. **它给出“需人工复核”而不是硬判**：低置信判定会被送人工复核，而不是随机选边。

### 7.3.1  扫描工作台的四种输入方式

| 输入方式 | 操作 |
|---|---|
| 粘贴代码 | 选语言下拉框 → 粘贴源码 → 「开始分析」 |
| 上传文件 | 拖拽到上传区或点击选择（支持多文件）→ 「开始分析」→ 批量时显示实时进度 → 完成后可「下载报告」 |
| URL 扫描 | 输入目标站点 URL → 「开始分析」→ 自动抓取页面脚本逐个扫描，结果显示页面标题、发现脚本数、各脚本分析 |
| GitHub 仓库 | 输入仓库地址 → 设置最大扫描文件数（默认 20）→ 「开始分析」→ 浅克隆 → 遍历 → 批量扫描 → 显示汇总 |

### 7.3.2  高级选项

在扫描工作台点击「高级选项」可展开：

| 选项 | 说明 |
|---|---|
| 多模型投票 | 勾选后选择 ≥ 2 个模型，系统顺序加载各模型并投票聚合结果（更准但更慢） |
| 两阶段扫描 | 系统**唯一**扫描路径（工具召回 + LLM 自一致率裁决），无需勾选即生效；本开关仅控制下方采样数设置是否可调 |
| 自一致率采样数 | 两阶段 LLM 裁决的采样次数（1~10，默认 3）。采样越多越准、越慢 |

### 7.3.3  API 文档

后端提供完整的 REST API，访问 `http://localhost:8765/docs` 查看 Swagger 交互文档。

调用示例（单文件分析）：

```bash
curl -X POST http://localhost:8765/api/analyze \
  -H "Content-Type: application/json" \
  -d '{
    "code": "import sqlite3\ndef get_user(name):\n    c = sqlite3.connect(\"db\").cursor()\n    c.execute(\"SELECT * FROM users WHERE name='\''\" + name + \"'\''\")",
    "language": "python",
    "filename": "vuln.py"
  }'
```

## 7.4  输入限制与支持范围

支持 7 种代码语言及对应文件类型；单段代码最多 200 万字符、单文件最大 2 MB、单次批量最多 200 个文件（总计 10 MB）、GitHub 扫描默认 20 个文件（上限 500）。完整限制表见附录 C；超限会被前端直接拦截提示（后端再做一道同样的校验，返回 413），不会白等一场。

## 7.5  高级功能

扫描工作台「高级选项」里：

「自一致率采样数」与「多模型投票」两张开关的作用机制与建议见 §7.3.2；这里补充第三个：

| **RAG 知识库** | 检索内置的漏洞知识注入判定过程，增强可解释性 | 默认关；开启后推理时间增加 <2% |

## 7.6  在编辑器里用（VS Code / IntelliJ 插件）

**前置**：后端服务已启动并保持运行（插件只是“遥控”后端，后端关了插件就不能用）。

### 7.6.1  VS Code

1. **安装**：VS Code → 扩展面板 → `⋯` → **从 VSIX 安装** → 选软件包内的 `vuln-scanner-1.3.0.vsix`；
2. **用法**：打开代码文件 → 右键 →「凿凿: 分析当前文件」；结果面板除漏洞判定与修复建议外，还展示**信任层明细**（每条候选的置信度、裁决档位、共形预测、反事实验证、证据门），低置信候选单独列入“需人工复核”；每个确认的漏洞按行号标**红色波浪线**（可配置关闭）；
3. **批量**：命令面板（`Ctrl+Shift+P`）→「批量扫描工作区」；
4. **常用设置**（搜 `vulnScanner`）：后端地址 `backendUrl`、保存时自动扫描 `autoScanOnSave`（1.5s 防抖）、批量文件上限 `workspaceMaxFiles`。

> ![图 7-5 VS Code 插件](assets/vscode_plugin.png)
>
> **图 7-5  VS Code 插件：行级诊断与信任层明细**（确认的漏洞按行号标红波浪线；右侧面板逐条候选展示裁决档位、置信度、CWE 类型与共形预测 / 反事实 / 证据门状态；与图 6-8 为同一界面）

### 7.6.2  IntelliJ IDEA

1. **安装**：`File → Settings → Plugins → ⚙ → Install Plugin from Disk...` → 选 `vuln-scanner-0.1.0.zip` → 重启；
2. **用法**：编辑器中选中代码（不选则扫整个文件）→ 右键 → **凿凿 漏洞扫描**（或 `Ctrl+Alt+Shift+V`），结果以气球通知弹出：结论、修复建议与信任层摘要（置信度 · 裁决档位 · 共形预测 · 反事实 · 证据门）。

> IntelliJ 版定位为演示版：无波浪线标记与批量扫描。

## 7.7  命令行速查

无需打开网页，直接复用扫描引擎（**不需要**先启动后端服务）：

```bash
python -m app.launcher.vuln_scanner_cli <命令>

health                                    # 健康检查（模型/服务是否可用）
scan app/main.py                          # 扫单个文件
scan app/main.py --format json            # 输出 JSON（方便脚本处理）
batch ./src --output report.md            # 批量扫目录 + 导出报告
batch ./src --limit 20 --no-recursive     # 限量、不递归
url https://example.com                   # 扫网页脚本
github <仓库地址>                          # 扫 GitHub 仓库（浅克隆）
```

通用参数：`--model <模型名>` 切模型、`--rag` 开知识库、`--format text|json`。

适合接进 CI 或脚本里做提交前检查（扫描失败时退出码为 1）。

## 7.8  离线使用与模型管理

- **完全离线运行**：联网只是首次下载依赖和模型时需要。系统运行期不访问外网（HuggingFace 强制离线模式、Semgrep 规则已随软件本地化）；
- **换 / 加模型**：Web 界面右上角模型管理抽屉可拉取、删除、切换模型（带实时下载进度）；命令行方式：`python -m app.launcher.vuln_scanner_cli --model <模型名> <命令>`，或设环境变量 `VULN_SCANNER_MODEL`；

> ![图 7-6 模型管理抽屉](assets/model_drawer.png)
>
> **图 7-6  模型管理抽屉**（当前活动模型、已安装模型、可拉取模型列表与「拉取」入口；下载带实时进度条；与图 6-9 为同一界面）
- **模型有两档精度**（界面会显示当前形态）：

## 7.9  常见问题 FAQ

| 问题 | 处理 |
|---|---|
| 扫描很慢（>60 秒/文件） | 大概率在用 CPU 推理。看启动日志 `[硬件检测]`；有独卡却走 CPU 时重启启动脚本，或显式设 `VULN_SCANNER_BACKEND=ollama` |
| 结果全是“需人工复核” | 模型可能没正确加载：`python -m app.launcher.vuln_scanner_cli health` 检查；确认模型名一致 |
| 报显存不足（OOM） | 降低上下文窗口：设置环境变量 `VULN_SCANNER_NUM_CTX=4096` |
| 启动报端口被占用 | `netstat -ano \| findstr 8765`（Windows）/ `lsof -i :8765`（Linux/macOS）找到进程杀掉 |
| VS Code 插件没反应 | 确认后端已启动且 `http://localhost:8765/api/health` 能访问；核对插件设置 `vulnScanner.backendUrl` |
| 波浪线没显示 | 设置里 `vulnScanner.markDiagnostics` 需为 `true`；个别无法定位到行的情况只展示面板结果 |
| Linux 上模型没进项目目录 | 系统自带 ollama 服务抢占：执行一次 `sudo systemctl disable --now ollama` 再重启脚本 |
| RAG 相关报错 | 多为知识库未初始化或旧向量库需重建（见第八篇故障排查） |

## 7.10  已知边界（使用前请读一遍）

我们对能力边界持如实态度，以下是用户应该知道的：

1. **速度**：语义分析的成本是时间——单文件典型 5~15 秒，长文件（自动切片后逐段分析）可能到分钟级。它定位是“审计增强”，不是秒级 lint；
2. **“需人工复核”会占一定比例**：系统对没有确定性证据的判定选择保守（宁可交给人）。这是防漏报、防误判的设计代价，不是故障；
3. **两类漏洞是弱项**：① 跨文件的复杂攻击路径（只扫单文件时看不到全局数据流）；② “缺失型”漏洞（认证缺失、CSRF、竞态等“该有而没有”的问题）——此类没有确定性校验手段，置信不足时都会转人工复核；
4. **两档部署形态精度不同**：高精度形态（Transformers + LoRA）优于发布模型（Ollama 量化形态）。界面会如实显示当前用哪一档；
5. **结论是辅助，不是法律**：所有“安全”判定都建议结合业务上下文理解——系统能看懂代码语义，但看不懂用户没写出来的需求约束。
