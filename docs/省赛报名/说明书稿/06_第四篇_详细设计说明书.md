## 4.1  Stage 1 召回设计

> ![图 4-1 自研工具链](assets/self_developed_tools.png)
>
> **图 4-1  自研工具链流水线**（从代码输入到 SARIF 导出的完整自研工具链；8 个工具中 7 个为零依赖实现，第 8 个 `ExternalScanner` 是唯一封装第三方工具的适配层）

### 4.1.1  自研工具 1：TaintTracker（污点分析）

基于 tree-sitter 的轻量污点分析（v2，线性数据流）：

- 按语句顺序扫描：source 赋值给变量 v → v 入污染集；赋值右值含污染变量 → 左值入集；
- 只有 sink 调用的参数里出现污染变量才报路径，不再做 source×sink 笛卡尔积；
- 消毒识别：仅类型无关函数 `int()/float()/bool()/shlex.quote()/intval()/filter_var()` 包裹、SQL 参数化 → 标记 sanitized；
- 单文件过程间摘要（两遍法）：第一遍生成摘要，第二遍在调用点拼接；
- 支持语言：Python / JavaScript / TypeScript / Java / PHP。

**关键实现细节**：

| 细节 | 设计要点 |
|---|---|
| 跨语言语义消歧 | 同一调用名在不同语言映射不同漏洞类型——JS/TS 中 `exec(` 对应 Command Injection，Python 中对应 Code Injection |
| 危险度排序 + 截断 | 7 种漏洞类型按危险度赋值（Command/Code/反序列化=4，SQL/SSTI=3，XSS/路径=2），每作用域最多输出 50 条路径，按 `(-risk, sink_line, source_line)` 排序截断 |
| 语境安全判定 | ① Command Injection：`subprocess` 列表参数不经 shell 解析即安全；② Template Injection：纯 kwargs 值插值安全；③ Path Traversal：白名单 + `abspath/realpath` + `startswith` 防御链三者共存判安全 |
| Web 框架参数自动 source | Python 检测 `@app.route`/`@api.route`/`@router.get` 装饰器；Java 检测 `@RequestParam`/`@PathVariable`/`@RequestBody` 等注解，参数视为 source 种子 |
| f-string 插值正确处理 | 逐字符扫描 + `fstring_brace_depth` 计数处理嵌套花括号，整体保留 `{interpolation}` 不剥离，避免污点传播断裂 |
| 跨语言赋值语法支持 | Python walrus（`:=`）/named_expression/augmented_assignment、JS/TS/Java/PHP 的各类赋值节点逐一适配；复合赋值运算符（`+=` / `.=` / `??=` / `<<=` 等 15 种）单独处理——其右值为表达式，若按普通赋值只取第一个子节点会漏掉污点来源 |
| 补充 source/sink 词表 | PHP 的 `->loadHtml(` 归为 XSS sink 等（按语言限定，避免跨语言误匹配） |

**类型作用域陷阱（历史教训）**：全局消毒表曾把 `html.escape`/`urllib.quote`/`re.escape` 等**仅对特定类型有效**的函数应用于所有污染类型，导致 SQL 拼接处包 `html.escape` 的流被误判“已消毒”而丢弃（跨类型漏报）；且 `escape(` 会匹配 `unescape(`（反防御）。现只保留类型无关的消毒函数，HTML/URL 编码类消毒改由 LLM 裁决层判断。

### 4.1.2  自研工具 2：Prefilter（正则预筛）

- 命中安全模式且未命中漏洞特征 → 判安全；仅命中漏洞特征 → 判漏洞；两者都命中或都没命中 → 交 LLM 复核；
- 硬编码凭证标记：`has_secret_marker` 命中时不直接判漏洞，而是抑制安全判定，强制 LLM 复核；
- **两阶段架构中 Prefilter 只产出候选，不短路终判**。

**关键实现细节**：

| 细节 | 设计要点 |
|---|---|
| 规则元数据统一表 | `PREFILTER_RULE_INFO` 每条规则统一关联 taint_type/cwe/risk/severity，`scanner.py` 与 `two_stage_scanner.py` 共用同一数据源，避免规则映射漂移 |
| 字符串字面量感知 | 线性扫描定位配对括号时跟踪 `in_str` 状态跳过字符串内容 |
| 长文件安全规则门控 | `longfile_threshold=150`，超过此行数跳过安全规则只跑漏洞规则——防止“前半段参数化查询掩盖末尾隐藏漏洞” |
| 高置信漏洞规则覆盖安全特征 | `pickle.loads`/`yaml.load` 等高置信规则即使与安全特征共存也直接判漏洞 |
| 硬编码凭证正则修复 | 原 `\b` 词边界在 `DB_PASSWORD` 等下划线前缀上失效，修复为 `(?<![A-Za-z0-9])` 负向后行断言 |

### 4.1.3  自研工具 3：CodeSlicer（AST 代码切片）

文件 < 150 行不切片；≥150 行按顶层函数/类方法切分，每个切片含上下文头 + 类骨架 + 当前函数完整代码。

**切片聚合语义**：任一 chunk 有漏洞 → 整文件判漏洞（保守策略，宁误报不漏报），取风险最高的 chunk 结果。

**批量解码正确性**：`generate_batch` 必须**左 padding**（decoder-only 批量解码右 padding 时短序列的“最后一个 token”是 pad，生成从 pad 位置继续产生不可靠输出）；批量失败（如 OOM）**逐条回退**而非整批报废。

### 4.1.4  自研工具 8：ExternalScanner（外部工具封装层）

封装 7 种第三方安全工具，统一为五类扫描能力，输出归一化为 `ExternalFinding`（rule_id/severity/type/位置）：

| 能力 | 工具 |
|---|---|
| SAST | Bandit / Semgrep |
| Taint | Semgrep taint |
| Secrets | Gitleaks / detect-secrets |
| SCA | pip-audit |
| IaC | Trivy config + trivy fs |

**关键实现细节**：

- **本地规则优先 + 在线回退**：优先用本地化规则（离线可用），缺失回退官方 registry 包；
- **规则 ID 映射顺序敏感**：`codei` → Code Injection 必须先于 `cmdi` 判断，否则 `codei_xxx` 规则被误归为 cmdi；
- **Semgrep taint 字段三级降级**：依次尝试 `extra.metavars` → `extra.dataflow_trace` → `extra.taint_source/sink`；semgrep OSS 1.172 taint JSON 不含以上任何字段，source 位置由 TaintTracker 或裁决层补全；
- **Trivy 离线标志**：`trivy fs` 必须带 `--skip-db-update`、`trivy config` 必须带 `--skip-policy-update`——实测带参数 0.4s、不带 60.1s；
- **自研 Semgrep 召回规则六件套**（`graduation_project/semgrep_rules/`）：四条 `mode=taint` 型（`sqli_taint` 28 pattern / `cmdi_taint` 32 / `xss_taint` 27 / `codei_taint` 18）+ 两条结构化补位型（`go_cmdi_shell` 22 / `c_cmdi_system` 8），均整文件扫描（修复“长文件切片后 chunk A 的 source 与 chunk B 的 sink 被割裂”），注释明文“本规则只做召回，不做终判”。

  **结构化补位规则的动机**（两例，均源于语言审计实测）：

  | 规则 | 官方规则缺口 | 补位判据 |
  |---|---|---|
  | `go_cmdi_shell` | 官方 `dangerous-exec-cmd` 只匹配 `exec.Cmd{...}` 结构体字面量，**完全不匹配 `exec.Command(...)` 函数调用**——后者才是 Go 主流写法（语料池实测 `exec.Command(` 4 个样本 vs `exec.Cmd{` 0 个） | 检测「执行族 API + shell 解释器」组合结构 |
  | `c_cmdi_system` | 安全审计包中 C 规则 9 条全指向内存安全（格式化串 / 随机数 / 竞争），**命令注入零覆盖** | 检测 `system(cmd)` / `popen(cmd, mode)` / `execvp(cmd, ...)` 等执行族 API 且**命令串非常量字面量**；判据有 CERT C POS30-C（“Do not use the system() function”）背书 |

  > `c_cmdi_system` 采用**结构化检测而非 taint**，原因：C 的典型链经 `snprintf(cmd, ..., argv[1])` 以**输出参数**写入，semgrep taint 无法跨函数参数传播（语言固有）。非常量命令串交给 Stage 2 裁决——LLM 能看到 `cmd` 的构建处与来源。

## 4.2  Stage 2 裁决设计

### 4.2.1  自一致率置信度

对同一 finding 以 `temperature > 0` 采样 N=3 次，置信度 = 判真票数 / 有效票数。

**无效票语义与文件级 None 传播**：

- 分母用**有效票**（`votes_true + votes_false`）而非 N——解析失败/推理出错的票不代表“否决”；
- 全部票无效时 `confidence=0`、`confirmed=False`，由聚合层判 `None`（需复核）；
- 文件级聚合统一把低置信确认/平票/低置信否决转成 `has_vulnerability=None`，防止“需人工复核”信号在汇总层被掩盖成“安全”。

### 4.2.2  裁决档位四分类

每个 finding 裁决后按 `(confirmed, confidence)` 定档：

| 档位 | 条件 | 去向 |
|---|---|---|
| `confirmed_vulnerability` | 判真且 conf ≥ 0.8 | 直接判漏洞 |
| `confirmed_review` | 判真但 conf 0.5~0.8 | 进人工复核清单 |
| `dismissed_safe` | 判假且 conf ≥ 0.8 | 排除 |
| `dismissed_review` | 判假但 conf 0.5~0.8 | 进人工复核清单 |

阈值只有一个：`_CONF_AUTO = 0.8`。**≥ 0.8 直接采信，其余一律进人工复核**（低置信确认、平票、解析失败同档处理）。

> 为什么不做“三档阈值”：N=3 时自一致率的可能取值只有 `{0, 1/3, 2/3, 1}` 四个点，任何介于 1/3 与 2/3 之间的边界都不产生行为差异。写一个不存在的 0.5 档只会让读者以为存在“低置信也算结论”的中间态，故代码中只保留一个边界。若将采样数 N 提高到 5~10，取值空间变密，才需要重新设计分档。

### 4.2.3  裁决上下文的行号精确对位

裁决 prompt 中 source/sink 的行号必须能直接对位源码。切片由“文件级上下文头 + 函数体”拼装：头部单独输出且不带行号，函数体从原文件按行截取并加 `N| ` 前缀；整文件 chunk 禁止拆分（否则代码以 `\n` 结尾时 split 多出的尾部空串会让首行被误判为 header）。

### 4.2.4  训练对齐裁决格式

裁决 prompt 使用训练对齐的 `has_vulnerability` 格式（与 α0.5 训练格式一致）。**历史缺陷（已修复）**：解析器曾只认 `is_confirmed` 字段，而 prompt 要求输出 `has_vulnerability`——注释声称“双格式兼容”但代码从未实现该分支。后果：真实 CVE-fix 复杂输入下模型遵循 prompt 输出 → 3 票全 invalid → 候选裁决全转 review，recall 被误判为“工具零覆盖”。补齐 `has_vulnerability` 解析分支后，两阶段 CVE-fix recall 由 **0.556 提升至 0.882**（同组态前后对比：TP 5→15，review 11→3）。

> **数字口径提醒**：真实 CVE-fix 片段（20 段）上的两阶段 recall 有两个数值并存，**各自组态不同，不可混用**：
>
> | 数值 | 组态 | 出处 |
> |---|---|---|
> | **0.882** | 解析器修复后首轮（2026-08-20），本轮内部对比口径 | 上述“0.556 → 0.882” |
> | **0.941** | 官方口径 anchor 轮（2026-09-01），已纳入统一打分体系 | 见第三篇 §3.6.1 |
>
> 第三篇 §3.6.1 的系统级成绩表引用的是 **0.941（anchor 口径）**；本节描述的是解析器缺陷修复的**效果对比**。两者不矛盾，并排出现时须注明组态。

## 4.3  2.5 代信任层

> ![图 4-2 2.5 代信任层全流程](assets/trust_layer_25.png)
>
> **图 4-2  2.5 代信任层全流程**（Stage 2 裁决输出 → 三层门控（共形预测 / 反事实验证 / 确定性证据门）→ 信任分级 A-E → 五重回填门控 → 信号回填 / 负向记忆（只降权）/ 人工复核）

信任层作用于 Stage 2 裁决之上，由**三个门控层 + 一套分级回填机制**构成：

| 层级 | 名称 | 类型 |
|---|---|---|
| Layer 1 | 共形预测 | 统计门控 |
| Layer 2 | 反事实验证 | 因果门控 |
| Layer 3 | 确定性证据门 | 静态门控（零 LLM 成本） |
| 回填 | 信任分级 A-E + 四重门控 | 写入侧防污染 |

> 图示的三层门控互补关系：统计门控与因果门控负责“判断质量”，确定性证据门负责在过度自信的推理后端上兜底；三者输出汇入 A-E 分级，只有 A/B 级能通过四重门控回填工具记忆。

### 4.3.1  确定性证据门（零 LLM 成本静态核验）

与推理后端无关、零 LLM 成本的确定性校验。设计动因：transformers（bf16）后端 FP 全部是“全票但错”——共形/反事实验证依赖的投票分歧信号在高精度后端上不出现（Q4 量化噪声天然压制模式匹配型捷径，bf16 保留了过度自信），统计门结构性失明。

| 门 | 判据 |
|---|---|
| `sink_defended` | sink 邻域（前 4 后 3 行）已含该漏洞类型的已知防御特征（参数化 execute / `shlex.quote` / `html.escape` / `realpath` / `autoescape` / `json.loads`）→ 模型没识别已有防御 = 疑似模式匹配误报 |
| `no_input_entry` | 纯顶层字面量脚本且无外部输入入口（request/input/argv/environ），且**仅对无任何函数/类定义的模块级脚本**应用 → 污点无从产生 |

命中**不否决**（不判 False），仅把该 finding 排除出“直接判漏洞”依据转人工复核——门是保守的：宁可 review 不错杀 TP（真漏洞的 sink 邻域不会出现完整防御特征，真污点文件必有输入入口）。

**生效语言范围（如实声明）**：本门目前仅覆盖 Python / JavaScript / TypeScript 三种语言——防御特征库只有这三种语言的签名。Java / PHP / Go 样本不走本门，其兜底依赖 Layer 2 反事实验证。扩语言时须先补对应防御签名再扩白名单，否则“签名查不到”会退化为无条件跳过，等于白扩。

### 4.3.2  Layer 1：共形预测（统计门控）

**机制**：以标签条件非一致性分数做三分类预测 `{漏洞}` / `{安全}` / `{不确定}`：

- 非一致性分数：`s(x, 漏洞) = 1 − 判漏洞比例`、`s(x, 安全) = 判漏洞比例`；
- 全无效票特殊处理：`valid = 0 → s = 1.0`（全部票解析失败时对两个标签都“完全不像”，天然落入不确定）；
- 在带真实标签的校准集上拟合标签条件分位数阈值（`alpha=0.1` 对应 90% 目标覆盖率），阈值随模型导出持久化；
- 分位数线性插值 `idx = level*(len+1) − 1`，`predict` 用 `s ≤ q + 1e-9` 浮点容差；
- **加载失败可审计降级**：文件缺失或解析失败时返回未校准状态，预测全部落入“不确定”并回退旧投票逻辑，而不是抛异常中断扫描。

**校准的 exchangeability 前置条件与当前状态（如实声明）**：

覆盖率保证成立的前提是“校准集与生产分布可交换”。项目在自查中发现：此前生产端自动加载的校准文件是在**同一测试集**上拟合的（in-sample），该前提被破坏、“90% 覆盖率”不成立。处置是**把该文件移出自动加载路径**（保留存档、不再参与生产推理），并让扫描器在未显式指定校准源时保持未校准。

因此**当前生产组态下 Layer 1 处于未校准状态**：不做统计裁决，全部判定交由后续门控与投票逻辑处理。这一取舍的理由是：宁可不宣称一个不成立的统计保证，也不用一个来源不干净的阈值去影响判定。

**定位说明**：本层的价值在于它提供了一个**与判定阈值解耦的统计门控接口**——一旦获得独立同分布的校准集（例如用滚动开发集校准），即可在不改动上下游的前提下启用。它不构成本系统结论正确性的必要条件。

### 4.3.3  Layer 2：反事实验证（因果门控）

在 sink 行内注入防御后重判，区分“真理解”与“模式匹配”：

- **防御模板最小化设计**：仅对 sink 行内做消毒包裹（f-string 加 `shlex.quote`、字符串拼接包裹、execute 拼接改参数化、单引号拼接 `replace("'","''")`、open 包 `realpath`、补 `autoescape`、`pickle.loads` 改 `json.loads`），不破坏代码结构保证语法正确；
- **SQL 扰动“语义保持”**：改参数化时**保留原查询字符串**（`.execute(原查询串, (变量,))`）——原实现把查询整体改写会让模型误判“换了查询逻辑”而非“加了参数化”，扰动失去因果检验意义；
- **`already_defended` 范围限定**：判定“原始代码是否已含同类防御”限定在 source→sink 区间（source 未知时退化为 sink 前 15 行窗口），不做全文搜索；
- **finding 级裁决**：验证用 finding 级 triage prompt（只裁决本 finding），不用开放扫描 prompt；
- **翻转判定用单次低温裁决**（不 N 采样，省 5 倍推理）；
- **仅 `already_defended` 才降级**：真漏洞扰动后仍判漏洞（flipped=False）是正确行为，绝不能降级。

### 4.3.4  信任分级回填（工具-模型自适应闭环）

> ![图 4-3 信任分级回填门控](assets/trust_graded_feedback.png)
>
> **图 4-3  信任分级回填门控**（A-E 分级 → 五重回填门控 → 回填工具记忆 / 转为负向记忆（只降权）/ 转人工复核 三条去向）

模型输出按判定质量分 A-E 级，只有 A/B 级（判定正确）可回填，C/D 级反向使用（D 级误报转为负向记忆）。**回填写入发生在“最终结论确定之后”**——即聚合完成、三道门控都已生效之后，用最终采信结论而非模型原始投票作为写入依据。

回填门控（**五重**，前四重防“模型不自信”，第五重防“模型自信但错”）：

0. **与模型无关的证据门（前置否决）**：最终结论为“需人工复核”、或该判定被证据门拦截、或反事实验证判存疑时，**一律拒收**——这类判定正是“模型可能错了”的信号，不能作为工具记忆的依据；
1. **全票门槛**（`votes == N`）；
2. **跨样本聚合**（≥2 独立文件）；
3. **双向可撤销**（高置信否定清零已积累确认）；
4. **独立验证集门控**（待学习池特征须经独立验证集复验才转正）。

> 门控 0 的必要性来自一个实测现象：在高精度推理后端上，模型的误报形态恰恰是“三次采样全票确认”——全票反映的是“模型很自信”，与“模型很可能对”是两件事。只用投票一致性做门槛，等于用一个与已知失效模式正交的量去设防，因此必须叠加与模型无关的证据。

**关键实现细节**：

| 细节 | 设计要点 |
|---|---|
| 双向可撤销 | 高置信确认 ≥ 2 个独立文件且确认数 > 否定数 → 撤销此前积累的负向记忆（修复前确认分支无撤销路径，模型两次全票假阴性就能永久杀死一条规则召回） |
| 单次否定不降权 | 否定必须 ≥ 2 个独立文件才形成有效负向记忆；单次否定只累加计数 |
| **负向记忆只降权、不剔除** | 模型判定“这条规则在这个文件上是误报”时，只降低该规则**在本文件**的候选排序权重（`priority_factor`），**不从候选集合中删除**。原因：规则是否误报取决于**文件**而非规则本身——同一条规则在 A 文件上是不容置疑的证据、在 B 文件上可能是正确告警；按规则级“见到就跳过”会制造样本级静默盲区。该设计曾因规则级过滤导致工具召回系统性崩塌（历史事故），故把动作从“剔除”降级为“降权”，并保留完整留痕 |
| 类型校正去重计数 | `corrected_type_counts` 按 (file, corrected_type) 去重，读写端口径一致 |
| 待学习池 | 收录“工具漏召但 LLM 全票判中”的代码特征，须经独立验证集复验才转正 |
| 正向 boost | 已回填高置信信号的规则 `boost_priority` 返回 `1.0 + confidence`，Stage 1 候选按此排序——模型回填不只过滤，还正向影响候选顺序 |
| 确定性工具免疫 | 模型意见**仅作用于裁决档**（taint/prefilter/sast/iac）；直出档（secret/sca，确定性工具）不参与回填、也不受模型意见影响 |
| 自动持久化 | `record()` 变更后自动 `save()`（原子写：tmp + `os.replace`） |

> **闭环小结**：门槛参数写入代码、读写端语义一致、未达门槛保留原值（防止模型错误判定污染确定性工具）；三个去向的决策依据均为最终采信结论——确认 → 排序加权，否定 → 按文件降权，类型校正 → 严格条件下更新映射。**没有任何一条路径会降低工具层的召回面**。

### 4.3.5  防锚定的三层结构

同一份错误提示，Q4 后端 0/3 全票否决、bf16 后端 3/0 全票确认——“全票但错”说明模型对工具锚点过度顺从。应对不是全局降服从性，而是**条件性服从**：

| 层 | 机制 |
|---|---|
| 推理层 | prompt 中低信任位置型规则显式注入“⚠ 此告警来自位置型规则（无 source→sink 数据流证据链），历史误报率高……不要顺着工具标注的方向走”；prefilter 标“可信度中等”；带 source→sink 链的标注“可信度较高” |
| 锚点来源分级 | 高信任标注**只在 source/sink 确实由工具产出时**授予。位置型候选本身没有 source/sink 文本，模型判真时会自述锚点并回写到候选上——若不加区分，模型自述的行号会被下游当成“工具引擎产出的证据链”授予高信任，形成自我确认。实现上为候选记录锚点来源（`tool` / `model_vote`）并分级注入措辞，同时为反事实验证保留一份**锚点回填前**的候选快照 |
| 聚合层 | 确定性证据门 |
| 回填层 | 信号注册表 |

### 4.3.6  多数票类型投票（回声票加权）

文件级聚合多个裁决的 vulnerability_type 时，投票键 = `(总票数, 独立票数, 该类型所在 finding 的最高严重度)`。

**独立票** = 模型输出类型 ≠ 工具 taint_type 归一化结果——“回声票”只是复读工具标注，无独立信息量（工具标 XSS、模型跟着输出 CWE-79 是回声；工具标 B324、模型独立判出 CWE-327 是独立判断，平票时独立判断胜出）。

**文件级存在性判定**：任一 finding 多数票判真即文件判真（不因无关 finding 否决而对冲），但排除两类：① `category=="llm"` 的合成 finding；② `evidence_gate` 拦截的判真。

## 4.4  复核兜底机制

工具规则覆盖不可能 100%，工具盲区在裁决路径上会静默放行（裁决式任务只问“工具告警是否为真”，**模型不会自主发现工具没召回的漏洞**）。为此系统设有**两个复核出口**：

| 出口 | 触发条件 | 判定 |
|---|---|---|
| ① **无候选复核** | 文件无任何工具候选时触发；具体策略由 `no_candidate_mode` 控制，分三档组态（见 §4.4.1） | 复核命中且全票判真 → 采信为漏洞 |
| ② **裁决全否决兜底复核** | 全部候选被裁决否决、文件将被判安全时，再做一次全文件兜底复核 | 命中且全票判真 → 采信为漏洞 |

> **术语说明**：出口① 内部有 `full_recheck` / `targeted` / `sampled` **三档组态**（那是“同一出口的三种策略”，不是三个出口）；系统对外共**两个复核出口**。

### 4.4.1  无候选复核的三档组态

| 组态 | 生效场景 | 行为 |
|---|---|---|
| **`targeted`（生产默认）** | **所有生产入口**：单文件分析、批量上传、GitHub 仓库、URL 抓取 | **三档定向复核**：按“文件风险分 × 盲区命中”分配注意力，零盲区文件不送 LLM——替代全量复核（后者成本随文件规模线性增长，且大多花在零风险文件上） |
| `full_recheck` | vLLM 端点；以及显式指定用于演示 / 消融 | 每个无候选文件**全量** LLM 复核，消除“无证据判安全”静默放行 |
| `sampled` | 扫描器**类默认**与评估组态 | 10% 抽样复核（监控工具层漏报率，省算力） |

**场景 → 组态对照（代码核实）**：

| 扫描场景 | 默认组态 | 可覆盖方式 |
|---|---|---|
| 单文件分析（粘贴 / 上传单文件） | `targeted` | `VULN_SCANNER_BATCH_RECHECK_MODE` |
| 批量上传 | `targeted` | 同上 |
| GitHub 仓库 | `targeted` | 同上 |
| URL 抓取扫描 | `targeted`（跟随批量） | `VULN_SCANNER_URL_RECHECK_MODE` |
| vLLM 端点 | `full_recheck` | 代码内固定 |
| 评估 / 消融 | `sampled`（类默认） | 评估脚本参数 |

> 三个生产入口共用同一组态常量——`_two_stage_scan()` 的参数默认值即 `BATCH_NO_CANDIDATE_MODE`（默认 `targeted`），不做“按入口分场景”的差异处理。这样设计是为了消除“行为随调用顺序漂移”：早期实现让请求级参数覆盖共享配置后不回滚，导致跑过一次仓库扫描后，后续单文件扫描会静默沿用仓库扫描的组态。

> **口径提醒**：三档必须严格区分——**生产默认是 `targeted`**；若引用“10% 抽样复核”，须注明其为类默认 / 评估组态；`full_recheck` 只在 vLLM 端点与显式指定时出现。

### 4.4.2  无候选复核的判定门槛

**抽样算法细节**（反直觉设计）：

- **复核票数上限 3**：`n = max(1, min(3, self.n_samples))`——复核最多 3 票，是“最便宜的兜底”，用更少票换取速度；
- **温度取 max**：`temperature = max(self.temperature, 0.7) if n > 1`——多票采样需足够温度打破同模态重复；
- **计数器口径防污染**：裁决全否决兜底调用时 `count_monitor=False`，不计入 `no_candidate_total`。

### 4.4.3  `targeted` 组态的三档定向复核

`targeted` 以「文件风险分 × 盲区命中」把无候选文件分为三档，把复核预算集中到真正有攻击面的文件上：

| 档 | 判定条件 | 复核动作 |
|---|---|---|
| **A 档** | 有盲区 **且**（风险分 ≥ 阈值，**或** 高优先级盲区命中 ≥ 2 条） | 盲区片段 × min(3, n) 票（与全量复核同置信级别） |
| **B 档** | 有盲区但低危；**或** 零盲区但高风险分 | 片段 × **1 票**。单票判真**不具采信资格**，一律转人工复核——“一票通过”是没人反对，不是多票一致；而无工具证据的采信必须是最高置信级别 |
| **C 档** | 零盲区 **且** 低风险分 | 不送 LLM，显式留痕“未获得复核预算”；但仍按 10% 抽样，抽样命中则降级为 B 档 |

**为什么“零盲区”不能直接等于“不送 LLM”**：盲区规则覆盖的是**工具写不了规则**的形态（越权、过滤可否绕过），而 SQL 注入 / 命令注入 / 路径穿越 / XSS 这类**工具本该召回**的形态并不在盲区表里。若一律按“零盲区 → 跳过”处理，一旦工具因规则不覆盖、语言不支持或新框架而零召回，这些漏洞就被静默放行——正是本系统一贯要消除的静默性。因此加两道保险：① 风险分高（有外部源 + sink + 入口点 = 有实际攻击面）却零召回，是**工具失效的信号**，比“文件没内容”更值得复核，故降 B 档；② C 档按 10% 抽样复核，在线估计零盲区文件的漏报率。

**风险分阈值**：含外部源 + sink + 入口点的业务文件典型得分 20~40，纯工具层 / 数据传输对象为负分，高优先级档阈值为 12 分。

**省时的两个来源**（可分别关闭以做消融）：① C 档省掉整次调用（大仓库的主要收益）；② A/B 档把“整文件”换成“盲区片段”（自检实测 5575 → 285 字符，约 5%），模型从“读 1000 行找漏洞”变成“看几个带行号的短片段判漏洞”。

**在线漏报率估计（分层口径）**：模块级计数器把复核结果按**抽样机制**分层统计。只有 C 档按比例随机抽样命中而升级的那部分是无偏随机样本，可用来估计“工具层漏报率”（并给出二项比例的置信区间，样本不足时只报区间不报点估计）；A/B 档是按“风险分 × 盲区”**定向挑选**的样本，命中率只能称为“定向复核命中率”，不能当作漏报率——否则会把“专挑高风险文件复核”的选择偏差算成工具的能力缺陷。分层后，这个指标从“看似精确的单一数字”变成“随机层给率 + 定向层给命中率”的两组可引用数字，把工具召回漂移变成可观测且可辩护的指标。

**复核采信形态校验**（防止 LLM 在工具盲区上瞎判）：

- 注入型漏洞（有标准 sink 和标准防御的）必须满足 ① 代码存在该类型标准 sink 特征；② sink 邻域（±8 行）无该类型标准防御 → 任一不满足转人工复核；
- 缺失型/其他漏洞（CSRF/认证缺失/弱密码/硬编码/竞态/XXE 等无确定性验证手段的）不做形态校验，全票采信并**如实标注“模型语义兜底”**；
- 跨文件调用（sink 在外部文件时“调用导入函数”= 可能存在外部 sink）不误拦。

## 4.5  关键工程机制

### 4.5.1  优先级调度器

基于 `heapq` 优先级队列，交互式扫描（HIGH）优先于批量扫描（LOW）：

- `ScanTask` dataclass 按 `(priority, seq)` 排序，优先级相同时 FIFO；
- 单工作线程与各后端串行并发模型对齐，Python 层显式排队；
- 每 `client_id` 最多排 8 个任务，防止单一批量扫描霸占队列；
- 工作线程通过 `loop.call_soon_threadsafe` 把结果回填到 `asyncio.Future`；
- 请求头 `X-Scan-Scope` 让调度器把插件交互式扫描排 HIGH、批量排 LOW；
- **配额桶由服务端事实决定**：批量入口（单文件批量 / 仓库 / URL）各自生成一个服务端批次标识作为配额分组键，客户端无法通过轮换请求头把自己的任务拆成多个桶绕过每客户端上限；`X-Client-Type` 亦做白名单收口，未知取值统一归入默认桶。

**关停时的任务收尾**：调度器停止工作线程前，会把仍在队列中的任务**整体置为异常**，并对关停后到达的新请求立即返回异常。原因：工作线程退出后队列中任务永远不会再被取走执行，若 `Future` 不回填，端点的 `await` 会永久挂起，拖住服务优雅停机。这属于“不留悬挂状态”的一贯原则在关停路径上的体现。

### 4.5.2  约束解码兜底

CoT + JSON 解析失败时，用 `format=json` 约束解码重试，数学上保证输出可解析。这是 parse_fail 从 18/87 降到 0/87 的关键机制之一。

> 注：该机制是 Ollama 后端独有能力；LlamaCPP 后端未启用 GBNF 语法约束，退化为普通 generate + 警告。

### 4.5.3  手写括号深度匹配 JSON 解析

LLM 输出解析的“最后一道防线”。非贪婪正则在遇到 `"reason": "使用了 {username} 导致 SSTI"` 时会提前截断，而手写状态机跟踪字符串内/外的花括号深度，收集所有平衡闭合的 `{...}` 候选逐个 `json.loads`。

### 4.5.4  CWE 编号确定性纠正

模型对漏洞“语义分类对、编号记错”（如 SQL 注入写成 CWE-29）是纯记忆错误，纠正模块在输出后做确定性查表纠正，**零 token 开销**。幂等且对表外长尾原样放行。

| 细节 | 设计要点 |
|---|---|
| 关键词排序防子串歧义 | 按“更具体优先”排列（NoSQL 在 SQL 之前、CSRF 在 XSS 之前），避免子串误匹配 |
| 短关键词词边界保护 | `cmdi`/`codei`/`logi` 等用词边界正则，避免匹配 `cmdispatch`/`logical` |
| evidence 守卫四级优先级 | ① 字段命中表内语义关键词 → 直接用；② 字段已含明确 CWE 编号 → 尊重模型判断；③ 无编号 → 用 evidence 二次提取；④ 都未命中 → 原样返回 |
| 父子族匹配双向遍历 | 同时遍历 reported→expected 与 expected→reported 父链 |

### 4.5.5  行号内容锚定纠正

模型输出的 source / sink / fix_suggestion 采用“行号锚定”格式（如 `line 7: request.args.get('file')`）。行号是纯“数行”任务，模型容易数错，但 `line N:` 后面的行文本内容通常可靠。本机制用内容在源文件中定位真实行号并覆盖，**零 token 开销**：

- 支持 `line N:` / `L N:` / `第 N 行:` 三种锚点形态，纠正后统一输出 `line N:`；
- 三级评分：整串相等/代码骨架包含 → 1.0；最长无空白代码片段包含 → 0.95；去中文后相似度兜底；
- 高分优先、同分取距原始行号最近者（行号幻觉通常是“差几行”而非跨文件乱跳）；
- 匹配不到可靠锚点（< 0.6）原样保留，不做破坏性覆盖。

### 4.5.6  修复建议验证

验证模型输出的修复建议是否语法正确、是否真正移除危险模式。修复建议为“行号锚定的单行局部建议”，验证器主职是抓幻觉行号。

| 细节 | 设计要点 |
|---|---|
| 补充危险模式表 | 15 条补充模式，覆盖 Java 命令执行 / Java SQL 拼接 / Java 路径拼接 / Flask SSTI 拼接 / 弱哈希（Java 与 Python 两侧）/ SSRF 拼接 / 开放重定向拼接 / SSTI 组合特征；选取原则是“必须是危险用法（拼接、弱算法）而非 API 存在”——否则修复后的安全写法仍会命中，导致“修复无效”误判 |
| Java 双候选包壳策略 | 生成两个候选编译单元（声明放类体 / 语句放 main 方法体），两种都失败才判语法不合法 |
| JS CJS→ESM 回退 | `node --check` 默认按 CJS 解析，`import`/`export` 会误报，CJS 失败后自动用 `--input-type=module` 重试 |
| extract_code 取最后一个代码块 | fix_suggestion 含多个代码围栏时取最后一个 |

### 4.5.8  多模型投票聚合规则

- **has_vulnerability**：多数票决定；**50/50 平票 → `None`（转人工复核）**；
- **consensus**：全票一致 = unanimous / 有少数派 = majority / 平票 = split；
- **agreement_ratio**：多数方票数 / 有效票数（排除 error 的 None 票）；
- **结构化字段**：取自多数方首个模型；平票时结构化字段仍取判真侧（供复核参考），但**结论本身是“需人工复核”**；
- **explanation/raw_output**：取自首个与最终结论一致的模型；
- 全部模型失败 → `has_vulnerability=None`、`error="all models failed"`。

> **平票为什么不判漏洞**：两个模型各执一词时，“证据最强对立”恰恰是最不该给强结论的情形。系统在 Stage 2 的平票口径是“转人工复核”，多模型通道必须与之一致——否则会出现“同一系统两套平票语义”，且是最弱证据给出最强结论。

**通道边界**：多模型投票仅对 Ollama 后端开放。进程内后端每次只能加载一个本地模型，传入多个模型名会指向同一模型（“三票同源”假投票），因此后端以 501 门控、前端按健康检查中的模型管理能力禁用该选项。

**顺序加载/卸载策略**：逐个模型加载 → 扫描 → 立即卸载（`keep_alive=0`）→ 加载下一个，任一时刻显存中只驻留一个模型。`finally` 块保证即使中途异常也能卸载。

### 4.5.9  模型管理能力门控（501 而非 500）

进程内后端没有运行时拉取/删除能力，`/api/models/*` 返回 501 并附能力清单。501 的语义是“我知道这个功能是什么，但当前后端不支持”，让前端可以优雅降级（如隐藏“拉取模型”按钮）。

### 4.5.10  多后端抽象与精度权衡

四种后端工厂按类型构建对应客户端。后端为前端提供检测报告式信息（基座量化位宽、LoRA 是否被量化、运行设备等），让用户直观理解“为何 HF/LoRA FP16 与 Ollama Q4 发布态是两档精度”。

**merge 通道永久关闭**：transformers 后端 `self.merge = False` 硬编码，环境变量与构造参数均被忽略。原因（代码注释明文）：NF4 4bit 基座上 `merge_and_unload` 把 LoRA 增量折回 4bit 存储，归因能力显著退化（strict 0.709 → 0.525）。

### 4.5.11  训练/推理一致性保证

- 模型注册表每个模型绑定 `prompt_variant`，推理时自动选择对应的 system prompt；
- `:latest` 标签归一化避免误判“未安装”重复拉取；
- `deprecated` 字段标记过时模型，UI 标记“已过时”但仍可使用；
- **回退链路**：未登记模型回退基础 prompt；
- **裁决/验证 prompt 一致性与运行时同步**：训练对齐裁决要透传到每一处 prompt 组装（曾出现 system 已是训练格式、裁决 user 却问旧字段的不一致）；切模型后 system_prompt 需运行时统一刷新（`sync_runtime()`）——跨组件共享的 prompt 状态应在运行时统一刷新，不能依赖构造期捕获。

### 4.5.12  URL 抓取的多层防护

| 层 | 措施 |
|---|---|
| 协议白名单 | 仅允许 http/https |
| IP 分类 | 拦截内网/回环/链路本地/保留地址 |
| DNS rebinding 缓解 | 双重解析一致性校验 |
| 重定向控制 | 每一跳重新校验，最多 5 跳 |
| 响应体限制 | 流式读取，超过 2 MB 截断 |
| 代理感知的 SSRF 校验 | 检测到将经 HTTP 代理发出时，**跳过 IP 级校验**（见下） |

**代理感知的校验豁免**：代理模式下 `requests` 把主机名原样交给代理、由代理解析并建连——本机 `getaddrinfo` 的结果与实际连接目标无关，IP 级校验（内网地址拦截、rebinding 复检）**只在直连时有意义**。若在代理下照常校验，会出现“本机 DNS 被污染 → 解析为空 → 误拦可达站点”的假阴性（大陆网络下部分 CDN 域名即属此情况，经代理实测 HTTP 200）。因此实现上先判断该请求是否经代理，再决定是否施加 IP 级校验。

### 4.5.12.1  库文件与压缩产物的过滤策略

URL 扫描面向的是**站点自有代码**，第三方库与打包产物不属于攻击面，进入 LLM 裁决只会消耗预算并产生假阳性。因此在抓取入口设三道过滤：

| 过滤 | 判据 | 实现要点 |
|---|---|---|
| **第三方库 URL** | 主机名 / 路径 / 文件名中的库名关键词 | **hostname 匹配与 path 匹配必须分正则**：hostname 永不含 `/`，带路径的模式（如 `google.com/recaptcha`、`gitee.com/libs`）写进 hostname 正则**永不命中**——此处曾因未区分而静默失效 |
| **自托管库副本** | 库名 + 可选“扩展名尾巴” | 只写 `jquery\.min\.js` 会漏掉 `/resources/js/bootstrap.min.js` 这类**站点把 CDN 库下载到自己服务器**的副本（形态与自有代码相同）；按“库本身非攻击面”原则同样过滤 |
| **压缩/打包产物** | 内容启发式（无网络请求）：带 `sourceMappingURL` 注释；或平均行长 > 250 字符；或过半行单行 > 2000 字符（内容 ≥ 4KB 时判定） | 压缩产物**标识符被破坏、变量名全毁**，LLM 语义裁决价值极低，召回多为打包器形态假阳性（实测某仓库 53/57 个 webpack chunk 全部进裁决、逐条被驳回，预算几乎白烧）。默认跳过并**显式回报**计数（可设环境变量恢复全量扫描）——遵循系统“不静默丢弃”的一贯原则 |

> 被跳过的文件数会显式回报给用户，而非静默丢弃；这与 §4.4「复核出口显式留痕」、第四篇 §4.5.17「预算外文件必须可审计」属同一设计原则。

### 4.5.13  GitHub 仓库扫描的沙箱约束

`git clone --depth 1` 浅克隆到 `tempfile.mkdtemp`，120 秒超时，`GIT_TERMINAL_PROMPT=0` 禁交互凭据提示，扫描后 `shutil.rmtree` 清理；跳过目录用**路径段精确匹配**而非子串匹配（子串匹配会误伤 `x.gitlab` 等合法目录名）。

**遍历与预算分离**：遍历阶段只做“防内存爆炸”的硬上限（文件数 3000 / 总字节 200 MB），**不做按遍历顺序的截断**——扫描谁由风险分决定（见 §4.5.18）。两者必须有足够差距：若收集上限不够大，风险排序只能在一个被顺序截断的小集合里排，靠后的认证 / 接口目录可能压根没被收集到。为避免这条不变量随时间失效，代码把它做成**导入期断言**：请求层文件数上界是一个独立常量，与收集上限绑定校验，一旦有人把上界调到接近收集上限，服务启动即失败而不是静默退化。

### 4.5.14  向量知识库设计

存储选型与检索参数（`BAAI/bge-m3` 多语言 embedding、`HF_HUB_OFFLINE` 强制离线、三级模型路径解析、集合与检索参数）见第五篇 §5.3。本节只关心工程行为：Chroma 向量库**延迟到首次使用才初始化**，初始化失败静默降级为纯 LLM 判定并记忆失败，避免反复重试。

### 4.5.15  输入限额的前后端双端一致防线

后端定义 `MAX_CODE_CHARS=2M / MAX_BATCH_FILES=200 / MAX_SINGLE_FILE_BYTES=2MB / MAX_BATCH_TOTAL_BYTES=10MB`，超限返回 **413**（非 400/500）；前端用同值先做客户端拦截（超限 toast“已跳过 N 个文件”）。本地单机服务也做输入限额 + 前后端双重校验，且用 413 精确表达“请求实体超限”语义。

### 4.5.16  国内镜像下载的工程闭环

| 细节 | 设计要点 |
|---|---|
| HF_ENDPOINT import 时序 | 在**任何 `huggingface_hub` import 之前**设置——hf 的 endpoint 在首次 import 时固定，这是唯一可靠时机 |
| NO_PROXY 强制直连 | 把镜像域名追加进 `NO_PROXY`，避免代理秒断 + 白耗 GB 级代理流量 |
| socks 规范化 | 把裸 `socks://` 修正为 `socks5://`，否则抛 `Unknown scheme for proxy URL` |
| 断点续传 + 退避重试 | HTTP Range 续传写入 `.incomplete` 后缀；416（Range 越界）时目标文件已存在直接判完成；网络抖动指数退避最多 5 次；`downloaded == total` 不符则删除重来 |
| **下载源白名单** | 模型下载端点只接受可信模型来源域名，并对目标地址再做一次“解析后 IP 分类”校验（防域名被劫持指向内网）。此前该端点接受任意 URL，可被用来探测内网服务 |
| **下载大小上限** | 单文件 8 GB 上限：`Content-Length` 已知且超限时直接拒绝（不留半成品），流式累计超限时中止并删除半成品；超限属确定性错误，不进入退避重试 |
| 代理环境变量的并发原子性 | 镜像直连配置（`NO_PROXY`）与代理协议规范化都是对进程级环境变量的“读—合并—写”。两个下载并发时无锁的读改写会互相覆盖丢项，故用进程级锁串行化该临界区（临界区仅内存操作） |

### 4.5.16.1  进程内推理的墙钟超时（可用性底线）

**问题**：四种推理后端共用同一个 `generate(..., timeout=...)` 调用契约，但进程内（Transformers）后端的生成发生在当前进程里，请求层超时对它是**无效参数**——一旦生成卡住（显存抖动、驱动挂起、超长输入触发换页），它会一直占住推理线程。而扫描调度器只有一个工作线程，且明确声明“线程无法安全强杀”，结果是**整个服务停止响应，用户只看到进度条一直转**。

**处置**：为进程内生成加**墙钟停止条件**——在解码循环中检查累计耗时，超时即停止生成并返回一个显式错误结果；错误经既有的“无效票”路径进入复核，不需要改动上层任何逻辑。同时把裁决路径的生成长度上限收紧到与裁决输出规模匹配的值（裁决只输出固定字段 JSON），既降低卡死时的浪费，也降低生成途中开始复读的概率。

**并把不可见变可见**：调度器的“疑似卡死”标记（执行时长超过阈值）此前只存在于队列状态接口里，仪表盘与启动器都读不到。现提升为健康检查的顶层降级标记，使“引擎可能卡住”成为可被界面与运维感知的状态。

### 4.5.17  工具层盲区定位（行级提醒，不产生 finding）

传统工具只能召回**可规则化**的漏洞形态；有一大类风险“规则写不了”——授权/越权（IDOR，需业务语义）、过滤是否可绕过（取决于下游）、跨函数跨文件污点、加密用法是否安全、隐式信任边界。这些若写成规则，要么漏得厉害，要么误报爆炸。

设计：把它们做成**行级盲区提醒注入 prompt**——只描述“工具看不到什么”，把判断权完整交给模型。三条硬约束（缺一不可，否则就是换皮的告警）：

1. **不产生 finding**：盲区不进候选集、不进裁决、不影响漏洞判定结果；
2. **永不进信号注册表**：盲区被模型否定是正常且高频的（本就是低置信提示），一旦允许其进入工具负向记忆，该机制会在几轮扫描后自我清空；
3. **中性措辞**：统一用“工具无法判定 X，请确认 X”，**绝不写“此处存在 XX 漏洞”**——后者会锚定模型、抬高判真率。

知识来源为**先验分类**（公开漏洞形态目录），与“从样本挖掘 + 独立验证集审批”的学习通道严格分离，防止样本过拟合。纯确定性：同输入必同输出。默认开启，可通过环境变量关闭以供消融对比。

### 4.5.18  文件级风险打分与注意力预算调度

**修正的架构缺口**：仓库/URL 批量扫描此前按目录遍历顺序取前 N 个文件即停止——这是**盲目截断**。大仓库中工具目录、数据模型目录常排在认证、接口目录之前，有限名额可能被低危文件占满，高危文件压根没进扫描（此时优化“单文件复核多快”没有意义）。

方案为**纯确定性**的文件风险打分 + 预算分配：

- 打分只用**语言习语级知识**（路径语义：认证/接口/支付/加密等 + 公开漏洞形态词表），**不从任何测试样本挖掘**——样本挖掘属于独立的学习通道（须经独立验证集审批），两者严格分离以防过拟合；
- 分配在给定预算（文件数 / 总字符数）下按分从高到低取；未覆盖的文件**显式回报**（`BudgetPlan.uncovered`），绝不静默丢弃——与本系统“消除静默性”的一贯原则（被抑制、被剔除的候选均留痕）同构：预算外文件也是“没扫到”的一种，必须可被审计；
- 可选**同构折叠**：大仓库中常有几十个近重复的模型/数据传输对象文件，按结构指纹折叠后只扫代表文件，其余记入 `duplicates_folded`。

纯确定性（同输入必同输出、无随机、无 LLM）→ 可复现、可审计、可作为消融实验对象。

### 4.5.19  列表形式命令调用的安全性判定（唯一入口）

**修正的历史缺陷**：多处实现曾把“列表形式 subprocess 调用”无条件当作安全/防御，导致 `subprocess.run(["sh","-c",user])`、`find -exec`、`git --upload-pack` 等**由解释器执行载荷的真注入**在召回层、证据门/复核门、安全白名单被系统性拦截（漏报）。

规则：列表形式默认不经 shell 解释（构成防御），但参数中出现 **shell / 解释器或执行语义参数**时，载荷会被该解释器执行，仍构成命令注入。该判定封装为**唯一入口**供各层（反事实验证、污点分析、schema、prompts）复用，**禁止在各层自行复制“列表形式 = 安全”的局部判断**——单一事实来源，避免判定漂移。



## 4.6  设计依据

### 4.6.1  路径依赖与部署设计

| 设计 | 依据 |
|---|---|
| 一键启动脚本依赖装进当前解释器同环境运行 | 避免依赖分裂（torch 对了却缺 tree_sitter / 工具装到别的环境） |
| Windows bat 不切 UTF-8 代码页 | 脚本路径可能含中文，切 UTF-8 后 cmd 仍按 ANSI 解析 `%~dp0` 会“吃掉”命令行尾部；保持默认代码页 + echo 文本用 ASCII |
| torch 构建硬件分档 | 按 compute capability 分档（12→RTX50、8.9→40 系、7.5→20 系、6.x→10 系）；AMD 按 RDNA 代数选 rocm 版本；<6GB 显存走 CPU torch |
| 同版本 CPU→GPU 替换先卸载再装 | 否则 pip 认为已满足 |
| 不主进程 import torch | 避免清理前就弹 DLL 入口点错误窗口 |

### 4.6.2  llama-cpp-python 的两个真实坑

- **坑 1**：llama-cpp-python 0.3.34 加载 **safetensors LoRA 推理会卡死（hang）**，GGUF LoRA 才是原生格式 → 优先选 `adapter_model.gguf`；
- **坑 2**：CUDA wheel 不打包运行时 DLL，不在 PATH 会致 llama.dll 加载失败、GPU offload **静默回退 CPU** → 前置注入 `nvidia/*/bin` 到 PATH；
- **预编译 wheel 静默 CPU-only 坑**：PyPI 预编译 wheel 是 CPU-only，直接 pip install 会用 wheel **忽略 CMAKE_ARGS**，导致 GPU offload 静默失效 → `--no-binary llama-cpp-python --force-reinstall` 强制源码编译 + `FORCE_CMAKE=1`，编译后二次校验 `llama_supports_gpu_offload()`。

### 4.6.3  依赖冲突定位与固定

semgrep 严格锁 `opentelemetry ~=1.37.0`，chromadb 的 grpc exporter 被升到 1.44.0，common/proto/sdk 被“撕成两半” → `ModuleNotFoundError`。修复：全部 otel 包钉回同一版本，并写“检测家族版本 >1 个不同主版本即判定撕裂”的自动对齐。经典“两个依赖各自合法、合起来崩”场景。

### 4.6.4  “存在但损坏”的坏依赖检测

PATH 可见 ≠ 可运行：安全工具安装区分“缺失”与“存在但损坏”（实际跑 `--version` 冒烟）；应用级运行时依赖用子进程 import 冒烟（避免污染本进程 importlib）；修复后复查冒烟。

### 4.6.5  CI 的“永不阻断 PR”设计哲学

LLM 扫描作为“可选信息”而非硬门槛——Ollama 不可用、模型缺失、单文件出错都只输出警告并退出码 0。三处可写：① **分层依赖检查**（核心层不得反向依赖 app 层，否则阻断）；② **离线模式**（CI 无 HF 缓存，Scanner 自动回退纯 LLM 模式）；③ 模型拉取失败自动回退。

### 4.6.6  已识别取舍与设计边界（如实声明）

本节集中记录设计中**明知代价而选择**的部分，供评审对照，避免把取舍当成疏漏：

| 取舍 | 选择 | 代价 | 理由 |
|---|---|---|---|
| 共形预测的启用状态 | 未校准时不启用（当前生产即为未校准） | 放弃一层统计门控 | 校准文件来源不满足可交换性，“覆盖率保证”不成立；不宣称不成立的保证优先于多一层门控 |
| 复核预算分配 | 无候选文件按风险分 / 盲区分档，零风险文件不送模型 | 这部分文件的结果是“未复核”而非“已安全” | 推理预算有限；把“没看过”如实标注，比让每个文件都过一次模型更诚实也更可行 |
| 规则级误报治理 | 只降权、不剔除 | 误报规则仍会产出候选、仍消耗裁决预算 | 误报取决于文件而非规则，按规则“见到就跳过”会制造样本级静默盲区（有历史事故） |
| 进程内推理 | 单进程单工作线程串行 | 批量扫描按文件数线性增长，无并发吞吐 | 显存约束下的确定性与可诊断性优先；高吞吐场景另设 vLLM 端点 |
| 全票门槛与误报 | 保留全票判定的回填资格，但叠加与模型无关的证据门 | 需要更多门控代码 | 全票刻画的是“模型很自信”而非“模型很可能对”，单独使用与已知失效模式正交 |
| 跨文件数据流 | 单文件为主，跨文件攻击路径为弱项 | 复杂跨文件漏洞漏报 | 单文件分析无需构建跨文件索引，可保持离线、可解释；跨文件属后续工作 |
