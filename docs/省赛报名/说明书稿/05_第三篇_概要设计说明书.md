## 3.1  总体架构

系统采用**两阶段扫描架构**，并在其之上叠加信任层与复核兜底，形成完整的判定流水线：

```
源代码
  │
  ▼
┌─────────────────── Stage 1：工具召回（4 路并行） ───────────────────┐
│  Semgrep taint    TaintTracker    Prefilter    ExternalScanner      │
│  （污点规则）      （AST 污点）    （正则预筛）  （secret/sca/sast/iac）│
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
                    有候选 ─────┴───── 无候选
                      │                  │
                      ▼                  ▼
        ┌──────────────────────┐   ┌──────────────────────┐
        │ Stage 2：LLM 裁决     │   │ 无候选复核（兜底）    │
        │ N=3 次采样自一致率    │   │ full_recheck 全量复核 │
        └──────────┬───────────┘   └──────────┬───────────┘
                   ▼                          │
        ┌──────────────────────────────┐      │
        │ 2.5 代信任层                  │      │
        │ 确定性证据门 + 共形预测       │      │
        │ + 反事实验证 + 信任分级回填   │      │
        └──────────┬───────────────────┘      │
                   ▼                          ▼
              ┌────────────────────────────────────┐
              │ 聚合结论（四分类）                  │
              │ confirmed_vulnerability / confirmed_review │
              │ dismissed_safe / dismissed_review          │
              └──────────┬─────────────────────────┘
                         ▼
        全部候选被否决时 → 裁决全否决兜底复核 → 最终结论
```

> ![图 3-1 两阶段扫描架构](assets/two_stage_architecture.png)
>
> **图 3-1  两阶段扫描架构**（完整形态：Stage 1 工具召回 → Stage 2 LLM 裁决 → 2.5 代信任层 → 聚合结论 → 兜底复核 → 输出；4 路并行召回 / N=3 裁决 / 三档无候选复核）
>
> 图注补充：「无候选复核」方框对应 `no_candidate_mode` 三档组态——单文件 / GitHub 扫描走 `full_recheck`（全量），批量与 URL 扫描默认走 `targeted`（三档定向），评估组态为 `sampled`（10% 抽样）。三档口径见第四篇 §4.4.1。

**架构的核心反转**：LLM 的任务从"在全文中发现漏洞"（开放生成）变为"对具体 finding 判定真伪"（封闭判别）。只取包含 source/sink 行的 chunk 作为裁决上下文，聚焦 LLM 注意力；每条判定有工具证据做锚点，幻觉空间被大幅压缩。

**关键组态（代码核实）**：

| 项目 | 值 | 说明 |
|---|---|---|
| `triage_aligned` | `True` | 裁决 prompt 使用训练对齐的 `has_vulnerability` 格式 |
| `no_candidate_mode` | **分场景**：单文件 / GitHub 扫描 `full_recheck`；批量 / URL 扫描 `targeted` | 无候选文件的复核策略（三档组态见第四篇 §4.4.1） |
| `n_samples` | `3` | 裁决采样次数 |

> **组态辨析**：`full_recheck`（无候选文件全量 LLM 复核）适用于单文件 / URL / GitHub 等安全关键场景；**批量扫描（大仓库）默认走 `targeted` 三档定向复核**，避免全量复核成本随仓库规模线性增长。审计 / 评估场景可显式指定 `sampled`（10% 抽样）。

## 3.3  扫描引擎主线

### 3.3.1  Stage 1：工具召回

四路并行召回（线程池 `max_workers=4`；subprocess 型工具释放 GIL，延迟从"顺序求和"降为"取最大"）：

| 路径 | 手段 | 产出 |
|---|---|---|
| Semgrep taint | 自研规则六件套（taint 四件：sqli/cmdi/xss/codei；结构化补位两件：go_cmdi_shell/c_cmdi_system） | 带数据流的候选 + 工具缺口补位 |
| TaintTracker | tree-sitter 线性数据流污点分析 | source→sink 路径 |
| Prefilter | 正则预筛（漏洞特征/安全特征） | 候选 + 置信标记 |
| ExternalScanner | Bandit / Semgrep / Gitleaks / Trivy / pip-audit / detect-secrets | secret / sca 直出，sast / iac 进裁决 |

**跨工具去重**：semgrep OSS 的 taint JSON 不含 metavar（source/sink 为空），与 TaintTracker 命中同一条数据流时主键永不相等。去重逻辑用 `(taint_type, sink_line)` 辅助索引把"空证据候选"归并到已有 finding，保证同一条流只裁决一次。

### 3.3.2  Stage 2：LLM 封闭裁决

对每个候选构造裁决 prompt，进行 N=3 次采样（温度 > 0），以**有效票**判真票占比作为置信度：

- 置信度 ≥ 0.8 → 自动判定；
- 0.5 ~ 0.8 → 标记"需人工复核"；
- < 0.5 → 不自动结论。

> 分母使用有效票（`votes_true + votes_false`）而非 N——解析失败/推理出错的票不代表"否决"，除以 N 会稀释真实一致率。

### 3.3.3  2.5 代信任层

在裁决之上叠加四重门控，详见第四篇 §4.3。

### 3.3.4  复核兜底

系统共有**两类复核出口**：无候选复核（内部按 `no_candidate_mode` 分 `full_recheck` / `targeted` / `sampled` 三档组态）/ 裁决全否决兜底复核。详见第四篇 §4.4。

### 3.4.3  结果交换格式

- **SARIF 2.1.0**：两阶段结果按置信度映射 level（≥0.8 error / 0.5~0.8 warning / <0.5 note）；每条 confirmed finding 携带 confidence / votes / source / sink / 传播链 / 修复建议；带 `partialFingerprints` 稳定哈希，可跨扫描去重。与 GitHub Code Scanning、VS Code Problems、JetBrains Qodana 原生互通。
- **Markdown 报告**：表头（生成时间/语言/耗时）+ 漏洞字段表 + 说明 + 修复建议 + 模型原始输出折叠块；批量版含漏洞汇总表。

## 3.5  部署形态与运行环境

### 3.5.1  四种推理后端

| 后端 | 形态 | 定位 |
|---|---|---|
| **Ollama**（默认兜底） | Q4_K_M 合并量化的发布模型 v9max | 兼容性最好、依赖最少 |
| **Transformers** | NF4 基座 + FP16 LoRA 进程内推理 | 精度最高（保 LoRA FP16） |
| **LlamaCPP** | Q4 GGUF 基座 + 运行时 FP16 LoRA | 速度与精度折中（实验性） |
| **vLLM** | 常驻服务进程（AWQ/GPTQ 4bit + `--enable-lora`） | 高吞吐服务化 |

### 3.5.2  后端自动解析顺序

1. `VULN_SCANNER_BACKEND` 显式设置时优先（`ollama` / `transformers` / `llamacpp`）；
2. 配置了 `VULN_SCANNER_ADAPTER`，或软件目录下探测到合法 LoRA adapter（优先 α0.5 stage2）**且运行时兼容**时，自动选 **Transformers**；
3. 否则回退 **Ollama**——探测到 adapter 但本机跑不动 transformers 时也会自动回退并打印告警。

## 3.6  效果指标（选摘）

> **数字口径**：以下数字全部取自《素材库_论文写作素材收集.md》2026-09-08 统一口径，可由 `scripts/score_batch.py` 复现。
> 评分规则：`acc = (TP+TN)/(TP+TN+FP+FN)`（已裁决样本）；`strict` = 判真且 CWE 归因正确；两阶段系统的未决率与 acc 成对引用。

### 3.6.1  系统级成绩（两阶段架构）

| 系统组态 | 测试集 | recall | FPR | acc | 未决率 | strict | 加权 |
|---|---|---|---|---|---|---|---|
| 两阶段·完整信任层 | 87 合成 | **1.000** | **0.0435** | **0.987** | 13.8% | **0.923** | **0.862** |
| 两阶段·干净评估 | 87 合成 | 1.000 | 0.0435 | 0.987 | 12.6% | 0.774 | 0.786 |
| 两阶段·真实 CVE 片段 | CVE-fix 20 | 0.941 | — | 0.941 | 15.0% | 1.000 | 0.864 |
| 两阶段·真实完整文件 | rolling_dev 50 | 0.645 | — | 0.645 | 38.0% | 0.450 | 0.480 |
| 纯 LLM 对照 | 87 合成 | 0.967 | 0.154 | 0.931 | 0 | 0.898 | 0.829 |

**架构收益直观对比**（两阶段 vs 纯 LLM）：FPR 由 0.154 收敛至 0.0435；CWE 归因 strict 由 0.898 提升至 0.923。

### 3.6.3  传统工具对比（14 段典型样本）
