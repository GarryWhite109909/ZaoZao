## 一、评审标准（先说清楚我凭什么下判断）

我用四条尺子，按优先级排序：

| 尺子 | 含义 | 为什么排这个位置 |
|---|---|---|
| **R1 语义诚实** | 数据模型能否如实表达「我不知道」。任何把"未判定"压缩成"安全/漏洞"的设计都是错的，无论它省了多少成本 | 因为它是**下游一切指标的前提**。判错可以改，语义撒谎改不了 |
| **R2 单一事实来源** | 同一个决策只能有一个权威输入。同一结论若由"模型自述"和"工具产出"两条来源共同构成，必须显式区分 | 因为混淆来源会产生**自我确认回路**，而回路里的 bug 无法通过回归测试发现 |
| **R3 收益/风险对称** | 一个动作若"收益小、失败后果不可逆且不可见"，就不该放在默认路径上 | 因为它决定**事故的分布**，而不是平均指标 |
| **R4 度量有效** | 指标度量的东西必须等于它声称的东西 | 因为**度量错了比没度量更糟**——它会把错误决策合法化 |

下面 6 条"必须改"、2 条"可用性缺口"、5 条"做得好、只需微调"，全部按这四条尺子排。

## 二、必须改的四条（R1/R2/R3 违规）

### S1 反馈回路的写入时机在纠正之前 —— 记录的结论与纠正的结论相反

**现状（执行顺序是硬事实）**

| 序 | 动作 | 行号 |
|---|---|---|
| 1 | `_adjudicate_all()` → 内部 `_adjudicate_one()` → **`signal_registry.record()` 写入工具长期记忆** | `two_stage_scanner.py:1193` → `:3028` |
| 2 | Layer 2 `_counterfactual_pass()`（扰动翻转 → 判定"模式匹配存疑"） | `:1201` |
| 3 | Layer 3 `_evidence_gate_pass()`（`sink_defended` → "模型漏看已有防御 = 误报"） | `:1205` |
| 4 | `_aggregate()` 出最终三态 | `:1208` |

`record()` 只吃模型的原始投票：

```python
# two_stage_scanner.py:3026-3035
        if self._signal_registry is not None:
            self._signal_registry.record(
                rule_id=rule_id,
                confirmed=final_confirmed and valid_votes == self.n_samples,
                n=self.n_samples, votes_true=votes_true,
                votes_false=votes_false, votes_invalid=votes_invalid,
                file=filename, taint_type=finding.taint_type,
                corrected_type=corrected_type,

```

**为什么不对（R2）**

Layer 3 判「模型漏看防御」= **模型在这个文件上错了**。但这一笔在它之前已经按 `confirmed=True` 记进了 `confirmed_files`：

- `signal_registry.py:87-96` `ready` 的条件就是 `len(confirmed_files) >= 2 且 > rejected_files`
- `signal_registry.py:186-189` 确认分支会**解除抑制**
- `signal_registry.py:262-267` `boost_priority` 据此把该规则候选**排到前面**（`:1874` 的 `kept.sort`）

于是：**一个被系统自己认定为"模型误报"的判定，成为"该规则可信"的证据。** 方向恰好相反，且写进去之后没有任何回滚路径（Layer 2/3 的结论从不回改注册表）。

**再往上一层看：门控维度选错了**

`signal_registry.py:13-19` 声明的四重门控是「全票 / 跨样本 ≥K / 双向撤销 / 类型校正分离」，`add_to_learn_pool` 的第五条是「独立验证集」。**五条门控全部在度量"模型有多自信"，没有一条在度量"模型有多可能对"。** 而项目自己留下了完全相反的经验：

```python
# two_stage_scanner.py:1528-1530（证据门 docstring）
# 背景（四维矩阵复盘）：transformers（bf16）端 FP 全部是"全票但错"——共形/
# 反事实验证依赖的投票分歧信号在高精度后端上不出现
```

**用"全票"当可信度门槛，而系统自己的记录是"高精度后端的误报全部是全票"** —— 门控度量的量与它想防的东西正交。这不是调参问题，是维度选错。

**改成什么**

```python
# ① record() 的输入改为"最终采信结论 + 与模型无关的证据"，而不是原始投票
def record(self, rule_id, *, final_verdict: Optional[bool], n, votes_true, votes_false,

           suppress_on_neg: bool = True) -> None:
    # 门控 0（新增，与模型无关）：任何一条成立即拒收
    if final_verdict is None:                       # 最终是"需复核" → 不足以改写工具记忆
        return
    if evidence_gate:                               # Layer 3 命中 → 判定为疑似误报，绝不可作为"可信"证据
        return
    if counterfactual and counterfactual.get("already_defended") and not counterfactual.get("flipped"):
        return                                      # Layer 2 存疑 → 同上
    ...

# ② 写入时机移到链路末：在 _aggregate 之后，按"最终采信"回填
#    two_stage_scanner.py:1199-1208 之后新增一段 _signal_backfill(result)
```

**附带收益**：这样 `record()` 天然只接受"通过全部门控的采信判定"，与说明书 4.3 宣称的「只有通过四重门控的 A/B 级输出才写入工具记忆」**第一次真正对齐**——现在的实现是把模型的原始投票当 A/B 级。

**工作量**：`signal_registry.record` 改签名 + 新增 `_signal_backfill` 约 60 行，`signal_registry.py` 自带的 5 组单测需同步改断言。

### S2 「未复核」必须是数据模型的一等公民 —— 现在它复用了 `has_vulnerability=False`

**现状**

```python
# two_stage_scanner.py:2149-2152  targeted C 档：零盲区，不送 LLM
        if tier == "C":
            _monitor_incr("recheck_tier_c")
            return {"sampled": False, "tier": "C", "has_vulnerability": None, ...}
```

```python
# two_stage_scanner.py:1012-1019  调用方把它判成"安全"
            if recheck.get("tier") == "C":
                # 定向复核 C 档：零盲区 → 未送 LLM。
                # 关键：这不是"复核判安全"（那需要 LLM 真的看过），而是
                # "注意力预算未覆盖"。故 decision 单独取值，且**不转人工**——
                # 否则每个零风险文件都会变成一条待办，review 队列被淹没。
                result.has_vulnerability = False
                result.stage1["decision"] = "no_candidate_no_blind_spot"
```

注释把问题说得很准（"这不是复核判安全，而是注意力预算未覆盖"），但**结论是错的**：为了不让 review 队列被淹没，让判定层去说一句它自己都不相信的话。

**为什么不对（R1 + 层次错误）**

1. **语义撒谎**：`has_vulnerability=False` 在下游全部被读成"已判安全"。`_aggregate`（`:3200-3215`）、前端 `cardHTML` 的 Safe card 分支（`scan.html:2192-2199`，注释写"未发现漏洞"）、安全评分（`nivis-common.js:233-239`，安全不扣分）——**三处全部把它当"已确认安全"消费**。
2. **层次错误**："review 队列会被淹没"是**展示层**的容量约束。用展示层的容量去决定判定层的输出，等于让 UI 决定真相。正确的分层是：判定层如实输出"未经复核"，展示层决定怎么聚合与折叠。
3. **它还会污染统计口径**：说明书 3.6 的 `Acc 已裁决准确`、表 3-4 的 `未决率`，其分母都依赖"哪些样本是已裁决的"。把 C 档塞进 `False`，会让"已裁决"这个集合在开启 targeted 之后**含义改变**。

**改成什么**

在结果对象上给"复核覆盖度"一个显式字段，判定层不再借道 `has_vulnerability`：

```python
# TwoStageResult 增字段（与 has_vulnerability 正交）
review_coverage: str = "llm_checked"   # llm_checked / not_covered / unknown
# stage1 已留痕 decision="no_candidate_no_blind_spot"，把它提升为顶层语义
```

- **判定层**：C 档输出 `has_vulnerability=None` + `review_coverage="not_covered"` + `decision="no_candidate_no_blind_spot"`。
- **聚合层**（`:3199-3265`）：C 档不参与"文件级 True/False"的推导，走 `None` 分支。
- **展示层**：新增第三类卡片「未复核（工具零召回、未命中盲区，未送 LLM）」，与「安全」「需复核」并列。review 队列的淹没问题交给**展示层聚合**解决：

```
本轮 180 个文件：已裁决 26（漏洞 3 / 安全 21 / 需复核 2）· 未复核 154
[展开未复核文件清单]
```

一行汇总 + 可展开，比 154 张待办卡清爽，也比 154 个假的"安全"诚实。
- **评分口径**：`not_covered` 与"需复核"同档——**单列不扣分、也不计入安全**；`scan.html` 的评分函数需要新增一个 counts 分类（当前只有 critical/high/medium/low/info）。

**这条是全项目最重要的一条**：它同时修掉 R1（语义）、并且让 A 档那个「粘滞 no_candidate_mode」bug 的后果从"静默判安全"降级为"静默未复核"——**同一个 bug 的危害级别直接掉一档**。修 S2 的收益超过修 A1。

### S3 规则级抑制这个动作本身应当取消

**现状**

```python
# signal_registry.py:236-238
                    if (len(sig.rejected_files) >= MIN_AGREE_SAMPLES
                            and not _is_protected_rule(rule_id)):
                        sig.suppressed = True
```
```python
# two_stage_scanner.py:1861-1866  读端：命中即从候选集合里删掉
            if (f.category in _ADJUDICATE_CATEGORIES and f.rule_id
                    and reg.is_suppressed(f.rule_id)):
                skipped.append(f.rule_id)
                continue
```

**为什么不对（R3：收益/风险严重不对称）**

| 维度 | 评估 |
|---|---|
| 收益 | 省掉该规则每条候选的 N=3 次采样 |
| 风险 | 该规则在**所有文件**上永久不再产生候选 → 真阳性从召回层面消失，且**不可见**（有 `_last_suppressed_rules` 留痕，但改不了结论） |
| 补偿 | 抑制后强制复核（`:1873` `self._last_suppressed = True` → `_maybe_recheck(force=True)`）——**补偿措施把主要收益吃掉了**：仍然要花 LLM 采样，只是换了条路径 |
| 事故记录 | `signal_registry.py:220-223`「triage_default 轮 recall 崩塌至 0.25 的根因」；`:42-44`「生产池曾实锤压掉 python-xss-taint / python-sqli-taint 全族」；`eval_two_stage.py:317-319`「fixed3 期间 B608 等 10+ 规则被两次全票否决入池，fixed4 加载后候选在进裁决前被吞，**结果依赖样本顺序**」 |
| 正面收益记录 | **零** |

**而且注释已经自己把这条策略论证为错的了：**

```python
# signal_registry.py:38-44
# 规则级抑制的粒度缺陷：规则是否误报取决于"文件"（B608 在 hard_bypass_01 的
# replace 假净化上是否决性证据，在别的文件可能是正确告警），规则级抑制 → 样本级
# 盲区且静默（工具层零召回无任何提示）。
```

注释写明了"规则级 vs 样本级"是维度错误，代码的应对是**给自有链级规则开豁免**（`_PROTECTED_RULE_PREFIXES`），而不是**修掉这个维度错误**。修法与事故的关系是：三次事故全部来自抑制动作，每次修法都是加一道护栏（≥2 独立文件、保护前缀、读端同口径豁免），**护栏越加越多，动作本身没动**。

**改成什么：把"抑制"降级为"降权"，永不移出召回集合**

```python
# signal_registry.py
# 删除 Signal.suppressed 的读端语义（is_suppressed → 保留函数但恒 False，或直接删）
# 新增样本级负向记忆：
class Signal:
    rejected_files: list[str]      # 已有，保留
    def priority_factor(self, file: str) -> float:
        """按文件的负向记忆降权（保留候选，只改变顺序与预算分配）。"""
        if file in self.rejected_files:
            return 0.6                   # 同文件被否过 → 排后，但仍进裁决
        return 1.0 + self.confidence if self.ready else 1.0
```

三点配套：
1. `_apply_signal_registry` 只做**重排**，不再 `continue` 跳过；`suppressed_skipped` 计数改为 `deprioritized`。
2. 真正的"省算力"需求交给**已有的正解**——注意力预算 `risk_budget`（`main.py:230-237` 的思路是对的：选谁扫由风险分决定，而不是由"这条规则被判过误报"决定）。把负向记忆作为 risk_score 的一个负项，让它和盲区、入口点等信号**在同一张账单里竞争**。
3. 抑制池的"防噪"价值若真的存在，用**候选级**表达：`(rule_id, 文件结构指纹)` 为键，而不是 `rule_id` 为键——这才与注释认下的"误报取决于文件"一致。

### S4 共形预测的实际作用与它的宣称不匹配，且生产正在加载一个已知泄漏的校准文件

**现状：三层错位**

**① 生产加载的是一个项目自己标注为"覆盖率保证不成立"的文件**

```python
# eval_two_stage.py:323-325
    #   b) 共形校准：未显式 --calibrate-from 时，禁用 TwoStageScanner 启动时自动加载
    #      models/conformal_calibration.json——该文件是 08-16 在**同一 87 段测试集**上
    #      的历史结果拟合的（in-sample 泄漏，覆盖率保证不成立）。显式给源才校准。
```

| 路径 | 行为 |
|---|---|
| 评估（`eval_two_stage.py:335-338`） | `VULN_SCANNER_CONFORMAL_CALIB=0` → **禁用** |
| 生产（`two_stage_scanner.py:820-824`） | **自动加载** `models/conformal_calibration.json`（该文件当前存在，131 B） |

即：**评估用干净的、生产用泄漏的。** 而说明书 4.3「默认覆盖率 90%」、5.2「评估侧拟合、生产端加载，可审计降级」据此而写。

**② 分数空间在 N=3 上没有分辨率**

```python
# conformal.py:48-54
    def score_vuln(votes_true, votes_false, votes_invalid) -> float:
        valid = votes_true + votes_false
        if valid == 0:
            return 1.0
        return 1.0 - votes_true / valid
```

非一致性分数是**投票比的确定性函数**。N=3 时取值只有 `{0, 1/3, 2/3, 1}` 四个点，`alpha=0.1` 的 0.9 分位数只能落在这四个点上 → "90% 覆盖率"是**在四点上取的一个阈值**，粒度远不足以称为统计保证。"覆盖率"这个性质要求分数是**连续的、与标签有单调关系**的量；投票比在 N=3 时几乎不携带这种信息。

**③ 它放宽了判定，然后被另一个门收紧回去——净效果为零**

```python
# two_stage_scanner.py:3246-3251
        # vulnerable 接管必须存在高置信判中（≥_CONF_AUTO）：共形会把 T2/F1(0.667)
        # 也判 vulnerable（净化校准后阈值放宽），低置信判中不能直接判漏洞（safe_05
        # 类 FP 根因），须走 strong_confirmed 分支（进 review 或反事实验证）。
        if cf_unanimous and cf_sets[0] == "vulnerable" and strong_confirmed and not cf_unflipped:
```

这段注释是**结构性自证**：共形把 `confidence=0.667`（= N=3 时 2/3 票，即常见情形）也判 `vulnerable`，比 `_CONF_AUTO=0.8` **更宽**；于是必须再挂一个 `strong_confirmed` 把它收回来。一个门控放宽、另一个门控收紧，净效果为零——对外则宣称这是"带覆盖率保证的统计门控"。

唯一真正独立生效的分支是「全员共形 = safe 且无任何 confirmed → 提前判安全」（`:3238-3243`），其行为与"该文件所有裁决均未被判真"高度重合。

**为什么不对（R4 + R1）**

Layer 1 的**叙事权重**（"2.5 代信任层"的核心组件、术语表、图 4-2）远高于它的**实际判别力**。而它同时在生产上引入了一个"来源不干净、且无分辨率"的先验。懂共形预测的评委只需问两个问题就能问到底：**"校准集多大？和测试集重叠吗？分数是什么分布？"** 而答案分别是"87 段同一测试集上拟合的"、"重叠"、"四个离散值"。

**改成什么（三条路，我推荐第 1 条）**

1. **诚实降级（推荐，零成本）**：
   - 立刻删除 / 重命名 `models/conformal_calibration.json` → `conformal_calibration.in_sample_leaked.json`，让生产回到"未校准 → 全部 uncertain → 回退投票逻辑"（`:3015` 的 `if self._conformal is not None and self._conformal.calibrated()` 已经支持这个降级路径，代码无需改）。
   - 文档把 Layer 1 从"统计门控"改为"投票一致性规则的显式化"，从"90% 覆盖率保证"改为"未校准状态下不启用，仅作可扩展点"。
   - 收益：**去掉一个说不清的宣称，比保留一个会被问穿的宣称更安全**。竞赛评委对"诚实标注边界"的评分通常高于"过度包装"。
2. **真做共形（成本高，只有在你愿意补实验时选）**：把非一致性分数换成**连续量**（单票的 `log P(has_vulnerability=True)`、或生成序列的对数似然），`n_samples` 提到 5~10，用 **rolling_dev 50 段冻结集**校准（与 87 段评测集严格不重叠），并报告经验覆盖率曲线（nominal vs empirical）。这样"覆盖率保证"才立得住。
3. **降级为探索性组件**：保留代码，默认 `use_conformal=False`，论文里作为"我们尝试过并评估了它不适用"的负面结果——**这也是很体面的论文素材**。

**为什么不对**

**（a）判定条件与宣称的来源不符 —— 存在模型自述锚点污染（R2）**

**（b）措辞变更的驱动样本量不足（R4）**

**用 3 段样本决定一条会系统性影响全部裁决方向的 prompt 措辞。** 而这正是项目自己在别处反复立规矩禁止的做法：

- `blind_spots.py:22-24`「**中性措辞**：……绝写"此处存在 XX 漏洞"——后者会锚定模型、抬高判真率（`prompts._TRUST_NOTE_CHAIN` 已实证：prompt 里的信任标注会实质影响模型判断）」

同一份代码里：一个模块（blind_spots）因为"信任标注会实质影响模型判断"而严格约束自己只用中性措辞；另一个模块（prompts._TRUST_NOTE_*）**正在做那次被引为证据的强标注**，且变更依据是 3 段样本。

**改成什么**

1. **补上锚点来源字段**（这是最小改动、收益最大）：

       ...
       anchor_source: str = "tool"      # tool / model_vote
   ```

   elif has_chain:

       trust_note = ...
   ```
2. **Layer 2 用未污染的原 finding**：在 `_adjudicate_all` 里 `verdict.finding = finding.to_dict()` 之前深拷贝一份 `verdict.finding_raw`，反事实验证读 `finding_raw`。
3. **把 prompt 措辞纳入受控变更流程**：`_TRUST_NOTES` / `_TRUST_NOTE_CHAIN` / `V3_PROMPT` 任何改动，PR 描述里必须附**rolling_dev 50 段冻结集上的 strict / micro / 未决率三元组**，缺一不可合入。建议直接在文件顶部写死这条规矩（与 `blind_spots.py:65-68` 的"措辞纪律"同一形式），并写进 `.github/workflows/pr-review.yml`。

### S6 漏报率估计量有选择偏差 —— 需要重新设计估计量，不只是改名

（在上一轮 A 档里已作为 B4 报过，这里给完整设计。）

**现状**

```python
# two_stage_scanner.py:90-93
    snap["estimated_miss_rate"] = (
        round(snap["recheck_vuln_found"] / snap["recheck_sampled"], 4)
        if snap["recheck_sampled"] else None
    )
```

分母 `recheck_sampled` 递增于 `:2003`（sampled 模式，按 `sampling_rate` 随机）与 `:2156`（tier A / tier B）。tier A 的入选条件是**"文件风险分 ≥12 或高优先级盲区 ≥2"**（`:2131-2141`），是**按可疑度挑选的样本**。把随机样本与可疑样本混在一个分母里，`漏报数/复核数` 必然高估工具真实漏报率。前端把它标为「工具漏报率估算（n=…）」（`scan.html:1978/1996`），论文的召回漂移分析也会引用它。

**为什么不对（R4）**：这个数字一旦被当作"工具层漏报率"引用，会让"工具层召回不够 → 所以需要模型兜底"这个核心论点**建立在偏高的数字上**。评委只要问一句"你的复核样本是怎么抽的"，这个数字就失效——而它本来可以是项目最有说服力的创新点（在线测漏报）。

**改成什么：分层报告 + 只对随机层给"率"**

```python
_MONITOR = {
    ...
    # 随机层（无偏）：只有 C 档抽样命中走这里 —— random.random() < sampling_rate
    # 现成判据已存在：:2146-2147 命中时 why="c_tier_sampled"，据此分流即可，无需新判据
    "rand_recheck_n": 0, "rand_recheck_hit": 0,
    # 定向层（有偏，报"命中率"而非"漏报率"）
    "tier_a_n": 0, "tier_a_hit": 0, "tier_b_n": 0, "tier_b_hit": 0,
}

# 落点：two_stage_scanner.py:2215-2216 的 `if hv is True: _monitor_incr("recheck_vuln_found")`
# 改为按 why 分流：
#     if hv is True:
#         _monitor_incr("rand_recheck_hit" if why == "c_tier_sampled" else f"{tier_name}_hit")
# 并在 :2154-2156 同步分流分母。

# snapshot
snap["miss_rate_unbiased"] = (rand_hit / rand_n) if rand_n else None      # 可对外称"漏报率估计"
snap["tier_a_hit_rate"] = (a_hit / a_n) if a_n else None                  # 只能称"高危文件复核命中率"
snap["miss_rate_ci"] = _wilson_ci(rand_hit, rand_n)                       # 给区间，别给点估计
```

前端文案随之改：`未覆盖层随机抽样 n=… → 漏报率 95%CI [a%, b%]`，与 `高危定向复核 n=… → 命中率`。**三个改动（分层、给区间、改名）之后，这个指标从"会被问倒"变成"方法论亮点"**：在线估计工具漏报率本身就是很漂亮的设计，只是现在的口径把它做成了不可引用。

**附加建议**：`n<5` 时前端已经会标"样本不足仅供参考"（`scan.html:1985-1987`）——这个意识是对的，但点估计加个括号挡不住引用。**低于 30 就只显示区间，不显示点估计**。

## 四、可用性层面的两条策略缺口

### S7 进程内推理的 `timeout` 是假参数 —— 而它是唯一工作线程

**现状**

```python
# transformers_client.py:728-741
    def generate(self, prompt, system_prompt=None, temperature=0.0,
                 max_tokens: int = 2048, keep_alive=0,
                 timeout: int = 300, num_ctx=None, ...) -> Dict:
```
`timeout` **在整个 `generate` 函数体内从未被使用**（全文出现位置只有签名 `:735`、`generate_structured` 的透传 `:980/:1003`、`unload_model` 的 `:700`）。对比 `llm_client.py:218` 的 Ollama 路径：

```python
resp = requests.post(self.api_chat, json=payload, timeout=timeout)   # ← 真超时
```

**为什么不对（R3）**

- 四个后端对外宣称**同一个 `generate(..., timeout=...)` 契约**，上层（`_sample_votes` `:2932`、`_maybe_recheck` `:2181`、counterfactual）都依赖"超时后返回 `{"error": ...}` 字典"这个契约（`:2203-2207`、`:2054-2056` 的 `except` 兜底）。
- 进程内推理**不会抛异常也不会超时**——它会一直持有 `self._gen_lock`（`:760`）。
- 而调度器只有**一个工作线程**（`scheduler.py:214`），且自己声明无法强杀：`scheduler.py:103-104`「线程无法安全强杀，故不硬中断，仅在 `status()` 中标记 `possibly_stuck`」。
- 结论：**一次 `model.generate()` 卡死（OOM 后显存抖动、驱动 hang、超长 prefill 触发换页）= 整个服务停止响应，且只在 `/api/queue/status` 里留一个标记。** 这是被接受的可用性单点，但它和"作品要一键启动、普通人能用"的定位冲突——用户看到的是"扫描一直转圈"。

**改成什么（低成本，两处）**

1. **墙钟停止条件**（HF 生态标准做法，不改并发模型）：
   ```python
   class _WallClock(StoppingCriteria):
       def __init__(self, seconds: float): self.dl = time.time() + seconds
       def __call__(self, input_ids, scores, **kw): return time.time() > self.dl

   # generate 内，构造 kwargs 时：
   if timeout and timeout > 0:
       kwargs["stopping_criteria"] = StoppingCriteriaList([_WallClock(timeout)])
   # 生成后判断：text 为空且已超时 → 返回 {"error": f"进程内推理超时（{timeout}s）"}
   ```
   这样 `timeout` 从假参数变成真参数，`_sample_votes` 的"无效票"语义（`:2939` `votes_invalid += 1`）自动生效，**不需要改任何上层逻辑**。
2. **收紧生成预算**：裁决场景的 `max_tokens` 默认 2048（`:733`）对"短 JSON 输出"过宽。`prompts.py` 自己的口径是裁决 prompt 目标 ~1500 字符、输出是固定字段 JSON（`build_triage_prompt` docstring `:998-1004`）。把裁决路径显式传 `max_tokens=768`，卡死时的白烧从 2048 token 降到 768，同时也降低"生成途中开始复读"的概率。
3. （可选）`possibly_stuck` 不该只躺在 status 里：超过 `exec_timeout` 时**向 `/api/health` 暴露为 degraded**，让启动器/仪表盘能提示"引擎可能卡住，建议重启"，把不可见变成可见。

### S8 客户端配额键不该由客户端决定

（A5 的完整设计。）现在 `resolve_client_id` 的末行是 `return c or fallback`（`scheduler.py:421`），任意字符串都成为独立桶，轮换 `X-Client-Type` 即绕过 `max_per_client=8`。

**改成什么**：让"桶"由服务端事实决定，客户端只能在其中**选择用途**而非**选择身份**。

```python
def resolve_client_id(client_type: Optional[str], fallback: str = "web",
                      batch_id: Optional[str] = None) -> str:
    # 批量入口固定用服务端生成的批次 id（同一次批量 = 同一个桶，不可自报）
    if batch_id:
        return f"batch:{batch_id}"
    c = (client_type or "").strip().lower()
    return c if c in _KNOWN_CLIENTS else fallback      # 白名单收口，未知一律归 fallback
```
配套：`_scan_files_scheduled` 生成一个 `uuid4().hex[:8]` 作为 `batch_id` 传入（`main.py:1217`、`:1114`），使**一次批量扫描只占一个桶**；插件侧若要独立配额，走白名单内的 `vscode`/`intellij`。
