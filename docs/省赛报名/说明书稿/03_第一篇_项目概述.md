# 第一篇  项目概述

> **本篇对应官方材料**：引言性概述（置于功能需求说明书之前，提供背景与定位）

## 1.1  作品名称与定位

**作品名称**：码安管家——LLM 驱动的漏洞分析站
**软件名称**：凿凿（ZaoZao）（内核引擎代号 Nivis）

凿凿是一套**在用户本机运行**的代码安全分析系统。其基本工作方式是：由传统安全工具快速定位代码中的可疑点，再由本地部署的大语言模型对每个可疑点做语义判断——它是不是真漏洞、属于哪一类 CWE、应当如何修复。

系统面向的核心问题，是传统静态分析工具与直接使用大模型这两条路径各自的局限。二者的对比见下表：

| 维度 | 传统工具（Bandit/Semgrep） | 凿凿（LLM 驱动） |
|---|---|---|
| 检测方式 | 固定规则模式匹配 | 代码语义理解、上下文感知 |
| 漏洞覆盖 | 已知漏洞模式 | 可发现变体/非典型漏洞 |
| 输出形式 | 漏洞类型 + 规则编号 | 自然语言解释 + 修复建议 |
| 多语言 | 工具专属规则集 | 跨语言统一理解 |
| 误报控制 | 规则泛化能力差 | 上下文判断过滤/净化逻辑 |

**系统定位**：它比规则工具“懂语义”（能理解数据流、识别有效防御、解释漏洞原理），比云端服务“更私密”（代码、模型、知识库全部留在本机，运行期可完全离线）。

**输出内容**：对源代码进行安全审计，输出**漏洞判定 + CWE 类型 + 风险等级 + 污点来源/触发点 + 自然语言解释 + 修复建议**。

## 1.2  开发背景与问题

### 1.2.1  软件安全形势

软件安全漏洞造成的经济损失与社会影响持续扩大。IBM《2024 年数据泄露成本报告》显示，全球单次数据泄露事件平均损失达到 488 万美元，较 2023 年增长 10%，为历年最大增幅；其中由系统漏洞利用引发的泄露事件占比持续位于前列。中国国家互联网应急中心（CNCERT）发布的《2024 年上半年我国互联网安全态势报告》指出，上半年收录的通用软硬件漏洞数量同比增长 17.9%，Web 应用层漏洞仍为攻击者主要入口。

在漏洞数量持续增长的同时，安全缺陷的修复成本随发现阶段后移而急剧上升，代码安全审计因此在软件开发生命周期中的位置不断前移，成为 DevSecOps 实践的关键环节。然而人工代码审计受制于审计员的产能——逐条核对规则文档、理解数据流上下文、判断防御是否有效，单条告警的理解与验证往往需要数十分钟量级，难以匹配漏洞增长的速度。

### 1.2.2  现有技术路径的局限

| 路径 | 局限 |
|---|---|
| 传统静态分析（SAST） | 规则驱动，只能覆盖已知漏洞形态；规则泛化能力差导致高误报；对需要理解数据流与业务语义的漏洞（认证缺失、信任边界绕过）天然覆盖不到 |
| 云端大模型直接分析 | 代码需上传第三方，隐私合规风险；无法离线；输出不稳定，缺可核验的证据链 |
| 本地大模型直接全文分析 | 开放生成任务下模型注意力被长文件稀释，漏报与幻觉并存；无工具证据锚定，结论不可追溯 |

### 1.2.3  本作品的解法

针对上述三处局限，本项目做了三个**第一性选择**——它们共同构成本作品与“把大模型接进扫描器”的分界线：

**选择一：把大模型的任务从“发现”改成“判断”。** 开放生成任务里，模型既要在一整份文件里找线索、又要判断线索真伪，注意力被长文件稀释，结论无法锚定。本系统改为**两阶段**：Stage 1 由确定性工具（Bandit / Semgrep / Gitleaks / Trivy 等）把可疑点召回齐全——这一步是规则擅长的；Stage 2 由本地大模型对**每一条具体候选**只回答一个封闭问题：“这条告警是不是真漏洞、属于哪一类 CWE、怎么修”。模型不再需要在全文里“大海捞针”，只需要在带行号的证据片段上做判别。错误的来源因此变得可归因：要么“工具没召回”，要么“裁决判错”，二者可分开度量、分别修复。

**选择二：让工具与模型互相修正，而不是单向调用。** 裁决结论不直接采信、也不直接丢弃，而是先经信任层分级，只有通过五重门控的高质量判定才被允许回填工具层记忆（候选排序加权 / 类型映射校正 / 按文件的负向记忆降权）。这意味着工具不只是“给模型喂线索”，它自己的误报特征也在被模型的判定修正——形成**工具-模型自适应闭环**。为防止闭环反过来污染确定性工具，回填门槛被写成代码参数而非口头原则。

**选择三：如实表达“不确定”和“没看过”。** 安全工具最常见的失效模式不是判错，而是把“没检查”呈现成“没问题”。本系统把结论拆成四态：发现漏洞 / 安全 / 需人工复核 / **未复核**。低置信判定转人工复核；受限于注意力预算而未被模型处理的文件标注“未复核”，**不冒充“已判安全”**。所有门控在这条原则上是一致的——它们只负责把判定降级到人工复核，从不代替人下结论。

此外，三项工程约束贯穿始终：**完全离线**（代码、模型、知识库均不出本机）、**可复现**（评估口径与冻结测试集固定，一键复现）、**可卸载**（全部数据在项目目录内，分级清理）。

## 1.3  目标用户与使用场景


| 目标用户 | 典型场景 | 使用方式 |
|---|---|---|
| 开发者个人 | 交代码前自查一段“拿不准安全不安全”的逻辑 | Web 界面粘贴代码 |
| 开发团队 / 项目负责人 | 提交 / 发布前把整个项目过一遍 | 批量扫描 + 导出 Markdown 报告 |
| 采购 / 引入方 | 评估一个开源仓库能不能引入 | GitHub 仓库扫描 |
| 日常编码者 | 写代码时随手查当前文件 | VS Code / IntelliJ 插件 |
| 自动化流水线 | 提交前检查、CI 集成 | 命令行工具 CLI |

**系统提供四种使用方式**：Web 界面、命令行工具、VS Code 插件、IntelliJ 插件。四者共享同一个后端服务，功能对等。
