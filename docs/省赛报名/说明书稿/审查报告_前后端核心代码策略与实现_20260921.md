缺口：**任何** `http(s)://` 目标都会被拉取（内网、`127.0.0.1:8765` 自身、云元数据 `169.254.169.254`），且 `_resumable_download`（`:1972-2083`）**只做完整性校验（`downloaded == total`）不做大小上限**（`:2056-2058`），响应体多大就写多大 → 单次请求即可填满磁盘。

**更值得单独一提**：

```python

    ...
    no_proxy |= {h for h in hosts if h and h.strip()}
    val = ",".join(sorted(no_proxy))
    os.environ["NO_PROXY"] = val
    os.environ["no_proxy"] = val
```

在 `run_download` 线程里以 `_no_proxy_for_mirrors(urlparse(url).hostname)` 调用（`:2404`），而 `url` 是**用户输入** → 任意 hostname 被写进**进程级** `NO_PROXY`，并且**永不清理**。这会持续改变**该进程内所有后续出网请求**的代理行为（包括其它端点、模型拉取、chromadb 首次下载），属于「请求参数污染全局配置」。同一函数里 `_normalize_socks_proxy()`（`:1949-1962`）也改写进程级 `HTTP_PROXY/HTTPS_PROXY/ALL_PROXY`，虽然是幂等规范化，但同样属于「请求处理中修改进程级环境变量」这一类。

**修复建议**

1. `download-gguf` 入口加与另两个端点同源的校验：
   ```python
   url_err = validate_target_url(url)
   if url_err:
       return JSONResponse({"error": url_err}, status_code=400)
   ```
   若担心误伤 GitHub 大文件 URL，改成**白名单 host** 更贴合语义：只允许 `huggingface.co` / `hf-mirror.com` / `github.com` / `objects.githubusercontent.com`（GFW 友好场景下这几个已覆盖全部模型来源），其余一律 400。
2. 给 `_resumable_download` 加 `max_bytes`（建议 8GB，覆盖最大 GGUF），超限即中止并 `unlink` 半成品；同时把 `Content-Length` 与已下载量一并校验。
3. `_no_proxy_for_mirrors` 只在**已知镜像域名**上生效：
   ```python
   _TRUSTED_MIRROR_HOSTS = {"hf-mirror.com", "mirror.ghproxy.com", "github.com", "huggingface.co"}
   host = (urlparse(url).hostname or "").lower()
   if host in _TRUSTED_MIRROR_HOSTS:
       _no_proxy_for_mirrors(host)
   ```
   或者改为「构造显式 `requests.Session(trust_env=...)`/`proxies=` 参数」而不是改环境变量——这样作用域天然限制在本次下载。

### A4 ★★ `download-hf` 的 `model_id` 可越出 `models/transformers/`

```python
# graduation_project/paths.py:181-190
def local_hf_model_dir(repo_id: str) -> Path:
    name = repo_id.split("/")[-1] if "/" in repo_id else repo_id
    return find_project_root() / "models" / "transformers" / name
```

`main.py:2188-2198` 直接把请求里的 `model_id.strip()` 传进来，**未做任何字符校验**（对照 `download-gguf` 对 `filename` 有显式穿越检查）。取最后一段后，`..` 是合法取值。实测（`pathlib` 真实行为）：

| 输入 `model_id` | 取出 `name` | 结果路径 |
|---|---|---|
| `Qwen/Qwen3-8B` | `Qwen3-8B` | `models/transformers/Qwen3-8B` ✅ |
| `..` / `../..` / `a/../../..` | `..` | `models/transformers/..` = `models/` |
| **`..\..`** | `..\..` | **`models/transformers/..\..` = 项目根** |

Windows 上 `Path` 把 `\` 当分隔符，所以 `..\..` 这一形态一次上跳两级。写入目标是「下载的模型目录」，攻击面是**任意目录写入/覆盖**（目录内容由下载内容决定，`hf_hub` 下载会创建多层文件）。

**修复建议**

```python
def _safe_model_dir(base: Path, name: str) -> Path:
    name = name.strip().replace("\\", "/").split("/")[-1]
    if name in ("", ".", "..") or any(c in name for c in ':*?"<>|'):
        raise ValueError(f"非法模型名: {name!r}")
    target = (base / name).resolve()
    if not target.is_relative_to(base.resolve()):      # Py3.9+ 用 os.path.commonpath 亦可
        raise ValueError(f"目录越界: {target}")
    return target
```
并把 `local_hf_model_dir` / `local_vllm_model_dir`（`:225-232`，同一写法）都改为调用它。`download-hf` 端点再加一层 `try/except ValueError → 400`。

### A5 ★★ 调度公平性建立在客户端自报请求头上，可被绕过

```python
# app/backend/services/scheduler.py:402-421
def resolve_client_id(client_type: Optional[str], fallback: str = "web") -> str:
    if not client_type:
        return fallback
    c = client_type.strip().lower()
    if c in ("web", "browser"): return "web"
    if c in ("vscode", "vs code", "code"): return "vscode"
    if c in ("intellij", "idea", "jetbrains"): return "intellij"
    return c or fallback          # ← 任意字符串都成为独立 client_id
```

而配额就是按这个 id 记的：

```python
# app/backend/services/scheduler.py:196-206
            pending = self._client_counts.get(client_id, 0)
            if pending >= self._max_per_client:       # 默认 8
                self._reject(future, RuntimeError(...))
```

`main.py:1079 / 1251 / 1424` 用 `request.headers.get("x-client-type")` 取值。**同一次批量扫描只要轮换 `X-Client-Type`（或干脆删掉走 `fallback="web"` 与再补一个随机值交替），配额就形同不存在。** 注释里承诺的「防止单批霸占」在有恶意/有 bug 的调用方下不成立。

**修复建议**：把配额键做成「不可自报」或「自报 + 服务端事实」的组合：
- 最简单：`client_id = f"{normalized_header or 'web'}"` 前面再拼一个服务端可观测事实，例如 `X-Client-Instance`（插件生成的持久 UUID）缺失时**回退到全局桶** `"anon"`，而不是让每个任意值各占一个桶——即 `return c if c in _KNOWN_CLIENTS else fallback`，把 `:421` 的 `return c or fallback` 改成白名单收口。
- 更彻底：批量入口（`/api/batch`、`/api/github-scan`、`/api/url-scan`）固定使用**单一服务端批次 id** 作为 client_id，不走请求头。

顺带：`PRIORITY_NORMAL = 1` 在 `:52` 的注释说是「`resolve_priority` 的兜底值」，但 8 处调用全部显式传 `PRIORITY_HIGH`（`main.py:1003/1037/1493/1622`）或 `PRIORITY_LOW`，`PRIORITY_NORMAL` 只在 `status()` 统计（`:325/343`）里出现——注释描述的兜底路径在生产上永不生效。

### B1 多模型投票「平票 → 判漏洞」，与两阶段「平票 → 需复核」口径冲突


两处矛盾：
1. **同一系统两套平票口径**：`two_stage_scanner` 的平票是 `has_vulnerability=None`（转人工复核，`_aggregate` 注释 `:3073-3074`）；多模型路径平票却是「判漏洞」，而 `agreement_ratio=0.5` 恰好等于两阶段里「低置信确认」的下界。**在证据最强对立（50/50）时给出了最强的结论**。
2. **与说明书的宣称冲突**：2.3 写「需人工复核是设计行为……宁可多一道人工复核，也不漏报真漏洞、不错杀不确定的判定」；但多模型平票不走这条路径，前端 `cardHTML` 对 `_kind==='multi'` 渲染的是**漏洞卡**（`scan.html:2268-2279` 的 `voteInfo` 只是附注「势均力敌 · 50%」）。

好处是**不会撞** `max_queue=50`（这点是好的，我原本怀疑 200 文件批量会被拒，实测不会），代价是：
- 200 个文件 × 单文件 5~15s（`scan.html:568-575` 的本机实测口径）= **17~50 分钟**，且期间推理无并行；
- 调度器的优先级机制在批量场景退化为「文件之间可插队」，不等于并发能力。

这与 2.7「性能预期」和 3.2「52 个核心文件」的工程感之间会形成落差。**建议**：要么在文档里如实写「单卡串行推理，批量按文件数线性增长」（已有雏形但没点明串行），要么给 Ollama 之外的批量通道（vLLM `continuous batching` 已有 `/api/vllm-analyze`）做一次批量压测数据，把「为什么不做并行」写成显式取舍。

### B3 NDJSON 推送用「线程池 + 1~2s 轮询」实现跨线程取队列

```python
# main.py:1817-1825（/api/models/pull）；:2299-2310（download-hf）；:2473-2483（download-gguf）
        while True:
            try:
                chunk = await asyncio.get_event_loop().run_in_executor(
                    None, lambda: chunk_queue.get(timeout=1),
                )
            except Exception:

```

- 每 1~2 秒向默认线程池投一个「只为等待队列」的任务。默认池 `min(32, cpu+4)`，在批量扫描已占用 4 个 worker（`two_stage_scanner.py:1622`）且 `_clone_and_collect`/`fetch_url` 走 `asyncio.to_thread` 的情况下，这是可避免的池竞争。
- 正确做法是现成的：`asyncio.Queue` + 生产线程里 `loop.call_soon_threadsafe(q.put_nowait, chunk)`——调度器自己就是这么做的（`scheduler.py:270-272`），同一份代码库里已有更优范式。
- `asyncio.get_event_loop()` 在协程内已弃用（应用 `asyncio.get_running_loop()`），属低成本现代化项。
- `except Exception` 吞掉所有异常并当作超时处理，包括线程池关闭等真实故障。
