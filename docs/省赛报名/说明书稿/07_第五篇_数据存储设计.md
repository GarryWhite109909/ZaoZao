# 第五篇  数据存储设计

> **本篇对应官方材料**：数据库设计说明书（如必要）
> **说明**：本系统**无独立数据库**（不依赖 MySQL / PostgreSQL / SQLite 等关系型数据库服务）。系统运行所依赖的全部数据以**本地文件 + 向量库 + 浏览器本地存储**三类形式持久化。本篇按官方「如必要」的口径，如实描述本地数据存储设计。
> 本篇为新写章节（约 2~3 页），素材已按 2026-09-19 代码实测核实。

## 5.1  总体说明

系统的数据设计目标是**单机自持、离线可用、隐私不出本机**。因此刻意避免了数据库服务依赖，采用三类本地持久化形式：

| 类型 | 载体 | 用途 | 是否入库分发 |
|---|---|---|---|
| 文件存储 | `models/` 下各类 JSON / YAML / 模型权重 | 模型注册表、校准参数、抑制信号、规则文件、adapter | 规则文件入库存档；权重按形态分发 |
| 向量知识库 | `data/chroma_db/` | 漏洞知识检索（RAG） | 否（本地构建） |
| 浏览器本地存储 | `localStorage` / `sessionStorage` | 扫描历史、报告记录、主题偏好 | 否（客户端） |

**设计原则**：

1. **确定性工具与模型信号的文件分层**——确定性规则文件与模型回填信号分开存放，抑制过滤只作用于裁决档，确定性工具自判不受模型意见影响；
2. **运行期不联网**——HuggingFace、Semgrep 规则全部本地化，`HF_HUB_OFFLINE=1` + `TRANSFORMERS_OFFLINE=1`；
3. **可卸载**——所有运行期数据都在项目目录内，卸载脚本可按范围清理（见 §5.5）。

## 5.2  文件存储

### 5.2.1  数据目录总览

```
自持数据/
├── models/
│   ├── signal_registry.json          # 工具-模型闭环：规则负向记忆 / 排序加权 / 类型校正
│   ├── conformal_calibration*.json   # 共形预测校准阈值（生产当前未加载，见 §5.2.3）
│   ├── semgrep_rules/                # 本地化 Semgrep registry 规则（离线可用）
│   ├── adapter_*/                    # LoRA 适配器（按 stage 分目录存放）
│   ├── ollama/                       # Ollama 模型存储（启动器锁定到此目录）
│   └── <GGUF 基座>.gguf              # LlamaCPP 后端基座（用户自备）
├── data/
│   └── chroma_db/                    # 向量知识库（见 §5.3）
└── logs/                             # 运行日志
```

### 5.2.2  信号注册表 `signal_registry.json`

**用途**：记录模型对每条工具规则的判定质量信号，是本系统"工具-模型自适应闭环"的持久化载体。

| 字段（语义） | 说明 |
|---|---|
| 规则计数 | 按 `(rule_id, taint_type)` 累计的确认/否定计数 |
| `confirmed_files` / `rejected_files` | 独立文件级去重集合（跨样本聚合门槛的基础） |
| 负向记忆 | 该规则在**哪些文件**上被高置信否定——读端据此**降低该文件上该规则的候选排序权重**，不删除候选 |
| `corrected_type_counts` | 按 `(file, corrected_type)` 去重的类型校正计数 |
| 待学习池 | "工具漏召但模型全票判中"的代码特征，须经独立验证集复验才转正 |

**读写特性**：

- **写入时机**：在**最终结论确定之后**写入（聚合完成、三道门控均已生效），以最终采信结论而非模型原始投票为写入依据；
- **写入后自动 `save()`**，采用原子写（临时文件 + `os.replace`）；
- **读入门槛（五重）**：与模型无关的证据门（结论为需复核 / 被证据门拦截 / 反事实存疑 → 拒收）→ 全票门槛（`votes == N`）→ 跨样本聚合（≥2 独立文件）→ 双向可撤销 → 独立验证集门控；
- **未达门槛保留原值**——防止模型的错误判定污染确定性工具；
- **只降权、不剔除**：读端对负向记忆只做排序降权，候选集合始终由确定性规则产出，模型不改变工具层的召回面；
- **评估隔离**：评估时以 `--no-signal-feedback` 关闭回填，避免"测量与自举"相互污染（历史事故：跨轮次累积的负向记忆导致工具召回系统性崩塌）。

### 5.2.3  共形校准文件与其当前状态

**用途**：存放共形预测的标签条件分位数阈值，把"评估侧拟合 → 生产端加载"打通。

| 字段（语义） | 说明 |
|---|---|
| `alpha` | 显著性水平，默认 0.1（目标覆盖率 90%） |
| 标签条件分位数 | 漏洞 / 安全 两个标签各自的非一致性分位数 `q` |
| 校准元信息 | 校准集规模、生成时间 |

**契约约束**：

- 校准数据必须带**真实标签**（每条为完整 N 采样投票向量 + label）；
- **禁止 in-sample 校准**——校准集必须与生产分布可交换，否则覆盖率保证不成立；
- **加载失败安全降级**——文件缺失或解析失败时返回未校准状态，预测全部落入"不确定"并回退旧投票逻辑，不中断扫描。

**当前状态（如实声明）**：项目自查发现此前生产端自动加载的校准文件是在**同一测试集**上拟合的（in-sample），不满足上述可交换性前提。处置是把该文件移出自动加载路径并保留存档（文件名带 `in_sample_leaked` 标识以免误用），生产端因此处于**未校准状态**——Layer 1 不参与判定，结论交由其余门控与投票逻辑。需要启用时，应以独立开发集重新校准并显式指定校准源。

### 5.2.4  规则文件 `models/semgrep_rules/`

Semgrep registry 规则包（`p/security-audit`、`p/owasp-top-ten`）本地化为纯文本 YAML 并随软件入库，版本固定。

| 项目 | 说明 |
|---|---|
| 更新方式 | `python tools/fetch_semgrep_rules.py`（幂等，已存在则跳过；需联网） |
| 校验方式 | `python tools/fetch_semgrep_rules.py --check` |
| 缺失降级 | 规则文件缺失时，工具层自动降级为在线拉取（并提示） |

> 另有一组**自研 Semgrep 召回规则**位于核心包内（taint 四件 `sqli_taint` / `cmdi_taint` / `xss_taint` / `codei_taint`，结构化补位两件 `go_cmdi_shell` / `c_cmdi_system`），与上述官方 registry 规则是**两个目录两套规则**，用途不同：前者为自研整文件召回（含工具缺口补位），后者为通用安全审计规则集。

### 5.2.5  模型权重与适配器

| 形态 | 存储 | 尺寸 |
|---|---|---|
| 发布模型 v9max（Ollama） | `models/ollama/`（启动器锁定） | 约 4.7 GB（Q4_K_M GGUF） |
| LoRA 适配器 | `models/adapter_*/`（含 `adapter_model.safetensors`） | 数十 MB 级 |
| 基座（Transformers 形态） | HuggingFace 本地缓存 | 数 GB（NF4 量化后约 4.5 GB） |

**adapter 定位规则**（分层探测）：主位 `models/adapter*` → 兜底训练产物目录；打分时**上线物 stage2 优先于 stage1 / 历史 checkpoint**，保证上线版本不被训练轮次产物顶替。

### 5.2.6  Schema 与训练口径一致性

输出 schema 在核心层与两个推理客户端中定义，三处必须同步。历史问题：schema 定义了某字段但训练标签中 99% 不使用，导致模型"按 schema 修正输出"引发格式不匹配——**三处 schema 必须同步**是本系统的数据一致性约束。

## 5.3  向量知识库

### 5.3.1  存储形态

| 项目 | 选择 |
|---|---|
| 向量库 | Chroma（本地持久化目录 `data/chroma_db/`） |
| embedding 模型 | `BAAI/bge-m3`（多语言，100+ 语言） |
| 集合名 | `vulnerability_knowledge` |
| 检索参数 | 查询文本取源码前 2000 字符；`n_results = 3` |

### 5.3.2  设计依据

- **选型 `bge-m3` 而非英文小模型**：知识库主要是中文漏洞资料，英文专用模型的向量化质量不足；
- **强制离线**：运行时设置 `HF_HUB_OFFLINE=1` + `TRANSFORMERS_OFFLINE=1`，绝不联网下载；
- **三级模型路径解析**：环境变量 `CHROMA_EMBEDDING_MODEL_PATH` → HuggingFace 本地缓存自动发现（按快照目录命名规则搜索 + 配置校验）→ 明确错误提示；
- **延迟初始化与优雅降级**：Chroma 首次使用时才初始化，初始化失败静默降级为纯 LLM 模式并记忆失败（避免反复重试）——这是"RAG 增加 <2% 推理时间"的工程依据。

### 5.3.3  构建与重建

向量库**不随软件分发**（体积大且可由知识源重建），系统附带知识库构建脚本。首次使用或需要重建时（如更换 embedding 模型后），运行软件包内的构建脚本即可：

```bash
# 在软件根目录执行：从随附的知识源重建向量库（会覆盖旧库）
python <随附脚本>/build_knowledge.py
```

**触发场景**：

| 场景 | 是否需要重建 |
|---|---|
| 首次启用 RAG | 需要（本机尚无向量库） |
| 日常扫描 | 不需要（库已就绪，直接加载） |
| 更换 embedding 模型 | 需要（旧库向量与新模型不兼容） |
| 检索结果明显异常 | 需排查，必要时重建 |

> 构建过程需要本地已缓存 embedding 模型（见 §5.3.2 三级路径解析）；构建完成后运行时强制离线，不再联网。

## 5.4  前端持久化

### 5.4.1  localStorage 用途

| 键（语义） | 内容 | 说明 |
|---|---|---|
| 扫描轮次 | 本轮扫描的文件与结果 | 页面刷新不丢失 |
| 扫描结果 | 历史结果缓存 | 供报告历史页读取 |
| 报告历史 | 已生成报告的索引 | — |
| 主题偏好 | 深/浅色主题设置 | `<head>` 内联脚本在 CSS 加载前读取，规避闪烁 |
| 模型管理状态 | 当前激活模型等 | — |

### 5.4.2  设计要点

- **双保险入账**：批量 NDJSON 流式结果以双保险保证"一轮只入账一次"；
- **容量超限的降级策略**：结果对象携带完整源码，大批量扫描后序列化体积可能超过浏览器存储配额。写入失败时**不静默丢弃**：先剥离体积大头（原始代码、模型原始输出）降级重试，仍失败才告警——保证"历史与报告继续可用"是默认行为，而不是配额一满就整体失效；
- **旧数据自动迁移**——数据结构演进后，读取时兼容旧格式并升级；
- **sessionStorage 补充**：深度健康检查结果（最坏 30s+）用 sessionStorage 缓存 + `AbortController` 在页面切换时主动中止；
- **无服务端用户数据**——浏览器本地存储是纯客户端数据，清除浏览器数据即清空，不影响系统运行。

## 5.5  数据生命周期

### 5.5.1  运行期数据产生与销毁

| 数据 | 产生 | 销毁 |
|---|---|---|
| GitHub 仓库副本 | 浅克隆到系统临时目录 | 扫描后 `shutil.rmtree` 立即删除（120 秒超时保护） |
| URL 抓取内容 | 内存流式读取（超 2 MB 截断） | 不落盘 |
| 批量扫描结果 | 内存 + 浏览器 localStorage | 用户清除浏览器数据 |
| 信号注册表 | 每次裁决后原子写入 | 卸载脚本或手动删除 |
| 共形校准文件 | 评估侧拟合后导出（生产当前未加载） | 卸载脚本或手动删除 |

### 5.5.2  网络访问边界

| 阶段 | 是否联网 |
|---|---|
| 首次安装 | 需要（下载依赖 + 模型） |
| 日常运行 | **不联网**（HF 强制离线、Semgrep 规则本地化） |
| GitHub 仓库扫描 | 需要（克隆目标仓库，仅此功能） |
| URL 抓取扫描 | 需要（抓取目标页面，仅此功能） |

### 5.5.3  卸载清理范围

卸载脚本按本机实际检测结果动态清理：

1. 后端进程（端口 8765）与 Ollama 服务进程；
2. 当前 Python 环境中的本项目相关包与 pip 下载缓存；
3. Ollama 拉取的模型（含 `OLLAMA_MODELS` 指定目录）；
4. Ollama 本体（按平台：winget / brew / apt / dnf / pacman / zypper / apk / 官方脚本）；
5. Linux 系统级 CUDA / ROCm 组件（需 sudo，仅 apt 系）；
6. **本地运行数据**：`data/chroma_db`、`outputs/`、`logs/`、`__pycache__`、`*.egg-info`、`.pytest_cache`、HuggingFace / torch / chroma 缓存等；
7. 已安装的编辑器插件（尽力而为）；
8. 整个项目文件夹。

**不会自动删除**：外部扫描工具（bandit / semgrep 等系统级共享工具）；conda 环境本身；npm 全局包；部分共享基础库。

**注意事项**：`~/.ollama` 与 `~/.cache/huggingface` 是全局目录，卸载会删除其中**所有**模型/缓存（包括其他项目用到的）；依赖装进哪个 Python 环境，就必须用哪个环境运行卸载脚本。

### 5.5.4  数据可信度保障机制

系统的数据设计中有三条与"数据可信度"直接相关的机制，属于存储层的制度性约束：

| 机制 | 内容 |
|---|---|
| **冻结集锁定** | 关键测试集用 SHA-256 哈希锁定，强制"冻结集永不入训练轮" |
| **泄漏审计** | 训练/测试文件按 3 行滑动窗口计算 Jaccard 相似度，>30% 视为高重叠直接删除，>15% 人工复核 |
| **评估隔离** | 评估环境与自举机制隔离（关闭信号回填、禁用 in-sample 校准加载）——"测量"与"自举"必须分离 |
