## 一、立项与摸底（2026-06-28）

**选题**：基于大语言模型的代码安全分析系统。核心假设是——传统静态分析工具（Bandit / Semgrep）是"固定规则模式匹配"，只能覆盖已知漏洞模式；而 LLM 具备代码语义理解能力，能发现变体漏洞、给出自然语言解释与修复建议。

**第一步不是搭系统，而是摸底**：exp_01 用 Ollama 本地模型对 14 个典型漏洞/安全样本做基础扫描实验，验证"LLM 能否读懂代码里的漏洞"。初期用 gemma4:12b/26b 跑通了"LLM 判定 + JSON 结构化输出"的最小闭环，同时用 exp_02 建立 Bandit / Semgrep 传统工具基线、exp_03 验证 RAG 知识库增强，三条线并行。

## 二、实验严谨性第一课（06-29 ~ 07-06）

这是整个项目方法论的地基，也是第一个重要教训。

### 2.1 答案泄露事件

评审中发现自己最初的 14 个样本源码里写着 `# 期望/漏洞/安全` 这样的注释——**模型可能靠读注释"作弊"而非分析代码**。删除注释重跑后 gemma4:12b 仍保持 100% 准确率，才确认模型有真实语义理解能力。后来在 exp_04 难样本集（42→87 段）上又发现 47 个文件的 docstring 泄露 CWE 编号与漏洞位置、2 个文件名引用了误导性的 CVE 编号、3 条 RAG 知识条目的示例代码与测试样本几乎一字不差（"通过 RAG 泄露答案"）——全部修复后重跑。

> **教训（贯穿全项目）**：指标好看之前先问"有没有泄漏"。这个意识在后面的训练数据审计（v4 泄漏事件、α0.6 十五版审计）中反复发挥作用。

### 2.2 三轮模型选型

| 轮次 | 模型 | 结论 |
|------|------|------|
| 1 | gemma4:12b | 准确率好但慢（45s/样本）；且多模态参数浪费显存 |
| 2 | qwen2.5-coder:14b | 速度提升 2.6 倍（17s），但发现它对安全写法理解不足，RAG 可纠正误报 |
| 3 | deepseek-coder-v2:16b 专项 | **判定失败**：prompt 膨胀 3 倍耗时翻倍，安全样本误报率 100% 纯靠后处理兜底——知识盲区不是 prompt 能救的 |
| 定型 | **qwen2.5-coder:7b** | 无需任何后处理即 100%/0%/100%，7.7s/样本，体积减半——小而强的代码专用模型胜出 |

期间还有一段 hardware 插曲：exp_04 跑到第 23 个样本时主机出现异响，判断为 600W 电源接近负载极限，暂停实验更换 1200W 电源——大负载本地实验的稳定性和硬件冗余从此纳入考虑。

### 2.3 难样本集与 6 模型对比

构建 87 段 v3 样本集（典型漏洞 / 安全对照 / 绕过式过滤 / 跨文件污点 / 真实 CVE 片段 / 长文件隐藏漏洞 / 混淆噪音），每段 12 列 ground truth 标注。结果审查阶段又修正了 3 个"安全对照样本里藏着附带漏洞"的真值错误（如 PreparedStatement 样本里硬编码了数据库凭证）——**安全对照样本要全方位审查，不能只看主防护点**。

6 模型 × 87 段横向对比（修正后）：gemma4:12b/26b 准确率最高（94.3%），deepseek 误报最严重（44.4%），qwen2.5-coder:7b 召回 88.3% 但速度体积综合最优——维持基座选择。

### 2.4 Prompt 消融（exp_05）与天花板

系统对比 5 种 Prompt 策略 × 87 样本：**CoT 是最优单一策略**（召回 95.0% / 准确率 89.7%），"prompt 越长越好"被证伪（三合一组合反而不如纯 CoT）；白名单是"压误报但损召回"策略；Few-shot 双刃剑。更重要的是：**5 个变体都漏掉同一个绕过样本**——论证了 Prompt 工程存在天花板，为下一阶段 LoRA 微调提供了必要性依据。

另完成了 AST 代码切片实验（tree-sitter，150 行以上按函数切分）：解决了长文件"注意力衰减"（隐藏在 300 行文件末尾的 SQL 注入从误判理由到正确检出），但也暴露了切片的边界——它解决"模型没看到"，解决不了"模型不认识"。

## 三、微调深水区（07-07 ~ 07-19，Qwen2.5-Coder-7B 时代）

exp_06 训练主线开启，在 16GB AMD RDNA4 显卡（RX 9060 XT + ROCm）上做 QLoRA：

- **第一轮 r16_e5**：事后通过训练步数反推，发现用的是旧"换皮增强"数据 + 严重过拟合——写下 P0/P1/P2 诊断清单（wenti.md），全部整改。
- **第二轮 r8_e1**：修复 5 个旧错、新退化 4 个。对 7 个错误做根因分类（顽固老旧知识 / SSTI 概念混淆 / 推理结论断裂 / 跨文件认知局限），成为论文错误分析章节的骨架。
- **3B vs 7B 对比**：3B 微调后误报率反而从 29.6% 暴涨到 42.3%——**弱基座上 LoRA 容量不足**，确定 7B 为微调基座。
- **Phase 1 学习率网格搜索的反直觉发现**：dev_loss 最低的配置 ≠ 评估最优。**高基座上学习率是过拟合旋钮，不是性能旋钮**——降 loss 让 FPR 暴涨 11.5pp。
- **Phase 2（r=32 增容）失败**：严格召回仅 +1.6pp，FPR 暴涨 +19.2pp——得到论文核心论据之一：**LoRA 增容 ≠ 知识注入**。
- **Phase 3 KnItLM 知识注入突破**：在 Base 模型上做 CPT（CVE/CWE/OWASP 语料 1400 条）再把 LoRA 权重 merge 进 Instruct 模型，严格召回 41.0% → **63.9%**，幻觉率 56.1% → 29.1%——证明"先注入知识再保留对话能力"的路线可行，但其副作用（参数化查询幻觉）也如实记录。
- 工程侧：AOTRITON attention 启用让训练步时 -58%；ROCm 7.2.4 升级；TunableOp 离线调优。

## 四、基座切换与 SFT 迭代（07-20 ~ 08-01，Qwen3-8B 时代）

Qwen2.5 时代的天花板已现（Phase 2 失败、Phase 3 有副作用、Phase 4 提示蒸馏受限），决定**整体切换基座到 Qwen3-8B**，旧时代评估结果全部归档（基座不同不可比）。

先建立锚点，随即发现一个重要事实：**合成集虚高**——Qwen3-8B 在 87 段合成集上召回 0.967，但在 20 个真实 CVE 修复样本上只有 0.375，差 59.2pp。从这一刻起，**真实 CVE-fix 测试集成为模型好坏的第一裁判**，合成集只作回归参考。

随后是本地 4bit QLoRA 的 **SFT v2~v9 七轮迭代**，每轮都有明确的数据假设和证伪结论：

| 版本 | 结果 | 教训 |
|------|------|------|
| v2 | ✅ 首个可信 SFT，CVE-fix 0.375→0.625 | 干净数据就有大幅收益 |
| v3 | 合成集更好但 CVE-fix 回退 | CoT 清单化有副作用 |
| v4 | ❌ 指标虚高 | **训练-测试泄漏**（63 条与测试文件 30%+ 行级重叠），引入 Jaccard 泄漏审计制度 |
| v5_clean | ✅ 当时最佳 | 数据清洗是第一生产力 |
| v6 | ❌ 负迁移 | hard-negative 样本让模型对安全代码过度敏感 |
| v7 | ✅ CVE-fix 0.800（20 样本） | 但要警惕"新增样本命中测试集"造成的假象 |
| v8 | ❌ 判别焦虑 | 教"CWE 边界对比"反而让模型纠结到误判 |

同期 **DPO 在本地 RDNA4 上三次全部失败**（8bit OOM 黑屏、fp16 OOM、4bit 梯度失效），数据留待云端——这是本地 16GB 消费级显卡的能力边界，诚实记录。

## 六、蒸馏与云端训练：v9max 发布（08-02 ~ 08-07）

本地数据量与算力双双触顶，走"API 蒸馏 + 云端训练"路线：

1. **三模型蒸馏**：DeepSeek V4-Flash（7700 条）+ Kimi K3（2000 条）+ GLM-5.2（1500+ 条）按统一格式契约（CoT ≤5 步、三段式输出、负样本 1:3）生成约 11200 条数据；经 CWE 归一化、泄漏审计、矛盾/重复清洗后 **7692 条**入库训练。
2. **云端 A800 bf16 全精度训练**（突破本地 16GB 限制）：Qwen3-8B + LoRA r=8 + rsLoRA，1636 步约 4.1 小时。
3. **格式不匹配事件的诊断**：云端模型 20/20 都把修复代码放进 `fix_code` 字段导致评估脚本提取为 0。逐层排查后定位根因是**训练数据自相矛盾**——schema 声明了 `fix_code`，但 99% 的训练标签不用它。同步修正 schema、两个推理客户端的 guided decoding 硬编码副本、评估脚本——**schema、训练标签、推理约束三处必须严格对齐**。
4. **发布 v9max**：merge LoRA → GGUF Q4_K_M → Ollama Registry（`garrywhite109909/graduation-vuln-scanner:v9max`）。**CVE-fix 真实集召回 0.375 → 0.950（HF 管道）**，合成集召回保持 1.000。

## 七、架构转折：从"单模型"到"两阶段信任层"（08-08 ~ 08-19）

这是项目最重要的架构决策，起点是三个诚实的再审视：

### 7.1 三个再审视

1. **方法学再审视（G0 重跑）**：文件名泄漏修复改变了所有 LLM 实验的 prompt 构造，历史指标不可比——全部重跑，exp_01 从"100%"回落到诚实的 92.9%。
2. **量化缺口诊断**：发布形态（Ollama GGUF Q4_K_M）的 CVE-fix 召回只有 0.75~0.79，远低于 HF 评估管道的 0.95。定位结论：不是"量化 vs 未量化"，而是**两种 4-bit 管道的差异**（HF 管道 LoRA 增量保持 FP16；发布形态把 base+LoRA 合并后整体重量化）。
3. **FN 根因分析**：逐个读取漏报样本的原始输出，发现真实 CVE 上的漏报几乎都是**"过度信任防御"**——被 LDAP 转义迷惑、把 eval 合理化为"封装在函数里"、不认识 loopback 信任绕过。这些恰恰是**静态数据流分析不会被骗到**的地方。

### 7.2 两阶段架构

于是把系统重构为**"工具召回 + LLM 裁决"两阶段**：Stage 1 由 Bandit/Semgrep/Gitleaks/Trivy 等确定性工具召回候选并生成结构化提示；Stage 2 由微调模型（Nivis-α0/α0.5，两阶段训练：stage1 打底 + stage2 回收 dev 续训）对候选做裁决；再加一层**信任层**（2.5 代架构）：共形预测统计门控 + 反事实验证 + 信号注册表（信任分级 A-E、跨样本聚合、双向撤销），低置信候选进人工复核而不是硬给结论。

期间通过对照实验完成了关键的归因分流：26 个非正确样本中 62% 是工具漏召，且这批盲区纯 LLM 判对 15/16——**否决了"按漏洞类型补规则"的方向，转向工具与模型自适应闭环**（工具问题修工具，模型问题归训练，禁止对着测试集反向拟合规则）。

### 7.3 达标

| 配置 | recall | FPR | accuracy |
|------|--------|-----|----------|
| 纯 LLM（α0.5，combined） | 0.967 | 0.154 | 0.931 |
| **两阶段 fixed5（干净环境，论文主数据）** | **1.000** | **0.043** | 0.862 |
| 两阶段 @ 真实 CVE-fix 20 段 | **0.882**（strict 0.882，cwe_mismatch=0） | — | 反超纯 LLM 对照（0.850） |

> 方法学教训同样固化进了操作规范：抑制池跨跑污染（评估必须 `--no-signal-feedback`）、in-sample 共形校准失效、**"规则对着测试集结果反向拟合 = 作弊"铁律**、工具问题/模型问题归因分流铁律。

## 九、核心结论（写给评审）

1. **SFT 的收益集中在"判别与格式"，CWE 归因能力要靠架构补足**。v9max 把真实 CVE 召回从 0.375 拉到 0.950，但 strict 归因不升反降；最终靠 CWE Normalizer 后处理 + 两阶段证据链把 strict_recall 做到 0.882。这是全项目最诚实也最有价值的一条结论。
2. **合成集会撒谎**。合成集与真实 CVE 之间的 59.2pp 差距，决定了本项目此后一切评估以真实 CVE-fix 集为准。
3. **"工具召回 + LLM 裁决 + 信任层"优于任何单一形态**：工具不会被"防御措施"骗到，LLM 能理解语义变体，信任层把不确定性显式交给人工而不是假装确定。系统级 recall 1.000 / FPR 0.043（fixed5）。
4. **数据可信度优先于数据数量**：从 1866 条换皮数据到 7692 条蒸馏数据再到 10167 条十五版审计数据，每一轮指标跃升背后都是数据治理，而不是更大的 LoRA 或更长的 prompt。
5. **方法学纪律是实验可信任的前提**：答案泄露、测试集泄漏、跨跑污染、in-sample 校准——每一个坑都转化为一条操作规范铁律。

## 十、踩坑精选（给后来者）

- **训练数据自相矛盾是隐蔽瘤**：schema 声明 `fix_code`、训练标签却不用——模型有能力时会"修正"成 schema 的样子，反而暴露评估脚本没防到。schema / 训练标签 / guided decoding 约束三处必须同步。
- **高基座上学习率是过拟合旋钮**：dev_loss 降 ≠ 评估变好，FPR 会暴涨。
- **弱基座微调有害**：3B 微调后 FPR 暴涨 12.7pp；LoRA 增容（r=32）不等于知识注入。
- **消费级 16GB 显卡的能力边界**：QLoRA SFT 可行，DPO 不可行（梯度失效），大规模训练上云。
- **本地部署的量化管道差异**：HF（NF4 基座 + FP16 LoRA）与 GGUF 合并量化是两种 4-bit，引用指标必须注明管道。
- **Windows GBK 控制台**：任何 print 非 GBK 字符的脚本必须显式 `reconfigure(encoding="utf-8")`，否则中文注释乱码能让 bat 的 cd 命令失效。
- **不要信单一指标**：dev_loss、合成集召回、"100% 准确率"都可能是泄漏或虚高的投影——交叉验证 + 真实集 + 泄漏审计缺一不可。
