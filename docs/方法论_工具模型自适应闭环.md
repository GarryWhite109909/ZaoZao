# 方法论决策记录：从"补规则"到"工具-模型自适应闭环"

> 本文档记录 2026-08-13 对两阶段架构的一次**方法论级决策转变**：放弃"按漏洞类型补静态规则"的路径，转向"静态工具定位 + LLM 语义兜底 + 裁决置信回填"的自适应闭环。为论文"工具-模型协同"章节提供完整决策链与实证数据。
>
> 关联文档：`docs/方法论_工具召回与LLM裁决.md`（v1.0 架构设计，2026-08-07）；本文档是其**实证迭代与范式修正**。
> 状态：决策已定，第 1 步实施中

---

## 一、触发背景：工具链 vs 纯 LLM 的对照实验（exp_07，87 段）

两阶段工具链（Stage1 工具召回 + Stage2 LLM 裁决）与纯 LLM（开放生成）在同测试集、同裁决模型（α0, combined_nosource）下对比：

| 指标 | 纯 LLM | 工具链·修复前 | 工具链·P0/P2 修复后 |
|------|--------|--------------|---------------------|
| recall | 96.7% | 93.6% | **95.7%** |
| FPR | 11.5% | 19.1% | **11.1%** |
| accuracy | 94.3% | 89.7% | **93.8%** |

修复后工具链 FPR 已优于纯 LLM、accuracy 接近——但**26 个非正确样本的逐环节归因**暴露了更深的结构问题：

| 归因环节 | 样本数 | 占比 | 性质 |
|---------|--------|------|------|
| 工具漏召（`stage1_no_candidate`） | 16 | 62% | 规则盲区，不产出候选 |
| 模型裁决低置信摇摆 → review | 8 | 31% | 可疑点对、判定对，仅投票不一致 |
| 模型高置信判错 | 2 | 8% | 消毒/常量 source 被误判 |
| prompt 注入 / 解析失败 | 0 | 0% | **链路本身完全兼容** |

**关键数据**：16 个工具漏召样本（XXE/整数溢出/授权/IDOR/反序列化/Spring4Shell 等无 source 型漏洞），**纯 LLM 判定正确 15/16**——模型天然会，工具规则覆盖近零。

## 二、决策点 1：为什么"补规则"是死路（2026-08-13 否决）

面对 16 个盲区样本，第一直觉是"从训练集提炼模式、给 Prefilter/semgrep 补规则"。否决理由：

1. **数量论不成立**：漏洞形态无数（CWE 数千、变体无限），"每类漏洞写一条检测"必然规则膨胀，且新漏洞永远追不上。工具层的价值不应建立在覆盖所有漏洞上。
2. **测试集泄漏风险**：基于 87 段逐样本反推规则是评测作弊；规则必须来自通用模式，但"通用模式"的边界难以守住，独立验证集又稀缺。
3. **语义类漏洞本质不适配规则**：整数溢出、缺失授权、越权是"上下文语义"问题（是否校验、是否边界检查），静态子串/结构匹配天然低精度——补规则只会把 FPR 打回去（这正是 P0 修复前 FPR 19.1% 的教训）。
4. **归因证据指向"模型会、工具不会"**：16/16 盲区中纯 LLM 对 15 个——问题不在模型能力，在架构把模型能力锁死在工具之下。

## 三、决策点 2：范式转变 —— 工具与 LLM 各干擅长的事（不是并行分工，是互为喂养）

用户以 **ISAM（索引顺序文件）** 类比点破：真正的 1+1>2 不是"索引+顺序并存"（1+1=2 的接力），而是**索引服务顺序文件、索引随数据追加自动更新**——两个结构长在同一个文件上互相放大。

### 3.1 旧心智（被否决）：工具试图覆盖一切

```
工具规则 = 漏洞分类表（补规则 → 规则膨胀 → 追不上）
LLM = 全文大海捞针（成本高、无证据）
两者单向箭头：工具 → LLM，工具是死的
```

### 3.2 新心智（采用）：自适应闭环

```
扫描 → 工具给候选（定位 + 证据链，recall 优先、不求全）→ LLM 裁决每个候选
                                                                   ↓（回填，缺的这环）
                              信号置信表：被确认的信号升权、被否定的降权
                              + 待学习池：LLM 判中但工具漏召的代码特征
                                                                   ↓（下次扫描）
                              工具按权重排序候选 → 高置信信号直接命中，不再全文扫
```

| ISAM 概念 | 漏洞扫描映射 |
|-----------|-------------|
| 顺序文件追加记录 | LLM 发现新漏洞模式 → 进"待学习池" |
| 索引自动追加项 | 待学习信号转成工具候选（LLM 下次只需验证） |
| 索引维护代价 | 权重表随裁决回填更新（数据驱动，非代码） |
| 查询加速 | 工具按置信排序，LLM 聚焦验证，不再全文找 |

**与补规则的本质区别**：补规则是"发现一类漏洞就写死一条检测"（100 万条死路）；置信表是"工具记住哪些信号被模型验证过、值得优先看"（**覆盖范围随使用自动扩张，且权重是软的，不产生硬匹配新误报**）。

### 3.3 职责再定义

| 漏洞类型 | 负责方 | 依据 |
|---------|--------|------|
| 有 source 型（SQL/XSS/命令注入/路径穿越） | 静态工具（现有规则已够） | 静态可达、规则精准、成本近零 |
| 无 source 型（授权/溢出/弱随机/反序列化/XXE/日志注入） | **LLM 直接判定（兜底）** | 需语义理解，规则覆盖近零，模型 15/16 天然会 |

工具停止按 CWE 扩张，新定位：① 有 source 型确定性召回 + 证据链；② 大文件切片定位；③ 其余交给 LLM。**工具当"结构层"，LLM 当"语义层"，且 LLM 的判定回填喂养工具定位。**

## 四、实施路径（三层递进）

| 步骤 | 改动 | 预期收益 |
|------|------|---------|
| **第 1 步**：架构信任修正 | 无候选复核命中时**采信 LLM 结果**（判 True 即报），而非转人工 review | 救回 14 个 review（recall → ~100%） |
| **第 2 步**：自增强闭环 | 裁决结果回填工具置信表（被确认升权/否定降权），工具定位随使用自举 | 工具实际召回随轮次单调上升（实证曲线 = 论文硬贡献） |
| **第 3 步**：双向解锁 | 工具从"规则匹配"降级为"结构标注"（recall 优先、不管精度），LLM 基于标注做全局判定，判定回填标注层 | 工具精度不必高（LLM 兜底），LLM 成本大降（只看标注点） |

## 五、论文叙事（结论性表述）

> 两阶段架构并非"工具规则覆盖所有漏洞"，而是**静态工具负责确定性召回与证据链（有 source 型漏洞），LLM 负责语义判定兜底（无 source 型漏洞），并以裁决置信回填形成"定位—核验—回填"的自适应闭环**——在 recall 不输纯 LLM、FPR 优于纯 LLM 的前提下，获得确定性证据、可控成本、大文件可扩展性，且工具定位精度随使用单调提升（自举）。**工具与模型各干擅长的事、互为喂养，是 1+1>2 的协同，而非 1+1=2 的接力。**

## 九、工具帮助模型：四分支探讨记录（2026-08-13）

> 本质论断：**工具找可疑点 = 给模型生成提示（hint）**。提示质量决定链路上限——提示到点上模型可能判对（标号或对或错）也可能仍分析不出（能力问题）；提示不到点上则产生误导。

### 9.1 四分支框架（实证验证）

| 分支 | 含义 | 数据证据（87 段） |
|------|------|------------------|
| 提示到点上 → 判对 → 标号对 | 工具类型准，模型跟对 | typical_01_sql、typical_03_cmd |
| 提示到点上 → 判对 → **标号错** | 漏洞判对了，但类型/CWE 跟着工具 rule_id 错 | **7 个判 true 样本标号全错（多为误标 XSS）** |
| 提示到点上 → **分析不出** | 工具提示了但模型低置信摇摆 → review | typical_15/16（B105 硬编码密钥） |
| **提示不到点上 → 误导** | 工具给错候选，模型被带偏判 true | 修复前 safe_03/safe_17（列表参数/数值插值） |

### 9.2 新发现：标号错分支的根因（裁决 prompt 缺陷）

7 个判 true 样本 CWE 全标错（典型：typical_13_auth_bypass exp=CWE-306 → 标 CWE-79 XSS；typical_22_csrf exp=CWE-352 → 标 CWE-79 XSS；hard_bypass_08_jwt exp=CWE-347 → 标 CWE-79 XSS）。根因：

1. 工具召回靠 **semgrep-sast 泛规则**（"返回字符串/渲染"一律归 XSS），rule_id 类型本身错；
2. 裁决 prompt（`build_triage_prompt`）**只问 is_confirmed 二分类，从不让模型重判"到底是什么漏洞"**；
3. `vulnerability_type` 从工具 rule_id 硬映射 → 跟着错。

### 9.3 推论：类型校正（并入第 2 步的②）

裁决层改为：is_confirmed + **若确认则同时输出真实漏洞类型（不信任工具 rule_id）** → 回填工具类型映射。模型帮工具不只"帮找模式"，还**帮修正类型标注**（7 个标号错样本 + 工具类型标注随使用自愈）。

## 十、模型帮助工具：信任分级框架（探讨稿，2026-08-13）

> 用户核心警示：**模型帮助工具需要更谨慎或更聪明，否则模型回填给工具的错误信息（错误规则/错误类型）会把工具教坏**。不是所有模型输出都值得回填。

### 10.1 模型输出的信任分级（按"模型判定质量"分桶）

| 级 | 模型判定 | 是否可回填 | 回填内容 | 风险 |
|----|---------|-----------|---------|------|
| A | 判定正确（不误报不漏报）+ 标号对 | ✅ 高可信 | 信号置信↑ + 类型标注 | 极低 |
| B | 判定正确 + **标号错**（判对漏洞但类型错） | ⚠️ 部分 | **只回填"判定对"信号，不回填错误类型** | 中——标号污染 |
| C | 判定正确 + 分析错但上报有漏洞（碰巧对） | ❌ 不可回填 | 无 | 高——假阳性入池 |
| D | 判定错误：误报（安全判成有漏洞） | ❌ 禁止回填 | 无（或反向：抑制对应信号） | 最高——教坏工具 |
| E | 判定错误：漏报（有漏洞判安全） | ❌ 无输出可回填 | 无（本身是工具的损失） | 低 |

### 10.2 关键风险场景（必须防）

- **D 级误报被回填**：模型把 safe_08_shlex（shlex.quote 消毒）判成漏洞 → 若"subprocess 特征=漏洞"入池 → 工具以后遇到 shlex.quote 的代码也报 → **误导扩散**。
- **C 级碰巧对被回填**：模型分析理由错但 has_vulnerability 对 → 若按"特征"回填，学到的不是"为什么危险"而是"什么形式像危险"。
- **B 级标号错被回填**：模型判对是漏洞但标成 XSS → 工具类型映射被污染 → 后续同类样本全标错。

### 10.3 谨慎回填设计原则（响应"更谨慎/更聪明"）

1. **置信度门槛**：仅 `votes_true==N`（3/3 全票一致，confidence=1.0）的判定可回填；低置信（T2/F1 等）一律不进池（它们正是"模型没把握"的信号，也是 review 的来源）。
2. **跨样本聚合**：同一信号（rule_id/特征指纹）须在 **≥K 个独立样本**上被一致判中才回填（防单样本偶然）；K 建议 2~3。
3. **类型回填分离**：标号回填只采"模型明确输出的 vulnerability_type 与工具 rule_id 冲突且模型高置信"的情形；模型无把握时保留工具原标注。
4. **双向可撤销**：回填信号若后续被高置信否定（votes_false==N），必须降权/移出待学习池——**工具的记忆必须能被新的正确判定覆盖**，否则错误一旦入池永久污染。
5. **独立验证集门控**：待学习池新增信号须在独立验证集（真实 CVE 仓库，非 87 段）上复验；误报爆炸的候选直接淘汰（与"补规则"的防泄漏机制一致）。
6. **A/B 级才回填，C/D 级反向使用**：D 级（模型高置信判 true 但独立验证证明是安全）→ 该特征进**抑制池**（工具见到就跳过），变"模型帮工具避坑"。

### 10.4 与 ISAM 类比的收尾

ISAM 的索引维护**不是盲目追加**——插入要维持顺序、冲突要校验。对应到本架构：**回填是"带门控的索引更新"**：置信门槛=插入校验，跨样本聚合=唯一键冲突检查，双向撤销=删除/更新，验证集门控=索引完整性审计。**模型帮工具是"审过的增删改"，不是"无脑追加记录"**——这才是 1+1>2 且不养蛊的闭环。

### 11.10 transformers 端 FPR 分化根因确认与确定性证据门（2026-08-15）

**根因确认**（逐 finding 票型对比，ollama 20260814_230517 vs transformers 20260815_001541）：

| 样本（safe） | ollama Q4 | transformers bf16 |
|---|---|---|
| noise_02（参数化正确+注释误导） | **0/3 全票否决**（判对） | **3/0 全票确认**（判错） |
| noise_03（字面量拼接） | **0/3 全票否决**（判对） | **3/0 全票确认**（判错） |
| safe_09（正确授权，recheck） | 判安全（对） | 判漏洞（错） |
| typical_01（真 SQLi，对照） | 3/0 确认 | 3/0 确认（两边都对） |

**结论：不是"投票分歧被共形路由"，是 Q4 量化噪声把边缘样本的决策边界推向"安全"**（对尖锐学成的模式匹配捷径构成扰动，类似隐式正则化），而语义理解型的真漏洞判断对权重扰动鲁棒、两后端一致。bf16 保留过度自信的模式匹配 → "全票但错" → 共形 `{漏洞}`+conf=1.0 → 高信任类别跳过反事实 → FP 直通。**统计门依赖的分歧信号在过度自信后端上不出现 = 结构性失明**，与置信度校准无关，须补与后端无关的确定性门。

**两项修复（`two_stage_scanner.py`）**：

1. **确定性证据门 `_evidence_gate_pass`**（零 LLM 成本，复用 `counterfactual._DEFENSE_SIGNATURES`）：
   - `sink_defended`：sink 邻域（前 4 后 3 行）已含该类型防御特征（参数化 execute / shlex.quote / html.escape / realpath / autoescape / json.loads）→ 模型漏看已有防御 → 拦 noise_02 类；
   - `no_input_entry`：全文件无任何外部输入入口（request/input/argv/environ/函数定义）→ 污点无从产生 → 拦 noise_03 类；
   - 命中不否决（不判 False），仅排除出 strong_confirmed → 转人工复核（宁可 review 不杀 TP）。
2. **recheck 全票门**：`_maybe_recheck` 由单次（temp 0.1）改为 N=min(3,n_samples) 采样投票（temp 0.7），`trust_llm_recheck` 采信仅限全票一致（votes_true==N）；多数但非全票 → `recheck_low_conf_review`。无工具证据的采信必须是最高置信级别（safe_09 类 bf16 单次误报根因）。

**前置 bug 顺带修复**：`_infer_taint_type` 对文本 lower() 但规则号正则是大写（`B60[2347]`/`B608`），规则号推断路径实为死代码（此前全靠 evidence 关键词兜底）——正则改小写。

**离线仿真验证**（真实测试集代码 + 真实结果 finding 重建，不调 LLM）：

- noise_02（真实 sink=14）→ `sink_defended` 拦截 ✓；noise_03 → `no_input_entry` 拦截 ✓
- 全部 strong-confirmed TP 放行（含 hard_longfile_01 真实 sink=318 表名拼接：sink 邻域无防御特征 → 不拦 ✓）
- safe_08 三条 sast 判中同时被拦（本就 review，无行为变化，复核理由更明确）

**预期**（待台式机全量重跑验证）：transformers FP 4→2（noise_02/03 转复核；safe_09 若复核 3 票全真仍可能 FP，safe_17 为模型能力残留），FPR 预期 ~0.10-0.14；ollama 侧行为不变（noise_02/03 本就被模型正确否决，未被 confirmed，门不触发；hard_crossfile_03 若复核票非全票则转复核）。**风险点：第 1 步救回的 8 个盲区样本须全票才能继续被采信**——重跑时验证 recall 是否保持 ~0.95+。

### 11.11 strict_recall 三重损伤归因与两项修复（2026-08-15）

**同样本配对分析**（纯 LLM 20260812_234641 vs 工具链 2.5 代 20260814_230517，同为 TP 的 55 样本）：

| 配对分类 | 数量 | 机制 |
|---|---|---|
| 两边都标对 | 19 | — |
| 纯错→工对（工具链修复） | **4** | 工具 taint_type + CWE Normalizer 把乱标拉回：eval→CWE-94、path regex→CWE-22、两个 SSTI→CWE-1336 |
| 纯对→工**丢类型** | **5** | 工程缺陷：`no_candidate_recheck_vuln` 分支直接 return，recheck verdict 的类型字段被丢弃（XXE/XPath/整数溢出/Spring4Shell/fastjson 全中招） |
| 纯对→工**标错** | **3** | 提示误导：泛规则错锚点把 md5_password→CWE-79、race→CWE-79、tarfile_symlink→CWE-918 |
| 两边都错（共同盲区） | 24 | CWE 语义边界（授权/IDOR/session/溢出），模型能力，α1 战场 |

整体：纯 LLM strict 0.500（31/62）vs 工具链 0.414（24/58）——工具链的 +4 修复被 -5 工程 -3 误导抵消还倒贴。**修掉工程损耗后工具链 strict 应 ≥ 纯 LLM**，证明"标号自动纠正工具链提升严格准确率"的直觉成立。

**两项修复**：

1. **recheck 类型回填**（`two_stage_scanner.py`）：`_maybe_recheck` 透传首个判真票的 vulnerability_type/risk_level/explanation/fix_suggestion；采信分支写入 result（fix_suggestion 过行号纠正）。预期 +5 strict。
2. **裁决 prompt 防锚定**（`prompts.py`）：按候选 category 注入来源可信度标注——sast/iac（位置型规则，无数据流证据链）标注"历史误报率高，类型与位置都可能是错的，请独立判定"；taint（有污点链）标注"可信度较高"。另加判定规则 5"漏洞类型独立判定"（工具标注是模式匹配猜测，如鉴权缺失是 CWE-862 不是工具标的 XSS）。**条件性服从而非全局降低服从性**——高信任提示本该采信，全局降低会伤 TP。预期压 transformers 端"全票但错"与 3 个标错样本。
3. **文件级类型多数票 + 回声降权**（`two_stage_scanner._aggregate`，2026-08-15 追加）：逐样本追踪发现"纯对→工标错"的 3 例中有 2 例**不是模型判错，是聚合代码丢了多数信号**——`_aggregate` 原取"第一个非空类型"：typical_17 中 5 条判中里模型有 2 票输出正确的 CWE-327（B324/insecure-hash 裁决），但列表首个是 xss-taint 锚定出的 CWE-79 被直接采信；hard_cve_07 的最终类型来自 B108 的裁决而 raw 字段来自 B202（类型与来源非同一 finding）。修复：类型按已确认裁决投票，排序键 = (总票数, **独立票数**, 该类型所在 finding 最高严重度)。**独立票** = 模型输出类型 ≠ 工具 taint_type 归一化结果——"回声票"（工具标 XSS→模型跟着输出 CWE-79）只是复读工具标注，无独立信息量；平票时独立判断胜出（typical_17 复刻验证：CWE-79×2（1 回声）vs CWE-327×2（均独立）→ CWE-327 胜出 ✓）。自检用例 13 全组合复刻通过。typical_27（仅 1 条判中且为错锚点）属纯锚定，聚合层无信号可用，归 prompt 防锚定 + α1 DPO。

**susceptibility 的定位**：模型对锚点的顺从度是模型属性（Q4 噪声天然压制、bf16 保留），推理期无法改模型本身，但可分三层对冲——①prompt 条件性服从（本次，推理层）；②确定性证据门（11.10 已做，聚合层，不依赖模型自纠）；③DPO 偏好对（α1，结构层根治：错误提示+确认=rejected / 错误提示+否决=chosen）。三层都不改模型权重即可先落地前两层。
