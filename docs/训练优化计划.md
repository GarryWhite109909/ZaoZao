## 二、三类弱点的根因（基于原始输出）

### review 的三个来源
1. **投票分裂**：N=3 多数判漏但非全票 → review（真实集 cve_fix_0001 LDAP、0003 eval）；
2. **形态守门拦截**：模型全票误判漏洞，被 `_recheck_type_plausible` 拦下转人工
   （safe_03 subprocess 列表全票判 CWE-77、safe_05 参数化 LIKE 全票判 CWE-89、noise_03/06 字面量脚本）
   ——表面是 review 问题，底下仍是 FP 能力问题；
3. 裁决输出 invalid（stage1 曾 100% invalid）——已由 stage2 recycle-dev 修复。

### FP 模式：形态触发
见 sink 形（execute/system/LIKE/shell）即报警，对"参数化在别处完成/无外部入口/字面量脚本"
否定证据权重不足；跨文件防御失明（hard_crossfile_01 FP CWE-943）。

### FN 模式：两类
1. 过度信任防御（v9max 时代 0001/0003/0005/0006 根因）；
2. **现代框架习语盲区**：最新两个 FN（cve_fix_0005/0006.js，均 CWE-441）为 Next.js
   monkey-patch / 中间件白名单鉴权。训练集框架分布：flask 1402 / express 929 /
   spring 467 / django 401 / fastapi 225，**middleware 仅 85、React 7、Next.js ≈ 0**。

## 四、训练集优化方案

**原则：变体要变"语义结构"（框架习语/语言/防御位置/文件形态/攻击面入口），不是变表面 token。**

1. **针对 FP —— 补"形似实安全"**：
   - 防御形态扩充：PDO / Go database.sql / mysql2 占位符 / ORM filter；跨函数封装防御；
     框架自动转义（Jinja2 autoescape、React JSX）。
   - 无污点形态：顶层字面量脚本、常量表驱动、配置里的"危险函数"、测试代码假 sink。
   - **Minimal pairs（最高优先）**：成对生成"只差一个防御/来源"的正反例，锐化决策边界而不偏移阈值
     （v6 只加负样本失败的原因是改了阈值，minimal pair 不改）。
2. **针对 FN —— 补语义漏洞与现代框架**：
   - 框架习语专项：Next.js/Nuxt middleware 与路由白名单、Express 中间件链、FastAPI dependencies、
     Spring filter/interceptor；用真实 CVE fix commit 当种子让教师换框架重写同型漏洞。
   - 信任边界专项（CWE-441/601/918/863）：XFF/IP 可信度、redirect SSRF、webhook URL 可控。
   - 跨文件污点样本组（source 在 A、净化在 B、sink 在 C），几乎为零 → 补。
   - CWE 长尾按失败频率加权。
3. **针对 review —— 两手**：
   - 一致性靠上述数据；同难样本多表面变体同标签压采样方差。
   - **把 supplement_alpha05_triage.jsonl（adjudication 格式）正式入训**——已生成未使用，
     不该靠 recycle 运气学会裁决格式。
4. **数据来源**：
   - testset_cve_fix 生产管道批量化为训练集产几百条种子（与 20 段按 CVE 编号去重即可）；
   - 教师对抗出题（植入隐蔽漏洞 / 回答"防御可否绕过"，第二教师交叉验证）；
   - PrimeVul/BigVul 经教师过滤后 10~20% 混入，不当金标；
   - 配比：python 31% → ~20%，JS/Java 上调；rust/csharp 放弃或明确不管。
5. **迭代纪律**：用 CVE 管道顺手留一个滚动 30~50 条真实 dev 集（不训练、不选型，发布前测一次），
   防止继续对着 fixed5 迭代导致提升不可信。

## 五、训练格式优化（alpha05 格式小改，不推翻）

1. **CoT 加深 + 固定检查清单**：枚举 source → 可达性 → 防御有效性逐一验证 →
   **是否存在第二入口/替代通道** → 结论。后两步直接对应两个 FN 根因。
2. adjudication 任务样本入训（同四.3）。
3. JSON 字段顺序统一（现在 source 有时在 has_vulnerability 前，与 system 声明不一致）。
4. system 里两个 few-shot 换型：一正例 + 一个"形似实安全"防御识别例。
5. 清洗 160 条语言缺失样本。
6. 构建脚本断言七字段齐全且 fix 行号真实存在。

## 六.5 无模型实测验证（2026-08-22 补充，全部只跑工具层/规则层，未调用任何 LLM）

### 实测 1：工具层对列表形式命令注入的告警行为（生产默认 semgrep+taint+prefilter 全开）
| 样本 | 工具告警 |
|---|---|
| `subprocess.run(["sh","-c",user])` **真注入** | bandit B603（sast，低信任档） |
| `subprocess.run(["find",...,"-exec","rm",...])` **真注入** | bandit B603（sast） |
| `subprocess.run(["ping","-c","1",host])` 安全 | **semgrep taint 规则（高信任档）+ B603** |

### 实测 2：三层确定性防线对 `["sh","-c",user]` 的判定（完整 FN 链实证）
1. **裁决提示词**（prompts.py:969-972）："列表形式必为误报，不得判真" → 指示模型拒绝真注入；
2. **证据门防御签名**（counterfactual._DEFENSE_SIGNATURES）：
   `'Command Injection': shlex\.quote|subprocess\.run\(\s*\[|shell\s*=\s*False` ——
   任何列表形式被当成"已防御"，模型判中也会被降权剔除；
3. **复核形态门**（_recheck_type_plausible）实测输出：对 sh -c 与 find -exec 真注入均返回
   `plausible=False, 拦截理由="所有 Command Injection 的标准 sink 均已防御（模型漏看已有防御）"`
   ——即使 LLM 全票 3/3 正确判真也不被采信，转 review。

**结论**：`sh -c`/`find -exec` 类列表形式注入在本管线上**任何路径都到不了 has_vulnerability=True**
（最好结局是 review，通常是被判安全）。修复方向：防御签名与提示词改为
"列表形式默认安全，**除非** argv 含 shell/解释器（sh/-c、bash/-c）或执行语义参数（-exec、
upload-pack/receive-pack 等）"；三层（提示词/签名表/形态门）需同步修。
注意保留对安全 ping 类的拦截能力（taint 规则对安全列表形式也告警，提示词规则在该场景是正确的）。

### 实测 3：截断风险（P4）降级
- 训练 assistant 字符数：中位 1151 / p90 1652 / p99 3252 / max 5469（中文≈1字/token，1024 上限偏紧）；
- 但 exp_07 结果文件未存 raw_outputs，历史记录中 stage2 裁决 invalid=0，**无实际截断实锤**；
- 结论：理论风险（复核通道用 7 字段全格式、真实大文件最长），降为低-中，建议提到 2048 作保险并记录 finish_reason。

### 顺带发现
生产路径自动加载的共形校准 `models/conformal_calibration.json` 的 n_calib=88（即 87 段合成集）——
**校准集与主测试集同源**，q_vulnerable=0.333 属 in-sample 校准，评估时已用
`--no-signal-feedback`/`VULN_SCANNER_CONFORMAL_CALIB=0` 规避，但生产默认是加载的。

## 六.6 列表形式命令注入修复（2026-08-22 已实施，回归 23/23 通过）

"列表形式=安全"的错误假设原散布在四层，本次统一收敛到新模块
`graduation_project/shell_safety.py`（唯一判定入口）：

| 层 | 文件 | 修复内容 |
|---|---|---|
| 签名表 | `counterfactual.py` `_DEFENSE_SIGNATURES['Command Injection']` | 列表形式默认防御，但 argv 含 shell/解释器/执行语义参数时不算；覆盖面扩到 run/Popen/call/check_output/check_call 同族 |
| 召回层 | `taint_tracker.py` `_context_safe_sink` | 此前对列表形式一律 return True 吞告警；现在执行语义 argv 正常上报为高信任 taint 候选 |
| 白名单 | `schema.py` 安全模式2 | sh -c 类即使带 isalnum 校验也不得判安全模式 |
| 提示词 | `prompts.py` triage 判定要求3 | "必为误报"改为"通常不是注入，但列表形式不等于安全"+ 执行语义参数列举 |

回归脚本：`scripts/verify_listform_cmd_fix.py`（23 断言全过）。验证要点：
- 放行：sh -c / find -exec / git --upload-pack / python -c 四类真注入在签名表、复核门、证据门、schema 全部不再被拦；带 request 源的 sh -c 在召回层产生 taint_tracker 高信任候选（此前仅 bandit B603）；
- 保留：安全 ping 列表、safe_03/noise_03/noise_06 三个原始 FP 样本仍被各门拦截；
- **遗留**：ALPHA05_PROMPT 要求1 的"列表参数"措辞未动（它是训练 system prompt，
  改动会破坏与 fixed5 的评估可比性）——随下一轮训练数据口径修正一起改。
- **观察点**：签名表覆盖面扩展到 Popen/call/check_* 族，若下次跑 87 段指标波动，优先排查此处。

## 八、CVE 真实语料管道（2026-08-22 已建成，试跑通过）

**输出结构**：`experiments/exp_06_finetune/corpus/`

```
│   ├── corpus_NNNNN.{ext}
```

3. 跨 testset_cve_fix + 两池按 CVE ID / commit SHA 去重；
4. 每样本记录 frameworks 标记（nextjs/express/spring 等 19 种），供工具层按框架挖 sink/defense 词表。

**用法**：

## 七、工具层还要不要投入？

**结论：不再堆规则追召回，架构已转向"LLM 兜底 + 规则加速"。**
- 数据支撑：合成集工具覆盖约 60%、真实集 45% 漏召，但漏召兜底 16 盲区样本救回 15/16；
  规则永远追不上框架新形态（无任何现成 semgrep 规则会命中 Next.js middleware 漏洞模式）。
- 仍值得投入的三件事：
  1. learn_pool/signal_registry 闭环做实（机制已有，08-15 才接上读取端，让它真正积累数据）；
