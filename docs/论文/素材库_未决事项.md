## α0 评估记录（2026-08-12，A1 闭环）

**配置**：transformers 后端 + **no-merge**（PeftModel 运行时叠加 LoRA，保留 adapter FP16 最大精度）+ 4bit NF4 基座 + 训练 prompt（`combined`/V3_PROMPT）+ 贪心解码。结果文件：`experiments/exp_06_finetune/results/alpha0_87_full.json`。

### 87 合成集完整指标

| 指标 | 值 | 说明 |
|------|-----|------|
| recall | **91.8%**（56/61） | 有漏洞样本召回率 |
| accuracy | **97.6%**（80/82 有效） | 有效样本正确率 |
| FPR | **3.85%**（1/26） | 安全样本误报率 |
| strict_recall | **70.9%**（39/55） | 严格 CWE 编号+漏洞类型全对 |
| parse_fail | **5/87**（5.7%） | 4 个漏洞样本 + 1 个安全样本 |

### 失败样本明细

**parse_fail（5）**：
- `hard_cve_02_python_log_injection.py`（CWE-117 日志注入）
- `typical_17_md5_password.py`（CWE-327 弱加密）
- `typical_33_php_type_juggling.php`（CWE-843，271s 长耗时=输出超长打满 max_new_tokens）
- `typical_35_java_deser.java`（CWE-502 反序列化，271s）
- `noise_03_harden_string_concat.py`（安全样本）

**FN（1）**：`hard_longfile_01_hidden_sql.py`（CWE-89，181 行长文件隐藏 SQL 注入漏报）

**FP（1）**：`noise_06_shell_true_hardcoded.py`（shell=True 但命令为硬编码常量，被误判）

### 关键观察
1. **CWE 编号记忆是主要短板**：strict_recall 70.9% 明显低于 recall 91.8%，15 个 cwe_mismatch 中大量是"判对类型但编号记错"（如 CWE-78 写成 CWE-77、CWE-306 写成 XSS、CWE-639 写成 XSS）—— 这正体现 CWE Normalizer（查表工具）的价值。
2. **271s 长耗时样本 = parse_fail**：`typical_33`/`typical_35` 输出超长打满 2048 token 导致 JSON 解析失败，是 no-merge 模式下的边界问题。
3. **no-merge 下 batch 提速失效**：batch=4 时每批因 LoRA 运行时叠加反而更慢（实测逐档 OOM，且每批 7 分钟），故最终改回单条串行。此结论已记入 batch_probe 实验。

## α0 全历史 prompt 消融（2026-08-12，A 类补充）

**目的**：把所有独立分支 prompt 全量纳入统一对照（含更早时期），找出 α0 真正最优 prompt。

**配置**：merge 模式（adapter 合并）+ 4bit 基座 + 贪心解码（temp=0.0/seed=42）+ 87 段 exp_04 样本。规整结果：`experiments/exp_06_finetune/results/alpha0_all_variant_regressed.json`。

**merge 模式关键结论（与 exp_05 在 qwen2.5-coder:7b 基座上的结论相反）**：
1. **few_shot 最优**：acc 95.3%、fpr 仅 3.8%、strict_acc 65.1%。训练把 few-shot 在基座上的"激进判 True"偏见洗掉，few-shot 反而稳定输出格式（fpr 从基座 29.6% 降到 3.8%）。
2. **长 prompt 复读退化不存在**：few_shot/combined 无退化，short（767字）fpr 反而飙到 34.6%——证明 B 类假设（长 prompt→复读）在 merge 下不成立。
3. **规则未完全内化**：no_rules 掉到 acc 86.2%、recall 91.8%，显式白名单/硬编码规则仍有价值，不能删。
4. **strict_schema 救格式有效但非最优**：parse_fail=0，strict_acc 63.2%，但 fpr 19.2% 偏高。

### no-merge 针对性验证（5 个问题样本，验证新变体是否解决 A/B 类问题）

同一模型 `models/adapter`、同解码，唯一差异是 merge 与否：

| 变体 | hard_cve_02 | noise_03 | typical_17 | typical_33(PHP) | typical_35(Java) | parse_fail |
|---|---|---|---|---|---|---|
| combined（训练用） | ✗parse_fail | ✗parse_fail | ✗parse_fail | ✗parse_fail(275s) | ✗parse_fail(276s) | **5/5** |
| strict_schema | ✗parse_fail | ✅TN | ✅TP | ✅TP(79s) | ✗parse_fail(292s) | 2/5 |
| short | ✅TP | ✗FP | ✅TP | ✅TP(40s) | ✅TP(32s) | **0/5** |
| few_shot | ✅TP | ✗FP | ✅TP | ✅TP(45s) | ✅TP(86s) | **0/5** |

**no-merge 验证结论**：
1. **A/B 类问题根因 = no-merge 数值精度**，非 prompt 本身：combined 在 no-merge 下 5/5 全 parse_fail（含 typical_33/35 打满 275s+ 复读），而 merge 下 combined parse_fail=0。**FP16 adapter 叠加 4bit 基座的低精度漂移是根因**。
2. **short/few_shot 在 no-merge 下也能救格式**（parse_fail=0），因 prompt 更短决策更稳，抗住低精度漂移；但代价是 noise_03 误报（FP）。
3. **生产建议**：用 merge 模式 + few_shot（acc 95.3%、fpr 3.8%、parse_fail 0）。no-merge 仅在有"最大精度"研究需求时使用。
