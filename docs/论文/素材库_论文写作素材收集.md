## 附录：写作口径须知

论文定稿前必须与代码/仓库保持一致的**口径事实**，引用数据时按此核对，避免"系统与论文不一致"：

1. **当前默认模型是 Nivis-α0（`garrywhite109909/nivis-alpha0`）**，不是 v9max。α0 已训练、已设默认、但**无任何评估结果**（合成集/CVE-fix 均无文件）。引用"当前最佳"指标前须补 α0 评估，或明确把 α0 定位为"已训练未评估的过渡模型"。（详见 1.1.12 与待办清单 A1/C1）
2. **推理 prompt 已统一为 `prompts.V3_PROMPT`**（combined：SYSTEM_PROMPT + CoT 5 步 + 3 组 few-shot，4448 字符），不再按模型绑定 `BASE_PROMPT`。三模型 `prompt_variant` 全部为 `"v3"`。（详见 1.2 决策 6 与待办清单 C2）
3. **三轮 Prompt 消融结论不同**：Qwen2.5 首轮 CoT 最优 → Qwen3-8B 第二轮 +consistency 最优 → repeat=3 后 combined 最优。论文叙事应以"随基座与统计可靠性迁移"为主线，勿引用单一"CoT 最优"。（详见 1.1.1 / 1.1.11）
4. **数据文件与训练版本重名**：`final_train_chatml_v2.jsonl`（8421 条）≠ SFT v2（823 条）；`final_train_chatml_v3.jsonl`（8616 条）≠ SFT v3（832 条）。引用任何"vN"指标前须写清是数据文件还是训练版本。（见待办清单 C3/C4）
5. **指标口径须区分管道**：同一模型在 HF 管道（NF4+FP16 LoRA）与 Ollama 发布形态（Q4_K_M 合并量化）下指标不同（如 CVE-fix recall 0.95 vs 0.75~0.79）。引用时注明管道。（详见 1.1.3 / 1.1.4）
6. **L1-L4 分层审查只有 L1 有落地产物**：L2/L3/L4 为"框架就绪、需 API key"，仓库无运行产物，论文不得写成"已执行"。（见待办清单 A5）
7. **负样本 1:3 是蒸馏任务计划值**，清洗后实际 ≈1:1.2（3493/4199）。引用"负样本配比"时注明是计划还是实际。（见待办清单 A4）

#### 1.1.5 DPO 尝试与失败记录

| # | 配置 | 结果 | 根因 |
|---|------|------|------|
| 1 | 8bit + max_len=1024 | OOM 黑屏 | 8B 8bit + DPO 双前向超 15GB VRAM |
| 2 | fp16 + max_len=512 | 立即 OOM | 8B fp16 本身就超 16GB |
| 3 | 4bit + max_len=512 | 跑完但 grad_norm=0 | 4bit NF4 + DPO 双前向梯度回传失效，loss=ln(2) 不下降，dmesg 记录 amdgpu drm panic |

> **结论**：DPO 在本地 16GB 消费级 GPU 上无法用于 Qwen3-8B。8bit OOM、4bit 梯度失效，是 ROCm/bitsandbytes 与 DPO 双前向的硬约束，非参数可解。DPO 数据（`dpo_merged.jsonl` 104 条）已保留，若换云端 GPU 可直接复用。

#### 1.1.11 exp_05 第二轮消融（v2，Qwen3-8B，8+2 变体，2026-08-02）

> 原素材库只收录了首轮（Qwen2.5，5 变体）和 G0 重跑，**完全漏掉第二轮**。第二轮是 Qwen3-8B 基座上的逐维度叠加消融，也是 `BASE_PROMPT`/`V3_PROMPT` 选型的直接依据，论文第 4.5 节必须引用。

**实验设计**：以 base（纯角色+schema+输出格式，482 字符）为起点，逐个叠加 6 个维度：+scope（CWE 长尾清单）、+whitelist（安全模式白名单）、+hardcoded（硬编码凭证规则）、+cot（5 步思维链）、+lineno（行号锚定+≤5 步）、+consistency（CoT↔JSON 结论一致性校验），另有 +all（六维叠加）、+consistency+scope、+consistency+scope+cot 三个组合。87 样本 × repeat=1（temperature=0.1）。

**结果（多数表决口径，Qwen3-8B）**：

| 变体 | recall | FPR | accuracy | 说明 |
|------|--------|-----|----------|------|
| base | 0.934 | 0.192 | 0.897 | 纯基线 |
| +scope | 1.000 | 0.308 | 0.908 | 召回最高但 FPR 高 |
| +whitelist | 0.885 | 0.077 | 0.897 | FPR 最低 |
| +hardcoded | 0.750 | 0.038 | 0.805 | 召回暴跌（硬编码规则过度压制） |
| +cot | 0.885 | 0.192 | 0.862 | 不如 base |
| +lineno | 0.967 | 0.385 | 0.862 | FPR 最高（行号约束引发误报） |
| **+consistency** | **0.967** | **0.115** | **0.943** | **loose 综合最优** |
| +all | 0.951 | 0.231 | 0.897 | 六维全加反而回退 |

**关键结论**：
- `+consistency`（结论一致性校验）在 Qwen3-8B 上是唯一显著优于 base 的维度（accuracy +4.6pp），这与首轮"CoT 最优"完全不同——**最优 prompt 策略随基座变化**。
- `+hardcoded` 把召回从 0.934 打到 0.750，说明硬编码凭证规则在 Qwen3-8B 上是强干扰；`+lineno` 使 FPR 翻倍到 0.385。
- 该轮结果保存在结果 JSON 中，但 **strict 口径（CWE 归因）未持久化**：`prompts.py` 注释声称"base 在 strict 准确率上最优 55.8%"，仓库内找不到支撑该数字的存档（v2 JSON 未存 vulnerability_type），属"口头结论未落库"，论文引用前需重算或补跑。
- 三轮关系：首轮 CoT 最优（Qwen2.5）→ 二轮 +consistency 最优（Qwen3-8B loose）→ G0 重跑 combined 最优（repeat=3）。论文叙事建议以"随基座与统计可靠性迁移"为主线，而非单一"CoT 最优"。

### 1.2 策略转变与关键决策

#### 决策 1：从"LLM 做所有事"到"工具召回 + LLM 裁决"的架构反转

- **背景**：原始管道是 Prefilter → Slicer → LLM 全量扫描，LLM 被迫在每个文件上"大海捞针"
- **问题**：80-90% 文件无任何可疑特征，对它们调用 LLM 是纯浪费；LLM 自报 confidence 不可信
- **反转**：静态工具(Semgrep taint/TaintTracker/Prefilter)做候选召回，LLM 只对有候选的少数文件做封闭二分类裁决
- **论点**：判别比生成可靠——发现漏洞要求在指数级空间搜索，裁决只需验证一条 source→sink 证据链
- **来源**：`docs/方法论_工具召回与LLM裁决.md`

#### 决策 2：从 Qwen2.5-Coder-7B 到 Qwen3-8B 的基座切换

- **直接原因**：parse_fail 蒙蔽（18/87 样本因输出截断被排除，FPR 虚低 13pp）；CVE-fix 测试集标签错误
- **深层原因**：Phase 1-3 在 Qwen2.5 上的微调已到天花板（LoRA 增容失败、CPT 知识冲突）
- **关键发现**：切换后 parse_fail 归零，真实 FPR 27% / strict_recall 46% 暴露——旧 baseline 的"低 FPR"是假象
- **来源**：`docs/决策主线_考古重建.md` 事件 17

#### 决策 3：从 CPT 知识注入到 Prompt Distillation 的方向转变

- **触发点**：用户提出"知识注入是不是需要模型原本没有相关知识，否则自带的和我注入的会互相矛盾"
- **根因**：CPT 在基座已具备相关知识时引发知识冲突与负迁移（第一次"成功"是泄题假象，第二次"爆炸"才是真实能力）
- **转向**：放弃 CPT，转向推理分布对齐（PD），后因 Qwen3-8B 性能优势主动放弃 PD 路线
- **来源**：`docs/决策主线_考古重建.md` 事件 15

#### 决策 4："本地探索 → 云端放大"双轨路线

- **背景**：本地 16GB GPU 可做 QLoRA SFT 但无法做 DPO（8bit OOM、4bit 梯度失效），手写数据量天花板 914 条
- **策略**：本地低成本验证数据/方法论 → 云端 A800 bf16 全精度释放能力
- **闭环**：v2~v9 本地迭代验证数据质量 → 三模型 API 蒸馏 7692 条 → 云端 A800 4.1h 训练 v9max
- **来源**：`docs/方法论_Nivis-α1训练.md`

#### 决策 5：从手写 CoT 到三模型 API 蒸馏的数据规模化

- **动机**：本地手写数据量 914 条已达极限，无法支撑进一步训练
- **分工**：DeepSeek（7700 条，C/C++ 内存/Web 漏洞）/ Kimi K3（2000 条，跨文件长上下文）/ GLM-5.2（1500+ 条，CWE+CVSS 严格格式）
- **三条铁律**：CoT ≤5 步 ≤590 token、三段式统一输出、负样本 1:3 配比
- **清洗**：11200 → 7692 条（CWE 归一化 + Jaccard 泄漏审计 + 矛盾清除）
- **来源**：`docs/决策主线_考古重建.md` 事件 24

#### 决策 6：推理 prompt 统一为 V3_PROMPT（2026-08-10）

- **背景**：v9max 训练/评估时用 BASE_PROMPT，G0 对照又证明 combined 变体在合成集 FPR 最优；α0 改用 combined 家族训练后，继续"按模型绑定 prompt"会形成三套不一致
- **决策**：所有推理入口（model_registry + 三个 client + two_stage_scanner）统一 `prompts.V3_PROMPT`（SYSTEM_PROMPT + CoT 5 步 + 3 组 few-shot，4448 字符），注册表三个模型全部 `prompt_variant="v3"`
- **意义**：这是"训练/推理一致性"原则的第二次落地（第一次是 v5→LITE、v9max→BASE）；论文应把 prompt 选型写成"随数据版本演进的决策链"而非一次性结论
- **来源**：git 72b5fa2；`app/backend/services/model_registry.py`

#### 决策 7：Nivis-α0 发布（已发生但未记录决策过程）

- **事实**：2026-08-09~10 完成训练、adapter 入库、Ollama 安装、注册表设为默认，但 README/过程.md/实验台账均无对应条目，属于"代码先于文档"的未闭环决策
- **风险**：答辩时若评审看到默认模型是 α0 而论文只写 v9max，会产生"系统与论文不一致"的质疑

- **来源**：git 684821b / 72b5fa2；`docs/论文/参考.md`

### 1.3 失败经历与教训

#### 失败 1：样本答案泄露（两次发现）

- **第一次**（06-28）：14 个样本源码含 `# 期望/漏洞/安全` 注释直接泄露答案，100% 准确率无法证明模型真实能力
- **第二次**（07-05）：全面审查发现 47 个文件泄露答案注释 + 1 个 ground truth 错误 + RAG 示例代码去重
- **修复后**：v3 准确率从 v2 的 89.7% 降到 78.2%——v2 的高指标是注释泄露造成的假象
- **教训**：盲测原则要求 prompt 与源码均无答案，文件名也算泄露面
- **来源**：`docs/决策主线_考古重建.md` 事件 1/5

#### 失败 2：v4 训练-测试泄漏

- **问题**：63 个训练样本与 20+ 测试文件存在 30% 以上行级 Jaccard 重叠
- **后果**：指标不可信被废弃；v4 的漂亮数字是泄漏造成的假象
- **修复**：v5 引入 Jaccard 泄漏审计，清洗 100 条泄漏/近泄漏样本
- **教训**：数据可信度比指标绝对值更重要
- **来源**：`docs/决策主线_考古重建.md` 事件 20

#### 失败 3：v6 hard-negative 负迁移

- **操作**：为降 FPR 追加 6 个 FP 的正确拒绝 CoT 作为正样本
- **结果**：FPR 仅降 3.9pp，但 CVE-fix recall 从 0.571 跌到 0.429（降 14.2pp）
- **根因**：模型对安全代码过度敏感，在真实 CVE 上错判
- **教训**：简单 hard-negative SFT 得不偿失，应以"多样安全代码 + 防御机制教学"替代
- **来源**：`docs/决策主线_考古重建.md` 事件 21

#### 失败 4：v8 对比 CoT 判别焦虑

- **操作**：新增 24 条"CWE-89 vs CWE-90"的反事实对比 CoT 样本
- **结果**：FP 从 6 增至 8，LDAP 注入从 TP 退步为 FN
- **根因**：对比 CoT 让模型在 CWE 边界上纠结到误判安全；训练样本含"无漏洞但建议改进"的矛盾信号
- **教训**：对比 CoT 引发判别焦虑，不适合小模型；训练样本不得含矛盾信号
- **来源**：`docs/决策主线_考古重建.md` 事件 23

#### 失败 5：DPO 本地三次失败

- **尝试 1**：8bit + max_len=1024 → OOM 黑屏
- **尝试 2**：fp16 + max_len=512 → 立即 OOM
- **尝试 3**：4bit + max_len=512 → 跑完但 grad_norm=0（梯度无法回传到 LoRA 层）
- **根因**：DPO 需要 policy + reference 双前向，显存需求接近 SFT 两倍
- **教训**：16GB 消费级 GPU 无法训练 8B DPO，偏好优化需要 24GB+ 或云实例
- **来源**：`docs/决策主线_考古重建.md` 事件 22

#### 失败 6：LoRA 增容 ≠ 知识注入

- **操作**：Phase 2 将 LoRA rank 从 8 提升到 32 + rsLoRA + 2 epoch
- **结果**：strict_recall 仅 +1.6pp，FPR 暴涨 +19.2pp，CWE 错标 32→32 完全没动
- **教训**：高基座上增大 LoRA rank 未带来知识注入，反而让模型多学了"风格"导致 FPR 暴涨
- **来源**：`docs/决策主线_考古重建.md` 事件 13

#### 失败 7：CPT 知识冲突

- **操作**：KnItLM CPT 在 Base model 上注入 CVE/CWE/OWASP 知识，LoRA 权重 merge 到 Instruct
- **结果**：第一次"成功"（strict_recall +23pp）是泄题假象；第二次"爆炸"（宽松 accuracy 跌至 80%）
- **根因**：基座已具备相关知识时注入会引发知识冲突；LoRA 在 Base 上训练后合并到 Instruct 数学上不严格成立
- **教训**：CPT 知识注入在基座已具备相关知识时引发负迁移
- **来源**：`docs/决策主线_考古重建.md` 事件 15/18

#### 失败 8：合成集虚高 59.2pp

- **发现**：Qwen3-8B baseline 在合成集 recall 0.967，在 CVE-fix 真实集仅 0.375
- **差距原因**：真实 CVE 漏洞模式更隐蔽（防御措施迷惑、危险合理化、信任边界绕过、跨文件数据流）
- **教训**：合成集会系统性高估模型能力，须用真实 CVE-fix 数据集验证泛化
- **来源**：`docs/决策主线_考古重建.md` 事件 19

#### 失败 9：v7 CVE-fix recall 被简单样本拉高（复盘发现）

- **表面数据**：v7 在 20 扩展 CVE-fix 上 recall 0.800，看似比 v5（7 样本 0.571）提升 +22.9pp
- **复盘真相**：原本 7 个真实 CVE 上 v7 recall=0.429（**退步**），新增 13 个手工扩展样本上=1.000（全部命中），整体 0.800 被简单样本拉高
- **标注修正后**：v7 strict_accuracy 从 0.640→0.728（合成集）、0.650→0.700（CVE-fix）
- **核心瓶颈**：剩余 20 个 cwe_mismatch 的根因是模型有"归因偏置"——倾向把不熟悉的 CWE 归为 CWE-89/79/200/798
- **教训**：扩展测试集时须区分真实 CVE 与手工样本，分别统计；recall 提升不等于真实能力提升
- **来源**：`experiments/exp_06_finetune/results/EXPERIMENT_LEDGER.md` v7 复盘节

#### 失败 10：fix_usable=0 瓶颈误判

- **旧结论**："fix_usable=0 瓶颈在 FixVerifier 危险模式覆盖面"→ 扩 12 条补充模式后自检通过
- **重算结果**：对 20 条 CVE-fix 结果用扩展后 FixVerifier 重算，fix_usable 仍 0/15，指标无任何变化
- **真正瓶颈**：14/15 样本 `model_fix_suggestion` 为空——模型 verdict JSON 未输出 fix_suggestion 字段（BASE_PROMPT 有要求但 Ollama v9max 在该 eval 配置下未遵守），FixVerifier 根本没有输入可验
- **教训**：瓶颈定位须沿管道上游追溯，不能停在下游组件；评估侧已改进失败原因拆分"模型未输出fix_suggestion"与"未抽到代码块"
- **来源**：`experiments/exp_06_finetune/results/EXPERIMENT_LEDGER.md` G0 节

### 1.4 巧妙的实验设计

#### 设计 1：AST 代码切片解决长文件注意力衰减

- **问题**：qwen2.5-coder:7b 对 3 个长文件样本二值判定全对但理由错误——把文件开头的 `DB_PATH` 误判为硬编码凭证，漏掉文件末尾隐藏的 SQL 注入
- **方案**：tree-sitter AST 切片，文件≥150 行按顶层函数/类方法切分，每切片含文件级上下文头 + 当前函数代码，chunk 间 OR 合并（保守策略宁误报不漏报）
- **效果**：longfile_01 理由从错误的 CWE-798 修正为正确的 CWE-89 SQL 注入
- **局限**：对需要领域知识的漏洞（如 SSTI）效果有限——切片只能解决"模型看到漏洞函数"的问题
- **来源**：`docs/决策主线_考古重建.md` 事件 8

#### 设计 2：双口径评估指标（loose + strict）

- **loose 口径**：只看 `has_vulnerability` 布尔值
- **strict 口径**：同时校验 CWE 编号完全匹配
- **意义**：strict_recall 暴露了 loose recall 虚高的问题，CWE 归因准确率才是真实瓶颈
- **来源**：`experiments/exp_06_finetune/scripts/evaluate.py`

#### 设计 3：Jaccard 行级重叠审计

- **方法**：对每对训练-测试文件计算 3 行滑动窗口的 Jaccard 相似度
- **阈值**：>30% 视为高重叠（直接删除），>15% 视为中重叠（人工复核）
- **意义**：v4 因泄漏被废弃后建立的标准流程，后续所有数据版本均须通过
- **来源**：`docs/方法.md` §4.3

#### 设计 4：多模型顺序加载/卸载策略

- **方案**：逐个模型加载 → 扫描 → 立即卸载(`keep_alive=0`) → 加载下一个，任一时刻显存中只驻留一个模型
- **优化**：`scan_files` 让每个模型一次性处理全部文件，模型加载次数 = 模型数（而非模型数 × 文件数）
- **保障**：`finally` 块保证即使中途异常也能卸载
- **来源**：`app/backend/services/multi_model_scanner.py`

#### 设计 5：三模型蒸馏 L1-L4 分层审查框架

- **L1 规则校验**（全量，免费，自动）：JSON schema / CWE 合法性 / CoT 步数 / 一致性
- **L2 三模型交叉投票**（全量，API）：DeepSeek 样本 → GLM + K3 复审，标记分歧
- **L3 闭源模型仲裁**（分歧 + 抽样）：Claude Opus 4.1 主审 + GPT-5 副审
- **L4 金标准集校准**（一次性）：50-100 条金标准评估生成模型准确率
- **设计理由**：三大中国模型有共同盲区和预训练语料重叠，不能做最终裁决；闭源模型能力代差能识别开源模型认知错误
- **来源**：`experiments/exp_06_finetune/scripts/audit/`

#### 设计 6：自一致率置信度（N 次采样）

- **方案**：对同一 finding 以 temperature > 0 采样 N=5 次，置信度 = 判真票数 / N
- **映射**：≥0.8 自动判定，0.5-0.8 标记"需人工复核"，<0.5 不自动结论
- **统计依据**：自一致率是多数表决的软化，与已有多数表决机制同构
- **来源**：`docs/方法论_工具召回与LLM裁决.md` §3.3

### 1.5 实验难点

1. **消费级 GPU 显存约束**：8B 模型 4bit 量化后约 4.5GB，加上 LoRA 梯度/优化器/激活值，SFT 峰值 12-14GB，DPO 需双前向超 16GB
2. **数据可信度保障**：从答案泄露 → 训练-测试泄漏 → 合成集虚高，每一步"漂亮指标"都需自我审计验证
3. **CWE 精确归因**：strict_recall 从 baseline 0.459 到 v9max 0.607，提升困难，CWE 边界判别是小模型瓶颈；模型有"归因偏置"——倾向把不熟悉的 CWE 归为 CWE-89/79/200/798
4. **真实 CVE 泛化**：合成集 recall 1.000 不能代表真实漏洞检测能力，CVE-fix recall 从 0.375 到 0.950 跨越巨大
5. **蒸馏数据质量控制**：11200 → 7692 条的清洗损失（CWE 归一化 + 泄漏审计 + 矛盾清除），数量不等于质量
6. **评估管道一致性**：HF 管道（NF4+FP16 LoRA）与 Ollama 发布形态（Q4_K_M 合并量化）指标差距 0.95 vs 0.75-0.79，缺口来自两种 4-bit 量化管道差异
7. **prompt 优化不迁移**：combined prompt 在合成集上全面最优（FPR 7.7%），但优势不迁移到真实 CVE（75% vs base 79%）
8. **过度信任防御模式**：v9max 在 CVE-fix 上的 3-4 个 FN 全是"过度信任防御"——LDAP 被转义迷惑、eval 被函数封装迷惑、loopback 信任绕过，支撑两阶段"工具召回 + LLM 裁决"架构的必要性
9. **测试集扩展的统计陷阱**：v7 扩展 CVE-fix 从 7→20 样本时，新增 13 个手工样本全部命中（recall=1.000），而原 7 个真实 CVE 上退步至 0.429，整体 0.800 被简单样本拉高
10. **方法学修复连锁重跑**：文件名泄漏修复改变了所有 LLM 实验的 prompt 构造，导致 exp_01/04/05/06 全部需要重跑，历史结果不可比
11. **最优 prompt 策略随基座迁移**：Qwen2.5 上 CoT 最优 → Qwen3-8B 第二轮 +consistency 最优 → repeat=3 后 combined 最优，论文若引用单一"CoT 最优"结论会被第二轮数据推翻
12. **strict 口径结论未落库**：`BASE_PROMPT strict 55.8% 最优`只存在于代码注释，无结果 JSON 支撑；同理 α0 无任何评估，论文引用前必须补数据
13. **数据文件与训练版本命名碰撞**：`final_train_chatml_v2.jsonl`（8421 条）与 SFT v2（823 条）、`final_train_chatml_v3.jsonl`（8616 条）与 SFT v3（832 条）重名，复现与引用极易张冠李戴

## 二、后端模块

### 2.1 架构设计亮点

#### 亮点 1：优先级调度器

- **设计**：基于 `heapq` 优先级队列，交互式扫描(HIGH)优先于批量扫描(LOW)
- **关键结构**：`ScanTask` dataclass 按 `(priority, seq)` 排序，优先级相同时 FIFO
- **单工作线程**：与 Ollama `OLLAMA_NUM_PARALLEL=1` 对齐，Python 层显式排队
- **客户端配额**：每 `client_id` 最多排 8 个任务，防止单一批量扫描霸占队列
- **跨线程回填**：工作线程通过 `loop.call_soon_threadsafe` 把结果回填到 `asyncio.Future`
- **来源**：`app/backend/services/scheduler.py`

#### 亮点 2：多后端抽象与精度权衡

- **四种后端**：ollama / transformers / llamacpp / vllm
- **工厂方法**：`_build_default_client` 按后端类型构建对应客户端
- **精度报告**：`_build_backend_info()` 为前端提供检测报告式信息（基座量化位宽、LoRA 是否被量化、运行设备等）
- **来源**：`app/backend/services/scanner.py`

#### 亮点 3：训练/推理一致性保证

- **模型注册表**：每个模型绑定 `prompt_variant`，推理时自动选择对应的 system prompt
- **`:latest` 标签归一化**：去掉 Ollama 报告名称末尾的 `:latest`，避免误判"未安装"重复拉取
- **废弃标记**：`deprecated` 字段标记过时模型，UI 标记"已过时"但仍可使用
- **来源**：`app/backend/services/model_registry.py`

#### 亮点 4：SSRF 多层防护

- **协议白名单**：仅允许 http/https
- **IP 分类**：拦截内网/回环/链路本地/保留地址
- **DNS rebinding 缓解**：双重解析一致性校验——两次解析 IP 集合不一致则拒绝
- **手动重定向控制**：每一跳重新校验目标地址，最多 5 跳
- **响应体大小限制**：流式读取，超过 2MB 立即截断
- **来源**：`app/backend/services/fetcher.py`

#### 亮点 5：分层健康检查

- `/api/health/live`：轻量探针，即时返回（启动器用，避免超时）
- `/api/health`：深度检查，调 Ollama/外部工具（前端用，获取完整状态）
- **关键注释**：`health()` 端点特意用普通 `def` 而非 `async def`，避免同步阻塞卡死事件循环
- **来源**：`app/backend/main.py`

#### 亮点 6：NDJSON 流式通信

- **批量扫描**：每行一个文件结果，前端逐行解析显示进度
- **模型下载**：`queue.Queue` + daemon 线程 + StreamingResponse 实现实时进度推送
- **优势**：比 WebSocket 简单且兼容性更好
- **来源**：`app/backend/main.py`

#### 亮点 7：两阶段扫描架构（工具召回 + LLM 裁决）

- **Stage 1**：Semgrep taint（整文件） + TaintTracker（AST 轻量污点） + Prefilter 并行召回
- **Stage 2**：对每个候选 finding 构造 triage prompt，N=5 次采样自一致率裁决
- **关键反转**：LLM 任务从"在全文中发现漏洞"（开放生成）变为"对具体 finding 判定真伪"（封闭判别）
- **切片上下文**：只取包含 source/sink 行的 chunk 作为裁决上下文，聚焦 LLM 注意力
- **来源**：`graduation_project/two_stage_scanner.py`；`docs/设计草稿_P1_两阶段架构.md`

#### 亮点 8：工具层漏报的"抽样复核保险丝"

- 无候选直判安全的文件按默认 10% 比例（`VULN_SCANNER_RECHECK_RATE`）随机抽样做一次全量 LLM 复核
- 复核命中漏洞 → 文件级判 `None`（需人工复核）而非直接采信 LLM，避免"工具漏报被 LLM 顺水放行"
- 模块级计数器维护 `no_candidate_total / recheck_sampled / recheck_vuln_found`，`/api/analyze/two-stage` 返回快照，可在线估计工具层漏报率——直接回答"无候选判安全会不会漏"的评审问题
- **来源**：`graduation_project/two_stage_scanner.py`（`tool_recall_monitor_snapshot`/`_maybe_recheck`）

#### 亮点 9：CWE 标号自动纠正（后处理查表，不进 prompt）

- 模型对漏洞"语义分类对、编号记错"（如 SQL 注入写成 CWE-29）是纯记忆错误，`cwe_normalizer.py` 在输出后做确定性查表纠正，零 token 开销
- 幂等且对表外长尾（CSRF/日志注入等）原样放行，不做破坏性覆盖
- 两阶段架构中同样复用：把工具派生的 `taint_type` 统一成 CWE 标签
- **注意（与评估口径的冲突）**：SSTI 被映射为 `CWE-94 Server-Side Template Injection`，但测试集标注修正把 SSTI 定为 CWE-1336（CWE-94 只是父类）——**UI 显示层与严格评估层对 SSTI 的"正确编号"定义不一致**，论文须说明两套口径
- **来源**：`graduation_project/cwe_normalizer.py`

#### 亮点 10：SARIF 2.1.0 标准化导出

- 两阶段结果按置信度映射 level（≥0.8 error / 0.5~0.8 warning / <0.5 note），旧管道按 risk_level 映射
- 每条 confirmed finding 一条 result，携带 confidence/votes/source/sink/传播链/修复建议
- 与 GitHub Code Scanning、VSCode Problems、JetBrains Qodana 原生互通，是"系统可进 CI"叙事的关键证据
- **来源**：`graduation_project/sarif_report.py`

### 2.2 巧妙的工程逻辑

#### 逻辑 1：约束解码兜底

- CoT+JSON 解析失败时，用 `format=json` 约束解码重试
- 数学上保证输出可解析，避免 parse_fail
- **来源**：`app/backend/services/scanner.py`

#### 逻辑 2：多 chunk 合并策略

- 任一 chunk 有漏洞 → 整文件判漏洞（保守策略）
- 取风险最高的 chunk 结果
- 若有 error 且无漏洞 → 整文件判 error（避免部分失败被误判为安全）
- **来源**：`app/backend/services/scanner.py`

#### 逻辑 3：延迟初始化

- Chroma 和 TaintTracker 在首次使用时才初始化
- 初始化失败时优雅降级（回退纯 LLM）
- **来源**：`app/backend/services/scanner.py`

#### 逻辑 4：模型切换锁

- `switch_model` 与 `scan_code` 通过 `_model_lock` (RLock) 互斥
- 避免多 chunk 扫描中途切模型导致结果撕裂
- **来源**：`app/backend/services/scanner.py`

#### 逻辑 5：显存分档自适应

- `recommend_config` 按 GPU 显存分档推荐 `num_ctx`
- ≥15.5G → 16384 / 11.5-15.5G → 12288 / 7.5-11.5G → 9216 / 6-7.5G → 6144 / <6G → 降级 CPU
- 阈值按名义容量 × 0.95 取整，处理实际可用显存低于标称的情况
- **来源**：`app/launcher/bootstrap.py`

#### 逻辑 6：Ollama 桌面版抢占处理

- Windows 上 Ollama 桌面版(ollama app.exe)会在 serve 被杀后立即重启抢占 11434
- 启动器通过 `_stop_ollama` 先结束 app 再结束 serve，并轮询确认端口由自己启动的进程监听
- **来源**：`app/launcher/bootstrap.py`

#### 逻辑 7：Python 环境自动切换

- 检测当前 Python 的 torch 与硬件是否匹配（CUDA vs ROCm）
- 不匹配时用匹配的解释器重新执行启动器
- `VULN_SCANNER_REEXEC=1` 守卫防止死循环
- **来源**：`app/launcher/dependency_installer.py`

#### 逻辑 8：Qwen3 chat_template 修改 + thinking 禁用

- 原版 Qwen3 模板不含 `{% generation %}` 标签，导致 `assistant_only_loss=True` 时 loss mask 全部错误
- 训练脚本注入修改后的模板，在 assistant 部分包裹 `{% generation %}...{% endgeneration %}`
- 同时 patch `apply_chat_template` 默认禁用 thinking 模式（避免输出被 `<think>` 标签包裹）
- **来源**：`experiments/exp_06_finetune/cloud_train/train_qlora_cloud.py`（注意：`scripts/train_qlora_cloud.py` 是**没有该修复的过期副本**，见七）

#### 逻辑 9：模型文件"不落 C 盘"的目录锁定与迁移

- 启动即把 `OLLAMA_MODELS` / `HF_HOME` 锁到项目 `models/` 目录（Ollama 迁移为剪切+去重清理，HF 缓存迁移到 `.hf_home/hub`）
- `_needs_migration` 智能识别"只有过期 partial/重复文件"的源目录，直接清理不迁移；Windows 上先杀托盘 `ollama app.exe` 再杀 serve，避免桌面版抢占 11434 把模型重新下载到 C 盘
- 消费级用户视角：模型管理（下载/迁移/删除）是论文"本地部署工程化"章节的实打实素材
- **来源**：`app/launcher/bootstrap.py`；git 28d0c59/2d4948c 系列

#### 逻辑 10：多 chunk 批量解码（transformers 后端）

- 长文件切片后，若客户端支持 `generate_batch`，一次 forward 走完整 batch，摊薄权重读取、真正吃满 GPU 带宽（单条自回归是显存带宽瓶颈）
- Ollama/vLLM 不支持则回退顺序执行，能力自动降级
- **来源**：`app/backend/services/scanner.py`；`graduation_project/transformers_client.py`

#### 逻辑 11：裁决采样期的模型驻留策略

- `keep_alive=0`（用完即卸）在 N 次采样下会反复重载模型，延迟爆炸
- `_effective_keep_alive` 把采样突发期改为 300s 驻留，空闲自动释放；只在裁决/复核路径生效，主扫描仍尊重用户 keep_alive
- **来源**：`graduation_project/two_stage_scanner.py`

#### 逻辑 12：模型管理能力门控（501 而非 500）

- 进程内后端（transformers/llamacpp/vllm）没有运行时拉取/删除能力，`/api/models/*` 返回 501 并附能力清单，而不是误报 500 或假装成功
- 健康检查区分"引擎就绪"（资源就绪）与"模型已加载"，避免健康探测强制加载 8B 模型
- **来源**：`app/backend/main.py`（`_model_mgmt_gate`/`model_management_capabilities`）

## 六、项目级难点

### 难点 1：消费级 GPU 上的 8B 模型训练

- 16GB 显存约束：4bit 量化后 4.5GB + LoRA/优化器 1GB + 激活值 2-4GB = 峰值 12-14GB
- DPO 需双前向（policy + reference），显存需求接近 SFT 两倍，16GB 不可行
- ROCm/RDNA4 兼容性：bitsandbytes 4bit 在 gfx1200 上未出现报告的静默损坏，但需 AOTRITON attention 加速

### 难点 2：CWE 精确归因

- strict_recall 从 baseline 0.459 到 v9max 0.607，提升困难
- CWE 边界判别是小模型瓶颈（对比 CoT 引发判别焦虑）
- 34 类 CWE 覆盖，相近 CWE（如 CWE-89 vs CWE-90）易混淆

### 难点 3：FPR 抑制

- v9max FPR 0.423（恶化 +15.4pp），根因是模型对防御机制理解错误
- 三类典型误判：subprocess 列表形式误解为字符串拼接、不知道 shlex.quote 作用、过度怀疑白名单+abspath 双重防御
- 模型学到的是"看到危险函数名就报"，没学会"判断数据流是否真的能到危险点"
- 加更多安全样本标签治标，教"为什么安全"的 CoT 才治本

### 难点 4：真实 CVE 泛化

- 合成集 recall 1.000 vs CVE-fix recall 0.375（baseline），差距 59.2pp
- 真实 CVE 漏洞模式更隐蔽：防御措施迷惑、危险合理化、信任边界绕过、跨文件数据流
- CVE-fix 测试集 20 条中 13 条由 GLM-5.2 生成（非真实 NVD commit），可能仍被高估

### 难点 5：训练/推理一致性

- 训练用 HF 管道（NF4 4bit 基座 + FP16 LoRA 增量叠加）
- 发布用 Ollama 形态（base+LoRA 合并后整体 Q4_K_M 量化）
- 两种管道指标差距：CVE-fix recall 0.95 vs 0.75-0.79
- LoRA 信号在合并后整体量化时被损失

### 难点 6：跨文件污点分析

- 跨文件样本需要在实验脚本中特殊处理（把 input 文件作为上下文与 sink 文件一起送入模型）
- 单文件分析无法知道 base_dir 在调用方是常量
- Semgrep taint mode 修复跨 chunk 割裂：对原始整文件跑一次，将完整污点路径注入对应 chunk

### 难点 7：评估管道一致性

- schema 声明与训练标签不一致时，模型有足够能力会"修正"成 schema 定义的样子
- v9max 格式不匹配根因：schema 定义了 `fix_code` 字段，但 7692 条训练标签里 99% 不用它
- 三处 schema（schema.py + 两个 client）必须同步

### 难点 8：Qwen3-8B-Instruct vs Base 选型盲点

- Instruct 与 Base 在指令遵循、thinking 模式、chat template 上有本质差异
- 选型时未做对比测试，作者当时认为"是一样的"
- 实际选择（Instruct）与对话_内部备忘推荐（Base）不一致且未记录原因

### 难点 9：模型版本与文档断层（Nivis-α0）

- α0 已训练并设为默认，但 README/实验台账/论文大纲全部停留在 v9max；α0 无任何评估数据
- 系统"默认模型"与论文"当前最佳模型"不一致，是答辩被追问的高风险点；修复需补评估或统一文档
- **来源**：`app/backend/services/model_registry.py`；`docs/论文/大纲.md`；`docs/论文/参考.md`

### 难点 10：命名与口径混乱（数据文件 vs 训练版本、prompt 变体 vs 消融轮次）

- 数据文件 `final_train_chatml_v2/v3.jsonl`（8421/8616 条）与训练版本 v2/v3（823/832 条）重名；`scripts/` 与 `cloud_train/` 各有一份 train_qlora_cloud.py 且内容不同
- prompt 变体三轮消融结论不同（CoT / +consistency / combined），代码注释与文档各执一词
- 论文引用任何"vN"指标前必须写清是训练版本还是数据文件、哪一轮消融、哪个管道口径（HF / Ollama）

### 难点 11：蒸馏"计划配比"与"清洗后配比"偏离

- 任务规格计划负样本 1:3（2425 漏洞 / 7275 安全），清洗后 v9max 为 3493/4199（≈1:1.2）
- 清洗主要删除的是模板化/重复样本，负样本的清洗率明显高于正样本，但项目未记录原因；若论文用 1:3 论证"负样本充分"，评审可能用实际 54.6% 反推
- **建议**：补一段清洗阶段的正负样本流失统计，或如实写"清洗后约 1:1.2"

- 关键判断：strict_recall 的 35pp 缺口主要来自"被上下文迷惑"类 FN（如 cve_fix_0003 把 eval 合理化为安全），这类错误**靠更多 SFT 解决不了**，正是 DPO/GRPO 的适应症
- **来源**：`docs/方法论_Nivis-α1训练.md`（v1.0，2026-08-07，方案评审通过、状态"待实施"）

### 7.2 总体路线（规划）

```text
v9max (SFT 已完)
  ├─(可选) CoT-SFT 增量：仅当特定漏洞类别系统性薄弱时补 1.1 万条多教师蒸馏
  ▼
Stage A: DPO（纠"判断漂移"：错题构造 chosen/rejected 偏好对）→ 过评估门 G1
  ▼
Stage B: GRPO（用规则奖励直接优化 strict 指标，防 reward hacking）→ 过评估门 G2
Nivis-α1
  ▼
数据飞轮（贯穿全程：错题收集 → 教师重生成 → 回流训练 → 版本迭代 α2...）
```

- **顺序不可调换**：DPO 在前以最低成本修系统性误判、对稳定性破坏小；GRPO 在后会放大既有倾向，必须先由 DPO 修正判断分布，否则 GRPO 在错误模式上加速收敛
