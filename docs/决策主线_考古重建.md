## 一、核心方法论收获（五条）

1. **数据可信度比指标绝对值更重要**（事件 5/10/18/20）
   - v4 训练-测试泄漏产生漂亮但不可信的指标；v5 Jaccard 审计清洗后指标更可信
   - 评估集答案泄露会系统性高估模型能力，任何指标提升都须先用"删除泄露后重跑"验证

2. **高基座上 lr 是过拟合旋钮而非性能旋钮，LoRA 增容 ≠ 知识注入**（事件 13）
   - 7B 90.8% 高基座上，提 lr 让 dev_loss 降但 FPR 暴涨 +11.5pp
   - r=32 + rsLoRA + e=2 失败：严格 recall 仅 +1.6pp，FPR 暴涨 +19.2pp，CWE 错标 32→32 完全没动

3. **CPT 知识注入在基座已具备相关知识时会引发知识冲突与负迁移**（事件 15）
   - 用户原话："知识注入是不是需要模型原本没有相关知识，否则自带的和我注入的会互相矛盾"
   - CPT 第一次"成功"是泄题假象，第二次"爆炸"才是模型真实能力

4. **DPO 在 16GB 消费级 GPU 上不可行，"本地探索→云端放大"是可行的双轨路线**（事件 22/25）
   - 三次失败：8bit OOM / fp16 OOM / 4bit 梯度失效（grad_norm=0）
   - v9max 云端 A800 bf16 全精度训练 4.1h 完成，本地探索验证的数据与方法论在云端释放能力

5. **FPR 高的根因在模型理解不在数据量，教"为什么安全"的 CoT 才治本**（事件 27）
   - v9max 安全样本占 54.6% 但 FPR 0.423，根因是模型对防御机制的理解错误
   - 模型学到的是"看到危险函数名就报"，没学会"判断数据流是否真的能到危险点"

## 二、决策事件时间线（28 个）

### 阶段一：基座选型与首次泄漏发现（06-28 ~ 06-29）

#### 事件 1｜06-28~29 样本答案泄露首次发现与模型选型启动
- **情境**：exp_01/02/03 三个实验已完成，14 个样本源码里存在 `# 期望/漏洞/安全` 等注释直接泄露答案，导致 100% 准确率无法证明模型真实语义理解能力。主模型 gemma4:26b 耗时过长（~56s/样本）。
- **判断**：删除泄露注释后用 gemma4:12b 重跑，若仍保持 100% 即可证明模型真实能力；同时启动模型选型测试，候选 Qwen2.5-Coder 14B、DeepSeek-Coder-V2-Lite 16B。
- **结果**：删除注释后 gemma4:12b 仍 100% 准确。三模型对比中 qwen2.5-coder:14b 速度最快（18s/样本，是 gemma4 的 2.25 倍）且 JSON 稳定；deepseek-coder-v2:16b 输出非法 JSON。
- **反思**：文件名（如 `sql_injection_01.py`）仍可能泄露漏洞类型，属"弱提示"。deepseek 的 JSON 格式问题暴露了"格式遵循能力"是基座选型的重要维度。
- **方法论收获**：盲测原则要求 prompt 与源码均无答案，文件名也算泄露面；基座选型须同时考察准确率、速度、JSON 格式稳定性三维度。
- **来源**：[过程.md L3-83](file:///d:/code/毕业设计/Graduation-Project/docs/过程.md)

#### 事件 2｜06-29 难样本集扩充决策（14→42 段）
- **情境**：14 个典型样本仍 100%，但样本量小、难度低、安全对照样本仅 2 个（占比 14.3%），无法支撑毕设论文的统计意义和"LLM 优于传统工具"的核心论点。
- **判断**：按 P0-2 验收标准扩充到 30-50 段，覆盖 5 种难样本类型（绕过过滤、跨文件污点、真实 CVE、长文件、OWASP/DVWA），安全对照≥6、难样本≥6。
- **结果**：扩到 42 段（典型 12 + 安全 8 + 难 16 + 噪音 6），安全占比 38%。跨文件样本采用 input/sink 配对设计。
- **反思**：跨文件样本需要在实验脚本中特殊处理（把 input 文件作为上下文与 sink 文件一起送入模型），这成为后续 hard_crossfile 系列评估争议的伏笔。
- **方法论收获**：评估集设计必须包含足够安全对照样本（≥6）以支撑 FPR 统计意义；跨文件样本的 input/sink 配对设计需在评估流程中显式处理上下文注入。
- **来源**：[过程.md L87-131](file:///d:/code/毕业设计/Graduation-Project/docs/过程.md)

#### 事件 3｜06-29 硬件异响事件与电源瓶颈决策
- **情境**：P1-4 实验用 gemma4:12b 跑到第 23 个样本时机箱内突然出现明显异响。600W 电源在持续 100-150W CPU + 250W+ GPU 负载下接近极限。
- **判断**：暂停长耗时实验，下个月更换 1200W 电源后再继续；实验暂停期间做模型选型测试等不耗 GPU 的活。
- **结果**：P1-4 纯 LLM 难样本测试 23/42 完成、19 个未完成；P1-5 RAG 消融、P2-8 Top-K 对比均未开始。电源瓶颈直接导致了主模型从 gemma4 切到 qwen2.5-coder:14b。
- **方法论收获**：消费级硬件实验需在规划时考虑电源功率预算，长耗时实验应分批跑。

### 阶段二：模型选型与二次泄漏发现（06-30 ~ 07-06）

#### 事件 4｜06-30 DeepSeek 安全样本优化专项失败与主模型切到 qwen2.5-coder:7b
- **情境**：为纠正 deepseek 误报，将 SYSTEM_PROMPT 从 1663 字符膨胀到 5184 字符，并加 `safe_override` 后处理兜底。exp_01/03 在 deepseek 上达到 100%/0%/100%。
- **判断**：拉取更小参数的 qwen2.5-coder:7b 与 deepseek 对比。
- **结果**：qwen2.5-coder:7b 在 14 个典型样本上无需任何后处理即达 100%/0%/100%，平均耗时 7.7s（deepseek 的 1/3.5）。deepseek 的 100% 全靠 `safe_override` 兜底，纯 prompt 下安全样本误报率仍 100%。
- **反思**：deepseek 的根本问题是知识盲区（误判 `?` 占位符为拼接、误信 `subprocess.run` shell 默认 True），不是 prompt 不够长；prompt 臃肿让耗时翻倍但未改善判定逻辑。后处理白名单是外部规则覆盖而非模型能力改进，泛化性差。
- **方法论收获**：Prompt 工程无法纠正基座的根本知识盲区；准确率提升若来自后处理兜底而非模型能力，则不可信；基座选型须验证"纯 prompt 无兜底"下的真实表现。
- **来源**：[过程.md L264-387](file:///d:/code/毕业设计/Graduation-Project/docs/过程.md)

#### 事件 5｜07-05 实验严谨性二次审查：47 文件答案泄露 + RAG 代码泄露
- **情境**：准备跑 exp_04 v3 多模型对比前，对样本集和 RAG 知识库做全面审查，发现多处严重严谨性问题。
- **判断**：逐项修复——删除 47 个文件中泄露答案的注释、修复 1 个 ground truth 错误、重命名 2 个 CVE 误导文件名、对 3 个 RAG 示例代码去重。
- **结果**：exp_04 前 15 样本删除泄露注释后仍 100% 正确；exp_03 全部 14 样本 RAG 去重后仍 100%。但 v3 重跑后 P1-4 准确率从 v2 的 89.7% 降到 78.2%——**v2 的高指标是注释泄露造成的假象**。
- **反思**：关键反直觉发现——RAG 在 v3 上未带来提升（纯 LLM 88.4% 反优于 RAG+LLM 85.1%），说明删除泄露注释后模型基座已掌握典型漏洞模式，RAG 知识库没有提供额外增益。
- **方法论收获**：评估集的答案泄露会系统性高估模型能力，任何指标提升都须先用"删除泄露后重跑"验证；RAG 的价值不一定是提升召回，可解释性与知识可扩展性是其真正定位。
- **来源**：[过程.md L390-466](file:///d:/code/毕业设计/Graduation-Project/docs/过程.md)

#### 事件 6｜07-06 多模型对比结果可参考性审查与 3 个真值错误修复
- **情境**：6 模型 × 87 段 × repeat=1 共 522 次推理跑完后，用户要求"审查实验结果的可参考性，不要因为答案是错的导致实验结果不可参考"。
- **判断**：只读不写，对比 6 个模型的判定与 manifest 真值，对所有 FP/FN 样本阅读 raw_output 判断"模型判定是否真的错了"。
- **结果**：发现 3 个真值错误（safe_18 Java PreparedStatement 附带硬编码凭证、safe_13 CSRF token 附带反射型 XSS、safe_11 bcrypt 附带反射型 XSS）——4 个模型正确识别却被算 FP。修正策略是改样本代码让其真正安全（而非改真值为 true）。
- **反思**：安全对照样本的附带漏洞（硬编码凭证、反射型 XSS）非常隐蔽，编写样本时只关注主防护点却忽略了响应输出转义。多模型对比全部用 repeat=1 无置信区间，"gemma4 最优"结论可靠性有限。
- **方法论收获**：大规模实验结果需自动化审查 + 人工复核；安全对照样本设计须全方位审查所有潜在漏洞点；repeat=1 的单次实验存在随机性，关键结论需 repeat≥3 验证。
- **来源**：[过程.md L468-569](file:///d:/code/毕业设计/Graduation-Project/docs/过程.md)

#### 事件 7｜07-06 P1-5 消融分母对齐修复与"RAG 未带来提升"结论确立
- **情境**：复核 P1-5 RAG 消融对照实验时发现 B、D 两组各存在 1 个无判定样本，导致 4 组横向比较时分母不一致。
- **判断**：B 组 safe_06 用新 schema 重新解析即可救回；D 组 typical_33 输出截断需重跑 LLM。修复后 4 组均基于 87 有效样本。
- **结果**：修复后确立明确结论——**RAG 在本样本集上未带来检测能力提升**（A 组召回 91.7% < B 组 95.0%，A 组准确率 85.1% < B 组 88.5%）。
- **反思**：分母不一致的隐蔽性——单组实验合理但多组横向比较时若各组 invalid 数量不同，分母差异会让比较失去意义。
- **方法论收获**：消融实验的横向比较必须保证分母一致；"RAG 未带来提升"是反直觉但重要的发现，提示模型基座已足够强时 RAG 的边际价值在于可解释性而非召回率。
- **来源**：[过程.md L570-638](file:///d:/code/毕业设计/Graduation-Project/docs/过程.md)

#### 事件 8｜07-06 AST 代码切片实验：长文件注意力衰减的工程解
- **情境**：v3 多模型对比审查发现 qwen2.5-coder:7b 对 3 个 `hard_longfile_*` 样本虽二值判定全 True，但判定理由错误——模型把文件开头的 `DB_PATH="users.db"` 误判为硬编码凭证，漏掉文件末尾隐藏的 SQL 注入与 SSTI。这是长上下文注意力衰减的典型表现。
- **判断**：引入 tree-sitter AST 切片，文件≥150 行按顶层函数/类方法切分，每切片含文件级上下文头 + 当前函数代码，chunk 间 OR 合并（保守策略宁误报不漏报）。
- **结果**：longfile_01 理由从错误的 CWE-798 修正为正确的 CWE-89 SQL 注入（3/3 一致）；longfile_03 SSTI 仍漏（模型聚焦到 welcome 函数后仍判 False，认为 Jinja2 自动转义会防护）。
- **反思**：AST 切片对长文件隐藏的 SQL 注入有显著改进，但对需要领域知识的漏洞（如 SSTI）效果有限——切片只能解决"模型看到漏洞函数"的问题，不能解决"模型不认识漏洞模式"的问题。
- **方法论收获**：长上下文注意力衰减是 LLM 代码审计的固有瓶颈，AST 切片是工程解但有边界；不同的无训练手段解决不同问题，需组合使用。
- **来源**：[过程.md L641-703](file:///d:/code/毕业设计/Graduation-Project/docs/过程.md)

#### 事件 9｜07-06 Prompt 工程消融（exp_05）触顶，论证微调必要性
- **情境**：AST 切片完成后转向 prompt 工程消融，核心问题是当前 SYSTEM_PROMPT 各部分（白名单、硬编码规则、6 条要求、schema）的独立贡献不明。
- **判断**：设计 5 个变体（zero_shot / whitelist_only / few_shot / cot / combined）在 87 段上跑 435 次推理。
- **结果**：**CoT 是最优单一策略**（召回 95.0% / 准确率 89.7%），优于 combined 87.4%——"prompt 越长越好"是误区。白名单是"压误报但损召回"策略。cot 仍有 1 个难样本（hard_bypass_04_path_regex.py）漏报，4/5 变体都漏——论证了后续 LoRA/QLoRA 微调的必要性。
- **反思**：prompt 工程有天花板，cot 触顶后必须转向微调；跨文件污点是 prompt 工程盲区。
- **方法论收获**：Prompt 工程须做消融才能确定各组件贡献；CoT 引导污点分析是零样本最优策略但非万能；prompt 触顶是微调的触发信号。
- **来源**：[过程.md L706-765](file:///d:/code/毕业设计/Graduation-Project/docs/过程.md)

### 阶段三：微调迭代与训练失败诊断（07-07 ~ 07-19）

#### 事件 10｜07-07~08 exp_06 首个 QLoRA 训练与"换皮数据"诊断
- **情境**：exp_05 prompt 消融触顶后启动 exp_06 LoRA 微调，首个训练 `lora_r16_a32_e5_s42`。首批评估结果不理想。
- **判断**：通过 wenti.md 诊断分析，反推训练步数（995 步 = 5 epoch × 199 步/epoch）发现被评估的 r16_e5 模型实际用的是旧的"换皮增强"数据（1866 条），CoT 仍是 7 套模板，叠加 5 epoch 严重过拟合。
- **结果**：发现 3 个问题——①测试集泄露风险（`prepare_distill_corpus.py` 默认 `--include-exp04=True` 会读取评估测试集代码）；②评估指标太粗（只统计 has_vulnerability 二分类，不评估 CoT 质量、CWE 准确性、source/sink）；③dev 集与 train 同分布（15% dev 从同一数据集随机切分，dev_loss 0.011 不代表泛化好）。
- **反思**：被评估模型用的是旧数据，不能代表优化效果；data/ 被 .gitignore 排除是复现性致命隐患。
- **方法论收获**：训练数据须入库以保证复现性；dev 集与 train 同分布时 dev_loss 不能代表泛化能力，需独立 holdout；评估指标须校验 CWE/source/sink 而非只看二分类；训练步数反推是验证实际训练数据的有效手段。
- **来源**：[wenti_20260719.md L1-117](file:///d:/code/毕业设计/Graduation-Project/docs/_archive/wenti_20260719.md)；[过程.md L768-793](file:///d:/code/毕业设计/Graduation-Project/docs/过程.md)

#### 事件 11｜07-09~10 r8_e1 第二轮训练与 7 类错题根因分类
- **情境**：按 wenti.md P0/P1 优化清单改造后（LoRA 降到 r=8、epoch 5→1、lr 2e-4→5e-5/1e-5），启动 r8_e1 第二轮训练。
- **判断**：修复 5 个旧错，新退化 4 个。对 7 个错误做根因分类。
- **结果**：7 个错误分 4 类——A. 顽固老旧知识（3 个 FP：shell=True/subprocess 偏见是预训练先验，LoRA r=8 撼动不了）；B. 概念混淆+幻觉（2 个：SSTI 镜像错误）；C. 推理结论断裂（1 个 FN：推理对但结论错，捏造"已用 secrets"配合"安全"结论）；D. 跨文件认知局限（1 个 FP：单文件分析无法知道 base_dir 在调用方是常量）。还发现评估指标有水分——部分 TP 是"蒙对了方向但分析错误"。
- **反思**：shell=True 偏见是预训练先验，1 epoch 的 LoRA r=8 根本撼动不了，只能靠训练数据里的强对抗样本教；typical_19 的"推理对结论错"暗示模型从训练数据学到了"强行结论"模式。
- **方法论收获**：预训练先验（如 shell=True 偏见）是 LoRA 微调的硬边界，须用大量强对抗样本才能纠正；评估指标只看二分类会高估真实能力；错题根因分类是论文错误分析章节的核心素材。
- **来源**：[改进_历史分析_20260710.md L73-205](file:///d:/code/毕业设计/Graduation-Project/docs/_archive/改进_历史分析_20260710.md)；[过程.md L796-830](file:///d:/code/毕业设计/Graduation-Project/docs/过程.md)

#### 事件 12｜07-11 3B vs 7B 4 路对比 + DPO 试跑 + 30B teacher 验证
- **情境**：r8_e1 错题分析后需对比 3B 与 7B 微调效果决定主基座。
- **判断**：跑 4 路对比（7b_base / 7b_ft / 3b_base / 3b_ft），同时 DPO 试跑。
- **结果**：**7B 是更优微调基座**（高基座 90.8% accuracy + 低 FPR 11.5%）；3B 微调 FPR 暴涨（29.6%→42.3%），印证"弱基座上 LoRA 容量不足"判断。DPO 实际跑通 25 步完整训练无崩溃，但未评估就被 Phase 3 取代。
- **反思**：弱基座（3B）上 LoRA 微调会放大误报，基座能力是微调效果的前提；DPO 在本地是否可行存在历史判断矛盾（7-11 跑通 vs 7-27 三次失败），需区分"跑通"与"梯度有效"——后续 7-27 证实 4bit DPO 虽跑完但 grad_norm=0 梯度失效。
- **方法论收获**：基座规模与 LoRA 容量需匹配，弱基座上小容量 LoRA 会放大误报；DPO 的"跑通"不等于"训练有效"，须检查 grad_norm 与 loss 下降情况。

#### 事件 13｜07-17~18 Phase 1 lr sweep 反直觉发现 + Phase 2 LoRA 增容失败

#### 事件 15｜07-19 对话_内部备忘：CPT 两次"成功-爆炸"戏剧性转变的根因诊断
- **情境**：用户反馈"第一次做 cpt 好像泄题了，严格准确率涨到 66%，幻觉率降到 22%。但是第二次直接爆炸，宽松准确率都掉到 80%"。
- **判断**：通过对话分析，第一次 CPT"成功"很可能是泄题假象，第二次"爆炸"才是模型真实能力。
- **结果**：根因诊断三点——①底座模型领域错位（Qwen2.5-Coder-7B-Base 是代码生成模型，安全分析需要自然语言语义理解+风险推理）；②小数据 CPT 的灾难性遗忘（1400 条对 7B 模型极小，宽松准确率跌至 80%）；③训练配置问题（LoRA r=64 容量较大，小数据上高容量 LoRA 更容易过拟合）。
- **反思**：用户提出关键新论点——**"知识注入是不是需要模型原本没有相关知识，否则自带的和我注入的会互相矛盾"**。这切中了大模型知识注入研究的核心痛点"知识冲突/负迁移"。**决策方向**：放弃 CPT 路线，转向 Prompt Distillation（推理分布对齐而非知识注入）。
- **方法论收获**：CPT 知识注入在基座已具备相关知识时会引发知识冲突与负迁移；"自带知识 vs 注入知识"的矛盾是 CPT 失败的深层机制；推理分布对齐（PD）比知识注入（CPT）更适合基座已具备相关知识的场景。

#### 事件 16｜07-19 改进_历史分析 §6 类人学习范式与知识探测框架提出
- **情境**：对话中用户提出"能通过模型输出来反推他学过什么知识吗，从而选择性地注入知识，减少矛盾"——这对应大模型前沿研究的知识探测、课程学习、自训练/错题增强。
- **判断**：将"预习→学知识→学解题→刷题→复习→考试"类人学习范式映射到 LLM 训练流程，构建"探测-诊断-靶向注入-纠偏"的智能化框架。
- **结果**：设计 probe_model.py 三级探测（concept 概念辨析 / reasoning 推理深度 / attribution CWE归因），知识状态分三类（mastered/fuzzy/error）。靶向 CPT 过滤：mastered 跳过（避免知识冲突），fuzzy/error 纳入。错题驱动闭环：evaluate → extract errors → augment → retrain → re-evaluate，最大 2 轮、30% replay 防遗忘。
- **反思**：这个框架解决了"盲目注入知识导致冲突"的问题——不再追求"注入多少知识"，而是构建"探测-诊断-靶向注入-纠偏"的智能化框架。但后续脚本审查发现课程学习闭环未实现。
- **方法论收获**：知识探测是选择性注入的前提，"查漏补缺"而非"全面灌输"是避免知识冲突的关键；类人学习范式可无缝映射到 LLM 训练流程。

#### 事件 22｜07-27 DPO 本地三次失败：8bit OOM / fp16 OOM / 4bit 梯度失效
- **情境**：v7 的 FPR 0.231 远高于 8% 目标。DPO 通过 preference pairs 让模型学习"chosen 优于 rejected"，是降低 FPR 的自然选择。在本地 AMD Radeon RX 9060 XT 16 GB 上进行三次 DPO 尝试。
- **判断**：尝试 8bit / fp16 / 4bit 三种配置，预期至少有一种能在 16GB 显存上跑通。
- **结果**：三次全部失败——①8bit + max_len=1024：OOM 黑屏；②fp16 + max_len=512：立即 OOM；③4bit + max_len=512：跑完但 grad_norm=0（4bit NF4 + DPO 双前向梯度回传失效，loss=ln(2) 不下降）。失败产物归档到 `outputs/_archive_dpo_failed_4bit_grad_zero/`。
- **反思**：根因是 DPO 需要 policy 和 reference 两个模型同时前向传播，显存需求接近 SFT 的两倍。**这是 ROCm/bitsandbytes 与 DPO 双前向在消费级 16GB GPU 上的硬约束，非参数可解**。三次 DPO 失败与 v9 的数据量瓶颈共同指向同一结论：消费级 16GB GPU 只能支撑中等规模的 QLoRA SFT，无法承担偏好优化与大规模数据训练。
- **方法论收获**：DPO 在 16GB 消费级 GPU 上不可行（8bit OOM、4bit 梯度失效），偏好优化需要 24GB+ 显存或云实例；硬件约束是训练路线选择的决定性因素。

- **情境**：v9 数据备好后，为突破本地手写数据量瓶颈（峰值 914 条），采用 DeepSeek V4-Flash / GLM-5.2 双模型 API 蒸馏生成大规模训练数据（Kimi K3 原计划参与，脚本已编写但未启用）。
- **判断**：双模型分工——DeepSeek 7700 条（C/C++ 内存/渗透命令注入/Web 漏洞）、GLM-5.2 1500+ 条（CWE+CVSS 严格格式/负样本）；Kimi K3 的 2000 条（跨文件分块审计）**脚本已编写但未启用、未产生数据**。三条铁律：CoT≤5 步≤590 token、三段式统一输出、负样本 1:3 配比。
- **结果**：计划目标（含未启用的 Kimi）合计约 11200 条，但经 CWE 归一化、CWE 命名标准化、Jaccard 泄漏审计、清除矛盾/重复样本后，最终用于训练的 **7692 条**（漏洞 3493 / 安全 4199，安全占比 54.6%）。
- **反思**：**计划量→实际量的差距（约 11200→7692）说明蒸馏数据必须经过严格清洗才能用于训练，数量不等于质量**。长链推理（如 Kimi K3 计划中的跨文件分块审计）原生长链 8B 模型学不会，必须压成 ≤5 步、≤590 token——这是蒸馏到小模型的关键工程约束。
- **方法论收获**：双模型蒸馏须发挥各模型优势；蒸馏数据须严格清洗（CWE 归一化、泄漏审计、矛盾清除），数量不等于质量；长链推理须压扁为 ≤5 步才能蒸馏到 8B 模型。
- **来源**：[过程.md L1035-1044](file:///d:/code/毕业设计/Graduation-Project/docs/过程.md)；[v9max_数据生成提示词.md L1-30](file:///d:/code/毕业设计/Graduation-Project/docs/v9max_数据生成提示词.md)

#### 事件 25｜08-06 云端 A800 训练 v9max（bf16 全精度突破 16GB 限制）
- **情境**：本地数据合并清洗后，训练迁移到云端 autodl（bf16 全精度，突破 16GB 限制）。
- **判断**：用云端 A800 bf16 全精度训练，消除本地 4bit 量化带来的精度损失与 ROCm 兼容风险；max_seq_length=6144 显著高于本地的 2048，能处理跨文件、长调用链的审计任务。
- **结果**：训练配置 Qwen3-8B + LoRA r=8 + rsLoRA + lr=1e-4 + 2 epoch + alpha=16 + dropout=0.1，bf16，max_seq_length=6144，seed=42，warmup=0.1。数据划分 train 6539 / dev 1153（15%），train_loss ≈ 0.529，1636 步、约 4.1h。
- **反思**：云端 bf16 全精度消除了本地 4bit 量化的精度损失；本地探索验证数据与方法论，云端释放全精度与大规模数据能力，二者互补——这是"本地探索→云端放大"双轨策略的完整闭环。
- **方法论收获**："本地探索→云端放大"是消费级硬件下可行的工程路线；本地可用数据量与显存双受限但足以低成本验证数据/方法论，规模突破需云端全精度训练；云端训练须复用本地已验证的配置以保证可比性。
- **来源**：[过程.md L1046-1052](file:///d:/code/毕业设计/Graduation-Project/docs/过程.md)

#### 事件 26｜08-06~07 格式不匹配根因诊断：训练数据自相矛盾
- **情境**：云端模型 20/20 样本把修复代码放 `fix_code` 字段，评估脚本 `fix_extracted=0`。
- **判断**：最初判断"模型把代码放 fix_code 符合训练格式"。
- **结果**：**根因是训练数据自相矛盾**——schema 定义了 `fix_code` 字段，但 7692 条训练标签里 99% 不用它（代码全在 `fix_suggestion` 带 ``` 围栏，仅 70 条含 fix_code 字样）。模型按 schema 文字定义硬填了 `fix_code`，但训练里几乎无正面示例，输出质量不可用。**v9max 最初"模型把代码放 fix_code 符合训练格式"的判断是错的**。
- **反思**：schema 与训练标签必须严格对齐，且 guided decoding schema 也是对齐面。三处 schema（schema.py + 两个 client）必须同步。修复后 fix_extracted 0→17/20，fix_syntax_ok 0→15/20。
- **方法论收获**：训练数据自相矛盾是隐蔽瘤——schema 声明与训练标签不一致时，模型有足够能力会"修正"成 schema 定义的样子；guided decoding schema 是输出的实际约束；schema 变更须三处同步。
- **来源**：[过程.md L1054-1065, L1147-1150](file:///d:/code/毕业设计/Graduation-Project/docs/过程.md)

#### 事件 27｜08-07 v9max 评估：漏报清零但 FPR 上升，"模式匹配 > 深度理解"根因
- **情境**：v9max 训练完成并格式对齐后，在合成集 87 段与真实 CVE-fix 20 段上评估。
- **判断**：预期 v9max 在 recall 与 strict_recall 上超越 baseline，FPR 有所改善。
- **结果**：合成集 recall 1.000（61/61，0 FN，超越 baseline 0.967）、strict_recall 0.607（+14.8pp），但 **FPR 0.423（恶化 +15.4pp）**。真实 CVE-fix 20 段 recall 0.95（较 v7 的 0.800 再提升 15pp，相对 baseline 的 0.375 提升 57.5pp），仅剩 1 个 FN（cve_fix_0003.py，模型识别到 eval() 却将其合理化为"封装在函数里、非直接用户输入"）。
- **反思**：FPR 上升的主因不是训练数据不足（安全样本占 54.6%），而是**模型对防御机制的理解错误**——三类典型误判：①把 subprocess.run 列表形式误解成字符串拼接；②不知道 shlex.quote 的作用；③过度怀疑（识别出白名单+abspath 双重防御却用"abspath 行为可能因平台不同而异"合理化判漏洞）。模型学到的是"看到危险函数名就报"，没学会"判断数据流是否真的能到危险点"。
- **方法论收获**：v9max 在"检出能力"上已达发布水准（漏报清零、真实 CVE recall 0.95），但"FPR 抑制"与"CWE 精确归因"仍需后续偏好优化与防御机制教学来收敛；FPR 高的根因在模型理解不在数据量，加更多安全样本标签治标，教"为什么安全"的 CoT 才治本。
- **来源**：[过程.md L1066-1117](file:///d:/code/毕业设计/Graduation-Project/docs/过程.md)

#### 事件 28｜08-07 v9max 发布与最终模型 Nivis-alpha.1 定位决策
- **情境**：v9max 评估达标后，需决定是否继续追加训练或定位为发布版。
- **判断**：v9max 是漏洞检出能力大幅增强的已发布里程碑，但不是训练主线终点。基于 v9max 的评估缺口（FPR 0.423、strict_recall 0.607、cve_fix_0003 类 FN），最终模型 Nivis-alpha.1 将在 v9max 基础上完成收敛。
- **结果**：发布流程 tools/release_model.sh（merge LoRA → HF → GGUF f16 → Q4_K_M → ollama create）。关键改进：Modelfile 的 SYSTEM 从硬编码改为从 graduation_project.prompts.BASE_PROMPT 动态获取；temperature 0.1→0.0。产物 Ollama 模型 garrywhite109909/graduation-vuln-scanner:v9max（5.0GB Q4_K_M）。Nivis-alpha.1 收敛计划：①DPO 偏好优化（云端 A800）；②GRPO（可选）；③数据飞轮+CoT 教学；④攻克 cve_fix_0003 类 FN；⑤提升 fix_usable。
- **反思**：DPO/GRPO/数据飞轮/CoT 教学全部留给 Nivis-alpha.1，v9max 不再追加训练——避免在已发布里程碑上反复迭代导致定位模糊。DPO 的 rejected 必须用模型真实错误推理，非随便编标签。数据飞轮+CoT 教学比 DPO 更治本。
- **方法论收获**：已发布里程碑应冻结不再追加训练，后续优化在新版本上收敛；DPO/GRPO/数据飞轮/CoT 教学各有适用场景，须对症选择；"治本"方向（CoT 教学）优先于"治标"方向（DPO 压 FPR）。
- **来源**：[过程.md L1119-1163](file:///d:/code/毕业设计/Graduation-Project/docs/过程.md)
