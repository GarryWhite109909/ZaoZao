# 测试集建设方案（2026-08-22 定稿，待训练集冻结后执行）

> 结论先行：现有三个测试集无法测出泛化性能——87 段已饱和且身兼数职（仅作回归），
> CVE-fix 20 全漏洞无负样本且统计功效极低，rolling_dev 50 同样全漏洞。
> **最严重的洞：真实代码上的 FPR 从未被测量过**（所有真实测试材料中安全样本为零）。
> 本文档定义四层替代体系与全部执行细则。

## 一、四层测试体系

| 层 | 名称 | 内容 | 用途 | 引用政策 |
|---|---|---|---|---|
| L0 | 87 段合成集 | 现状不变 | 回归冒烟（防退步） | **论文不再引用为能力证据** |
| L1 | rolling_dev+safe | 50 vuln（已冻结）+ 50 real-safe | 真实 recall + **首个真实 FPR** | 发布前必测 |
| L2 | 锚定探针集 | 手写 50~60 题，带完整标注与考点标签 | 弱点归因诊断 | 论文可写"针对性评估"章节 |
| L3 | 盲测层（可选） | 训练冻结日之后新披露的 CVE | 时间性 held-out | 最高置信度的泛化证据 |

## 二、L1：real-safe 层构建细则（机械操作，无污染风险）

1. 对 rolling_dev 50 条逐条用 `fetch_fixed_files.py` 同款逻辑拉取修复后版本
   （输出到 `corpus/rolling_dev_safe/`，映射写入 `safe_map.json`）；
2. 修复 commit 中文件被删除/改名的条目跳过并在 map 中记录状态；
3. **标签即事实**：修复后版本 = 安全侧，无需任何模型参与判定；
4. 评估时成对呈现：`recall@vuln50 / FPR@safe50 / paired accuracy`（同文件正反对，
   还能直接统计"翻转一致性"——同一文件判对两侧的比例，是决策边界锐度的直接度量）。

## 三、L2：锚定探针集细则（**写作时机：alpha06 训练集冻结之后**）

### 3.1 题型 × 数量配额

| 题型 | 数量 | 探测目标 | 对应已知弱点 |
|---|---|---|---|
| 框架习语漏洞 | 15 | middleware 白名单绕过、中间件链顺序、dependency 缺失、filter 绕过 | cve_fix_0005/0006 型 FN |
| 信任边界/替代通道 | 10 | XFF/IP 可信度、redirect SSRF、webhook URL 可控、双通道差异 | CWE-441 家族 FN |
| 硬安全题 | 15 | 参数化封装在 helper、框架 autoescape、字面量脚本、假 sink | FP 弱点（形态触发） |
| minimal pair 边界题 | 10 | 成对出题，一防御之差 | 决策边界锐度 |
| 跨文件污点 | 5~10 | source 在 A / 净化在 B / sink 在 C | hard_crossfile 失败模式 |

### 3.2 标注 schema（每题一个 JSON，代码为独立文件）

```json
{
  "file": "probe_001_nextjs_middleware_bypass.ts",
  "language": "typescript",
  "expected_present": true,
  "expected_cwe": "CWE-863",
  "cwe_confidence": "certain|high",
  "source": {"line": 12, "content": "const target = req.query.redirect"},
  "sink": {"line": 31, "content": "res.redirect(target)"},
  "taint_path": ["L12 用户可控 redirect 参数", "L20 仅校验前缀 https", "L31 未校验主机部分"],
  "defense_points": [],
  "difficulty": "medium",
  "probe_tag": "framework_middleware",
  "pair_id": null,
  "why_vuln": "白名单仅校验 scheme 前缀，可用 https://evil.com 绕过（开放重定向）",
  "tool_blindspot_hint": "express/openredirect 规则不覆盖 next/server"
}
```

硬安全题额外必填 `defense_points`（数组：每个"看似危险的点 + 为何安全"）；
minimal pair 题两份共享 `pair_id`，除防御外代码逐 token 相同。

### 3.3 质量门槛（每题自证，不过不发）

1. 所有 source/sink 行号真实存在且 content 与该行逐字符一致（脚本自动校验）；
2. 漏洞题必须能写出一条从 source 到 sink 的完整数据流叙述；
3. 硬安全题必须枚举全部"危险形态点"并逐一给出安全理由；
4. 语言覆盖配额：TS/JS ≥10、Python ≥10、Java ≥5、Go ≥5，其余自由；
5. 难度分布：easy ≤20%、medium ~50%、hard ≥30%（hard = 需要框架语义或跨文件推理）。

### 3.4 污染控制（写作前后各一道门）

- **写作后**：与【最终版】训练集（含蒸馏产出）全量做归一化 Jaccard 与 AST 指纹比对，
  **阈值 0.3**（严于训练内部去重的 0.5）——命中即改题或换题；
- CVE ID 级去重：不得使用 train_pool/rolling_dev/testset_cve_fix 已含的任何 CVE；
- 写作期间不得参考教师生成的变体样本（避免被其分布锚定）。

## 四、工具层测量协议

1. 每个测试集单独报告 **stage1 工具召回率**（候选命中 expected sink 行 ±3 的比例），
   按 `语言 × CWE × 工具(semgrep/taint/prefilter)` 三维拆分；
2. 锚定集的 `tool_blindspot_hint` 字段汇总 → 输出《工具盲区清单》，
   直接作为 prefilter 新规则与语料挖词表的输入；
3. 评估报告必须**分开呈现**：模型 recall（端到端）与工具召回（stage1），
   两阶段架构的贡献拆分才可解释。

## 五、评估报告协议（论文口径）

- 能力证据只允许引用：L1 的 recall+FPR（含 paired accuracy）、L2 的考点归因表、
  L3 盲测（若做）；L0 仅表述为回归通过；
- 所有 recall 同时给两个口径：不含 review（历史可比）与全量含 review（诚实口径）；
- 报告模板字段：`{集合} × {adapter} × {recall, FPR, strict_recall, review率,
  stage1覆盖率, parse_fail}`。
