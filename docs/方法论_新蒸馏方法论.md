## 二、蒸馏数据分配评估：方向对，但有 3 处需调整

### ✅ 合理之处

- **总量 1.1 万条左右**对 8B SFT 是合理区间，DeepSeek 官方蒸馏 R1 时每档也就 80 万条通用样本，垂直安全任务 1 万级高质量样本足以支撑能力迁移。
- **GLM-5.2 专做 CWE+CVSS 标准化样本（800 条）** 的思路正确：8B 模型最缺的不是漏洞知识，而是稳定的结构化输出格式，GLM 在 JSON 合法性与指令遵循上的优势正好补这块。
- **DeepSeek 主力承担渗透/命令注入/Shell/配置**契合 V4-Flash 的 Agent 后训练偏向，这类任务本来就是它的强项。
- **漏洞修复样例单独成类（1200 条）**很有价值，避免模型只学会"报漏洞"不会"给补丁"。

### ⚠️ 需要调整之处

**调整 1：C/C++ 内存漏洞不要全押 DeepSeek，补入 K3 重构样本**

DeepSeek V4-Flash 的后训练重心是 Agent 而非内存安全推理，看雪实测其内存类漏洞"量高但近半误报"。而 K3 在 Redis 双重释放、跨 .so 调用链追踪上是公开实测最强的开源模型。建议从 2500 条里切出 600-800 条由 K3 生成，但**必须重构输出格式**——K3 原生长上下文输出（动辄数万 token 的调用链追踪）8B 学不会，要压成：

```
[漏洞类型] UAF  [CWE-416]
[位置] file.c:142
[关键证据] ptr 在 free() 后被 return path 引用
[3 步推理] 1) free 在 138 行 2) 142 行未置 NULL 3) return 触发解引用
[修复] free 后置 NULL / 改用 RAII
```

**调整 2：必须加入"跨文件分块审计"样本，这正是你文件切割工具的产出**

你提到用文件切割工具辅助 8B 识别长文件漏洞——这个能力路径需要显式蒸馏，否则模型只学会单文件扫描。建议新增 1000-1500 条"分块+全局摘要"样本，结构如下：

- **输入**：单个文件块（≤4K token）+ 上游调用方摘要（200 token 内）
- **输出**：该块内的漏洞 + 标注"需结合上游 X 函数验证"的待确认项

K3 在跨文件业务漏洞（越权、N+1、循环引用）上是强项，这类样本用 K3 生成再压扁最合适。原表里 Kimi K3"长代码库审计 ⭐⭐⭐⭐⭐"的能力你不蒸馏就浪费了。

**调整 3：CWE+CVSS 标准化样本从 800 提到 1500 左右**

8B 模型的格式遵循是最大短板，800 条对 6 类漏洞类型分摊后每类仅 100 余条，不足以稳定格式反射。清华/UCSD 的小模型微调实验表明，格式类样本量需占总样本 15-20% 才能让 8B 稳定输出结构化字段。

## 三、8B 蒸馏专项注意事项

**CoT 长度必须截断在 3-5 步**。DeepSeek-R1 蒸馏到 8B 的官方经验是：长 CoT 直接照搬会导致小模型"边想边说还反复修改"，准确率不升反降；将响应从 1120 token 压到 590 token 后，准确率从 63% 升到 89%。K3 的原始推理链动辄 2910 token，必须人工或用小模型代理做"理由压缩"，只保留锚定到具体行号的关键步骤。

**样本格式三段式统一**。无论哪个源模型生成，最终落到训练集都要统一成：`[代码片段] → [≤5步推理] → [结构化结论]`。混合 DeepSeek 的发散风格、GLM 的规整风格、K3 的长链风格直接喂 8B，会导致模型输出风格漂移。建议以 GLM 的字段schema 为锚，DeepSeek/K3 的输出改写填充。

**负样本不可省**。当前 6 类全是"有漏洞"的正样本，8B 会学到"见代码就报漏洞"的偏置——这正是你看雪实测里 DeepSeek 的毛病。建议每类按 1:3 配比加入"无漏洞"负样本，标注"已检查 X/Y/Z 点，未发现可利用路径"，这部分用 GLM-5.2 生成最稳。

**分块边界要对齐函数/类，不要按字符切**。你提到用了文件切割工具，切割粒度建议按函数边界而非固定 token 数，否则会把一个漏洞的 sink 和 source 切到两个块里，8B 永远学不会。每个块开头保留 200 token 的"上游调用摘要"作为伪全局上下文，这是让 8B 模拟 K3 长上下文能力的关键技巧。

**最后一点**：你的 8B 模型已能识别部分长文件漏洞说明分块路径走对了，但正确率不高大概率不是数据量问题，而是负样本缺失 + CoT 过长导致的"报得多但不准"。按上面调整后，建议先用 500 条做消融实验验证格式，再全量铺开。
