## 七A、提示质量审计指标（2026-08-18 定，工具层评估必须跑）

用户要求：工具层不能只查"过/不过"，要量化"提示到点、不瞎说、真正帮到模型"。
已固化正式脚本：`experiments/exp_07_two_stage_eval/prompt_quality_audit.py`
用法：`python prompt_quality_audit.py <result.json>`（无参数自动取最新 triage 结果）

五个指标（全部在 expected_present=True 漏洞样本上；工具职责/表现分离）：
  A. 工具召回覆盖率 = 工具产生>=1 confirmed 候选的漏洞样本/漏洞样本数
       —— 低=多数漏洞靠 LLM 复核兜底（工具层召回归责）
  B. 提示到点率(召回子集) = 存在>=1 提示类型与 ground-truth 同族匹配/召回样本数
  C. 噪音提示率(召回子集) = 提示了非主漏洞的额外类型/召回样本数
  D. 误导率(噪音被子集) = 噪音类型被模型判型采信/噪音样本数（真带偏=必须归因修复）
  E. 提示-判型一致性(到点子集) = 模型判型语义==工具到点提示语义/到点样本数

口径教训（防审计脚本自己"瞎说"）：
  - expected_cwe 是 CWE 编号须先解析归一（"CWE-89"→"SQL Injection"，77/78 同族）
  - bandit B 编号须按官方语义映射（B608→SQL、B301/B403→反序列化、B701→SSTI、
    B602/B603→命令注入），否则 b608 会被误判"误导"
  - child_process→命令注入(非代码注入)；render_template_string/jinja→SSTI(非XSS)
  - "噪音提示"≠"误导"：仅当噪音类型被模型采信（判型落在噪音上）才是真误导

fixed3 基线（工具层）：
  A 召回覆盖率 29.5%(18/61)  ← 主要短板，43 个漏洞靠 LLM 复核兜底
  B 提示到点率 100%(18/18)   ← 给了提示就找对点
  C 噪音提示率 16.7%(3/18)   ← typical_10/typical_35/hard_bypass_07 有额外噪音
  D 误导率 0%(0/3)           ← 模型免疫噪音，未被带偏（判型都正确）
  E 提示-判型一致性 88.9%    ← 2 例到点但模型判型语义未采信提示
