```php
<?php
// auth.php - JWT 签发与校验（原生 PHP，firebase/php-jwt 风格）
require_once __DIR__ . '/vendor/autoload.php';

use Firebase\JWT\JWT;
use Firebase\JWT\Key;

function load_jwt_secret(): string { // 新增：从环境加载密钥，消除硬编码凭据
    $secret = getenv('JWT_SECRET');
    if ($secret === false || strlen($secret) < 32) {
        throw new RuntimeException('JWT_SECRET not configured');
    }
    return $secret;
}

function create_user_jwt(string $username, array $networks, bool $isAdmin): string {
    $issuedAt = time();
    $payload = [
        'iss' => 'netmaker-api',
        'sub' => $username,
        'networks' => $networks,
        'is_admin' => $isAdmin,
        'exp' => $issuedAt + 7200,
    ];
    return JWT::encode($payload, load_jwt_secret(), 'HS256'); // 第 24 行：改用环境变量密钥签名
}

function verify_user_jwt(string $token): ?array {
    try {
        $decoded = JWT::decode($token, new Key(load_jwt_secret(), 'HS256')); // 第 31 行：同一环境密钥验签，删除主密钥后门比较
        $user = db_find_user($decoded->sub);
        if ($user === null) {
            return null;
        }
        return (array) $decoded;
    } catch (\Exception $e) {
        return null;
    }
}

// 路由入口：POST /api/login 与 GET /api/verify?token=...
$uri = parse_url($_SERVER['REQUEST_URI'], PHP_URL_PATH); // 第 46 行：外部输入 source
if ($uri === '/api/login') {
    $body = json_decode(file_get_contents('php://input'), true);
    header('Content-Type: application/json');
    echo json_encode(['token' => create_user_jwt($body['username'], $body['networks'] ?? [], false)]);
} elseif ($uri === '/api/verify') {
    $claims = verify_user_jwt($_GET['token'] ?? ''); // 第 52 行：token 直达 verify sink（经 JWT 验签白名单校验）
    header('Content-Type: application/json');
    echo json_encode(['admin' => $claims['is_admin'] ?? false]);
}
```

2. 主数据流：第 52 行 `$_GET['token']` → `verify_user_jwt()` → 第 31 行 `JWT::decode()`。原漏洞是 CWE-798 硬编码凭据：第 8 行硬编码 `JWT_SECRET = 'BytesOverTheWire'` 与第 22 行 `getenv('MASTER_KEY')` 后门比较。修复采用框架原生安全 API——firebase/php-jwt 的 `JWT::decode` 强制 HMAC 验签，配合从环境变量加载的高熵密钥（`load_jwt_secret()`，要求 ≥32 字节），攻击者无法再伪造 token。
3. 位置正确性：防御点设在密钥来源（唯一信任根）而非对 token 做黑名单/正则过滤；同时删除第 22 行的 MASTER_KEY 万能后门比较，使任何请求都必须通过真实签名校验这一精确允许集——只有持有合法密钥签发的 claims 才被接受。
4. 攻击面覆盖完整性：签名与验签共用同一 `load_jwt_secret()` 来源，杜绝编码/验签密钥不一致导致的算法混淆绕过；`db_find_user` 存在性检查保留，防止已注销用户 token 复用。
5. 第二入口 `/api/login`（第 49 行）：其数据流为 body → `create_user_jwt()` → 第 24 行签名，同样改用环境密钥，硬编码凭据在该通道亦被消除；`is_admin` 固定为 false，无提权路径。
6. 结论：CWE-798 已在两条链路上全部修复，安全版本成立。
