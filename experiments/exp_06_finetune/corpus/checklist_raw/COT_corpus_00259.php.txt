1. **枚举用户可控输入点**：`$this->config` 中的 `sql/from/where/groupby` 字段（第 76、86、93、101 行）来自用户可配置的自定义报表配置（columnConfigAction 端点），直接拼入 `$sql` 字符串；`$filters` 的 `property/value/operator`（第 111-113 行）拼入条件；`$sort/$dir/$offset/$limit`（第 33-42 行）拼入 ORDER BY 与 LIMIT。

2. **验证防御有效性**：
   - 第 96 行 `getColumns` 与第 152 行 `getBaseQuery` 使用正则 `/(ALTER|CREATE|DROP|RENAME|TRUNCATE|UPDATE|DELETE) /i` 黑名单过滤——这是黑名单，可被绕过（如多语句上下文、注释截断、无尾随空格变体、子查询注入等），不构成有效防御。
   - `$db->quoteIdentifier($sort)`（第 38 行）对排序字段做了标识符引用，但 `$dir` 仅白名单化为 ASC/DESC，LIMIT 拼接的 `$offset/$limit` 为 int 类型（strict_types 下安全）。
   - `$filter['value']` 经 `$db->quote()` 转义（第 121、131、140 行），值本身防护尚可；但 `$filter['property']` 仅经 `quoteIdentifier`，而 `quoteIdentifier` 不防所有注入场景。
   - **关键漏洞流**：`$this->config` 的 `sql/from/where/groupby` 原样拼接进查询（第 78、88、95、103 行），随后在第 158、161、163 行被包进外层 SELECT 并于第 31、32 行经 `fetchOne/fetchAllAssociative` 执行。攻击者拥有 reports_config 权限即可写入任意 SQL 片段（如 `sql: "SELECT * FROM users WHERE 1=1 UNION SELECT password,..."`），正则黑名单无法阻止 UNION/读文件等 SELECT 形态注入。

3. **第二入口检查**：`getData`（第 20 行）、`getColumns`（第 55 行）、`getAvailableOptions`（第 178 行）三条路径均调用 `buildQueryString/getBaseQuery`，全部使用同一份可控 config，均受同一无效黑名单保护，构成多个可达 sink。

4. **结论**：存在 CWE-89 SQL 注入。核心成因是用户可控 SQL 配置片段直接拼接执行，仅靠可绕过的关键字黑名单防御。风险等级 High（需 reports_config 权限，但可任意读取数据库数据）。修复应改为：配置中的 sql/from/where/groupby 不允许自由拼接，或至少强制完整语句级解析并参数化；黑名单正则不可作为唯一防线。
