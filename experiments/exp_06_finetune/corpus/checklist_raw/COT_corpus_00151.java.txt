## 漏洞分析报告

**步骤 1｜枚举用户可控输入点**
- 第 47–59 行及 Builder 各 setter（第 155 行起）的 port/dataPath/mode 等均为开发者在代码中以编程方式提供的配置，不属于远程攻击者可控输入。
- 真正的远程入口在第 92–97 行：Netty 启动 HTTP 服务，第 95 行将 `LocalS3RouterFactory.create(serviceFactory)` 生成的路由挂载到 `HttpServerInitializer`，任意客户端可提交 HTTP 请求体。其中创建桶端点处理的 `CreateBucketConfiguration` XML 文档是完全用户可控的输入。
- 该 XML 的反序列化由第 129 行注册进 ServiceFactory 的 `XmlMapper` 完成——这是本文件中用户输入到达解析器的唯一 XML 通道。

**步骤 2｜source→sink 数据流与防御有效性验证**
- 数据流：攻击者构造含恶意 DOCTYPE/外部实体的 XML 请求体 -> 第 95 行路由分发至处理器 -> 处理器取得第 129 行注册的 `XmlMapper` -> 底层为第 123 行 `new WstxInputFactory()` 创建的解析器 -> 反序列化时实体被展开。
- 防御检查：第 124 行仅设置 `IS_NAMESPACE_AWARE=FALSE`，只影响命名空间处理，与 DTD/外部实体解析无关；第 126 行 `FAIL_ON_UNKNOWN_PROPERTIES=false` 仅忽略未知字段。全文件未出现 `SUPPORT_DTD=false`、`IS_SUPPORTING_EXTERNAL_ENTITIES=false` 或 `FEATURE_SECURE_PROCESSING` 等任何针对 XXE 的加固，也不存在白名单或参数化机制可覆盖 XML 实体解析。因此该条流**无有效防御**，外部实体（file://、http:// 等）将被解析器实际解析。

**步骤 3｜第二入口/替代通道检查**
- 第 129 行将同一个未加固的 `XmlMapper` 以单例形式注册到全局 `ServiceFactory`，第 95 行的所有路由共享该实例——即除创建桶外，任何接受 XML 请求体的端点都复用同一不安全解析器，属于扩大影响面的第二通道。
- 文件内仅此一处 `XMLInputFactory` 构造（第 123 行），不存在另一条经过加固的备用 XML 解析路径，无法通过替代通道规避。

**步骤 4｜结论**
- 漏洞成立：CWE-611（Improper Restriction of XML External Entity Reference，XXE）。根因是第 123–125 行构建 XML 解析工厂时未禁用 DTD 与外部实体支持，第 129 行又将其暴露给全部请求处理器。
- 风险等级 **High**：攻击者可通过实体引用读取服务器本地敏感文件、发起内网 SSRF；服务默认监听 8080 端口（第 47、96 行）且对远程开放。
- 最小修复：在第 124 行处补设 `SUPPORT_DTD=false` 与 `IS_SUPPORTING_EXTERNAL_ENTITIES=false`。
