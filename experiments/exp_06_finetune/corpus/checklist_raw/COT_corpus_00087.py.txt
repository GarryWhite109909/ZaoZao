## 漏洞分析

**步骤 1｜枚举用户可控输入点并追踪数据流**

- 输入点 A：第 86 行从 `Cookie` 头解析出的 `_xsrf` 值 → 第 99 行传入 `_get_signed_value_urlsafe` → 第 47 行 `web.decode_signed_value` 用 `cookie_secret` 验签。到达的是验签型 sink，有密码学防护。
- 输入点 B：第 220 行 `get_argument('_xsrf')`、第 221–222 行 `X-Xsrftoken`/`X-Csrftoken` 头 → 第 235 行与服务端签发的 `handler.xsrf_token` 做精确相等比较，不匹配即 403。
- 输入点 C：第 195 行读取 `Sec-Fetch-Mode` 请求头（完全由请求方控制，跨站 JS 可指定其值）→ 第 196 行进入安全决策分支 → 第 206 行 `return False` → 第 215–217 行 `check_xsrf_cookie` 直接 `return`，整个 XSRF 校验被跳过。这是到达“安全控制 sink”的污染流。
- 输入点 D：第 171 行同一头部仅决定是否下发 cookie（`_set_cookie`），不构成鉴权绕过主通道。

**步骤 2｜逐条验证防御有效性**

- 流 A：HMAC 签名验证完整覆盖，伪造 token 无法通过解码验签，安全。
- 流 B：与签名后的服务端 token 精确比较，无语法拼接面，安全。
- 流 C：**无有效防御**。代码把客户端可完全控制的 `Sec-Fetch-Mode` 头直接当作同源信号用于授权决策。缺陷核心在第 196 行：`no-cors` 被**无条件**豁免，而对比第 197–198 行，`navigate`/`unspecified` 分支还额外要求方法属于 `{get, head, options}` 安全集合——`no-cors` 却覆盖包括 POST 在内的任意方法。攻击者页面执行 `fetch(target, {method: 'POST', mode: 'no-cors', credentials: 'include'})` 时，浏览器会附带 Cookie 并发送 `Sec-Fetch-Mode: no-cors` 的跨域请求，命中第 196 行豁免 → 第 206 行返回 False → 第 215 行提前返回，状态变更操作在无 XSRF token 的情况下被放行。

**步骤 3｜第二入口与替代通道检查**

- 第 192 行 `_token_authenticated` 跳过检查针对纯 API token 认证（无 cookie 凭证可供 CSRF 利用），不是本漏洞通道。
- 第 196 行 `websocket` 豁免同样信任该头，但 websocket 有独立 origin 校验路径；本文件内确认可利用的替代入口即 `no-cors` 分支本身，且它对所有 HTTP 方法生效，与 `navigate`+安全方法分支形成不对称豁免。

**步骤 4｜结论**

存在 CWE-352 CSRF 漏洞。攻击链：恶意第三方页面 → 以 `mode: 'no-cors'` 发起跨域带凭证请求 → 第 195 行读到 `no-cors` → 第 196 行命中无条件豁免 → 第 206 行返回 False → 第 215 行跳过 token 比对 → 受害者 cookie 身份下的写操作（如创建服务器、管理操作）被冒发。风险等级 High：需诱导受害者访问攻击页面，但一旦命中即可对任意 cookie 认证端点完成跨站写请求。
