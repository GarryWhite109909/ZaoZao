## 安全分析

**前置说明**：本题标注为 CWE-89（SQL 注入），且背景描述的是 `SimplePdo::insert/update/delete` 拼 SQL 的问题——但该类与任何数据库操作均不出现在本文件中。以下按清单逐条核实，结论以代码事实为准。

**1. 枚举用户可控输入点**
- 输入点①：第 21 行注册的 CLI 参数 `<controller>`，流入第 29 行 `execute(string $controller)` 的 `$controller`。
- 输入点②：`$runwayConfig['app_root']`（第 40–45 行）来自 `.runway-config.json` / 本地配置文件，属开发者配置而非运行时外部输入，视为可信。
- 全文无 HTTP 请求参数、无 PDO/mysqli/query 等任何 SQL 交互；第 29 行的 `execute()` 是 CLI 命令入口方法名，不是数据库执行 sink。

**2. 追踪 source→sink 数据流**
- 流 A：`$controller` → 第 53–55 行仅补全 `Controller` 后缀 → 第 57 行拼入 `$controllerPath` → 第 65 行 `mkdir(dirname($controllerPath), 0755, true)` 可在任意位置建目录。
- 流 B：`$controller` → 第 89 行传入 `persistClass()` → 第 106–107 行 `file_put_contents($this->projectRoot . '/' . $appRoot . 'controllers/' . $controllerName . '.php', ...)` 在任意可写路径创建 .php 文件。
- 附带观察：第 74 行 `new ClassType($controller)` 会把该字符串作为类名经第 108 行 `printFile` 打进生成的 PHP 文件，若 Nette 不校验标识符可能进一步造成写入内容注入，但此依赖库内部行为，不作为主结论。

**3. 防御有效性核验**
- 第 53 行 `preg_match('/Controller$/')` 只做后缀规范化，不拦截 `../`、`..\` 等穿越序列，属无效防御；`../../evil` 类输入原样通过。
- 第 58 行 `file_exists` 仅判存在性，不约束路径边界。两条流均无有效防御覆盖。
- **SQL 核验**：全文不存在任何 SQL sink，故 CWE-89 在本文件不成立，不得凭背景描述虚构 SQL 注入。

**4. 第二入口/替代通道**
- `persistClass()` 为 protected，仅被第 89 行调用一次；无其他路由、参数或间接调用通道。唯一外部可控源即 CLI 参数 `$controller`。

**5. 结论**
- 不存在 CWE-89 SQL 注入（无 SQL sink）；真实漏洞是 `$controller` 未过滤穿越序列直达 `mkdir`/`file_put_contents`，构成 **CWE-22 路径穿越/任意文件写入**。考虑这是需本地执行的脚手架 CLI 工具、写入内容基本固定，风险定为 Medium。因此最终 JSON 的 vulnerability_type 如实填 CWE-22，而非与代码不符的 CWE-89。
