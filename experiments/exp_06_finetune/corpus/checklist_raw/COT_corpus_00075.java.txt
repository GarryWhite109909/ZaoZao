## 漏洞分析报告：ConnectionSecrets.java（Kwik QUIC 库）

**步骤 1｜用户可控输入点枚举与追踪**
- 对端可控输入 ①：`computeInitialKeys(byte[] destConnectionId)`（第 95 行）——服务端场景下该连接 ID 来自远端 Initial 包，完全由对端控制；流向：第 96 行存入 `originalDestinationConnectionId` → 第 125 行 `hkdf.extract(initialSalt, originalDestinationConnectionId)`。此为 RFC 9001 规定的标准 HKDF-SHA256 流程，第 42/49/57 行的三个 STATIC_SALT 是 RFC 公开常量而非硬编码凭证，不构成注入 sink。
- 对端可控输入 ②：TLS 协商产物 `CipherSuite`/`Version`（第 132、169 行参数），受客户端 ClientHello 影响；流向第 140 行 `createKeys`。
- 对端可控输入 ③：版本协商期间对端发送旧版本包可触发 `getInitialPeerSecretsForVersion`（第 115 行）与 `recomputeInitialKeys`（第 128 行）。
- 本地输入：构造函数的 `wiresharksecrets` 路径（第 73 行）为运维配置，非对端数据。

**步骤 2｜source→sink 数据流防御验证**
- 算法选择流：第 144–157 行对 CipherSuite 做精确白名单匹配，仅允许 TLS_AES_128_GCM_SHA256 / TLS_AES_256_GCM_SHA384 / TLS_CHACHA20_POLY1305_SHA256 三种强 AEAD，其余在第 157 行抛 `IllegalStateException`；守卫位于 `createKeys` 入口，完整覆盖第 134、171、187 全部调用点，无可达弱算法分支——经典“弱算法”型 CWE-327 不成立。
- 但**密钥生命周期防护缺失**：第 66–67 行声明的 `clientSecrets`/`serverSecrets` 数组只在第 105–106、159、161 行被写入，全类不存在任何 discard/zeroize/置空逻辑；Initial 级密钥（第 105–106 行生成）在 Handshake/App 密钥生效后依旧滞留，且第 223–237 行四个 getter 对任意 `EncryptionLevel` 均可取回旧 Aead。RFC 9001 §4.9 明确要求废弃加密级别的密钥必须丢弃，此处违反——即背景所述 commit 745fd4e2 “不丢弃未使用的加密密钥”，归入 CWE-327（风险性密码学实现/密钥管理缺陷）。

**步骤 3｜第二入口与替代通道**
- 替代通道一（对端可达）：版本协商路径。对端借版本字段驱动第 128–129 行重算 Initial 密钥、第 115–116 行按任意版本新建 Aead；配合第 165–166 行 `setPeerAead` 双向交叉引用与数组长持引用，多代新旧密钥同时驻留内存，放大上一步缺陷的泄露面。
- 替代通道二（非对端可达）：第 182、198 行触发 `appendToFile`，第 204–209 行将流量密钥 hex 明文拼入内容并于第 212 行 `Files.write` 落盘——但前置条件是运维显式传入调试路径（第 78 行），属可选诊断功能，不是攻击者入口。
- 全文不存在 execute/system/eval/SQL 等注入型 sink，亦无其他路由或间接调用可将对端数据引向此类 sink。

**步骤 4｜结论**
无污点注入类漏洞；确认的漏洞为 CWE-327 密码学实现缺陷：对端可控的握手/协商事件驱动各级密钥生成后永不丢弃，退役密钥（含 Initial 密钥）全程滞留且可经 getter 访问，任一时点的内存泄露即可恢复全部历史流量密钥，破坏 QUIC-TLS 的密钥隔离与前向安全边界。因利用需叠加内存泄露等额外条件，定为 Medium。
