```code
"""SPA backend API with a strict CORS policy (CWE-942 hardened)."""
from flask import Flask, request, jsonify, Response

app = Flask(__name__)

# Exact-origin whitelist: no wildcard, no suffix/substring matching, no blind echo.
ALLOWED_ORIGINS = frozenset({
    "https://app.example.com",
    "https://admin.example.com",
})


@app.after_request
def apply_cors(resp: Response) -> Response:
    origin = request.headers.get("Origin", "")
    if origin in ALLOWED_ORIGINS:  # exact equality against a fixed set
        resp.headers["Access-Control-Allow-Origin"] = origin
        resp.headers["Access-Control-Allow-Credentials"] = "true"
        resp.headers["Vary"] = "Origin"
    # Non-whitelisted or missing Origin: no ACAO header is emitted at all.
    return resp


@app.route("/api/profile", methods=["GET"])
def profile():
    return jsonify({"user": "alice", "plan": "pro"})


@app.route("/api/profile", methods=["OPTIONS"])
def preflight():
    resp = Response(status=204)
    resp.headers["Access-Control-Allow-Methods"] = "GET, POST"
    resp.headers["Access-Control-Allow-Headers"] = "Content-Type"
    return resp


if __name__ == "__main__":
    app.run(port=8443)
```

第1步（类别定位）：本类核心特征是跨域策略宽度——`Access-Control-Allow-Origin` 的取值方式直接决定 CWE-942 是否成立。第 17 行是全文件唯一写入 ACAO 的 sink，其值来自第 15 行读取的 Origin 头回显，正是"开发图省事把 Origin 原样回显"的形态；但第 16 行存在白名单闸门。明确判定范畴：这是跨域策略问题，不是 SQL/命令注入，也不是 CWE-862/284 类越权。

第2步（输入点枚举与可达性）：外部输入点共两处——①第 15 行的 Origin 请求头，攻击者完全可控；②第 24/29 行的路由与方法声明本身不携带攻击者数据进入 CORS sink。可达性确认：第 15 行 origin → 第 16 行判断 → 第 17 行 sink，数据流连通；若第 16 行防御缺失，该流即为典型的反射式宽松 CORS（任意站点可携凭据跨域读取第 26 行的用户资料响应）。

第3步（防御类型/位置/覆盖面）：第 16 行 `origin in ALLOWED_ORIGINS` 是对第 7-10 行固定 frozenset 的精确等值比较，属白名单型防御；它不是黑名单、不是正则、也不是 startswith/endswith/子串替换，因此 `https://app.example.com.attacker.io`、`https://attacker.io/app.example.com` 等经典绕过形态全部失败。位置上校验紧贴 sink 前一行，且位于第 13 行 `@app.after_request` 钩子内，对全文件所有路由（含第 29 行 OPTIONS 预检）统一生效，覆盖完整；未命中白名单或 Origin 缺失时走第 20-21 行，完全不发 ACAO 头，浏览器将直接拦截跨域读取。

第4步（凭据与通配组合检查）：第 18 行 `Access-Control-Allow-Credentials: true` 只出现在白名单分支内部，且全文件不存在任何把 ACAO 设为 `*` 的代码路径，"通配符+凭据"这一最危险组合在结构上不可能出现；第 19 行 `Vary: Origin` 确保共享缓存不会把 A 源的 CORS 响应串发给 B 源，堵住缓存侧旁路。

第5步（第二入口/替代通道结论）：全文件仅 `/api/profile` 的 GET（第 24 行）与 OPTIONS（第 29 行）两个端点，二者响应都强制经过第 13 行的 after_request 钩子；文件内没有其他设置 ACAO/ACAC 的位置，也没有 blueprint、代理层或第二个应用实例可绕过该钩子。结论：不存在绕过白名单的替代通道，防御类型正确、位置正确、覆盖完整，判定为安全实现。
