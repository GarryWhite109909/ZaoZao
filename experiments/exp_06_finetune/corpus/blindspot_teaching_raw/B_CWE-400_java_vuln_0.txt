```code
package com.example.app.validation;

import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.regex.Matcher;
import java.util.regex.Pattern;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

/**
 * 输入校验模块：允许前端提交自定义正则表达式，对表单字段值做即时格式校验。
 */
@RestController
@RequestMapping("/api/validation")
public class UserRegexValidator {

    private final Map<String, Pattern> patternCache = new ConcurrentHashMap<>();

    @PostMapping("/check")
    public Map<String, Object> check(@RequestBody Map<String, String> payload) {
        String userPattern = payload.get("pattern");
        String fieldValue = payload.get("value");

        Pattern compiled = patternCache.computeIfAbsent(userPattern, Pattern::compile);
        Matcher matcher = compiled.matcher(fieldValue);

        long start = System.currentTimeMillis();
        boolean matched = matcher.matches();
        long cost = System.currentTimeMillis() - start;

        Map<String, Object> result = new HashMap<>();
        result.put("matched", matched);
        result.put("costMs", cost);
        return result;
    }
}
```

1. 本类核心特征：这是 CWE-400 Uncontrolled Resource Consumption 的典型形态——不可信输入驱动无界资源消耗，具体为灾难性回溯正则（ReDoS）。第 24 行用户可提交含嵌套量词的正则（如 `(a+)+$`、`(a|a)*`、`(\w+\s?)*$`），第 25 行用户同时控制被匹配串，第 31 行 `matcher.matches()` 在 java.util.regex 回溯引擎上执行，匹配失败时探索路径数随输入长度指数增长。必须明确：这不是命令注入/SQL 注入/代码注入——全程没有 shell、SQL 语句或脚本解释器参与，恶意输入消耗的是 CPU 时间与线程资源；也不是越权问题，而是资源消耗类缺陷。

2. 输入点枚举与可达性：本类唯一入口为第 22-23 行的 `POST /api/validation/check`，`@RequestBody` 反序列化出两个外部输入点——第 24 行 `payload.get("pattern")` 与第 25 行 `payload.get("value")`，均为攻击者完全可控。pattern 直达第 27 行 `Pattern.compile` 并于第 28 行构造 Matcher；value 直达第 28 行 `compiled.matcher(fieldValue)`；两条流在第 31 行 `matches()` 汇合执行。source→sink 之间无任何校验、改写或限制，可达性确认。

3. 防御逐项核查（对每条流）：①无长度限制——pattern 与 value 均可任意长；②无语法白名单——未禁止嵌套量词；即便加黑名单字符串过滤 `(a+)+`，也可写成 `(a|aa)+`、`(.*)*`、`(a*)*` 等等价灾难形式绕过，按规则此类可绕过过滤不算有效防御；③无超时——java.util.regex 的 Matcher 不支持超时，代码也未用可中断 CharSequence 包装或独立线程池隔离，第 32 行的耗时统计发生在匹配完成之后，对进行中的回溯毫无约束；④第 20/27 行 `patternCache` 不是防御——它只避免重复编译，既不校验语法也无容量上限，键完全由用户输入构成，攻击者可用海量随机 pattern 撑爆缓存构成内存型 CWE-400，且恶意正则常驻缓存影响后续请求。结论：两条数据流全程零有效防御。

4. 触发路径具体化：提交 pattern=`(a+)+$`、value=30 个 `a` 加一个 `!`，`matches()` 需穷举所有 a 的切分组合后才判定失败，回溯步数达 2^30 量级，单请求锁死一个 Tomcat 工作线程数分钟至数小时；5-10 个并发请求即可耗尽默认约 200 线程的工作池，造成全服务拒绝服务，完全落在 CWE-400 的危害定义内。

5. 第二入口/替代通道检查：本文件仅 `/api/validation/check` 一个路由方法，无其他方法读取 `patternCache` 或调用 Pattern/Matcher，不存在第二入口或间接调用通道；但这不减轻风险——单入口中 pattern 与 value 双双可控已构成完整触发条件，且第 27 行共享缓存使一次投毒跨请求持续生效。最终结论：存在 CWE-400 Uncontrolled Resource Consumption，风险等级 High。
