```code
<?php
declare(strict_types=1);

namespace App\Api\Report;

use PDO;
use PDOException;

// 报表检索接口: GET /api/report/search.php?keyword=...&owner=...
$dsn = 'mysql:host=db.internal.corp;port=3306;dbname=finance;charset=utf8mb4';
$pdo = new PDO($dsn, 'report_ro', (string) getenv('DB_PASS'), [
    PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
    PDO::ATTR_EMULATE_PREPARES => false,
]);

$keyword = $_GET['keyword'] ?? '';
$owner   = $_GET['owner'] ?? '';

$sql = 'SELECT id, title, owner, amount FROM finance_reports '
     . 'WHERE title LIKE :kw AND owner = :owner ORDER BY created_at DESC';

header('Content-Type: application/json; charset=utf-8');

try {
    $stmt = $pdo->prepare($sql);
    $stmt->execute([':kw' => '%' . $keyword . '%', ':owner' => $owner]);
    echo json_encode(['code' => 0, 'data' => $stmt->fetchAll(PDO::FETCH_ASSOC)]);
} catch (PDOException $e) {
    http_response_code(500);
    // 调试期遗留: 把驱动异常原文、SQL 模板与堆栈直接回显给前端
    $detail = $e->getMessage() . ' | SQL: ' . $sql . ' | trace: ' . $e->getTraceAsString();
    echo json_encode(['code' => 500, 'error' => $detail]);
}
```

1. **本类核心特征定位**：CWE-209 的典型形态是捕获底层异常后把异常对象内容原样写进响应体。本文件第 28 行 `catch (PDOException $e)` 捕获数据库驱动异常，第 31 行把 `$e->getMessage()`（驱动原始错误，含 SQLSTATE 码与库表线索）、`$sql`（第 19–20 行完整 SQL 模板）与 `$e->getTraceAsString()`（服务器绝对路径、调用栈）拼接为 `$detail`，第 32 行直接 `echo` 进 HTTP 响应。这属于错误信息泄露敏感内容（信息暴露类），不是注入或越权：第 25–26 行使用 `prepare` 加参数绑定，外部输入不进入 SQL 文本，因此不构成 CWE-89 SQL 注入，也与命令注入、XSS 无关——问题 solely 出在错误处理把内部细节回显给客户端。

2. **外部输入点枚举与可达性**：本文件的全部外部输入只有两个——第 16 行 `$_GET['keyword']` 与第 17 行 `$_GET['owner']`，入口为第 9 行注释所示 GET 路由 `/api/report/search.php`，不存在 Cookie、POST 体等其他输入。二者在第 26 行作为绑定参数进入 `execute()`。可达路径成立：任何令 prepare/execute 抛出 PDOException 的条件——超长 keyword 在严格 SQL 模式下触发 SQLSTATE[22001]、schema 漂移导致列不存在（SQLSTATE[42S22]）、数据库宕机或锁等待超时——都会把控制流转入第 28 行 catch，异常对象随后流向第 31、32 行。攻击者只需发送超长参数等普通请求即可稳定进入错误分支，source→sink 可达。

3. **逐条数据流与防御核查**：流 A：第 28 行异常对象 → 第 31 行 `$e->getMessage()` → 第 32 行响应体，泄露驱动错误原文与 SQLSTATE；流 B：第 19–20 行 `$sql` → 第 31 行拼接 → 第 32 行响应体，完整暴露 `finance_reports` 表名、全部列名与排序字段，等于向攻击者交付 schema 蓝图；流 C：第 31 行 `$e->getTraceAsString()` → 第 32 行响应体，泄露服务器绝对路径与代码调用结构。三条流上不存在任何防御：没有通用错误映射、没有脱敏或白名单、没有调试开关判断、没有只记日志不回显的处理——catch 块本身就是泄露点，防御覆盖面为零（并非可绕过的弱过滤，而是完全缺失）。

4. **危害定级**：响应体向任意未认证客户端泄露数据库内部错误、完整 SQL 模板与服务器路径，可直接支撑后续定向攻击（schema 侦察、路径探测），符合 CWE-209 的敏感信息经错误消息外泄定义，风险定为 High。另注：第 10 行 DSN 中的内网主机名 db.internal.corp 虽不经本 sink 直接回显，但同属应保护的内部细节，进一步印证该模块缺乏信息保密意识。

5. **第二入口/替代通道检查结论**：本文件仅有一个 HTTP 入口（第 9 行注释所示 GET 路由），`keyword` 与 `owner` 是同一入口的两个参数，最终汇聚到同一 sink（第 32 行），不存在其他路由、POST 分支或复制该 catch 模式的间接调用。需要补充的替代通道是：第 11 行 `new PDO(...)` 位于 try 之外，连接失败会抛出未捕获异常，在 display_errors 开启的常见部署误配下同样会把含 DSN 细节的错误页暴露给客户端——这进一步支持而非削弱结论。综合判定：存在 CWE-209 漏洞，风险 High。
