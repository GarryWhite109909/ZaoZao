	}

		this.stripExtension = stripExtension;
	}

	}

		}

	}

## vuln 版分析（3~4 步）

1. **输入点枚举与可达性**：唯一输入点是 HTTP 请求行中的 URI 路径，经 `ServletRequestPathUtils.getCachedPathValue(request)` 进入 `getViewName`。该路径完全由客户端控制且未做任何白名单/协议校验。第二入口检查：XFF、Referer、自定义 header 均未被读取；但 URL 编码的 `//evil.com` 或 `/redirect:http://evil.com` 形式的 lookupPath 可绕过仅去斜杠/扩展名的处理，属于同一攻击面的替代通道。
2. **数据流**：attacker-controlled lookupPath → `transformPath`（仅做去首尾斜杠、去扩展名、替换分隔符，均为格式变换而非安全校验）→ 拼接 prefix/suffix 后作为 view name 返回。
3. **Sink**：当应用配置 `/**` 映射且未显式指定视图名时，生成的视图名可被解析为 `redirect:` 视图（如请求 `/redirect:http://evil.com`），DispatcherServlet 发出 302 跳转到攻击者主机——信任边界缺陷：外部输入未经校验直接决定跳转目标。
4. **防御验证**：stripLeadingSlash/stripTrailingSlash/stripExtension 只影响外观，不阻止 scheme 注入或协议相对地址；无任何主机白名单。结论：CWE-601 成立。

## safe 版分析（3~4 步）

1. **修正点**：仅在 `transformPath` 末尾新增一处语义修正——检测结果中含 `:`（scheme 注入如 `redirect:`）或以 `//` 开头（协议相对地址）即返回空串，其余代码逐 token 相同。
2. **数据流复验**：同一 source（请求 URI）→ 同一变换链 → 新增校验点：任何能被视图解析器解释为绝对/重定向目标的形态（scheme 冒号、协议相对双斜杠）都被中和为空串，仅剩站内相对路径片段。
3. **攻击面覆盖完整性**：open redirect 的两个必要形态是带 scheme 的绝对 URL 和协议相对 URL；二者分别被 `contains(':')` 与 `startsWith('//')` 覆盖；URL 编码变体在进入本类前已被框架解码为 lookupPath，故同样命中检查。第二入口复查：header 类通道本就不存在，修正后亦无新增入口。
4. **残余风险**：空串视图名只会导致渲染失败或默认页，不产生跨域跳转。结论：CWE-601 已消除。
