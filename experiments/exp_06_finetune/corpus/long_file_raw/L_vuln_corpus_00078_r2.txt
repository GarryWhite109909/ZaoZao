# 全文通读与逐函数安全分析

## 一、文件结构与入口点总枚举

本文件是 CryptoJS 的 PBKDF2（基于口令的密钥派生函数）实现，全文共约 100 行，包含以下结构单元：

1. **第 1–5 行**：模块导入——`Base`、`WordArray` 来自 `./core.js`；`SHA1Algo` 来自 `./sha1.js`；`HMAC` 来自 `./hmac.js`。
2. **第 7–9 行**：类声明注释与 `export class PBKDF2Algo extends Base`（第 9 行）。
3. **第 11–37 行**：构造函数 `constructor(cfg)`（第 13 行起），含 JSDoc 与默认配置合并逻辑。
4. **第 39–88 行左右**：核心方法 `compute(password, salt)`（约第 47 行起），含 JSDoc、HMAC 初始化、密钥生成主循环、迭代循环、XOR 混合、结果截断。
5. **第 90 行至文末**：静态便捷函数 `export const PBKDF2 = (password, salt, cfg) => ...`。

**入口点清单（逐一枚举，覆盖全文）：**

| 编号 | 入口点 | 类型 | 位置 |
|---|---|---|---|
| E1 | `PBKDF2Algo.create(cfg)` / `new PBKDF2Algo(cfg)` 的 `cfg` 对象 | 参数入口（配置对象） | 第 13、22–28 行 |
| E2 | `compute(password, salt)` 的 `password` 参数 | 参数入口（敏感数据 source） | 第 47 行 |
| E3 | `compute(password, salt)` 的 `salt` 参数 | 参数入口 | 第 47 行 |
| E4 | 模块级导出 `PBKDF2(password, salt, cfg)` | 第二入口/替代通道 | 文末导出行 |
| E5 | `cfg.hasher` 可被调用方注入任意哈希算法对象 | 配置注入通道 | 第 25 行默认值 |
| E6 | 无路由、无文件 IO、无环境变量读取、无网络回调、无 eval/Function 构造器 | —— | 全文确认 |

该文件是纯密码学库代码：无 HTTP 路由、无 `fs`、无 `process.env`、无事件监听、无子进程调用。所有数据均来自同进程内的显式函数参数。

## 二、逐条 source→sink 数据流验证

### 数据流 D1：E1（cfg 配置对象）→ 第 22–28 行 `Object.assign`

```javascript
this.cfg = Object.assign(new Base(), { keySize: ..., hasher: SHA1Algo, iterations: 1 }, cfg);
```

- 调用方传入的 `cfg` 会**整体覆盖**默认值。这意味着攻击者若能控制 `cfg`，可注入任意 `hasher`（如自定义对象）、将 `iterations` 设为 0 或负数、将 `keySize` 设为超大值。
- **防御有效性验证**：此处**没有任何类型校验、范围校验或白名单**。`iterations` 未做 `Math.max(1, ...)` 下限保护；`hasher` 未校验是否为合法 Hasher 实例。按分析要求，缺失校验即视为无有效防御。
- **sink 追踪**：
  - `cfg.iterations` → 第 66 行 `for (let i = 1; i < iterations; i += 1)`。若 `iterations <= 1`，循环体不执行，退化为单次 HMAC——这正是默认行为本身，不构成额外崩溃风险；若为负数同样跳过循环，不抛错。
  - `cfg.keySize` → 第 58 行 `while (derivedKeyWords.length < keySize)` 与第 87 行 `derivedKey.sigBytes = keySize * 4`。若 `keySize` 为极大值（如 `1e9`），将导致内存耗尽/长时间阻塞（DoS）；但前提是攻击者能控制库调用方的配置参数——在库自身边界内这不是可远程触发的漏洞。
  - `cfg.hasher` → 第 51 行 `HMAC.create(cfg.hasher, password)`。注入非 Hasher 对象会导致后续 `.update/.finalize/.reset` 抛 TypeError，属可用性问题而非内存破坏。

### 数据流 D2：E2（password）→ 第 51 行 `HMAC.create(cfg.hasher, password)`

- password 作为 HMAC 密钥传入，随后在第 60 行 `hmac.update(salt)`、第 62 行 `hmac.finalize(blockIndex)` 中参与运算。
- **验证**：password 从不被拼接到任何字符串、不进入 `eval`、不写入 DOM、不作为路径或命令。它只流向 HMAC 内部的哈希状态。**无注入型 sink 命中**。唯一相关风险是 password 以字符串形式驻留于 JS 内存不可擦除——这是 JS 语言层面限制，CryptoJS 全系如此，不构成本文件的独立漏洞。

### 数据流 D3：E3（salt）→ 第 60 行 `hmac.update(salt)` → 第 61 行 `finalize(blockIndex)` → 第 84 行 `derivedKey.concat(block)`

- salt 进入 HMAC 消息流，输出 block 参与 XOR（第 74–76 行）并 concat 进派生密钥。
- **验证**：salt 不存在逃逸路径；XOR 循环以 `blockWordsLength` 为界（第 73 行取自本次 block），`intermediateWords` 与 block 长度一致（同一 hasher 输出），不存在越界读写（JS 数组语义下也不会越界）。无 sink 命中。

### 数据流 D4：第二入口 E4（模块级 `PBKDF2` 函数）

文末一行：

```javascript
export const PBKDF2 = (password, salt, cfg) => PBKDF2Algo.create(cfg).compute(password, salt);
```

- 该替代通道与 E1/E2/E3 完全同源同汇：`cfg` 同样未过滤直达 `Object.assign`，`password/salt` 直达 compute。**两个入口的攻击面等价**，不存在某入口有防御而另一入口绕过的差异——因为两处都**完全没有输入防御**，也就不存在“绕过”一说。
- 回调/异步通道检查：全文无 `setTimeout/setInterval/Promise/事件回调/中间件`，无第二执行路径。

## 三、黑名单/正则类防御核查

全文搜索：无正则字面量、无黑名单数组、无 `indexOf/includes` 过滤、无长度截断、无 try/catch 清洗。即**不存在“看似有效实则可绕过”的伪防御**，也**不存在任何真实防御**。这与 CryptoJS 上游实现一致——上游假设调用方自行保证参数合法性。

## 四、真实的安全弱点判定

虽然不存在注入/XSS/RCE 类漏洞，但从密码学工程角度，本文件存在一个**可论证的真实弱点**：

- 第 24–26 行默认配置：`keySize: 128/32`（128 位）、`hasher: SHA1Algo`、**`iterations: 1`**。
- 若调用方按文档示例直接使用 `CryptoJS.PBKDF2(password, salt)` 而不传 `iterations`，派生仅执行一次 HMAC-SHA1，暴力破解成本极低。这对应 **CWE-916（口令派生函数迭代次数不足）/ CWE-327（使用已破损或有风险的密码学原语——SHA-1）**。RFC 8018 明确建议迭代次数至少 1000（现代建议数十万次）并迁移到 SHA-256/HMAC-SHA2。
- 该弱点在库内**无法被修复性防御**（改默认值会破坏兼容性），属于需要文档警示 + 调用方显式传参缓解的设计缺陷，故风险评级为低到中。

## 五、结论汇总

- 注入/越权/反序列化/原型污染类漏洞：**不存在**（无相应 sink；`Object.assign` 目标为 `new Base()` 新对象而非用户可控原型目标，且 cfg 键覆盖的是实例自身属性，不触及 `__proto__` 写入 Object.prototype 的经典污染链——即便传入 `{__proto__: {...}}`，影响也仅限该实例配置，且需攻击者已能控制配置参数）。
- 真实弱点：默认 `iterations: 1` + 默认 SHA-1，构成弱 KDF 配置（CWE-916/CWE-327）。
