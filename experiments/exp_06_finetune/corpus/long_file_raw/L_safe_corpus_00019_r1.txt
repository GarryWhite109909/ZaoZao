## 编号分析（全文逐函数，行号锚定）

**1. 构造函数（第 20–230 行）—— Twig 环境初始化与模板路径注册**
- 第 33 行：`FilesystemLoader('./')` 以项目根为默认命名空间。第 36–90 行注册的路径全部来自 `$this->wiki->extensions`（服务端已安装扩展名）与配置项 `favorite_theme`（第 55 行，来自服务端配置文件 wakka.config.php），**均非 HTTP 入口直接可控**；且每个路径都经 `file_exists()`（第 88 行）校验后才注册。Twig FilesystemLoader 自身会拒绝解析到已注册根目录之外的路径，因此即使 `render()` 收到含 `../` 的路径也无法逃出项目根。
- 第 108–113 行：将 `$_GET/$_POST/$_REQUEST/$_SERVER/$_SESSION` 作为全局变量注入 Twig。这是把 source 暴露给**模板作者**（即开发者/管理员编写的模板代码），不是把 sink 暴露给匿名用户；模板文件本身位于服务器受控目录，攻击者需先获得写文件能力才能利用，属于“已失陷”前提，不构成本文件的独立漏洞。

**2. 各 Twig Helper（第 130–228 行）**
- `_t`（第 140 行）：`html_entity_decode(_t(...))`，翻译键由代码内固定传入，非用户输入。
- `url`（第 148–159 行）：tag/handler 进入 `Href()`，YesWiki 的 Href 内部对 handler 做白名单处理，且仅生成 URL 字符串，无直接文件系统或命令 sink。
- `urlImage`（第 178–212 行）：这是最敏感的 helper。`fileName/width/height/mode` 进入 `getResizedFilename` 与 `redimensionner_image`（第 199、204 行）。但注意：该 helper 只能在 Twig **模板源码**中调用（模板是服务端文件）；且刷新路径有四重防御叠加（第 200–203 行）：未休眠检查 + `file_exists` + `FILTER_VALIDATE_BOOL` 的 refresh + `UserIsAdmin()`。缩放函数本身对宽高做数值化处理。无匿名可达的 source→sink 流。
- `csrfToken`（第 165–177 行）：标准 Symfony CsrfTokenManager，类型校验完整。
- `renderAction`（第 222–225 行）：转交 Performer，动作名同样只能写在模板里。
- `reaction`（第 226–234 行）：`$entry['id_typeannonce']` 来自已渲染的条目数据，FormManager::getOne 走参数化查询层。
- `fileUrl`（第 229–232 行）：纯字符串拼接生成 URL，输出时仍受 Twig autoescape 保护。

**3. `addGlobal` / `renderInSquelette` / `hasTemplate`（第 233–251 行）**
均为薄封装，无新增 sink；`hasTemplate` 仅调用 loader 的 `exists()`，只读。

**4. `renderFromString` / `renderFromStringNoEscape`（第 256–265 行）—— SSTI 风险点**
这两个方法会把传入字符串当作 Twig 代码执行。若 `$templateString` 含用户输入即为 SSTI→RCE。但在本开源项目中，其调用方（如 `{{template}}` 类 action）在到达此处前已有 ACL/管理员限制，且本文件无法证明存在匿名直通的调用链——按“结论必须基于全文证据”的要求，不能在本文件内虚构一条不存在的入口。

**5. `renderSandboxedFromStringNoEscape`（第 272–303 行）—— 针对不可信字符串的防御性设计**
- 第 274–288 行：全新 Environment、ArrayLoader、无任何全局变量、无自定义函数泄漏；
- SecurityPolicy 白名单：标签仅 `if/for/set`（第 280 行），**不允许 include/import/block 等可逃逸标签**；方法与属性访问均为空数组（第 284、286 行），对象成员完全禁访；函数白名单仅 `date/fileUrl/max/min/random/range`（第 287 行），其中 `fileUrl` 是第 292–295 行重新绑定的闭包，只做字符串拼接返回，无文件系统副作用。
- 第 290 行 `global true` 强制所有访问走策略检查。白名单中的 `raw` 过滤器虽关闭转义，但数据 `$data` 由调用方提供且模板本身是不可信串而非存储型 payload 注入点，XSS 输出编码责任在渲染结果的消费端（页面上下文），不构成本文件的独立注入漏洞。
- 该方法的存在本身说明开发者已识别“管理员提供的模板串”这一威胁模型并做了沙箱加固。

**6. `render` / `renderTwig` / `renderPhp`（第 312–347 行）—— 文件包含 sink**
- 第 315–317 行：按后缀分流。
- `renderTwig`（第 322–328 行）：交给 Twig 渲染，loader 根目录约束生效。
- `renderPhp`（第 330–347 行）：`include $realTemplatePath`（第 343 行）看似危险，但三重前置：(a) 第 332 行 `hasTemplate` 要求路径必须命中已注册命名空间；(b) 第 335 行路径取自 `getSourceContext()->getPath()`，即 loader 解析后的真实路径，**不是原始输入**，Twig FilesystemLoader 已拒绝越出注册根目录的遍历；(c) 可命中的根目录只有项目内 `templates/`、`custom/templates/`、`tools/*/templates/` 等，攻击者需先能向这些目录写入 `.php` 文件（需服务器写权限）。`extract($data)`（第 338 行）变量覆盖风险同样要求控制 `$data`，而 `$data` 来自服务端调用方。
- 结论：source（HTTP 参数）到 sink（include）之间不存在本文件内可验证的有效通路；所有可控输入要么被 loader 根约束拦截，要么需要先具备服务器级权限。
