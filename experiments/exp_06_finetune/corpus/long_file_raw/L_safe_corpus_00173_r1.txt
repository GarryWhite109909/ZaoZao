# 全文逐函数安全分析（degit CLI 入口文件）

## 一、文件整体结构枚举

本文件为 degit 的 CLI 包装层，包含以下主要代码块：
1. 顶部导入区（第 1–8 行）
2. `main(argv)` 函数（第 10–96 行）
3. `run(src, dest, args)` 函数（第 98–112 行）
4. 底部自执行入口（第 114–119 行）

以下逐一分析每个入口点与数据流。

## 二、`main(argv)` 函数（第 10 行起）——入口点一：命令行参数

### 2.1 参数解析入口（第 12–19 行）

- 第 12 行：`mri(argv.slice(2), ...)` 解析 CLI 参数。**source = process.argv**。
- 第 13–16 行定义别名与布尔开关，无过滤作用。
- 第 21 行：`const [src, dest = '.'] = args._;` —— 用户完全可控的 `src` 与 `dest` 被解构出来。

### 2.2 help 分支（第 23–31 行）

- 第 25 行：`fs.readFileSync(path.join(__dirname, '..', 'help.md'), 'utf8')` —— 路径由 `__dirname` 拼接固定字符串构成，**不含任何用户输入**，不存在路径遍历。此 sink 安全。
- 第 26–28 行的 replaceAll 仅做 chalk 着色，输出到 stdout，无注入风险。

### 2.3 无 src 分支——交互式选择器（第 32–90 行）

这是第二入口通道：当用户不带参数运行时，程序从缓存目录读取历史记录。

- 第 34 行：`glob('**/access.json', { cwd: base })` —— `base` 来自 `./utils.js`，是 degit 固定的缓存目录（通常为 `~/.degit`），非用户本次可控。
- 第 38 行：`fs.readFileSync(`${base}/${file}`, 'utf8')` —— **sink 分析**：`file` 来自 glob 扫描结果。glob 以 `cwd: base` 为根扫描，返回的是 base 下真实存在的相对路径，攻击者若要控制此处路径，必须先能向用户缓存目录写入恶意命名的 `access.json` 文件——这属于另一前提漏洞而非本文件缺陷。且即便如此，glob 结果不会逃逸出 base 目录树。防御有效性：**依赖文件系统边界，可接受但非本文件引入的风险**。
- 第 39–40 行：`JSON.parse(json)` 解析 access.json 内容；第 42–44 行仅取 ref/timestamp 构造 Map 键值。timestamp 经 `new Date(...).getTime()` 转换，ref 仅作为 Map key 用于排序比较（第 63–66 行），**未流入 fs/exec 类 sink**。
- 第 48–57 行 `getChoice(file)`：
  - 第 51 行：`tryRequire(`${base}/${file}`)` —— 同上，file 来自 glob 扫描的 map.json，路径受 base 约束。tryRequire 加载 JSON/JS 文件属于潜在 RCE 面（require 可执行 JS），但前提同样是攻击者已能在本地缓存目录写入文件，超出本文件责任边界。
  - 第 53–55 行：构造 choices 的 message/name/value，均为纯展示数据。
- 第 59–72 行 enquirer prompt：`suggest` 回调（第 66–68 行）用 fuzzysearch 过滤，choices 值来自上述 map 数据；用户输入的搜索词只用于过滤，不进入 sink。
- 第 74 行：`fs.existsSync(options.dest)` / 第 75 行 `fs.readdirSync(options.dest)` —— **sink：dest 由交互输入提供**。existsSync/readdirSync 只读探测，不写入、不删除，风险极低（信息泄露面可忽略）。
- 第 77–87 行：目录非空时询问是否覆盖；`force: true` 在第 85 行被硬编码传入 run——注意这里即使用户在 toggle 中拒绝 force 也仅在未确认时 return（第 82–84 行），逻辑一致，无绕过。
- 第 89–91 行：`run(options.src, options.dest, {...})` —— src 来自缓存 map.json 中预存的 hash 值（历史上 degit 克隆过的仓库标识），dest 来自用户交互输入。

### 2.4 带 src 分支（第 93 行）

`run(src, dest, args)` —— src/dest 直接来自 argv，是主数据流起点。

## 三、`run(src, dest, args)` 函数（第 98 行起）

- 第 99 行：`const d = degit(src, args)` —— 将用户可控 src 交给核心库。核心库（index.js，不在本文件内）负责解析 `host:user/repo#ref` 并校验 host 白名单等；本文件不做二次校验，也不应做——职责分离正确。
- 第 100–106 行：info/warn 事件仅 `console.error` 输出 message，message 经 `.replace('options.', '--')` 处理，无命令拼接，无 shell 调用，终端转义序列理论上是唯一展示层面问题但 chalk/Node 不解释 ANSI 注入为命令执行，风险可忽略。
- 第 107 行：`d.clone(dest)` —— dest 作为克隆目标目录传入核心库。核心库内部使用 tar 流解压到该目录；dest 本身由用户指定目标位置属预期功能（CLI 工具语义），非漏洞。
- 第 108–111 行：错误处理仅打印并 exit(1)。

## 四、底部自执行（第 114–119 行）

- 第 115 行：`if (!process.env.VITEST)` —— 环境变量仅作测试跳过开关，不影响数据流。
- 第 116–119 行：`main(process.argv).catch(...)` —— 完整 argv 传入，与入口点一相同。

## 五、source→sink 数据流汇总验证

| # | source | sink | 防御评估 |
|---|--------|------|----------|
| 1 | argv → src（第 21 行） | degit() 构造器（第 99 行） | 校验委托给核心库白名单机制，本文件无黑名单式伪防御 |
| 2 | argv/交互 → dest（第 21/74 行） | existsSync/readdirSync（第 74–75 行）、d.clone(dest)（第 107 行） | 只读探测 + 预期写目录语义，无遍历放大 |
| 3 | 缓存目录 glob 结果（第 34/60 行） | readFileSync/tryRequire（第 38/51 行） | 路径被 base cwd 约束；利用前提是先攻破缓存目录写权限 |
| 4 | help.md 固定路径（第 25 行） | readFileSync | 无用户输入，安全 |
| 5 | 事件 message（第 100–110 行） | console.error | 纯输出，无 sink |

## 六、第二入口与替代通道检查

1. **交互式分支（无参数运行）**：src 取自本地缓存 map.json 而非直接 argv——攻击者需先污染 `~/.degit/**/map.json`，这要求本地文件写权限，届时已是更高权限前提，不构成本文件独立漏洞。
2. **环境变量**：仅 VITEST 开关（第 115 行），不进 sink。
3. **回调通道**：enquirer suggest（第 66 行）、事件监听（第 100–105 行）均不产生新的危险流。
4. 未发现隐藏的 exec/spawn/eval/子进程调用；本文件所有 fs 操作如上枚举。

## 七、结论

通读全文后：本文件是薄 CLI 层，真正的解析/下载/解压安全逻辑在核心 index.js 中；本文件内的所有 fs sink 要么路径固定（help.md），要么被 base 目录约束（缓存读取），要么是预期功能的用户指定目标目录（clone dest）。未发现可独立利用的注入、遍历或 RCE 漏洞。
