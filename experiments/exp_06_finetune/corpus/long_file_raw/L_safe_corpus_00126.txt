# 编号分析

1. **第 1–40 行（文件头/命名空间/use）**：纯声明，无入口点。

2. **构造函数（第 88–94 行）**：接收 `RouteCollection`、`RequestContext`、logger、defaultLocale。这些是开发者注入的配置对象，非用户输入 source。

3. **setContext / getContext / setStrictRequirements / isStrictRequirements（第 99–122 行）**：setter/getter。`strictRequirements` 若被设为 `false` 或 `null` 会放宽参数校验，但这是应用层显式配置决策，非外部可控输入。

4. **generate()（第 127–166 行）**：核心入口之一。
   - `$name`：路由名，仅用于 `$this->routes->get()` 查找，找不到即抛异常（第 152 行），不进入 URL 输出，无注入 sink。
   - `$parameters['_locale']`（第 129 行）：用于拼接路由名查找 `'.'.$locale`，同样只做集合查找；`strstr($locale, '_', true)` 循环仅截断，无输出路径。
   - `_canonical_route` 校验（第 155 行）防止 locale 路由劫持。

5. **doGenerate()（第 178–283 行）**：真正的 URL 拼装 sink 所在。
   - **变量 token 路径段（第 194–216 行）**：用户参数先经路由 requirement 正则校验（第 199 行）；即使 strictRequirements 关闭导致跳过校验，第 226 行 `strtr(rawurlencode($url), $this->decodedChars)` 对整条 path 做 rawurlencode，`.`/`..` 再被编码为 `%2E`（第 230–239 行），杜绝路径穿越与 scheme 注入。decodedChars 白名单字符（`/ @ : ; , = + ! * |`）均为 RFC 3986 中 path 内无特殊语义的子分隔符，且 `/` 是有意允许的层级符——这是设计行为而非漏洞。
   - **hostTokens（第 252–275 行）**：host 变量同样经 requirement 正则校验后拼入 authority。若 requirement 为空则任意值可入 host——但 host 变量值来自路由定义的占位符匹配结果或调用方传入，requirement 由开发者定义；Symfony 历史上确有 host 注入讨论，但该风险前提是开发者写了无 requirement 的 host 占位符并直接使用生成结果，属于框架契约内的配置责任，非本文件可利用缺陷。
   - **query string（第 297–300 行）**：`http_build_query(..., PHP_QUERY_RFC3986)` 全量百分号编码，随后 strtr 仅还原白名单字符（不含 `& = +`），防参数拆分。
   - **fragment（第 302–305 行）**：`rawurlencode($fragment)` 后还原白名单，`# ? /` 均被编码，无法逃逸 fragment。
   - **对象转换闭包（第 290–298 行）**：`get_object_vars`/`__toString` 仅做类型归一化，无危险调用。

6. **getRelativePath()（第 310–352 行）**：纯字符串运算，冒号前缀处理（第 347–350 行）已防御相对引用被误读为 scheme。

7. **第二入口/替代通道核查**：本类无 HTTP 直接入口，所有输入来自 `RequestContext`（由 Request 组件构建，baseUrl/host 已在上游编码）与调用方传参；无文件操作、命令执行、反序列化、eval 等 sink。唯一字符串拼接到 URL 的点均被 rawurlencode + 白名单 strtr 双重覆盖。

**结论**：全文未发现可利用漏洞；编码策略为白名单式且覆盖 path/query/fragment 三类 sink。
