# 逐函数安全分析（全文通读，行号锚定）

## 一、文件整体定位

本文件是一个纯工具模块（cost 工具类），无任何网络入口（无 Flask/FastAPI 路由）、无文件 I/O、无环境变量读取、无 subprocess/eval/exec/pickle 等危险 sink。所有函数均为纯计算与字符串格式化。以下逐一枚举每个函数及其数据流。

## 二、逐函数分析

### 1. `CostTracker.calculate_cost`（第 33–47 行）
- 入口点：三个参数 `input_tokens`、`output_tokens`、`model`（第 34–36 行），均为库内调用传入。
- 数据流：参数直接透传至 `get_estimated_cost(...)`（第 47 行）。该 sink 为成本估算计算，不涉及 SQL、命令执行、路径操作或 HTML 渲染。即使 `model` 为攻击者可控字符串，其用途仅是查表计价或作为字典 key，不存在注入面。
- 防御评估：无需防御；类型注解 `Optional[Union["Model", str]]` 表明设计上接受任意字符串模型名。

### 2. `CostTracker.calculate_cost_from_usage`（第 49–64 行）
- 入口点：`usage: RequestUsage` 对象与 `model`（第 52–53 行）。
- 数据流：透传至 `get_estimated_cost_from_usage`（第 64 行）。`RequestUsage` 是框架内部结构化对象，非外部原始输入；sink 仅做数值运算。无可利用路径。

### 3. `CostTracker.calculate_cost_from_agent_run_output`（第 66–81 行）
- 入口点：`agent_run_output: AgentRunOutput` 与 `model`（第 69–70 行）。
- 数据流：透传至 `get_estimated_cost_from_run_output`（第 81 行）。同上，sink 为数值格式化，无字符串拼接进危险上下文。

### 4. `CostTracker.calculate_cost_from_run_usage`（第 83–99 行）
- 入口点：`run_usage: RunUsage`（第 85 行）。
- 数据流：第 90–91 行对 None 做了防御性检查并返回 `"~$0.0000"`；第 92–93 行用 `or 0` 兜底 None 值——这是有效的健壮性防御（防 AttributeError / TypeError）。随后第 95 行进入 `get_estimated_cost` 数值计算。无注入面。

### 5. `CostTracker.extract_cost_from_string`（第 101–120 行）★ 重点审查
- 入口点：`cost_string: str`（第 105 行）——这是本文件中最接近“外部字符串输入”的 source，可能来自存储层反序列化的会话数据。
- 数据流：
  - 第 109–113 行仅做前缀判断（`~$` / `$`）后切片；
  - 第 114 行 `float(cost_string)` 是唯一转换 sink；
  - 第 115–116 行 `except (ValueError, TypeError): return 0.0` 捕获所有可能的解析异常。
- 攻击面验证：
  - **命令注入**：`float()` 不经过 shell，无此风险；
  - **代码执行**：Python 3 的 `float()` 不再接受 `inf`/`nan` 之外的字符串表达式，且即便接受也只是浮点值，不会 eval；
  - **异常逃逸**：`float()` 只抛 ValueError/TypeError，均被捕获；若传入非 str 类型（如 int），`startswith` 会抛 AttributeError——这是一个潜在健壮性瑕疵（第 109 行未先做 isinstance 检查），但属于 DoS-级微瑕且调用方为内部可信代码，不构成安全漏洞；
  - 返回值是 float，无法携带 payload 向下游传播。
- 结论：source→sink 数据流被 try/except 完全封闭，输出域收敛为 float 或 0.0，**有效防御**。

### 6. `CostTracker.get_name`（第 122–134 行）
- 入口点：`model` 参数（第 126 行）。
- 数据流：直接返回 `get_model_name(model)`（第 134 行）。返回值为 str，但本文件内无任何下游将其拼入 SQL/shell/HTML。跨模块传播超出本文证据范围，本文内不可判定为漏洞。

### 7. `CostTracker.get_provider_name`（第 136–158 行）
- 入口点：`model` 对象（第 140 行）。
- 数据流：第 142–143 行 hasattr 探测 `provider_name`；第 144–152 行探测 `model_name` 并用 `'/' in model_name` 切分（第 148–149 行，`split('/', 1)[0]` 无越界风险）；第 150–154 行前缀匹配黑名单式推断 provider（gpt-/claude-/gemini-），匹配失败回落 `"unknown"`（第 157 行）。虽然前缀匹配属“可绕过”式启发法，但其后果仅是 provider 名显示错误（功能性瑕疵），不触及任何安全 sink。**非安全缺陷**。

### 8. 模块级函数 `format_cost`（第 161–175 行）
- 入口点：`cost: float`、`currency: str = "USD"`（第 164–165 行）。
- 数据流：第 169–173 行 f-string 格式化。注意第 165 行 docstring 自述 currency “unused, always USD”，实际确实未使用 `currency` 变量——这是死参数，非注入点。f-string 中 `{cost:.4f}` 强制浮点格式化，若 cost 非 float 会抛异常而非注入。无风险。

### 9. 模块级函数 `format_tokens`（第 177–189 行）
- 入口点：`tokens: int`（第 180 行）。
- 数据流：第 183–188 行三分支格式化，纯算术与 f-string。负数会落入第一分支原样返回，仅影响显示。无 sink。

## 三、第二入口与替代通道核查

- **HTTP 路由**：全文无 import flask/fastapi/django，无路由装饰器——无第二入口。
- **文件/环境通道**：无 `open()`、`os.environ`、`os.getenv`、`pathlib`——无文件与环境变量 source。
- **回调/反序列化**：无 `pickle.loads`、`yaml.load`、`eval`、`exec`、`__import__`、`subprocess`——无动态执行 sink。
- **导入的下游函数**（第 15–20 行）：`get_estimated_cost*` 与 `get_model_name` 来自 `upsonic.utils.usage`，不在本文内；基于本文证据它们只接收数值/模型名用于查表，本文内无可判定的污点传播终点。
- **正则/黑名单审计**：全文唯一的“过滤”逻辑是第 150–154 行 provider 前缀匹配和第 109–113 行 cost 前缀剥离，二者均不承担安全职责，故“绕过”不构成漏洞。

## 四、总结

全部 9 个函数均为纯计算/格式化工具，source 全部来自库内部调用方，sink 仅为 `float()` 解析与 f-string 格式化，且关键解析处有完整异常兜底（第 115–116 行）。未发现注入、XSS、反序列化、路径穿越、SSRF、命令执行等任何漏洞类别。唯一可提的是 `extract_cost_from_string` 未校验入参类型（第 109 行对非 str 会抛 AttributeError）及 `format_cost` 的 `currency` 死参数，均属代码质量问题而非安全漏洞。
