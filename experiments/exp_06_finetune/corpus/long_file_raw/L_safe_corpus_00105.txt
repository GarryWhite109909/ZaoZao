## 编号分析

1. **类定位**：`DatabindContext` 是 Jackson databind 的抽象基类（反序列化/序列化上下文），本身不直接暴露 HTTP 入口；攻击面来自多态反序列化的 type id 解析。

2. **入口点枚举（全文）**：
   - `resolveSubType`（约第 100 行起）：source 为 `subClassName`（来自 JSON type id），sink 为 `getTypeFactory().findClass(...)` / `constructFromCanonical(...)`。注意：该方法注释明确说明不做 PTV 校验，因为调用方已先校验——这是设计契约，非漏洞。
   - `resolveAndValidateSubType`：source 为 `subClass`，先经 `ptv.validateSubClassName` 名称校验，再 `findClass` 加载，非子类型即抛异常；INDETERMINATE 时再走 `validateSubType` 类级校验。防御链完整。
   - `_resolveAndValidateGeneric`（泛型分支）：对带 `<` 的类型 id，剥离参数后校验容器名，`constructFromCanonical` 后校验 `isTypeOrSubTypeOf`，且当名称校验非 ALLOWED 时再做类级校验。
   - **关键点 [databind#5988] 修复**：本版本在容器通过校验后，遍历 `containedType(i)` 与数组成分调用新增的 `_validateTypeParameter`，递归校验每个类型参数（含嵌套泛型），堵住了 `ArrayList<EvilGadget>` 式绕过。旧版本缺失此步即为 CVE 类漏洞；当前代码已包含修复。
   - `objectIdGeneratorInstance` / `objectIdResolverInstance` / `converterInstance`：sink 为 `ClassUtil.createInstance`，但 source 是注解元数据（`ObjectIdInfo`、`converterDef`），非用户输入；且 converter 有 `Converter.class.isAssignableFrom` 类型检查。无外部可控数据流。

3. **第二入口/替代通道检查**：`constructFromCanonical` 在泛型分支中会解析任意类名，但解析结果必须 (a) 是 baseType 子类型，(b) 通过 PTV 名称或类级校验，(c) 其所有类型参数经 `_validateTypeParameter` 校验——替代通道均被覆盖。`_truncate`/`_quotedString` 仅影响错误消息长度，无注入 sink。

4. **结论**：全文未发现 source→sink 未受有效防御的数据流；泛型类型参数校验（#5988）已实现，递归覆盖嵌套与数组场景，`Object.class` 豁免合理。
