# PBKDF2Algo 安全分析报告

## 一、文件结构总览

本文件为 crypto-es 库的 PBKDF2 密钥派生模块，全文共约 110 行有效代码，包含以下主要组成部分：

1. **第 1–6 行**：import 语句（`Base`、`WordArray` 来自 `./core.js`；`SHA256Algo` 来自 `./sha256.js`；`HMAC` 来自 `./hmac.js`）——仅引入纯密码学原语，无网络、文件系统、进程等危险依赖。
2. **第 8 行至第 76 行**：`PBKDF2Algo` 类定义（含构造函数与 `compute` 方法）。
3. **第 78 行至第 105 行**：JSDoc 文档注释。
4. **第 106 行**：导出的静态便捷函数 `PBKDF2`。

## 二、入口点逐一枚举

### 入口点 1：`PBKDF2Algo.constructor(cfg)`（第 26–44 行）

- **参数来源**：调用方传入的可选配置对象 `cfg`。
- **数据流**：第 34–39 行通过 `Object.assign(new Base(), { keySize: 128/32, hasher: SHA256Algo, iterations: 250000 }, cfg)` 合并配置。
- **防御验证**：默认值中 `hasher: SHA256Algo`（第 37 行）、`iterations: 250000`（第 38 行）是针对 CVE/GHSA-mpj8-q39x-wq5h（CryptoJS 默认 SHA1 + 低迭代次数导致弱密钥派生）的安全加固（见第 30–33 行注释）。攻击者若能传入 `cfg` 可覆盖 `iterations` 为小值或 `hasher` 为弱哈希——但这属于**库 API 的正常可配置性**，非漏洞：PBKDF2 规范本身允许调用方选择参数，且该能力在文档（第 20–24 行示例）中明示。此文件内不存在将外部不可信输入直接路由到 `cfg` 的通道。
- **sink 分析**：`cfg` 最终流入 `compute` 中第 47 行 `hmac.update(salt)` 的迭代次数与哈希函数选择。无代码执行 sink（无 `eval`、`Function`、原型链污染写入）。注意：若攻击者可通过 `cfg` 注入 `__proto__` 等键，`Object.assign` 会将其复制到目标对象上——但目标为 `new Base()` 局部对象而非全局 `Object.prototype`，且 `Object.assign` 只复制自有可枚举属性，不会触发原型污染全局。风险限于本次派生实例，无跨实例影响。

### 入口点 2：`compute(password, salt)`（第 46–75 行）

- **source**：`password` 与 `salt`，类型声明为 `WordArray|string`（第 41–42 行 JSDoc）。
- **sink 枚举**：
  - 第 49 行 `HMAC.create(cfg.hasher, password)` —— password 进入 HMAC 密钥槽位。HMAC 内部对字符串会经 UTF-8 编码转 WordArray，属正常数据处理，无解释执行 sink。
  - 第 58 行 `hmac.update(salt)` —— salt 进入哈希输入缓冲区，同样仅为字节处理。
- **逐条数据流验证**：
  - **流 A**：`password → HMAC.create(第49行) → finalize/update 循环(第58、64行) → derivedKey(第72行 concat) → 返回值(第75行)`。全程为算术与字数组操作（XOR 在第 68–70 行），不存在 DOM、SQL、命令行、反序列化等危险 sink。返回值是派生密钥本身，如何使用由调用方决定，本文件不负责下游防护——这是密钥派生库的标准边界。
  - **流 B**：`salt → hmac.update(第58行)`。salt 长度不受限制，但 PBKDF2 规范允许任意 salt；无内存越界可能（JS 数组自动扩容）。
- **循环终止性检查（潜在 DoS 面）**：第 56 行 `while (derivedKeyWords.length < keySize)` 与第 62 行 `for (let i = 1; i < iterations; i += 1)`。若调用方传入超大 `keySize` 或 `iterations`，会导致长时间 CPU 占用。但这两个值来自第 34–39 行的配置合并，属于**调用方自担责任的性能参数**，与 CryptoJS 官方实现行为一致，不构成可被第三方触发的远程 DoS 漏洞（除非宿主应用把用户输入直接映射到这些参数——那是应用层问题，不是本文件的缺陷）。
- **正确性与安全相关细节**：
  - 第 60 行 `blockIndexWords[0] += 1` 正确递增块计数器，符合 RFC 8018。
  - 第 73 行 `derivedKey.sigBytes = keySize * 4` 截断输出至请求长度，防止多余字节泄露。
  - 第 65–70 行 XOR 累加逻辑正确：`blockWords[j] ^= intermediateWords[j]`，块长以首次迭代的 `blockWordsLength` 为准，与规范一致。

### 入口点 3：静态函数 `PBKDF2(password, salt, cfg)`（第 106 行）

- 单行委托：`PBKDF2Algo.create(cfg).compute(password, salt)`。数据流与上述两个入口完全相同，无新增 sink。

## 三、第二入口与替代通道排查

- **环境变量/文件系统/网络**：全文 import 仅限 `core.js`、`sha256.js`、`hmac.js`（第 1–6 行），无 `fs`、`http`、`process.env`、`child_process` 引用。无替代输入通道。
- **回调/事件监听**：类未注册任何事件监听器或定时器回调，无异步入口。
- **原型链面**：第 35 行 `new Base()` 作为 assign 目标隔离了 cfg 注入；`Base` 继承链（crypto-es core）不含可被本文件触发的危险方法。
- **正则/黑名单过滤**：本文件未使用任何正则或黑名单，因此不存在“黑名单可绕过”类问题。
- **时序侧信道**：第 68–70 行 XOR 为常数时间操作；PBKDF2 本身设计为耗时函数，比较逻辑不在本文件内。无可利用的早期退出分支泄露秘密信息（while 条件仅依赖 `keySize` 配置，非秘密）。

## 四、结论

通读全文后确认：所有 source（password/salt/cfg）→ sink（HMAC 哈希计算）的数据流均为纯密码学运算，无注入、无代码执行、无原型污染全局、无越权访问；针对已知 CVE GHSA-mpj8-q39x-wq5h 已通过提升默认迭代次数与更换 SHA256 主动加固。未发现安全漏洞。
