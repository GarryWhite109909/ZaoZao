## 编号分析

1. **第 1–16 行（makeJoined）**：仅做 DB 记录到模型的转换与 JSON 反序列化，无用户输入 source，无 sink。

2. **第 24–50 行（GetSharingById）**：入口参数为分享 id，直接作为缓存键和 DB 查询键，走参数化查询（db 层），无拼接 SQL，无路径操作。安全。

3. **第 52–66 行（GetSharings / GetSharingsByCreatorId）**：分页参数由调用方传入，DB 层处理，本文件内无 sink。

4. **第 68–97 行（GetSharingUnwrapPath）——核心风险点**：
   - 第 71–78 行：对非管理员创建者做了 BasePath 复校验（`utils.IsSubPath`），这是有效防御，但只覆盖“创建者 BasePath 变更”场景。
   - 第 79–81 行：**单文件分支**：`stdpath.Join(sharing.Files[0], path)` 直接使用未经过 `utils.FixAndCleanPath` 清洗的原始 `path`。虽然 `stdpath.Join` 内部会 lexical Clean，但这恰恰意味着 `../..` 会被规范化解析——例如 `Files[0]=/data/public`、请求 path=`../../private` 时结果为 `/private`，可逃逸出被分享目录范围。该分支没有任何后续校验确认结果仍位于 `sharing.Files[0]` 之下。source 是外部传入的分享子路径，sink 是实际文件系统访问路径的构造点。
   - 第 83–95 行：多文件分支先执行 `FixAndCleanPath(path)[1:]` 清洗（第 84 行），再按首段目录名匹配 `sharing.Files`，`rest` 来自清洗后的路径，相对安全；但匹配依据是 `stdpath.Base(c)`（第 90 行），若两个共享项 basename 相同可能映射到错误条目，属逻辑缺陷而非可直接利用的安全漏洞。

5. **第 99–107 行（CreateSharing）**：写入前对所有 Files 执行 `FixAndCleanPath`，防御到位。

6. **第 109–119 行（UpdateSharing）**：默认同样清洗；但存在 `skipMarshal` 参数（第 109 行），当调用方传 true 时跳过清洗直接落库——若上游某入口允许用户控制 sharing 内容且传 skipMarshal=true，则构成第二入口绕过通道；本文件内无法证实此类调用存在，需结合全文其他文件确认，此处记为可疑而非确证。

7. **第 121–137 行（UpdateSharingId / DeleteSharing / DeleteSharingsByCreatorId）**：id 删除操作走 DB 主键查询，无注入面；缓存删除逻辑正确。
