# 逐行分析

**入口点枚举（全文）**

1. **静态初始化 `initHtmlDefault()`（第 ~150-200 行）**：仅使用硬编码的字符串数组常量，无外部输入 source。`setupTags()` 遍历这些常量构造 Tag 对象。无 sink。

2. **公有 API 入口点**：
   - `TagSet(TagSet template)` 拷贝构造（第 ~40 行）：输入是另一个 TagSet 对象，仅做深拷贝（clone Tag），无字符串/IO sink。
   - `add(Tag tag)`（第 ~70 行）：接受调用方传入的 Tag 对象，写入内存 Map。无文件、网络、SQL、命令执行等 sink。
   - `valueOf(...)` 系列（第 ~110-140 行）：接受 tagName 字符串。数据流：tagName → trim → `get()` 查找 → 未命中则 `new Tag(tagName, normalName, namespace)` → `doAdd()` 存入 HashMap。sink 是内存 Map 的 key。HashMap key 无注入风险；tagName 来自 HTML 解析的 token 名或调用方代码，最终只影响解析行为，不构成 XSS/注入 sink 本身。
   - `onNewTag(Consumer<Tag>)`（第 ~160 行）：注册回调。回调由调用方提供并在 `doAdd()` 中执行——这是设计意图的扩展点，非漏洞；回调内容不在本类控制范围内。

3. **内部方法 `get()`（第 ~90 行）与 lazy clone pull-through**：从 source TagSet 克隆并 doAdd。纯内存操作。

4. **`equals/hashCode`（第 ~175-185 行）**：基于 Map 比较，无风险。

**source→sink 数据流验证**

- 唯一动态字符串来源是 `valueOf(tagName, ...)` 的 tagName 参数。追踪其去向：
  - `tags.computeIfAbsent(...).put(tag.tagName, tag)` —— 内存哈希表 key；
  - `tag.tagName = tagName`（preserveTagCase 分支）—— 对象字段赋值。
- 全文不存在以下 sink：Runtime.exec / ProcessBuilder、File I/O、URL 连接、SQL、反序列化 readObject、反射 Class.forName、XML 外部实体、HTML 输出拼接。因此任何“恶意 tagName”都终止于内存数据结构，无法到达可利用 sink。

**第二入口/替代通道检查**

- `customizers` 回调链：`doAdd` 中对每个新 Tag 执行 customizer。若调用方注册了危险 customizer 属于其自身责任，本类未引入默认危险行为；且 customizer 列表在拷贝构造中仅做浅复制引用（`new ArrayList<>(base.customizers)`），共享 Consumer 实例，但这是文档化的扩展机制而非安全边界破坏。
- `HtmlTagSet` 为 static final 共享实例，`Html()` 返回副本，避免了对全局默认集的污染——防御有效。

**结论**：该文件为纯内存数据结构管理类（jsoup 解析器配置），所有输入均来自进程内调用方，全部 sink 为内存 Map 写入，无 IO/执行/序列化 sink，无可达攻击路径。
