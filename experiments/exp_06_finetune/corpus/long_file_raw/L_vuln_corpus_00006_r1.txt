1. **第 20–22 行 `Encode`**：入口点是 HTTP 错误写出通道，`w http.ResponseWriter` 是最终 sink 所在；本函数本身只做委托（`enc.Encoder(ctx, ConvertErrors(err), w)`），未直接写响应体。

2. **第 25–52 行 `ConvertErrors`**：错误分发逻辑，无输入拼接，安全。

3. **第 54–62 行 `convertRouteError`**：`e.Error()` 来自路由器内部消息，非用户可控内容，风险低。

4. **第 64–81 行 `convertBasicRequestError`**：关键点在第 73–75 行——`prefixUnsupportedCT + strings.TrimPrefix(e.Reason, prefixInvalidCT)`。`e.Reason` 中包含请求中用户提交的 Content-Type 头原始值（kin-openapi 在解析失败时会把用户传入的 CT 值拼进 Reason）。该字符串未经任何转义/白名单校验，直接进入 `Title` 字段并最终回显给客户端。

5. **第 83–95 行 `convertErrInvalidRequired` / 第 97–109 行 `convertErrInvalidEmptyValue`**：仅输出参数名（来自 OpenAPI spec 定义，非用户输入），安全。

6. **第 111–140 行 `convertParseError`**：第 116–119 行将 `innerErr.Value`（即用户在 path/query 中提交的原始值）通过 `fmt.Sprintf(... %v ...)` 直接嵌入 `Title` 回显给客户端；第 133–136 行同样把 `rootErr.Value` 与 `rootErr.Reason` 拼入响应。这些值完全来自攻击者可控的 URL 参数，且没有任何编码或过滤。

7. **第 142–186 行 `convertSchemaError`**：

   - 第 167–175 行进一步把用户值按逗号拆分后重新拼成建议 URL `'?%s=%s'` 拼进 Detail——这是对用户输入的二次拼接放大，同样未做 HTML/URL 编码。
   - 第 153–154 行 `toJSONPointer(ptr)` 直接用 `/` 连接路径段，若段内含 `/` 或特殊字符会产生畸形 pointer，属轻微问题但非主漏洞。
