# YamlHelper.java 全文安全分析

## 编号分析（逐函数、行号锚定）

**1. 类结构与状态注入（第 27–41 行）**
- 第 30 行：`private static YamlParserProperties yamlParserProperties;` —— 静态字段持有配置。
- 第 33–36 行：构造器通过 Spring `@Autowired` 注入 `YamlParserProperties`。该类本身不是入口点：没有路由、没有参数解析、没有文件/环境读取，仅是工厂工具类。source 只能来自调用方传入的 YAML 字符串，本文件内不存在 source→sink 的直接数据流。

**2. `hasYamlSecurityPropertiesConfigured()`（第 38–43 行）**
- 判断 `yamlParserProperties != null` 且 `maxAliasesForCollections` 或 `codePointLimit` 任一非空。注意是“或”逻辑：只配了别名限制但没配大小限制时，`getLoaderOptions()` 中对应项保持 SnakeYAML 默认值（默认值本身也有合理上限），不构成漏洞。

**3. `newYaml()`（第 45–70 行）—— 关键风险点**
- 第 46 行标注 `@Deprecated`；第 48–51 行打印 WARN 日志并抛出堆栈，明确声明"THIS DOES NOT load yaml safely"。这是**已知的、有意的危险 API**：使用 `Constructor`（第 55 行）而非 `SafeConstructor`。
- 若攻击者可控的 YAML 流经此方法解析，`!!javax.script.ScriptEngineManager` 等 gadget 可触发反序列化 RCE。**但是**：(a) 该方法已被弃用并带运行时告警；(b) 本文件内无任何调用者；(c) 风险取决于上游调用点是否将用户输入喂给它。就本文件而言，这是“暴露的危险原语”，而非可直接利用的漏洞路径。

**4. `newYamlSafeConstructor()`（第 72–90 行）**
- 配置存在时用 `SafeConstructor(opts)`（第 78 行）；未配置时回退到 `new Yaml(new SafeConstructor())`（第 88 行）。两条分支均禁止任意类实例化，防御有效。

**5. `newYamlDumperOptions()`（第 92–110 行）**
- 两分支均使用 `SafeConstructor`（第 98、106 行），仅自定义 DumperOptions（影响输出格式，非解析面）。安全。

**6. `newYamlLoaderOptions()`（第 112–122 行）**
- 配置存在时忽略调用方传入的 `loaderOptions`（第 116–117 行）强制使用全局安全配置；否则透传调用方选项（第 120 行）。透传本身是设计意图，且 LoaderOptions 不含反序列化语义。安全。

**7. `newYamlRepresenter()`（第 124–137 行）**
- **潜在弱点**：第 126–128 行，配置存在时仍使用**调用方传入的任意 `Constructor`**（可能是允许任意类的 `Constructor`）。即全局安全属性无法约束此方法的反序列化行为。但这同样是“信任调用方”的工厂 API，本文件内无调用者、无外部输入直达。

**8. `getLoaderOptions()`（第 139–149 行）**
- 仅设置 alias 数量与 code point 上限，正确缓解 Billion Laughs 与超大输入 DoS。未设置时依赖 SnakeYAML 默认限制。

## 第二入口/替代通道核查
全文无 HTTP 路由、无 `@RequestParam/@PathVariable`、无文件 IO、无环境变量读取、无回调注册。唯一外部影响面是 Spring 注入的配置属性（受信配置源）。所有 `Yaml` 实例均返回给调用方，sink 在文件之外，需结合调用方才能构成完整利用链——本文件范围内证据不足。
