## 编号分析

**入口点枚举（全文）**
1. 第 96–97 行：`gotOpts.hooks.beforeRequest` 注册了 `errorIfInvalidUrl` 和 `errorIfHostnameResolvesToPrivateIp` —— 所有通过 `externalRequest` 发出的请求都会经过；
2. 第 98 行：`hooks.beforeRedirect` 只注册了 `errorIfHostnameResolvesToPrivateIp`，重定向链中每一跳也会做私网检查（覆盖了替代通道：重定向）;
3. 第 99 行：`init` 钩子仅在测试环境禁用重试，无安全影响；
4. 第 92 行：`config.get('env') === 'development'` 时全部校验直接 return —— 开发环境完全绕过，属已知设计取舍；
5. 第 105–108 行：`requestUrl.host === siteUrl.host` 放行本站，host 比较基于字符串，攻击者无法伪造 config 中的 siteUrl，可接受。

**防御有效性逐条验证**
- 第 10–22 行 `normalizeIPv4` 用 WHATWG URL 解析器归一化十进制/八进制/十六进制/整数形式 IP（如 `2130706433`、`0x7f.0.0.1`），第 12 行再经 `net.isIPv4` 确认 —— 有效防住了 IP 文字形式绕过黑名单；
- 第 25–36 行 `normalizeIPv6` 同理处理 IPv6 压缩/展开形式；
- 第 39–90 行 `isPrivateIPv4` 覆盖 10/8、172.16/12、192.168/16、127/8、169.254/16、100.64/10、198.18/15、0/8、240/4，覆盖面完整；未覆盖 192.0.0.0/24、198.51.100/24 等，但风险低；
- 第 93–95 行 `v4DottedMatch` 与第 101–110 行 `v4HexMatch` 处理 `::ffff:` 映射地址，正则锚定 `^::ffff:` 且格式受限，无法被注入绕过；
- 第 128 行 fail-closed：无法识别的格式一律视为私有 —— 正确方向；
- 第 137 行 `dnsPromises.lookup(options.url.hostname)` 解析后用 `isPrivateIp(result.address)` 判断 —— 这里是关键缺陷所在。

**核心漏洞：TOCTOU / DNS Rebinding（CWE-367/CWE-918 组合）**

数据流：
- source：调用方传入的任意 URL（`options.url`，第 137 行取其 hostname）；
- sink：第 138–144 行仅依据**这一次** `dnsPromises.lookup` 的结果决定放行；随后 got 库在第 145 行之后真正发起 TCP 连接时会**再次独立解析 DNS**。

两次解析之间存在时间窗口：攻击者控制权威 DNS，第一次返回公网 IP 通过检查，第二次（连接时）返回 `169.254.169.254` 或内网地址，即可打穿云元数据服务/内网。`beforeRedirect` 钩子同样只做单次 lookup，重定向跳转处存在同样的 rebinding 窗口。这是“先查后连”模式的经典缺陷，黑名单本身写得再全也无法弥补双解析不一致。

**次要问题**
- 第 104–107 行 host 字符串比较：若 siteUrl 为默认端口而请求 URL 显式带相同端口等大小写差异（`new URL` 已归一化 host 小写），基本安全，不构成漏洞；
- 第 92 行开发环境整体旁路：非生产部署下 SSRF 完全开放，属配置依赖风险。
