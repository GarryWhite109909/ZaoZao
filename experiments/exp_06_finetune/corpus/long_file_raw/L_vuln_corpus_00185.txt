**2. 数据流验证**

流 A（命令注入）：第 56 行 `os.Getenv("EDITOR")` → 第 58 行 `openEditor(editorEnv, config.YamlConfigPath)` → 第 84–85 行 `command := program + " " + cmdargs` 字符串拼接 → 第 88/90 行 `exec.Command("sh", "-c", command)` 或 `cmd /c command`。source 是环境变量 EDITOR，sink 是 shell 执行。EDITOR 由用户自己的 shell 环境设置，且该命令仅由本机用户主动运行 `sqls config` 触发——攻击者若能控制 EDITOR 已等价于能执行任意命令。属于设计上的“交给用户编辑器”，非跨信任边界漏洞，但确实是 `sh -c` 拼接模式（CWE-78 形态）。防御：无任何过滤/转义（黑名单也没有），但威胁模型下风险低。

流 B：第 64 行 `--log` 文件路径 → 第 68 行 `os.OpenFile(..., 0660)`，可写任意路径追加日志——本地用户权限内操作，无提权（不 setuid），不算漏洞。

流 C：第 71 行 `--config` → `config.GetConfig`，仅读取解析 YAML，本文件内无 sink。

流 D：stdin/stdout JSON-RPC（第 96–99 行）→ `server.Handle`，处理逻辑在 internal/handler，本文件不可见；基于全文证据无法判定其中存在 sink，不作猜测。
