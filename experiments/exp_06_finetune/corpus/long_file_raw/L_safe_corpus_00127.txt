# 逐点分析

## 入口点枚举
- 唯一入口：`getViewName(HttpServletRequest request)`（第 ~110 行），source 为请求 URI 路径，经 `ServletRequestPathUtils.getCachedPathValue(request)` 取得。
- 其余为 setter（prefix/suffix/separator 等），属应用配置而非用户输入。

## 数据流分析
1. **source**：`getCachedPathValue(request)` 取得 URL 解码后的 lookupPath。
2. **sink**：返回值作为 view name 交给 ViewResolver 解析。若视图名以 `redirect:` / `forward:` 开头，`UrlBasedViewResolver` 会执行重定向或转发 —— 这是本类历史上 CVE-2024-38816 类路径注入的关切点。

## 防御验证
- 第 ~114-120 行：对最终 viewName 显式检查 `startsWith(REDIRECT_URL_PREFIX)` 和 `startsWith(FORWARD_URL_PREFIX)`，命中即抛 400 `ResponseStatusException`。这是前缀黑名单，但针对的是固定常量前缀且检查发生在拼接 prefix 之后、返回之前，覆盖了完整结果字符串；由于 `redirect:`/`forward:` 是精确字面量，无编码变体可绕过 startsWith 检查。
- `transformPath` 仅做斜杠裁剪与扩展名剥离，不引入新 sink。

## 第二通道
- `separator` 替换只影响 `/`→自定义分隔符，不会产生 `redirect:` 字面量（除非管理员恶意配置 separator 含该前缀，属配置信任问题）。
- 若应用自行配置非默认 prefix/suffix 使 viewName 以 `redirect:` 开头，同样被上述检查拦截（检查在拼接后进行）。

## 结论
防御有效，未发现可利用漏洞。
