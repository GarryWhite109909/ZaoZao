## 编号分析

**1. 入口点枚举（全文通读）**
- 第 22–57 行 `Metadata()`：无外部输入参数，数据来自集群内 API（route、oauth server 元数据）。
- 第 59–81 行 `getOAuthAuthorizationServer()`：请求固定路径 `.well-known/oauth-authorization-server`，无用户输入。
- 第 83–98 行 `GetUserInfo(token)`：token 为 source（用户会话 token），sink 是第 89 行 `request("GET", "apis/user.openshift.io/v1/users/~", &token)`——token 仅作为 Authorization 头传入，未拼入 URL。
- 第 100–109 行 `getKialiNamespace()`：读取固定路径的 serviceaccount 文件，非用户可控。
- 第 111–146 行 `getKialiRoutePath()`：host 来自集群内 route 对象，需集群权限才能篡改，且仅用于拼接 redirect_uri 并经 `url.QueryEscape` 转义。
- 第 148–163 行 `Logout(token)`：token 为 source，第 156 行拼入 URL 路径。
- 第 165–211 行 `request()`：公共 sink；URL 前缀固定为 `https://kubernetes.default.svc/`（第 18 行），TLS 校验使用集群 CA（第 169–180 行），未禁用证书校验。

**2. 数据流验证**
- `Metadata` 流：namespace/route host → Sprintf → 返回给前端。redirect_uri 经 QueryEscape，host 来自受 RBAC 保护的 route 资源，攻击者需先攻陷集群，不构成独立漏洞。
- `GetUserInfo` 流：token 仅进 Header，不进 URL，无注入面。
- `Logout` 流：token 拼入 `apis/oauth.openshift.io/v1/oauthaccesstokens/%v`。理论上含 `/` 的 token 可造成路径变化，但该 token 本身就是调用者自己的 OAuth access token，删除自身 token 是预期功能；且该值来自 OpenShift 签发的合法 token 格式，正常流程不含路径穿越字符，实际利用需要伪造 token 值，而前端只传回服务端下发的真实 token。
- `request` 流：所有 URL 均拼接在固定的 `serverPrefix` 之后，目标主机不可控，不存在 SSRF 到任意主机的通道；TLS 使用集群 CA 校验，无中间人风险。

**3. 第二入口与替代通道**：文件内无 HTTP handler、无环境变量读取、无回调注册；唯一外部输入是两个函数参数 token，均已分析。错误信息中回显 body（第 205 行）仅面向已认证的管理端日志，敏感信息为用户自己的 token 操作结果。

**4. 结论**：各 source→sink 流均有固定前缀、Header 传递或转义约束，且依赖集群 RBAC 保护的数据源，基于全文证据未发现可利用的安全漏洞。
