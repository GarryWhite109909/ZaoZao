# 编号分析

1. **第 24-31 行：硬编码默认密钥**。`DEFAULT_SECRET_KEY` 是写死在源码中的 HMAC 密钥，且该文件属于开源项目（sureness），密钥对任何人公开可见。

2. **第 38-41 行：静态初始化块**。默认情况下 `secretKey` 直接由该公开常量派生（`Keys.hmacShaKeyFor`），即所有未显式调用 `setDefaultSecretKey` 的部署都使用公开已知的签名密钥。

3. **第 226-231 行：`parseJwt`**。使用共享的静态 `secretKey` 验签并解析 JWT。source 为外部传入的 token 字符串；由于验签密钥可被攻击者推算/已知，攻击者可自行伪造含任意 roles/perms claim 的 JWT 通过验签——这是典型的 CWE-798（硬编码凭据）→ 认证绕过链。

4. **第 235-240 行：`setDefaultSecretKey`**。允许运行时替换密钥，但：
   - 无任何强度校验、来源校验；
   - 写入的是**非 volatile 非 final 的 static 字段**，存在并发可见性问题；
   - 若部署方从配置/环境读取弱值传入，无最低长度防护（`hmacShaKeyFor` 仅在过短时抛异常）。

5. **第 194-210 行：`isNotJsonWebToken`**。仅做格式正则判断（BASE64_PATTERN），注释也明确“no verification”，本身不是安全防御，仅是预筛，不构成有效防线。

6. **第 213-222 行：`parseJwt` 异常面**。依赖 jjwt 库自身校验过期时间等，但签名密钥泄露使这些校验失去意义。

7. **第 44-190 行：各 `issueJwt` 重载**。参数直接进入 claims，无注入风险点（JWT claims 本身结构化）；`issueJwtAll` 第 178 行 `customClaimMap.forEach(jwtBuilder::claim)` 若调用方传入不可信 map 可覆盖标准 claim（如 exp），但这取决于上层调用方，本文件内不构成独立漏洞主链。

8. **第二入口确认**：除硬编码密钥外，`setDefaultSecretKey` 构成替代通道，但其风险为弱配置而非直接漏洞；主漏洞链仍是“公开默认密钥 → parseJwt 验签被伪造 token 绕过”。

9. **结论**：核心漏洞为 CWE-798 硬编码加密密钥，导致 JWT 伪造 / 权限提升（CWE-287 相关），风险等级高。
