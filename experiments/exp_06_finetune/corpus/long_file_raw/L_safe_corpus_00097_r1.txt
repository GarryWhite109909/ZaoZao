**3. source→sink 数据流逐一验证**

- **流 A：`req.url` → `source` → `buildURL(source, dest)` → 上游请求 url（第 56–70 行）**
  用户可控的 `req.url` 路径被拼入上游 URL。防御有效性检查：`buildURL` 来自 `./lib/utils`（本文件外），其语义是基于 `new URL(source, dest)` 解析——相对路径无法逃逸 host（`new URL('//evil.com/x', 'http://base')` 会换 host，但这要求 source 以 `//` 开头；而 Fastify 路由层收到的 `req.url` 以 `/path` 形式存在且路由匹配已约束前缀；此外若开发者显式传 source 也是自己控制）。在本文件范围内没有把原始 query/fragment 直接拼进 sink 的字符串拼接；query 由第 71 行 `getQueryString` 单独处理并交给请求库编码。无有效绕过证据。

- **流 B：缓存键混淆（第 63–68 行）**
  `cacheKey = dest + source` 为纯字符串拼接。理论上 `(dest='http://a/b', source='/c')` 与 `(dest='http://a/', source='b/c')` 键不同但 URL 相同——这只是冗余缓存项，不会导致取错对象后发往错误主机，因为取出的仍是 `buildURL` 的正确产物。反向冲突（不同 URL 得到相同 key 并复用错误 url 对象）需要 `dest+source` 完全相等而解析结果不同，而 `dest` 与 `source` 在同一部署中分别由固定配置和固定路由决定，本文件内无可达的攻击者控制点使两个不同 (dest, source) 组合产生相同键。故判为理论瑕疵而非可利用漏洞。

- **流 C：headers 复制（第 72–74 行）**
