## 编号分析

1. **第 30–45 行（插件初始化）**：`opts` 全部来自服务端配置，非用户输入，无外部 source。

2. **第 47 行起 `fastify.decorateReply('from', ...)`**：这是唯一入口点。`source` 参数由路由开发者传入；若未传（第 55–58 行），则取自 `req.url` 并去掉查询串——**用户可控的 HTTP 请求路径成为 source**。

3. **第 61–67 行（URL 构建与缓存）**：
   - 无缓存时 `buildURL(source, dest)`，`dest` 来自 `getUpstream`（默认为配置的 base）。
   - 有缓存时 `cacheKey = dest + source`，直接字符串拼接后查 LruMap。**关键缺陷**：不同 `(dest, source)` 组合可产生相同拼接串，例如租户 A 的 `dest='http://a.com/'`、`source='xhttp://b.com/'` 与租户 B 的 `dest='http://a.com/x'`、`source='http://b.com/'` 拼接结果完全一致。先到达者的解析结果会被缓存并供后者复用，导致**请求被转发到攻击者指定的上游（SSRF / 上游混淆 / 缓存投毒）**。黑名单/正则不涉及；LruMap 容量限制不能阻止碰撞。此为真实已知问题类别（fastify/reply-from 历史上的 URL 缓存混淆）。
   - 即使无多租户，`source` 未做 scheme/host 校验，若开发者把用户输入直接作为 `reply.from(source)` 的参数，也会形成开放代理——但插件契约允许显式指定路径，主责任在使用方；而缓存键碰撞在库内部即可触发。

4. **第 69–71 行（headers 处理）**：`filterPseudoHeaders` 过滤 h2 伪头；`headers.host = url.host` 强制覆盖 host，防止 host 头注入。防御有效。

5. **第 72–78 行 `getQueryString`**：`opts.queryString` 为服务端配置；否则透传 `url.search` 或 `reqUrl` 的查询串。查询串原样转发属于代理语义，且 `request.js` 内部会用其构建 URL，无额外 sink 注入点（header 注入已被 Node 层校验拦截）。

6. **第 80–108 行（body 处理）**：`opts.body` 为开发者传入；`this.request.body` 经 content-type 判断后 JSON 编码或透传，`content-length` 用 `Buffer.byteLength` 重算，无 CRLF 注入面（Node 会拒绝非法 header 值）。

7. **第 111–117 行**：GET/HEAD 带 body 直接抛错，防逻辑滥用。

8. **第 128–160 行（重试逻辑）**：`retryDelay` 默认基于随机数与 `retry-after` 头（上游响应，非用户直接控制）；`maxRetriesOn503` 上限 10，无无限循环风险。`setTimeout(run, after)` 中 `after` 若为上游返回的恶意大值仅造成延迟，不构成可利用漏洞。

9. **第 162–200 行（响应回调）**：错误分类映射到标准状态码；`copyHeaders(rewriteHeaders(...))` 转发上游头——上游响应头中的注入（如 set-cookie）属代理预期行为；`stripHttp1ConnectionHeaders` 处理了 h2 场景的连接类头。`this.send(res.stream)` 流式回传，无路径/命令 sink。

10. **第 205–230 行（辅助函数）**：`getQueryString`、no-op 函数、`createRequestRetry` 均无文件/命令/eval 类 sink。

11. **第二入口检查**：除 `reply.from()` 外无其他路由或回调接收外部数据；`onResponse`/`onError` 等回调由使用方提供，不在本文件内引入新 sink。

**结论**：全文唯一实质缺陷是第 62–64 行以字符串拼接 `dest + source` 作为缓存键导致的 URL 缓存混淆，可使请求被路由到错误（攻击者可控）的上游，构成 SSRF/上游混淆漏洞。
