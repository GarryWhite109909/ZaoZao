# 逐函数、逐行安全分析

## 一、文件结构总览与入口点枚举

本文件是 degit CLI 的命令行入口（bin），全文共包含以下主要代码块：

1. **模块导入区（第 1–9 行）**：`fs`、`path`、`chalk`、`mri`、`tiny-glob/sync.js`、`fuzzysearch`、`enquirer`、本地 `./index.js` 的 `degit`、`./utils.js` 的 `base` 与 `tryRequire`。
2. **`main(argv)` 函数（第 11–96 行）**：CLI 主入口，含三个分支——帮助分支、交互式选择分支、直接运行分支。
3. **`run(src, dest, args)` 函数（第 98–112 行）**：包装 degit 实例并执行 clone。
4. **顶层自动执行块（第 114–119 行）**：非 VITEST 环境下调用 `main(process.argv)`。

**入口点清单**：
- E1：进程命令行参数 `process.argv`（第 118 行传入，第 13 行 `mri(argv.slice(2), ...)` 解析）；
- E2：环境变量 `process.env.VITEST`（第 115 行，仅作开关判断，不进入数据流）；
- E3：磁盘文件系统读取——`help.md`（第 19 行）、`base` 目录下的 `access.json`（第 27–28 行）与 `map.json`（第 47 行）；
- E4：交互式用户输入 `enquirer.prompt` 返回值（第 52–70 行的 `options.src` / `options.dest` / `options.cache`，以及第 74–77 行的 `force`）；
- E5：子进程退出码 `process.exit(1)`（第 111、119 行）。

## 二、逐条 source→sink 数据流验证

### 数据流 D1：argv → mri → src/dest → run() → degit().clone(dest)

- **source**：第 13 行 `mri(argv.slice(2))` 解析出的位置参数；第 14 行解构 `const [src, dest = '.'] = args._;`
- **传播路径**：第 94 行 `run(src, dest, args)` → 第 100 行 `const d = degit(src, args)` → 第 108 行 `d.clone(dest)`。
- **sink 分析**：`clone(dest)` 内部会进行文件写入。dest 是完全由攻击者（即本机用户自己）控制的路径。
- **防御验证**：全文对 `dest` 没有任何校验、规范化或白名单——但这正是 CLI 工具的设计语义：degit 本来就是“克隆到指定目录”的工具，`--force` 覆盖目录也是文档化功能（第 73–86 行明确询问“Overwrite existing files?”）。使用者对本机参数拥有完全控制权，属于**预期功能而非漏洞**（等同于 `cp -r` 可写任意路径）。此外真正的文件操作发生在 `./index.js` 中，本文件未直接以 argv 值构造 fs 调用。
- **结论**：不构成漏洞。

### 数据流 D2：help.md 文件内容 → 正则替换 → stdout

- **source**：第 19 行 `fs.readFileSync(path.join(__dirname, '..', 'help.md'), 'utf8')`。
- **sink**：第 26 行 `process.stdout.write`。
- **防御验证**：三个 `replaceAll`（第 20–25 行）仅做 chalk 颜色包装，正则 `/^(\s*)#+ (.+)/gm`、`/_([^_]+)_/g`、`` /`([^`]+)`/g `` 均无回溯灾难风险（字符类简单、量词受限）。数据源是随包分发的静态文件，不可被外部注入。
- **结论**：安全。

### 数据流 D3：base 目录下 access.json / map.json → glob 枚举 → choices → enquirer → run()

- **source**：第 27 行 `fs.readFileSync(`${base}/${file}`, 'utf8')` 与第 48 行 `tryRequire(`${base}/${file}`)`；文件名来自第 26 行和第 46 行 `glob('**/...')` 在 `base` 目录内的扫描结果。
- **中间处理**：第 29 行 `JSON.parse(json)` —— 若 access.json 内容被篡改可抛异常，但异常沿第 117–119 行的 `.catch` 进入 `console.error(error)` 后退出，无进一步危害。第 30–35 行将 `[ref, timestamp]` 写入 Map，仅用于排序比较（第 56–58 行 `new Date(timestamp).getTime()`），不进入任何 sink。
- **sink**：choices 最终作为 `options.src`（第 66 行 prompt 选择结果）流入第 91 行 `run(options.src, ...)` → `degit(src)`。
- **防御/信任边界分析**：`base` 是 degit 缓存目录（通常为 `~/.degit` 或按 host/user/repo 分层）。能写入该目录的前提是已在本机拥有写权限——此时攻击者已可做任意事，属本地信任域。且这些 JSON 本身就是 degit 自身缓存机制的产物。黑名单/过滤缺失在此不适用：这是受信缓存数据，非跨信任边界输入。
- **第二入口检查**：即使 map.json 中混入恶意 ref 字符串，其流向仍是 `degit()` 解析器（index.js），最终表现为尝试从某 git host 拉取仓库——危害等价于用户手动执行 `degit evil/repo`，即用户自主行为。
- **结论**：不构成可利用漏洞。

### 数据流 D4：enquirer 交互输入 → options.dest → fs.existsSync / readdirSync / run()

- **source**：第 68 行 prompt 的 `dest` 输入。
- **sink**：第 88 行 `fs.existsSync(options.dest)`、第 89 行 `fs.readdirSync(options.dest)`、第 92 行经 `run()` 到 `d.clone(dest)`。
- **防御验证**：无路径校验，但同 D1——交互式用户为自己选择目标目录，属预期功能。`existsSync`/`readdirSync` 为只读探测，无写入原语。
- **TOCTOU 检查**：第 88–89 行检查空目录与第 92 行实际 clone 之间存在竞态窗口，但结合 `force: true`（第 93 行）语义，覆盖是用户明示同意的，竞态不改变授权状态。
- **结论**：不构成漏洞。

### 数据流 D5：event.message / error.message → console.error

- **source**：第 102、105、110 行的 degit 事件与错误消息。
- **sink**：stderr 输出。`.replace('options.', '--')` 仅做展示美化。终端转义序列注入理论上取决于上游 message 是否含 ANSI 序列，但消息由 degit 库内部模板生成，且输出到 stderr 不构成持久性危害。
- **结论**：安全。

### 数据流 D6：process.env.VITEST（第 115 行）

仅作布尔判断决定是否自执行，不流入任何 sink。非漏洞。

### 替代通道复查

- 无 HTTP/network 监听入口；无子进程 spawn 于本文件；无 eval/Function；无非字面量 require（tryRequire 仅作用于 base 下扫描到的 map.json，见 D3）。
- `glob('**/access.json', { cwd: base })` 若 base 下存在符号链接可能逃逸 cwd，但同样要求本地写权限，超出威胁模型。

## 三、总体结论

所有 source→sink 流要么终止于本地信任域内的预期 CLI 功能（D1/D4），要么数据源为包内静态资源或自身缓存（D2/D3），要么仅为日志输出（D5）。未发现跨信任边界的注入、任意文件读写、RCE 或反序列化漏洞。
