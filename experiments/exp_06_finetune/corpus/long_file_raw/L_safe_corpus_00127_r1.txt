# DefaultRequestToViewNameTranslator 安全分析

## 一、文件结构总览

本文件为 Spring Framework 中 `DefaultRequestToViewNameTranslator` 的完整实现，共约 160 行。类实现 `RequestToViewNameTranslator` 接口，职责是将请求 URI 转换为视图名。全文包含以下成员，逐一分析：

1. 常量与字段（第 55-63 行）：`SLASH`、`prefix`、`suffix`、`separator`、`stripLeadingSlash`、`stripTrailingSlash`、`stripExtension`
2. `setPrefix(String)`（第 70-72 行）
3. `setSuffix(String)`（第 79-81 行）
4. `setSeparator(String)`（第 88-90 行）
5. `setStripLeadingSlash(boolean)`（第 97-99 行）
6. `setStripTrailingSlash(boolean)`（第 106-108 行）
7. `setStripExtension(boolean)`（第 115-117 行）
8. `getViewName(HttpServletRequest)`（第 128-141 行）—— 核心入口
9. `transformPath(String)`（第 149-165 行）—— 内部转换逻辑

## 二、入口点枚举

**入口 1：`getViewName(HttpServletRequest request)`（第 129 行）**
- Source：`request` 参数。数据来源为 `ServletRequestPathUtils.getCachedPathValue(request)`（第 130 行），即 DispatcherServlet 在请求处理早期缓存到 request attribute 的解析后路径。攻击者可通过构造任意 URL 路径控制该值——这是唯一的外部输入 source。
- 该方法由 DispatcherServlet 在控制器未返回视图名时回调（框架内部调用链），非直接 HTTP 映射端点，但路径内容完全受客户端 URL 控制。

**入口 2-7：七个 setter 方法（第 70-117 行）**
- 这些是 Bean 配置属性注入点，仅在应用上下文装配时由开发者/配置调用，非运行时用户可控通道。除非应用将用户输入绑定到该 Bean 属性（非典型用法），否则不构成外部 source。

**第二入口/替代通道检查：**
- 无文件读取、无环境变量、无回调注册、无反序列化点。
- `transformPath` 为 protected，可被子类覆盖，但默认实现内无额外输入源。
- 唯一替代通道即同一 request 的 cached path attribute；若上游未解析，`getCachedPathValue` 会抛异常而非回退到原始 URI，避免了对未规范化路径的意外信任。

## 三、Source→Sink 数据流逐条验证

**流 1：cached path → transformPath → viewName 返回值**

- 第 130 行取得 path（source）。
- 第 131 行拼接：`prefix + transformPath(path) + suffix`。
- `transformPath`（第 149-165 行）仅做：去首斜杠（151-153）、去尾斜杠（154-156）、去扩展名（157-159）、替换分隔符（160-162）。这些均为字符串变换，无过滤语义，但也不引入新 sink。
- Sink 分析：返回的 viewName 的消费方是 ViewResolver 链。危险 sink 是当 viewName 以 `redirect:` 或 `forward:` 开头时，`UrlBasedViewResolver` 会执行重定向或服务端转发（开放重定向 / SSRF 类风险）。

**防御验证（关键）：**
- 第 132-135 行：检查 `viewName.startsWith(REDIRECT_URL_PREFIX)`，命中则抛 400。
- 第 136-139 行：同样检查 `FORWARD_URL_PREFIX`。
- 绕过可能性评估：
  - 检查在 prefix/suffix 拼接**之后**进行。若配置了 `prefix = "redirect:"`，则任何路径都会以 redirect: 开头并被拒绝——这是拒绝服务式误配，不是绕过。
  - 大小写变体（如 `Redirect:`）：Spring 的 UrlBasedViewResolver 本身使用大小写敏感的 startsWith 匹配，且此处防御与 resolver 语义一致；`redirect:` 协议前缀由 resolver 以相同常量匹配，故不存在“此处拦截失败但 resolver 接受”的不对称窗口。
  - 编码绕过：path 来自已解码并规范化的 cached RequestPath，`%72edirect:` 已被 servlet 容器解码为 `redirect:`，会被第 133 行捕获；无法通过双重编码注入字面冒号前缀逃逸 startsWith 检查。
  - 空字节/换行截断：startsWith 检查针对前缀本身，插入字符只会使前缀不匹配，同时也不会使下游 resolver 匹配前缀，无不对称性。
- 结论：防御为精确的前缀等价匹配（非黑名单正则），与 sink 消费方的判定条件一致，视为有效。

**流 2：viewName → 视图解析 → JSP/模板渲染**

- 若 viewName 不带 redirect/forward 前缀，ViewResolver 将其映射为应用内视图资源（如 `/WEB-INF/views/<name>.jsp`）。理论上含 `../` 的路径可能引发视图路径穿越，但：
  - Servlet 容器与 Spring 的视图资源解析对 `..` 有规范化处理；
  - 更重要的是，此类风险属于 ViewResolver 配置层面问题，且历史 CVE（如 CVE-2018-1270 相关讨论中的 view name 注入）已在框架层通过上述 redirect/forward 拒绝机制缓解；
  - 本文件自身不含文件系统访问代码，sink 不在本文件内，不能基于本文件断言漏洞存在。

**流 3：setter 注入的 prefix/suffix/separator → 字符串拼接**

- 第 131、162 行参与拼接，但来源为受信配置，非用户输入，不构成不可信数据流。

## 四、其他安全考量

- 第 134、138 行错误消息中回显了原始 path（`"Rejected path '" + path + "'"`），存在反射型内容回显的可能，但其作为 ResponseStatusException message 输出，Spring 默认不会将异常 message 直接写入响应体（需显式配置），且 path 来自 URL 而非 header，风险极低，不构成独立漏洞。
- 无 SQL、命令执行、反序列化、XML 解析等 sink。

## 五、结论

全文唯一的用户可控 source 是请求路径，其流向的危险 sink（redirect:/forward: 前缀触发重定向/转发）已被第 132-139 行的精确前缀拒绝机制有效防护，且该防护与下游 UrlBasedViewResolver 的判定条件一致，无可利用的不对称窗口。其余 setter 入口为受信配置通道。基于全文证据，未发现可利用漏洞。
