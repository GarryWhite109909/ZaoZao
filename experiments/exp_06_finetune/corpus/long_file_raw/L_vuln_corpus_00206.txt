## 编号分析

**入口点枚举（全文通读）**
1. **第 76 行**：`getRequest().getAttributes()` —— restlet 请求属性，全部并入 data 模型；
2. **第 77 行**：`getQuery().getValuesMap()` —— URL 查询参数整体并入 data 模型（未做任何编码）；
3. **第 78–83 行**：从 `getResourceRef()` 取 `path` 与 `query`，拼接为 `target`；

**逐条 source→sink 验证**
- `display_name`/`display_description`（第 85–86 行）：经 `ESAPI.encodeForHTML` 编码，有效防御。
- `display_scopes`/`display_claims`：所有值均经私有 `encodeForHTML`（第 111–114 行）编码，有效。
- **`target`（第 84 行）**：source 为第 80–82 行的请求 path+query，直接放入模板数据模型，无任何编码。若模板以 HTML 输出（该数据模型用于 FreeMarker 授权同意页），查询串中注入 `<script>` 等即形成反射型 XSS。路径+查询拼接本身也构成开放重定向/内容注入风险面。
- **`user_code`（第 90 行）**：source 是第 90 行的请求参数，攻击者可通过构造设备授权链接完全控制其值，未经编码直接进入渲染模型 → 反射型 XSS（对应 OpenAM 历史 CVE 类似模式）。
- **`user_name`（第 88 行）**：未编码；虽然通常来自会话，但在某些身份源下可含恶意字符，属次级风险。
- 第 77 行把整个查询参数 map 原样合并进模型，是第二入口/替代通道：任何模板引用的同名键都可被 URL 参数覆盖污染。
