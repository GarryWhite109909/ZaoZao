# 全文逐函数安全分析

## 0. 文件结构与入口点枚举（通读全文后的清单）

本文件是 Gogs 项目 LFS 模块的本地存储后端，全文共约 130 行，包含以下可被外部输入触达的函数与数据面：

- 第 24–44 行：`Storager` 接口定义（`Upload` / `Download` 两个对外能力）。
- 第 46–53 行：`Storage` 类型与常量 `StorageLocal`。
- 第 57–63 行：`LocalStorage` 结构体，含外部可配置字段 `Root`、`TempDir`。
- 第 65–67 行：`Storage()` 方法，纯常量返回。
- 第 69–74 行：`storagePath(oid)` —— **路径拼接核心**。
- 第 76–124 行：`Upload(oid, rc)` —— 上传入口。
- 第 126–144 行：`Download(oid, w)` —— 下载入口。

外部 source 有两类：(a) HTTP LFS batch API 传入的 `oid` 字符串（上游调用方将用户 JSON 中的 oid 转为 `OID` 类型传入）；(b) 上传请求体字节流。以下逐一验证。

## 1. `storagePath`（第 69–74 行）—— 唯一的路径构造 sink 前置点

```go
if len(oid) < 2 { return "" }
return filepath.Join(s.Root, string(oid[0]), string(oid[1]), string(oid))
```

防御分析：
- 仅检查长度 ≥2，**未做字符白名单校验**（合法 OID 应为 64 位十六进制）。
- `filepath.Join` 会做路径清洗（Clean），这意味着 `..` 序列不会被拒绝，而是被“规范化”——若 `oid` 以 `../` 开头，拼接结果会逃逸出 `s.Root`。
- 例如 `oid = "../../etc/cron.d/pwn"`：Join 结果为 `Root/././../../etc/cron.d/pwn` → 清洗后为 `<Root 上两级>/etc/cron.d/pwn`，成功穿越。
- 结论：`storagePath` 本身不构成有效防御，安全性完全依赖调用方是否先调用 `ValidOID`。

## 2. `Upload`（第 76–124 行）—— 防御完整的数据流

数据流：source=第 77 行参数 `oid` 与第 78 行 `rc`（请求体）→ sink=第 118 行 `os.Rename(tmpPath, fpath)`。

逐段验证：
- 第 79–81 行：`if !ValidOID(oid) { return ErrInvalidOID }` —— 在进入任何文件操作**之前**校验 OID。Gogs 的 `ValidOID` 要求恰好 64 个 `[0-9a-f]` 字符，黑名单/宽松正则不适用问题，这是严格白名单，视为**有效防御**。因此第 82 行 `storagePath(oid)` 的输出受控。
- 第 88–92 行：已存在文件直接短路，无写操作。
- 第 94–104 行：写入 `TempDir` 下由 `os.CreateTemp` 生成的随机名临时文件——文件名不受用户控制，无注入面。
- 第 106–113 行：`sha256` 校验（第 112–114 行），内容哈希必须等于 OID 才继续，防止用 OID A 写入任意内容。
- 第 116–119 行：`os.Rename` 到最终路径；即使并发竞态，因哈希校验在前，最终路径内容仍与 OID 一致。`os.IsExist` 容忍并发重复发布。
- 残余风险：`TempDir` 若与 `Root` 同盘则 Rename 原子；跨盘会退化为 copy+delete，但仍是安全失败而非漏洞。`os.ModePerm`(0777) 权限略宽，属低危配置问题，非可利用漏洞。

结论：Upload 数据流防御有效，无可利用路径。

## 3. `Download`（第 126–144 行）—— **缺失 OID 校验的路径遍历**

数据流：source=第 127 行参数 `oid`（来自 LFS download API 的用户可控字符串）→ 第 128 行 `storagePath(oid)` → 第 129 行 `osx.IsFile(fpath)` 探测 → 第 133 行 `os.Open(fpath)` → 第 139 行 `io.Copy(w, r)` 回显给客户端。

防御验证：
- **对比 Upload 第 79 行，Download 全程没有调用 `ValidOID`**。这是同一接口两个实现方法之间的防御不对称，属于典型的第二入口遗漏。
- 第 128 行 `storagePath` 如第 1 节所证，对 `../` 无抵抗。
- 攻击链：攻击者向 LFS batch API 提交 `operation=download`、`oid="../../home/user/.ssh/id_rsa"`（或任意 ≥2 字符的相对穿越串），服务端拼出 `Root/././../../home/user/.ssh/id_rsa`，`IsFile` 通过后 `os.Open` 打开并以响应体回传——**任意文件读取**。
- 替代通道核查：
  - 绝对路径注入（如 `/etc/passwd`）：`filepath.Join` 中绝对路径元素会使前面元素失效？注意此处 `string(oid)` 是第三个变参，Go 的 Join 会把整个结果 Clean 但不会因中间元素以 `/` 开头而丢弃前缀——实际测试中 `filepath.Join("/root", ".", "e", "/etc/passwd")` 得到 `/root/e/etc/passwd`，不逃逸；但 `oid="../secret"` 这类相对穿越始终有效，故漏洞成立不依赖此边界。
  - 空字节截断：Go 的 `os.Open` 拒绝含 NUL 的路径，不可用。
  - Windows 盘符/反斜杠：`..\..\` 在 Windows 构建下同样穿越；Linux 下 `\` 为普通字符，不影响主结论。
  - 第二入口确认：除 HTTP download API 外，若内部清理任务或复制逻辑复用 `Download`，同样继承该缺陷。
- 影响范围：以 gogs 进程权限读取服务器上任意可读文件，包括 `internal/conf` 中的数据库密码、SECRET KEY、`~/.gitconfig` 等，风险高。

## 4. 其余函数核查

- 第 65–67 行 `Storage()`：常量返回，无输入，无风险。
- 第 46–53 行常量定义：无风险。
- 第 57–63 行结构体：`Root`/`TempDir` 来自服务端配置，非用户 source（除非管理员误配，超出本代码责任）。

## 5. 最终判定

存在一个高危漏洞：`Download` 未校验 `oid` 即拼路径并打开文件，构成路径遍历导致任意文件读取（CWE-22 / CWE-23）。修复方式是在 `Download` 入口（第 127 行之后）加入与 `Upload` 第 79 行相同的 `ValidOID` 校验，并在 `storagePath` 内再做一次前缀 containment 断言作为纵深防御。
