# Moonraker LDAP 组件安全分析

## 一、文件结构总览

本文件为 Moonraker（3D 打印机服务端）的 LDAP 认证组件，全文约 110 行，包含以下主要函数/入口点：

1. `__init__`（第 22–60 行）：配置加载入口
2. `authenticate_ldap_user`（第 62–67 行）：异步认证入口
3. `_perform_ldap_auth`（第 69–104 行）：同步 LDAP 认证核心逻辑
4. `_validate_group`（第 106–118 行）：组成员校验
5. `load_component`（第 121–122 行）：组件工厂入口

## 二、逐函数入口点与数据流分析

### 1. `__init__`（第 22–60 行）——配置入口

**Source**：`config.gettemplate(...)` / `config.get(...)`，即 moonraker.conf 配置文件。配置文件由管理员本地控制，非远程用户可控。

- 第 24 行：`ldap_host` 来自配置。
- 第 27–28 行：`base_dn_template.render()` —— 模板渲染，模板可含 `{secrets...}` 等占位符，但内容仍由管理员写入配置文件。
- 第 30–33 行：`group_dn` 同上。
- 第 37–46 行：`bind_dn` / `bind_password` 同上。
- 第 48–56 行：`user_filter` 来自配置，且第 53–55 行强制要求包含 `USERNAME` token。

**Sink 分析**：这些值后续流入 `ldap3.Server()`（第 72 行）、`ldap3.Connection()`（第 84、96 行）、`conn.search(self.base_dn, ldfilt, ...)`（第 85 行）。由于 source 是管理员控制的本地配置文件而非 HTTP 请求参数，不构成注入型漏洞的攻击面。若管理员在配置中写恶意 filter 属于自伤行为，不算漏洞。

### 2. `authenticate_ldap_user`（第 62–67 行）——异步入口

- Source：参数 `username: str, password: str`（第 62 行），由上游认证框架（Moonraker 的登录 API `/access/login` 的 JSON body）传入，是**真正的外部用户可控输入**。
- 第 64–66 行：通过 `eventloop.run_in_thread` 将任务派发到线程池执行 `_perform_ldap_auth`。
- 第 63 行：`async with self.lock` 保证并发下串行执行，防止 ldap3 连接对象跨线程竞争——这是正确的防御。

数据流：HTTP 登录请求 → username/password → run_in_thread → `_perform_ldap_auth(username, password)`。此路径无任何过滤/转换，直接透传，需重点审查下游 sink。

### 3. `_perform_ldap_auth`（第 69–104 行）——核心 sink 所在

**Sink 1：LDAP filter 注入（第 78–82 行）**

```python
escaped_user = escape_filter_chars(username)          # 第 79 行
ldfilt = f"(&(objectClass=Person)({attr_name}={escaped_user}))"  # 第 80 行
if self.user_filter:
    ldfilt = self.user_filter.replace("USERNAME", escaped_user)  # 第 82 行
```

- 第 79 行使用 `ldap3.utils.conv.escape_filter_chars` 对用户名做 RFC 4515 转义，可防 `*)(uid=*))(|uid=*` 类注入。这是**库级正规转义函数**，不是黑名单或自写正则，属于有效防御。
- 第 82 行：当配置了自定义 `user_filter` 时，仅将转义后的 `escaped_user` 替换进模板。注意：替换的是已转义值，因此即使 filter 中有多个 `USERNAME` 占位符也全部被同一转义值填充，注入被阻断。唯一残留风险是管理员在 filter 中写了其他 LDAP 特殊字符（如未转义的 `*`），但那是配置作者自己的语义意图，且用户输入部分已被转义，无法借用户输入逃逸。
- 结论：filter 注入路径 **source(第62行 username) → escape(第79行) → sink(第85行 conn.search)** 防御有效。

**Sink 2：DN 注入 / 凭据传递（第 88、95–97 行）**

```python
rebind_success = conn.rebind(user.entry_dn, password)   # 第 88 行
...
conn_args["user"] = user.entry_dn                        # 第 96 行
conn_args["password"] = password                         # 第 97 行
```

- `user.entry_dn` 来自服务器返回的搜索结果条目（第 86 行），并非用户输入拼接而成；即使用户名中含特殊字符，entry_dn 是由目录服务器解析后的规范 DN，作为 rebind 的 DN 参数使用时 ldap3 会按 DN 处理，不存在 filter 上下文的注入面。
- `password` 作为绑定凭据传给 `Connection`/`rebind`，属预期用途，非 sink 漏洞。

**Sink 3：错误信息回显（第 90 行与第 103 行对比）**

- 第 90 行：`f"LDAP User '{username}' Not Found"` —— 用户名被拼入错误消息并可能经 HTTP 返回给客户端。这构成**用户枚举**信息泄露：攻击者可通过响应差异区分“用户不存在”与“密码错误”（第 103 行统一返回 `Invalid LDAP Username or Password`）。严格来说这是一个轻微的信息泄露问题，但在 LDAP 认证实现中极为常见，且该消息仅在 search 无结果时抛出，泄露程度有限。按题目要求“黑名单/正则视为可绕过”的标准衡量，此处不属于可利用的注入类漏洞，风险等级低。
- 第 101–102 行：`except LDAPExceptionError` 捕获后统一报错，避免异常细节外泄——防御良好。
- 注意第 100–103 行的控制流：rebind 成功但组校验失败时会落入 `else` 分支返回通用错误，逻辑正确。

**潜在逻辑缺陷核查（第 92–98 行）**：rebind 失败后新建连接验证凭据，若新连接建立成功即视为密码正确（with 块正常进入即 auto_bind 成功），随后调用 `_validate_group`。若组校验失败则落入 except/else 抛 401，无绕过路径。若 `self.group_dn is None`，`_validate_group` 第 109–111 行直接返回 True——符合配置语义。

### 4. `_validate_group`（第 106–118 行）

- Source：`user.memberOf.values`（第 113 行），来自 LDAP 服务器响应，非用户可控。
- 第 114–115 行：精确字符串相等比较 `group == self.group_dn`，无前缀匹配、无通配符，不可被构造绕过。
- 第 109–111 行：`group_dn` 未配置时默认放行所有通过密码验证的用户——这是配置缺省行为，需文档说明但不构成代码漏洞。

### 5. `load_component`（第 121–122 行）

纯工厂函数，无输入处理，无 sink。

## 三、第二入口与替代通道检查

- **第二入口**：Moonraker 中 `authenticate_ldap_user` 仅被认证管理器在 `/access/login` 与 API key/JWT 流程中调用，username/password 均来自请求体，无其他旁路（如 query string、header 直传）。
- **替代通道**：
  - 文件/环境变量通道：无，全部配置经 ConfigHelper。
  - 回调通道：无回调注册。
  - 并发通道：第 63 行 asyncio.Lock 已消除竞态。
  - 密码明文传输：第 74 行 `use_ssl=self.ldap_secure` 默认 False，若管理员未开启 TLS，凭据明文走网络——属部署配置问题，代码提供了开关，不算代码缺陷。
  - 时间侧信道：第 90 行提前抛错 vs 完整 bind 流程存在时间差，可用于用户枚举，同 Sink 3，属低危信息泄露。

## 四、结论汇总

| 数据流 | source | sink | 防御 | 判定 |
|---|---|---|---|---|
| filter 注入 | 第62行 username | 第85行 conn.search | 第79行 escape_filter_chars（库级转义） | 有效 |
| 自定义 filter 注入 | 第62行 username | 第82行 replace→第85行 | 替换值为转义后字符串 | 有效 |
| DN 注入 | 第86行 entry_dn（服务器返回） | 第88/96行 rebind/user | 非用户拼接 | 安全 |
| 错误回显 | 第62行 username | 第90行 error message | 无过滤 | 低危用户枚举 |
| 组校验绕过 | 第113行 memberOf | 第114行 == 比较 | 精确匹配 | 安全 |

核心注入面已被 `escape_filter_chars` 正确防护，无高危漏洞。唯一的真实缺陷是第 90 行错误消息导致用户枚举（含时间侧信道），属低风险信息泄露。
