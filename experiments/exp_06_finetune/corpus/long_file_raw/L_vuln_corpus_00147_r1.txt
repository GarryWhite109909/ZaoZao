# 编号分析（全文逐函数）

**1. 静态工厂与 XML 解析器配置（第 41–47 行）**
- 第 42–46 行：`XML_INPUT_FACTORY_SUPPLIER` 创建 `XMLInputFactory`，仅设置了 `ACCESS_EXTERNAL_DTD=""` 和 `ACCESS_EXTERNAL_SCHEMA=""`。
- 关键缺陷：**没有设置 `factory.setProperty(XMLConstants.SUPPORT_DTD, false)`，也没有设置 `IS_SUPPORTING_EXTERNAL_ENTITIES=false` 或禁用 XInclude**。
- 仅清空外部 DTD/Schema 访问只能阻止“通过 URL 加载外部实体”，但 **DTD 处理本身仍开启**：攻击者可在文档内部声明内部实体（internal general entity），利用实体嵌套展开造成 Billion Laughs / XML 炸弹（CWE-776），或依赖解析器实现差异的内部实体注入行为。黑名单式“只封外部访问”按分析要求视为可绕过、不构成完整防御。

**2. 构造函数 FullModel(...)（第 57–70 行）**
- 仅做非空校验和列表拷贝，无安全相关处理；字段为纯数据持有。

**3. Getter 与 toString()（第 72–110 行）**
- `toString()` 直接拼接用户可控字符串（id/description 等）。若调用方将其写入日志且未做日志框架编码，存在日志注入的理论面，但本文件内无 sink，不构成本文件内的实际漏洞。

**4. ParsingContext（第 113–133 行）**
- 纯数据容器，无防御逻辑。

**5. 入口点 parse(Reader reader)（第 135–157 行）**
- 第 136 行：`Objects.requireNonNull(reader)` —— Reader 即攻击者可控输入源（CGMES RDF/XML 文件内容）。
- 第 139 行：`createXMLStreamReader(reader)` —— **sink**：不可信 XML 进入仍允许 DTD 的解析器。
- 第 141–145 行：读取 FULL_MODEL 元素及其子元素；第 147–149 行 finally 中关闭并 gc 工厂——这只是资源管理，不影响实体处理安全性。
- 数据流：攻击者上传/提供的 CGMES 压缩包中的 `_EQ/_TP..._FullModel.xml` → `parse(reader)` → 第 139 行解析器 → 内部实体递归展开 → CPU/内存耗尽（DoS）。该入口是公开库 powsybl-cgmes 的标准导入路径，属于真实可达的第二入口之外的唯一主入口，且无任何替代防御通道（全文再无其他过滤）。

**6. readSubElement(...)（第 159–180 行）**
- 按元素名分发读取文本/属性；`getElementText()` 返回的内容同样来自已受实体影响的解析流，无额外净化。

## 结论
