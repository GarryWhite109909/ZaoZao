## 编号分析

**入口点枚举（全文）**
1. 第 63 行 `launchEditor(file, specifiedEditor, onErrorCallback)`：三个外部可控参数。`file` 来自调用方（典型场景是 dev server 的 HTTP 请求，如 webpack/vite 的 open-in-editor 端点）；`specifiedEditor` 可来自请求参数或环境变量；回调在第 34 行被透传。
2. 第 79 行 `guessEditor(specifiedEditor)`：返回的 `editor` 可能来自环境变量（EDITOR/VISUAL 等），也是外部输入。
3. 第 68 行 `fs.existsSync(fileName)`：仅做存在性检查，不是安全防御。
4. 第 48 行 `positionRE`：只剥离行号后缀，不构成过滤。
5. 第 85–98 行 WSL 分支：仅路径转换，无注入面。

**source→sink 数据流验证**

- **流 A（非 Windows，第 158 行 `spawn(editor, args)`）**：不经过 shell，参数数组形式传递，文件名不会被 shell 解释，安全。
- **流 B（Windows，第 149–156 行）**：sink 是第 153 行 `childProcess.exec(launchCommand, { shell: true })`，命令字符串拼接执行。
  - 第 130 行 `escapeCmdArgs` 只转义 `[&|<>,;=^]`，**未转义双引号 `"`**，也未处理延迟扩展字符 `!`。
  - 第 140–148 行 `doubleQuoteIfNeeded` 只在含 `^` 或空格时加引号，且引号内的 `"` 本身未被转义——含 `"` 的文件名可闭合引号并注入任意命令。
  - 注释（第 114–127 行）明确说明因框架需要支持特殊字符而放弃白名单校验，选择 `^` 转义方案，但该方案实现不完整。
- **流 C（editor 本身）**：第 149 行 `editor` 未经过 `escapeCmdArgs`（只对 `args` 做 map），若来自环境变量且含元字符同样可注入，但威胁模型较弱（本机环境变量）。
- **次要问题**：第 66/97 行 WSL 相对化、第 104 行直接 push 文件名，均汇入流 B。

**结论**：Windows 平台下存在命令注入漏洞（对应 launch-editor 的已知修复：后续版本在转义列表中补充了 `"` 等字符）。攻击者通过 dev server 接口传入形如 `foo" & calc & "` 的文件名即可触发 RCE。非 Windows 平台无此问题。
