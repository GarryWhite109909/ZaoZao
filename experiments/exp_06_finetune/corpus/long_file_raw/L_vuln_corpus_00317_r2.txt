# 逐行分析

先说明：我通读了全文（第 1–247 行），这是一个**纯领域值对象**，不是控制器/路由/入口文件。下面逐一枚举所有函数并验证数据流。

## 入口点枚举

该文件没有任何 HTTP 路由、请求参数读取、文件 I/O、环境变量或回调注册。所有“入口”仅是 PHP 方法调用，输入来源是调用方传入的参数。

## 逐函数分析

1. **构造函数（第 44–70 行）**：接收 `ContextSource`、`ruleIds`、`currencyId`、`languageIdChain` 等。第 66 行 `array_filter($languageIdChain)` 过滤空值、`array_flip/array_keys` 去重——这是数据规范化而非安全过滤需求；languageIdChain 后续用于 DAL 查询条件，Shopware 在存储层使用预编译 SQL 绑定，此处无 sink。
2. **createDefaultContext（第 74–79 行）**：默认 `SystemSource`，无外部输入。
3. **getter 系列（第 81–110 行）**：只读访问器，无 sink。
4. **createWithVersionId（第 112–129 行）**：`$versionId` 直接透传到新对象。versionId 在 DAL 中作为查询绑定值处理，非拼接 SQL 字符串；且调用方为内部版本管理逻辑，非用户可控字符串直接进 sink。
5. **scope()（第 136–148 行）**：接受 callable 回调——这是内部作用域切换模式（如 `system` scope），回调由框架代码提供，不来自用户输入；不存在回调注入面。
6. **isAllowed（第 178–183 行）**：对非 `AdminApiSource` 返回 `true`。这是设计语义：sales-channel/system context 本身不做 ACL 检查，权限校验在 `AdminApiSource::isAllowed` 内部完成。不是本文件的漏洞。
7. **setRuleIds（第 189–195 行）**：有 `rulesLocked` 防护（第 190–192 行），防止 sales channel 场景下规则被覆盖（这正是 Shopware 修复过的历史问题的防护措施）。`array_filter(array_values())` 清洗输入。
8. **enableInheritance / disableInheritance（第 203–229 行）**：临时布尔状态切换 + try 外恢复（注意这里没有 `finally`，若 `$function` 抛异常 considerInheritance 会停留在修改后的状态——这是健壮性小瑕疵，但 considerInheritance 只影响继承查询行为，不构成可利用的安全漏洞）。
9. **setTaxState / setRounding / lockRules（第 231–246 行）**：setter，taxState 的取值约束由类型注释约定，实际消费方按枚举匹配，不进危险 sink。
