# 编号分析

**1. 入口点枚举**
- 第 96–99 行 `B64Postprocessor.run`：入口为 Markdown 渲染后的 HTML 文本 + 配置项 `base_path`（第 108 行定义，默认 `"."`，由使用者传入）。
- `base_path` 与文档中的 `<img src="...">` 路径均为外部可控 source。

**2. source→sink 数据流验证**

- **流 A（相对路径）**：文档中 `<img src="../../etc/passwd.png">` → 第 74–75 行 `os.path.join(base_path, path)` → 第 76 行 `normpath` → 第 82 行 `open(file_name, "rb")`。`..` 未被任何过滤拦截，可穿越出 base_path。但 sink 要求扩展名命中白名单（第 78–80 行 `.png/.jpg/.jpeg/.gif/.svg`），`/etc/passwd` 不满足；攻击者需找到 base_path 之外、以图片扩展名结尾的文件（如上传目录中的 `evil.svg`）。SVG 内容会被原样 base64 嵌入输出 HTML——若下游直接渲染该 data URI，SVG 内嵌脚本可在同源执行（XSS 放大）。

- **流 B（绝对路径）**：第 72 行 `is_absolute` 为真时跳过 join，第 73 行直接 `normpath(path)` → 任意绝对路径读取，同样受图片扩展名限制。Windows 下第 30 行正则 `RE_SLASH_WIN_DRIVE` 在本文件定义但**从未使用**（util 内部可能使用，但本文件无防御）。

- **防御有效性评估**：
  - 扩展名白名单（第 78–80 行）：非黑名单，但仅限图片类型——它把任意文件读降级为“受限文件读”，不是完整防御；
  - 第 86 行裸 `except Exception: pass`：吞掉所有错误，无日志，掩盖异常行为；
  - 无路径规范化校验（如确认结果仍在 base_path 下）、无符号链接检查。

**3. 第二入口/替代通道**
- `base_path` 本身可被配置为 `/` 或敏感目录，与文档内路径组合实现任意位置读取。
- Postprocessor 阶段处理的是最终 HTML，`RE_TAG_HTML` 只匹配 `img` 标签的 `src`，无其他 sink（无 eval/exec/subprocess）。

**4. 结论**
存在漏洞：通过 Markdown 文档中的 img src 相对/绝对路径进行路径穿越，读取 base_path 之外的本地图片类文件并嵌入输出；对 SVG 类型还构成存储型 XSS 向量。严重性受“必须是图片扩展名”限制，评为中等。
