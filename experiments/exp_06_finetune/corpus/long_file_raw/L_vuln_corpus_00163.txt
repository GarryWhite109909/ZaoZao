## 编号分析（全文逐函数）

**入口点枚举：**
1. `UploadIssueAttachment` / `UploadReleaseAttachment`（第 32、37 行）→ `uploadAttachment`，source 为 multipart 文件 `ctx.Req.FormFile("file")`（第 46 行）。
2. `DeleteAttachment`（第 76 行），source 为 `ctx.FormString("file")`（第 77 行）。
3. `GetAttachment` / `ServeAttachment`（第 158/117 行），source 为路径参数 uuid。

**数据流逐一验证：**

1. **上传流（第 44–72 行）**：文件经 `NewLimitedUploaderKnownSize` 限大小，`uploadFunc` 内部做类型白名单（`IsErrFileTypeForbidden` 返回 400）。`header.Filename` 仅作为附件显示名存储（第 53 行），sink 是存储层与后续下载时的 `Content-Disposition`。Gitea 的 `httplib.ServeUserContentByFile` 对 filename 做转义处理（本文件外依赖），且不拼入任何 shell/SQL/路径。无直接 sink 漏洞。

2. **删除流（第 76–110 行）**：
   - 第 79 行校验 `attach.RepoID == ctx.Repo.Repository.ID`，防止跨仓库删除；
   - 第 81 行要求登录；
   - 第 87 行起：非 uploader 时按 IssueID/ReleaseID/其他分别要求写 issue 权限、写 release 权限或 admin/owner。逻辑完整，无绕过分支。
   - 唯一宽松点：uploader 本人即使已失去仓库写权限仍可删自己的附件——属设计取舍，非越权漏洞。

3. **读取流（第 117–156 行）**：
   - 第 124–128 行：新附件强制 `ctx.Repo.Repository.ID == attach.RepoID`，防跨仓库直链；
   - 遗留附件（cutoff 之前）跳过该检查，但随后第 131 行 `GetAttachmentLinkedTypeAndRepoID` 取得真实关联仓库并计算权限；未关联附件（unitType Invalid）仅 uploader 可读（第 136–139 行）；
   - 已关联附件走 `perm.CanRead(unitType)`（第 152 行）+ token scope 校验（第 154–157 行）。私有仓库不可读者得到 404。无绕过。
   - `ServeDirectURL` 与 `storage.Attachments.Open(attach.RelativePath())`（第 149 行）：RelativePath 由服务端 UUID 生成，非用户可控字符串，无路径穿越。

**第二入口/替代通道检查**：uuid 同时来自路径参数与表单字段，均汇入同一鉴权函数，无旁路。

**结论**：全文所有 source→sink 流均有有效权限校验，未发现可利用漏洞。
