## 编号分析（全文逐函数）

1. **第 44–52 行 `newOAuth2PendingAuth`**：state 由 `util.GenerateRandomBytes(32)` 经 SHA-256 生成，熵充足，不可预测、不可伪造。无注入面。

2. **第 68–74 行 `memoryOAuth2Manager.addPendingAuth`**：以 state 为 key 写入 map，加锁正确，key 为服务端生成的随机值，无碰撞/覆盖风险。

3. **第 82–95 行 `getPendingAuth`**：查 map 后仅校验时效（第 88–91 行）。**关键缺陷：取回后并未调用 `removePendingAuth(state)` 删除该条目**，即 state 在有效期内可被重复使用（非一次性）。OAuth2 的 state 本应一次性消费；若回调 URL 中携带的 state 泄漏（如通过 Referer、日志、浏览器历史），攻击者可在 `authStateValidity` 窗口内重放同一 state 走完回调流程。这是 source（HTTP 回调参数 state）→ sink（`getPendingAuth`）数据流上防御不完整的问题。

4. **第 97–108 行 `cleanup`**：定期清理过期条目，逻辑正确，但同样不解决“已使用未删除”问题。

5. **第 111–121 行 `dbOAuth2Manager.addPendingAuth`**：加密失败时静默返回（errcheck），pending auth 未落库会导致后续流程失败——可用性问题而非漏洞。

6. **第 123–127 行 `removePendingAuth` / 第 129–141 行 `dbOAuth2Manager.getPendingAuth`**：DB 版本同样只在过期时拒绝，取出后未删除 session，与内存版存在相同的“state 可重放”缺陷；且第 137–139 行过期判断依赖 `Timestamp`，与写入端 `IssuedAt + authStateValidity` 一致，无绕过。

7. **第 143–157 行 `decodePendingAuthData`**：类型断言 + JSON 反序列化到固定结构体，无多态反序列化风险；`TryDecrypt` 失败会返回错误。无漏洞。

8. **第二入口核查**：本文件无 HTTP handler、无环境变量、无文件读取入口；唯一外部输入是调用方传入的 `state` 字符串，仅作 map/DB key 查找，不存在路径穿越或注入 sink。替代通道（DB 共享 session）与内存通道行为一致，均受上述“未一次性消费”影响。
