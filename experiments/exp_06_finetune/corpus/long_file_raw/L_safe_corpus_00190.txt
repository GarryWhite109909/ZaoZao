## 编号分析

1. **第 10–19 行 typecheckRegex**：定义各类型白名单正则。注意 `very_dangerous_raw_string` 的模式为空字符串——空正则匹配任意输入，等于无校验。但该类型被显式命名为“非常危险”，且在第 262–270 行的 `shellUnsafeArgumentTypes` 中被列入黑名单（见第 6 步），不能用于 Shell 执行，故不构成直接漏洞。

2. **第 21–33 行 parseExecArray / 第 35–47 行 parseActionExec**：exec 数组路径。每个 segment 先经第 49–53 行 `parseExecSegment` 模板渲染，但渲染前必须通过第 39 行 `validateArguments` → 第 76–89 行 `typecheckActionArgument`，source（用户提交的 `values`）到 sink（命令参数）之间有强制校验闸门。

3. **第 55–74 行 parseActionArguments**：shell 路径。第 57–66 行对每个声明的 argument 逐一执行 `typecheckActionArgument`，失败即返回错误；之后才在第 68 行做模板渲染生成 shell 命令。校验先于 sink，顺序正确。

4. **第 91–172 行 redact 函数与 argumentSkipsValidation**：仅影响日志脱敏，非安全边界。`confirmation`/`html` 跳过校验，但二者均在 `shellUnsafeArgumentTypes` 黑名单中，无法进入 Shell。

5. **第 174–244 行 typecheck 系列**：
   - 空值走 `typecheckNull`（RejectNull 可拒绝）；
   - checklist 逐段走 `typecheckChoice`；
   - 有 Choices 时（第 190–193 行）强制精确匹配预定义值或实体实例值，用户无法注入任意串——这封堵了 checkbox/checklist 绕过路径；
   - `TypeSafetyCheck`（第 205 行起）中 `checkbox`/`checklist` 直接放行看似可疑，但由于第 190 行的 Choices 分支优先拦截，实际不可达任意值。

6. **第 258–275 行 isUnsafeShellArgumentType / checkShellArgumentSafety**：第二道防线。凡 `regex:` 前缀、url、email、multiline、raw_string、password、html、confirmation、无 Choices 的 checkbox 一律禁止与 `Shell` 同用，强制走 `exec`（数组形式，不经 shell 解释）。这是对黑名单正则可绕过性（如 `very_dangerous_raw_string`）的有效兜底。

7. **第 277–300 行 mangleInvalidArgumentValues 及后续 mangle 函数**：仅在合法值域内做标题→值的映射转换（datetime 补秒、choice 标题映射），映射失败时保留原值并交由后续 typecheck 拦截，不会引入未校验数据。

8. **email/url/datetime 校验（第 296–320 行附近）**：`mail.ParseAddress`、scheme 白名单 http/https、严格时间格式解析，均为标准库强校验；且这些类型同时被禁止用于 Shell，风险进一步收敛。

9. **替代通道检查**：文件内两条执行路径（exec 与 shell）均独立调用同一 `typecheckActionArgument`；`ValidateArgument`（第 118 行起）复用相同校验逻辑供 API 使用，无绕过分支。唯一理论残留是模板若引用了未在 `action.Arguments` 中声明的键值，其值不会经过本校验——但该行为取决于本文件之外的模板实现，就本文件证据而言不存在可确认的漏洞。
