**入口点枚举（全文通读）**
1. 构造函数（第 35–38 行）：`file_path` 由调用方传入，是唯一的文件型 source；`load_single_document` 仅控制聚合方式，无安全影响。
2. `_parse_note_xml`（第 124–143 行）：以 `file_path` 打开本地文件解析 XML，是核心 sink 所在。
3. `_parse_content`（第 68–78 行）：处理 XML 内嵌 content 文本，仅经 html2text 转 Markdown，不执行、不写文件，无 sink。
4. `_parse_resource`（第 81–91 行）：对 `data` 节点做 `b64decode` 并计算 MD5（第 86–87 行），结果只存入内存字典，未落盘、未执行；MD5 用于资源哈希属弱哈希但非可利用漏洞。
5. `_parse_note`（第 94–121 行）：递归处理 `note-attributes`，键值均来自 XML 文本，最终进入 Document 的 metadata/page_content，下游为数据对象而非危险函数。

**source→sink 数据流验证**
- 流 A：`file_path`（第 37 行）→ 第 137–138 行 `etree.iterparse(xml_file, ..., huge_tree=True, recover=True)`。关键问题：lxml 默认 `resolve_entities=True` 且未指定自定义 parser 禁用外部实体加载。`recover=True` 只是容错，`huge_tree=True` 反而放大了实体展开的资源上限，二者都不构成防御。攻击者控制的 .enex 中若含 `<!ENTITY xxe SYSTEM 'file:///etc/passwd'>` 或 http URL，实体内容会被解析进 `elem.text`，随后在第 105/107/116 行进入 `content`/`content-raw`/metadata，最终随 Document 内容外泄（LLM 场景下即注入到模型上下文）。这是典型 XXE（CWE-611），黑名单式过滤不存在——本代码根本没有过滤。
- 流 B：XML 内容 → `html2text`（第 72 行）→ page_content。纯文本转换，无 eval/exec/os.system，非漏洞。
- 流 C：`b64decode`（第 86 行）。解码后仅驻留内存并做 MD5，无文件写入或反序列化，非漏洞。
- 第二入口/替代通道检查：无网络请求、无环境变量读取、无回调注册、无子进程调用；`strptime`（第 111 行）格式固定且异常会直接抛出，无绕过面。全文确认唯一可利用通道就是 XML 实体解析。
