# 全文逐函数安全分析

## 1. 文件概览与入口点枚举

本文件是 zerogod（一个 mDNS/网络服务伪造蜜罐工具）的监听器模块。全文共定义以下函数与全局结构，逐一分析：

- 第 9–16 行：`Handler` 结构体（TLS 标志 + 处理函数指针）
- 第 19–28 行：`TCP_HANDLERS` 全局映射表（`_ipp`、`_ipps`、`_http`、`_https` 四个协议处理器）
- 第 30–45 行：`Acceptor` 结构体
- 第 47–54 行：`HandlerContext` 结构体
- 第 56–88 行：`NewAcceptor` 构造函数
- 第 90–124 行：`startTCP`
- 第 126–155 行：`startUDP`
- 第 157–163 行：`Start`
- 第 165–179 行：`Stop`

## 2. 入口点清单（source 枚举）

**外部网络入口：**
1. **TCP 入口**（第 97 行）：`lc.Listen(a.context, "tcp", fmt.Sprintf("0.0.0.0:%d", a.port))` —— 绑定所有网卡的指定端口，任何远程主机均可连接。
2. **UDP 入口**（第 128 行）：`net.ResolveUDPAddr("udp", "0.0.0.0:%d")` + 第 130 行 `ListenUDP` —— 同样绑定全部接口，任意来源 UDP 包可到达第 136 行 `ReadFromUDP`。

**配置/环境入口（间接 source）：**
3. `NewAcceptor` 的参数 `service`（第 56 行）、`port`、`tlsConfig`、`ippAttributes`、`httpPaths` —— 来自上层 mDNS 广播解析结果（攻击者可通过局域网 mDNS 欺骗注入 service 字符串），属于第二入口/替代通道。

## 3. 逐条 source→sink 数据流验证

### 数据流 A：service 字符串 → 处理器选择（第 56–88 行）

- **source**：第 56 行参数 `service`（可能来自不可信的 mDNS 网络数据）。
- **sink**：第 74–80 行 `for svcName, svcHandler := range TCP_HANDLERS { if strings.Contains(service, svcName)`。
- **防御验证**：使用 `strings.Contains` 做子串匹配而非精确匹配。问题一：Go 的 map 迭代顺序随机，若 service 同时包含多个关键字（如构造 `_http._ipp._tcp`），命中哪个 handler 不确定——非确定性行为。问题二：子串匹配可被绕过，例如服务名中嵌入 `_http` 子串即可让任意伪装服务走 HTTP handler。但该匹配的后果仅是选择哪个内置 handler，不直接构成内存破坏或注入 sink；且未匹配时回退到 `handleGenericTCP`（第 82–84 行）。此流风险为逻辑缺陷，非可直接利用漏洞。

### 数据流 B：客户端 TCP 连接 → handler 并发执行（第 104–118 行）

- **source**：第 105 行 `a.tcpListener.Accept()` 返回的远程连接（完全不可信）。
- **sink**：第 108–117 行 `go a.handler.Handle(&HandlerContext{...})`，将原始 conn 直接交给 ipp/http/generic handler。
- **防御验证**：无任何速率限制、连接数上限、超时设置或来源过滤。单个客户端可无限建立连接耗尽 goroutine 与 fd（资源耗尽面）。但这属于工具设计意图（蜜罐接受一切连接），且实际解析逻辑在 handlers 文件中，本文件不构成独立可利用漏洞。

### 数据流 C：TLS 配置注入（第 99–101 行）

- 第 99 行 `if a.tlsConfig != nil { a.tcpListener = tls.NewListener(...) }`。tlsConfig 由调用方传入，非用户可控路径；若上层传入弱配置则属上层问题，本文件无 sink 缺陷。

### 数据流 D：UDP 数据包 → Dump 输出（第 133–140 行）

- **source**：第 136 行 `ReadFromUDP(buffer[0:])` 读到的任意 UDP 载荷。
- **sink**：第 139 行 `Dump(buffer[0:n])` 及日志输出。
- **防御验证**：缓冲区固定 4096 字节（第 134 行），读取以 `buffer[0:n]` 切片限定长度，n 由 ReadFromUDP 保证 ≤4096，**无越界风险**。载荷仅被格式化打印，不进入命令执行或文件写入 sink。日志注入（伪造换行）仅影响日志可读性，风险极低。

### 数据流 E：端口/host 格式化拼接（第 97、128 行）

- `fmt.Sprintf("0.0.0.0:%d", a.port)`，port 为 uint16 类型（第 33 行），类型系统保证无格式化字符串注入或整数溢出。**安全**。

## 4. 第二入口与替代通道核查

- **mDNS 注入的 service 名**（经 NewAcceptor 第 56 行）是唯一跨信任边界的字符串输入，其唯一消费点是第 76 行 `strings.Contains` 与第 83 行日志格式化 `%s`——均无命令执行/SQL/路径 sink，无法升级为 RCE。
- **并发停止通道**：`Stop()`（第 165–179 行）写 `a.running = false`（第 168 行），而接收循环（第 106 行 `for a.running`）与 UDP 循环（第 137 行）在独立 goroutine 中读同一布尔值，**全程无 mutex/atomic 保护**。这是真实的 CWE-362 数据竞争：可能导致 Stop 后仍接受新连接，或在 TLS 包装的 listener 上产生未定义行为。此外第 172–173 行 `ctxCancel()` 后等待 `<-a.context.Done()`，但 startTCP 的 goroutine 并不监听 context.Done，依赖 running 标志退出，时序上可能死等至 Close 才解除阻塞——逻辑脆弱点。
- 另注意第 60 行局部变量 `context` 遮蔽了标准库 `context` 包名（命名缺陷，非漏洞）。

## 5. 结论

通读全文后：无注入、无越界、无反序列化类可利用漏洞；最实质的缺陷是第 168 行对 `running` 标志的无同步并发读写（CWE-362 TOCTOU/竞态），以及第 76 行基于 `strings.Contains` 的非确定性处理器选择（CWE-436/逻辑绕过，影响有限）。综合判定存在低危真实缺陷。
