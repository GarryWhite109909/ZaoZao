## 编号分析

**入口点枚举（全文）**
1. 第 44-95 行 `connect_to_server()`：POST 路由，接收 `provider_id`、`caldav_url`、`caldav_username`、`caldav_password`（第 51-54 行）。
2. 第 97-262 行静态方法 `sync(string $provider_id)`：可由 HTTP 路由或 CLI 调用（第 104 行注释），provider_id 来自路由参数。
3. 第 264-299 行 `disable_provider_sync()`：POST，接收 `provider_id`。

**数据流逐一验证**

- **SSRF 流**：第 62 行 `$caldav_url = request('caldav_url')` → 第 66 行 `test_connection($caldav_url, ...)` 发起出站 HTTP 请求。防御：构造函数第 27-30 行加载 `caldav_sync` 库时默认开启 `enable_ssrf_check => true`（仅当管理员显式定义 `Config::ENABLE_CALDAV_SSRF_CHECK = false` 才关闭）。默认配置下为有效防御；若管理员主动关闭则属运维决策而非代码缺陷。注意第 106 行 `sync()` 中重新加载库时未传该配置，但该路径的 URL 来自数据库已存设置（第 65 行 `find($provider_id)`），且写入端已受控。
- **越权流（connect_to_server）**：第 57-60 行检查 `cannot('edit', PRIV_USERS)` 且非本人时拒绝——普通 provider 只能配置自己的 CalDAV，admin 可配任意人。有效。
- **越权流（disable_provider_sync）**：第 280-283 行同样的权限检查，有效。
- **越权流（sync）**：第 112 行 `if (!$user_id && !is_cli()) return;` 仅要求登录，任意已登录用户可对任意 provider 触发同步。但同步目标 URL 是各 provider 自己存储的值，攻击者只能让服务器访问受害者自己配置的地址，无法注入新 URL，危害有限（信息泄露面：错误消息）。
- **SQL 注入**：所有 DB 操作走模型封装的参数化 where 数组（第 141-146、197、207-212 行等），Query Builder 绑定，无拼接。无 sink。
- **XSS**：输出全部经 `json_response`（JSON 编码），无直接 HTML 输出。远程 CalDAV 的 summary/description 写入 notes 字段（第 224、236 行），是否在其他视图转义不在本文件范围，本文件内无 sink。
- **信息泄露**：第 246-253 行将 Guzzle 异常的 `$e->getMessage()` 及响应 body 记入日志并部分返回给用户（第 254 行非 401 时返回原始 message）；第 296-298 行 `json_exception` 同样透出内部异常消息。已认证用户可获得内部错误细节——低危信息泄露。
- **敏感数据存储**：第 71 行明文保存 `caldav_password` 到 settings 表，无加密——设计弱点，低危。
- **CLI 下调用 `json_response`**：第 257 行在 CLI 场景会尝试输出 JSON，属健壮性小问题，非安全漏洞。
- **第二通道检查**：`sync()` 静态调用自 CLI 命令（注释第 104 行），CLI 无会话但 `is_cli()` 放行合理；HTTP 侧需登录。无未授权替代入口。

**结论**：默认配置下 SSRF 有开关保护、权限检查完整、无注入/XSS sink。存在两处低危问题：异常消息透传给前端用户（信息泄露）、CalDAV 密码明文入库；另 SSRF 防护依赖可选配置项，若被关闭即成 SSRF 漏洞（条件性）。综合判定为存在轻微问题但不构成高危可利用漏洞。
