# 逐行安全分析

## 入口点枚举

本文件是 vLLM 的 pooler 激活函数工具模块，无 HTTP 路由、无文件 I/O、无环境变量读取、无回调注册。唯一的外部输入通道是模型配置对象（`config: PretrainedConfig`），即第 8 行 `get_act_fn` 的参数。

## 主要函数逐一分析

**1. `get_act_fn`（第 8–47 行）**
- 第 14、17 行：读取 `config.num_labels` 与 `config.problem_type`，仅用于字符串比较（第 18/20/22 行）和整数传递给 `PoolerClassify`，不进入任何危险 sink。
- 第 27–33 行：从 `config.sentence_transformers["activation_fn"]` 或 `sbert_ce_default_activation_function` 提取 `function_name` 字符串——这是唯一的 source→sink 数据流。
- 第 38–41 行：防御检查——要求 `function_name.startswith("torch.nn.modules.")`。虽然前缀黑名单式检查在通用场景可被绕过（如 `torch.nn.modules.module.Module` 本身无害，但需评估是否存在危险类），但关键在于 sink 是什么：
- 第 42 行：`resolve_obj_by_qualname(function_name)()` —— 这是反射调用 sink。攻击面为：攻击者需能控制模型配置文件（hf_config），且必须指向 `torch.nn.modules.*` 下可无参实例化并用于张量变换的类。`torch.nn.modules` 命名空间内不存在代码执行类构造（如 `eval`/`os.system` 不在该命名空间下）；最坏情况是实例化某个异常模块导致 DoS/报错，且前提是攻击者已能提供恶意模型配置——此时攻击者本就可加载任意 pickle 权重或自定义模型代码（vLLM 加载 HF 模型本身即信任模型来源）。因此该限制是有效的纵深防御，实际风险可忽略。

**2. `resolve_classifier_act_fn`（第 50–58 行）**
- 第 53 行：act_fn 为 None 时委托给 `get_act_fn`；否则第 56 行仅做 `callable` 类型检查后原样返回。无新数据流。

**3. `PoolerActivation.wraps` / `forward`（第 63–83 行）**
- 纯类型分发与张量处理，无外部输入。

**4. `PoolerIdentity` / `PoolerNormalize` / `PoolerMultiLabelClassify`（第 86–100 行）**
- 纯张量运算（恒等、L2 归一化、sigmoid），无输入面。

**5. `PoolerClassify.__init__` / `forward_chunk`（第 103–121 行）**
- 第 105 行：num_labels 来自配置，仅影响 sigmoid/softmax 分支选择；即使传入异常大值也不会造成资源问题（softmax 按张量形状工作）。无漏洞。

**6. `LambdaPoolerActivation`（第 124–133 行）**
- 包装一个 callable 并在第 132 行调用。该 callable 仅来自第 42 行经前缀校验后的 torch.nn.modules 实例，或内部代码传入的合法 nn.Module，不可被外部直接注入任意 lambda。

## 第二入口与替代通道检查

全文无其他入口：无网络端点、无文件读写、无 subprocess/eval/exec/pickle 反序列化、无 SQL/模板渲染。`resolve_obj_by_qualname` 是唯一反射点，且受第 38 行前缀约束。

## 结论

唯一 source→sink 流为「模型配置中的 activation_fn 字符串 → 反射实例化」，已有 `torch.nn.modules.` 前缀白名单约束，且威胁前提（攻击者控制模型配置）本身等同于模型供应链信任边界已被突破，不构成本文件的独立漏洞。
