**source→sink 数据流验证**

- 流 A：`data-feeurl`（第 43 行）→ `getPaymentFee` fetch → 响应 `data.view` → **第 71 行 `orderTotalTr.insertAdjacentHTML('beforebegin', data.view)`**。服务器返回的 HTML 未经任何净化直接以 HTML 解析插入 DOM。若该接口可被参数影响、存在反射点或被中间人/子域劫持，即为存储/反射型 XSS。黑名单/正则不存在，无防御。
- 流 B：`fetchQrCode` 响应的 `data.qrCode` → 第 199 行 `qrCodeImg.src = qrCode`。img src 中 `javascript:` 在现代浏览器不执行，风险较低但仍是不可信数据进入属性。
- 流 C：第 137–139 行 `window.location.href = thankYouPageUrl + '?orderId=' + orderId`。thankYouPageUrl 来自页面属性，orderId 来自服务器响应；若任一被污染可实现开放重定向。
- 流 D：第 146 行 `removeQrCode` 将 `extractOrderToken()`（第 160 行，直接取自 location.href，未编码未验证）拼入请求 URL —— 属于客户端向服务端传递未净化输入，主要风险在服务端，且为第二入口/替代通道（URL 路径而非 DOM 属性）。
- 其余 sink（textContent、classList、createElement+textContent）均安全。

**结论**：最确凿的漏洞是流 A：网络响应 HTML 未经净化经 `insertAdjacentHTML` 注入 DOM（CWE-79）。流 C/D 为次要问题。
