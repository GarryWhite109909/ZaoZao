## 编号分析

1. **入口点枚举（全文）**：本文件是 showdown 的 `makehtml.table` 子解析器，唯一外部输入是参数 `text`（Markdown 源文本，第 2 行函数签名）。其余输入通道包括：`options`（用户配置，如 `options.tables`、`options.tablesHeaderId`）、`globals.converter.dispatch(...)` 的扩展事件回调（onStart/onEnd/onCapture/onHash 等，属受信任的扩展 API，非不可信 source）、以及内部辅助函数 `breakOnBlock`、`parse`、`preParse`、`parseTable`、`buildTableOtp`、`parseStyle`、`parseHeader`、`parseCell`。无文件系统、网络、环境变量等其他 source。

2. **source→sink 数据流 1：表格单元格 → HTML 输出**。不可信文本经 `tableRgx` / `singeColTblRgx` 匹配后进入 `preParse`，其中每行先经过 `showdown.subParser('makehtml.codeSpan')` 处理；随后在 `parseCell` 中调用 `spanGamut`（内含 escapeSpecialChars 等转义步骤）后才拼入 `<td>` 标签。管道上游的转义子解析器对 `<`、`"` 等做了实体编码，因此直接 XSS 路径被上游防御覆盖。

3. **数据流 2：表头 → id 属性**。`parseHeader` 中当 `options.tablesHeaderId` 为真时，`attributes.id = headerText.replace(/ /g,'_').toLowerCase()`。关键在于此时 `headerText` 已经先经过 `spanGamut` 转义（`parseHeader` 第一行即调用），双引号已变为 `&quot;`，无法闭合属性注入新属性或事件处理器。这是“先转义后使用”的正确顺序。

4. **数据流 3：`_populateAttributes(attributes)`**。attributes 来源有二：`parseStyle` 只返回固定的三个白名单 style 值（left/right/center）或空对象，无用户可控内容；id 来自第 3 点已转义的 headerText。无注入面。

5. **事件回调通道**：所有 `dispatch` 事件的 output 直接进入输出（如 `captureStartEvent.output` 分支）。但扩展注册是开发者主动行为，属于受信任的第二入口（类似插件 API），不构成不可信输入漏洞；且这与 showdown 官方扩展模型一致。

6. **正则与 DoS**：注释明确说明旧版 tableRgx 存在二次回溯问题并已被修复（lookahead + 单个贪婪 `[^\n]+`）；`breakOnBlock` 为线性扫描；`preParse` 的 split/map 均为线性。未发现新的 ReDoS 模式（无嵌套量词回溯）。

7. **黑名单/过滤评估**：`blockStartRgx` 仅用于切分块级结构，不影响安全；`\|` 转义处理交给后续 backslash-escape/codeSpan 通道，非安全依赖。未发现以黑名单作为唯一防线的 sink。

8. **结论**：全文通读后，所有到达 HTML 字符串拼接 sink 的不可信数据均先经过上游转义管道（spanGamut/codeSpan），id 属性构造顺序正确，style 为白名单常量，事件输出为受信任扩展接口。未发现可利用漏洞。
