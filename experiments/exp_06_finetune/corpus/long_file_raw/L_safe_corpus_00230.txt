# 逐点分析

**入口点枚举（全文通读）**

1. **构造函数（第 27-44 行）**：`is_cli()` 检查，非 CLI 直接 `exit`（第 30 行）。这是整个控制器的第一道防线——所有 HTTP 请求无法触达任何方法。CI4 中 CLI 路由仍可被本地用户/已入侵服务器调用，但这是设计意图。

2. **install()（第 52-58 行）**：无外部输入 source；`migrate('fresh')` 与 `seed()` 均为硬编码参数。输出 `$password` 到控制台（第 56 行），属预期行为。

3. **migrate(string $type)（第 70-73 行）**：source = CLI 参数 `$type`，sink = `instance->migrate($type)`。需看 Instance 库实现：migrate 仅接受 'fresh'/'up'/'down' 等白名单动作，非 SQL 注入面；即使传入任意字符串也只会导致迁移器报错/忽略，不构成 sink。

4. **seed()（第 82-85 行）**：无输入参数，纯固定种子数据。

5. **backup()（第 96-99 行）**：source = `$GLOBALS['argv'][3]`（CLI 第三个参数），sink = `instance->backup($path)`。潜在风险是路径可控的备份文件写入（任意目录写）。但：(a) 仅限 CLI 本地执行者；(b) 能在服务器上执行 CLI 的用户通常已有同等权限，写入自身可写目录不构成提权；(c) 无 Web 可达性（第 30 行拦截）。防御有效性：`is_cli()` 为有效防御（非黑名单/正则类）。

6. **sync()（第 110-121 行）**：数据来自数据库 providers 表，经 `FILTER_VALIDATE_BOOLEAN` 过滤后传给 `Google::sync((string)$provider['id'])`。id 为整型主键，且 Google::sync 内部按 id 查询使用查询绑定。无用户可控 source 直达危险 sink。

7. **help()（第 131-152 行）**：仅输出静态数组 + `config('version')`（框架常量），无注入面。

**第二入口/替代通道检查**：CI4 的 CLI 路由即唯一通道；HTTP 请求因构造函数 `exit` 被完全阻断，不存在绕过（`is_cli()` 基于 `PHP_SAPI` 判断，不可被请求头伪造）。`$GLOBALS['argv']` 只在 CLI 下有意义。

**结论**：所有 source→sink 流要么无外部 source，要么被 `is_cli()` 有效隔离，且 sink（migrate/backup/sync）本身不含 SQL 拼接或反序列化等危险操作。基于全文证据，未发现可利用漏洞。唯一值得注意的纵深防御建议：backup 的目标路径未做规范化校验，但在纯 CLI 威胁模型下风险可忽略。
