## 编号分析（全文逐函数）

1. **第 1–30 行（文件头与导入）**：纯模块导入，无网络、文件、环境变量入口；`TYPE_CHECKING` 为常量 False，无动态执行。

2. **第 32–50 行（Filter/MultibandFilter/BuiltinFilter 基类）**：`BuiltinFilter.filter` 将 `self.filterargs` 直接传给 `image.filter(...)`，即 C 扩展 `_imaging`。source 是实例属性 `filterargs`，sink 是 C 层 `image.filter`。对内置子类（BLUR~SMOOTH_MORE）`filterargs` 为硬编码常量，不可控。但 `Kernel` 类例外，见下条。

3. **第 52–86 行（Kernel.__init__）**：外部可传入 `size`、`kernel`、`scale`、`offset`。校验仅有 `size[0]*size[1] != len(kernel)` 抛错——这是长度一致性检查，但 **未验证 size 是否为 (3,3)/(5,5)**（文档声称只支持 3x3 与 5x5），也未验证 scale 非零或元素为有限数值。攻击者若从应用层拿到 Kernel 构造入口，可传如 `(1000,1000)` 的超大核配合等长列表、或 `scale=0`，直接进入 C 层 `image.filter`，造成极端内存/CPU 消耗甚至 C 层异常。防御不完整：黑名单式（仅长度相等）不算有效防御。

4. **第 88–120 行（RankFilter / MedianFilter / MinFilter / MaxFilter）**：`RankFilter.__init__` 校验了奇数 size 和 rank 范围（0 ≤ rank < size²），但 **size 本身无上限**，超大 size 在 `image.expand(self.size // 2)` 处会按 size 分配扩展图像内存——应用层若把用户输入映射到 size，构成无上限资源消耗（DoS）。这是有效校验缺失而非黑名单问题。

5. **第 122–152 行（ModeFilter）**：`size` 完全未校验（可为负数、0 或任意大整数），直接传入 C 层 `image.modefilter(self.size)`。负值/超大会在 C 扩展内触发错误处理或巨大窗口计算，属未经净化的参数直达 sink。

6. **第 154–200 行（GaussianBlur / BoxBlur）**：`BoxBlur.__init__` 正确校验了 `radius >= 0`（第 176–179 行）。但 **`GaussianBlur.__init__` 对 radius 无任何校验**（第 168–170 行），负数半径或含负分量的序列在第 180 行 `image.gaussian_blur(xy)` 直达 C 实现；历史上 Pillow 曾因类似负半径参数导致 C 层崩溃/异常（对应修复即给 BoxBlur 加校验，而 GaussianBlur 此版本仍缺同类防护）。不对称的校验说明该处是遗漏。

7. **第 202–230 行（UnsharpMask）**：`radius`、`percent`、`threshold` 全部未校验即传入 C 层 `image.unsharp_mask`。负 percent/threshold、异常大 radius 同样直达 sink。

8. **第 232–330 行（BLUR…SMOOTH_MORE 内置核）**：全部为硬编码常量元组，无外部输入，安全。

9. **第 332–430 行（Color3DLUT.__init__ / _check_size）**：size 被限制在 [2,65]，channels 限 3/4，表长被强制等于 items*channels——这些是有效白名单式校验。但 `table` 元素本身未做数值类型/范围校验，非有限浮点（NaN/inf 或任意对象）会进入第 425 行 `image.color_lut_3d(...)` 的 C 层。风险较低但存在类型混淆面。另注意 `generate()`（第 386–418 行）与 `transform()`（第 420–455 行）以回调 `callback` 填表——若应用层将用户输入反序列化为 callable 传入（如 pickle 场景），即为任意代码执行 source→sink 流，但本文件自身未提供该通道，需上游配合。

10. **第二入口核查**：全文件无路由、无环境变量、无文件读写、无 eval/exec/pickle。所有危险汇聚点均为 C 扩展调用（`image.filter/gaussian_blur/box_blur/modefilter/unsharp_mask/color_lut_3d`）。因此漏洞性质为「库参数校验不足 + 上游应用暴露构造参数」型 DoS/健壮性问题，而非直接的 RCE。
