## 编号分析

1. **第 60-90 行 `IsLogin`**：从 session 取 profile，若 `p.Mfa.Enable && !p.Mfa.Approved` 则 401。这是 MFA 中间态拦截点之一。

2. **第 92-170 行 `Login`**：source 为 `ctx.ReadJSON(&loginCredential)`（用户名/密码）。密码校验后构造 `profile`，其中 `Mfa.Approved: false`（第 130 行附近）。随后按 `authMethod` 分支：
   - **`jwt` 分支（第 145-152 行）**：直接 `h.jwtSigner.Sign(profile)` 并返回 token，**完全没有检查 `u.Mfa.Enable`**。即启用了 MFA 的用户，只要密码正确即可拿到有效 JWT，绕过 TOTP 二次验证。
   - default 分支写入 session，`Approved=false`，由后续接口拦截——但见下条。

3. **第 205-245 行 `GetProfile`**：从 session 取出 profile 后，用数据库用户重建 `UserProfile`，**新结构体未携带任何 Mfa 字段**（零值：Enable=false）。然后 `session.Set("profile", p)` 覆盖原 profile。攻击路径：用户正常登录（session 中 profile 为 Mfa.Enable=true, Approved=false）→ 在未完成 MFA 验证前调用 `GET /sessions`（GetProfile）→ session 中 profile 的 Mfa 字段被清零 → 所有依赖 `p.Mfa.Enable` 判断的中间件/接口视为无需 MFA。**完整的 MFA 绕过链，第二入口即替代通道。**

4. **第 247-270 行 `ListUserNamespace`**：`u.(UserProfile)` 无 ok 检查，未登录时 panic（DoS），属健壮性问题而非注入漏洞。

5. **第 272-345 行 `GetClusterProfile`**：`namespace` URL 参数仅用于 RoleBindings 查询的命名空间限定，label selector 由服务端拼接用户名，无越权读取；管理员直接放行是设计行为。

6. **第 347-360 行 `Install`**：路由注册确认上述入口均可被外部访问（`GET /sessions`、`POST /sessions` 带 authMethod=jwt）。

7. **`saveLoginLog`（第 172-188 行）**：IP 来自 RemoteAddr，仅落库，无 sink 风险。

结论：存在认证绕过类漏洞（MFA 可被绕过），source 是登录凭据/session profile，sink 是 JWT 签发与会话 profile 写回。
