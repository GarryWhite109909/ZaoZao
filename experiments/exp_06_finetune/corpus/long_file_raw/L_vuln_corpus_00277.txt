## 编号分析

**入口点枚举（全文通读）**
本文件是 SeaweedFS 的 S3 远程存储客户端插件，通过 `init()`（第 27-29 行）注册到 `remote_storage.RemoteStorageClientMakers["s3"]`。所有入口均为内部接口方法，source 来自 `remote_pb.RemoteConf`（存储配置）、`remote_pb.RemoteStorageLocation`（路径）和 `filer_pb.Entry`（文件元数据，含用户可控的 `Extended` 扩展属性）。无 HTTP 路由、无环境变量、无回调注入点。

**逐条数据流验证**

1. **第 38-66 行 Make**：`conf.S3Endpoint/S3Region/AccessKey/SecretKey` 直接进入 AWS SDK 配置。这些值来自管理员配置的 remote storage conf（需 filer 管理权限写入），属于受信配置面；且 SDK 会做基本校验。不构成漏洞。
2. **第 76-129 行 Traverse / 第 131-188 行 ListDirectory**：`loc.Bucket/Path` 进入 `ListObjectsV2Input.Prefix/Bucket`。这些是 AWS SDK 的结构化参数字段，非拼接进 URL 字符串，SDK 内部会正确编码；不存在前缀注入扩大列举范围的问题——prefix 本身就是调用方语义的一部分。防御有效（参数化 API）。
3. **第 190-214 行 StatFile / 第 232-242 行 Download / 第 339 行 DeleteObject**：同理，`loc.Path[1:]` 作为结构化 `Key` 参数传入，非 sink 型字符串拼接。安全。
4. **第 220-242 行 ReadFileWithConcurrency**：若 `size <= 0`，第 235 行生成非法 Range 头 `bytes=N-(N-1)`，会导致请求失败或异常行为——属于健壮性缺陷而非安全漏洞（无可控越界读取，Range 由服务端裁剪）。
5. **⚠️ 第 252-301 行 WriteFile —— 标签注入**：当 `conf.S3SupportTagging` 为真时，第 273-277 行将 `entry.Extended` 的键值直接字符串拼接：
   ```go
   tags = tags + k + "=" + string(v)
   ```
   第 287 行将其作为 `UploadInput.Tagging` 上传。S3 的 Tagging 参数是 URL 查询串格式（`key1=value1&key2=value2`）。`entry.Extended` 是文件扩展属性，可由任何有该目录写权限的客户端通过 filer 的元数据接口任意设置。攻击者只需在键或值中放入 `&` 或 `=` 字符（如值为 `a&admin=true&x=y`），即可在未编码的情况下注入额外的对象标签对。这是典型的注入型缺陷（CWE-74 / 编码缺失 CWE-116），黑名单/过滤不存在，属可绕过类别之外的根本性缺失编码。对比第 304-313 行的 `toTagging()` 使用结构化 `s3.Tag` API（SDK 自动编码），说明作者知道正确做法但 WriteFile 未使用。
6. **第 319-337 行 UpdateFileMetadata**：使用 `toTagging()` 结构化 API，安全（与第 5 条形成对照，佐证第 5 条是真实疏漏）。
7. **第 345-383 行 ListBuckets/CreateBucket/DeleteBucket**：bucket 名来自配置/管理操作，进入结构化参数，安全。

**第二入口/替代通道检查**：同一 Extended 数据也流经 UpdateFileMetadata（已用结构化 API），故唯一未防护通道是 WriteFile 的上传标签路径。
