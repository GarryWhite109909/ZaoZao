1. **入口点枚举**：
   - L96-135 `NewBuildCmd`：CLI 参数 `PATH`、`--file`、`--local`、`--output`、`--tag`、`--builder-image`、`--builder-image-pull`、`--update-metadata`、`--validate-metadata`、`--btfgen`、`--btfhub-archive`。

   - L372：环境变量 `SOURCE_DATE_EPOCH`。
   - Docker socket（`client.FromEnv`，L347）作为间接通道。

2. **数据流验证**：
   - **流 A**：`build.yaml` 的 `ebpfsource/wasm/metadata` → `buildCmd()`（L128-149）拼入 make 命令行参数 → `exec.Command`（L246）。这是本地开发者对自己机器执行命令，source 与 sink 同属调用者信任域，无提权边界跨越；且参数以 argv 形式传递而非 shell 字符串拼接，无 shell 注入面。非漏洞。
   - **流 B**：`opts.btfhubarchive` → bind mount Source（L394-398）→ 容器内 `/btfhub-archive`。同样是本地用户自愿挂载自己的目录。非漏洞。
   - **流 C**：`IG_SOURCE_PATH` → `pathHost` → bind mount `/work`（L385-390）。L354-358 用 `strings.HasPrefix(cwd, inspektorGadetSrcPath)` 校验——该前缀检查可被 `/ig-src` vs `/ig-src-evil` 绕过，属于不严谨的校验；但 `IG_SOURCE_PATH` 本身就是运行者自己设置的环境变量，挂载的是运行者本机目录，不存在跨信任边界的攻击者可控输入，故不构成可利用漏洞。
   - **流 D**：`opts.path` → `os.Chdir`（L191-195）。路径遍历无意义——用户本来就有任意文件系统访问权。
   - **流 E**：`opts.builderImage` → `pullImage`/`ContainerCreate.Image`。镜像名由本地用户指定，拉取任意镜像是预期功能。
   - **流 F**：`SOURCE_DATE_EPOCH` → `strconv.ParseInt`（L372-379），已做错误处理，仅影响时间戳字符串。

3. **第二入口/替代通道**：Docker API 通道中所有容器配置均由上述本地输入派生；`helpersFS` 为 embed 只读内容写入 outputDir（L215-228），不可控。

4. **结论**：所有 source→sink 流均在单一信任域（本地运行 CLI 的用户）内完成，无远程攻击者可控输入到达敏感 sink；exec 使用 argv 数组避免 shell 解释；YAML 用 `yaml.Unmarshal` 到强类型结构体，无反序列化代码执行风险。未发现可利用安全漏洞。
