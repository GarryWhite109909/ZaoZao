# 编号分析

**1. 入口点枚举（通读全文）**
- 第 27 行 `constructor(cfg)`：接受外部配置对象 `cfg`，是唯一外部输入入口。
- 第 60 行 `compute(password, salt)`：接受密码与盐（`WordArray|string`）。
- 第 116 行导出的便捷函数 `PBKDF2(password, salt, cfg)`：将三个参数透传给 `PBKDF2Algo.create(cfg).compute(...)`。
- 无路由、无文件 I/O、无环境变量读取、无网络回调——本文件为纯加密库模块。

**2. source→sink 数据流验证**

- **source：cfg 对象**（第 27/33-37 行）。第 32-36 行用 `Object.assign(new Base(), {keySize:128/32, hasher:SHA256Algo, iterations:250000}, cfg)` 合并。攻击者可传入恶意 `iterations`（如 0 或负数）或自定义 `hasher`：
  - 若 `iterations = 0`，第 79 行内层循环不执行，直接返回单轮 HMAC 结果——削弱密钥强度，但这是调用方主动配置，属误用而非漏洞；且默认值已按 GHSA-mpj8-q39x-wq5h 加固为 SHA256 + 250000 次（第 34-35 行）。
  - 自定义 `hasher` 需实现 HMAC 兼容接口，同样需调用方主动注入。
  - `keySize` 过大只影响性能/内存，无安全后果。
- **source：password/salt**（第 60 行）。仅流入 `HMAC.create`（第 64 行）和 `hmac.update(salt).finalize(blockIndex)`（第 74 行），均为纯计算 sink，无 DOM、eval、文件系统等危险 sink。
- **sink 检查**：全文 sink 仅限哈希/HMAC 计算（第 64、74、81 行）、数组异或（第 84-86 行）、`concat`（第 89 行）、`sigBytes` 赋值（第 92 行）。无字符串拼接进 HTML/SQL/shell，无动态代码执行。

**3. 第二入口与替代通道**
- 唯一替代通道是 ES module 导入（第 1-4 行导入 core/sha256/hmac），被导入的依赖本身不含输入解析逻辑。
- 无原型污染面：`Object.assign` 只覆盖实例 cfg 属性，不会污染 `Base.prototype`（除非调用方故意传 `__proto__` 字面量对象，但那是调用方代码问题，且 `new Base()` 作为 target 不受影响）。
- 无回调注册、事件监听、定时器等异步入口。

**4. 已知历史问题核对**
注释第 30-31 行明确引用了 crypto-es 的 GHSA-mpj8-q39x-wq5h（默认迭代次数过低），本实现已通过提高默认值（SHA256、250000 次）修复，属于防御性改进而非残留缺陷。

**结论**：该文件是纯函数式 KDF 实现，所有输入仅进入计算型 sink，不存在 XSS/注入/RCE/反序列化等可利用漏洞；可配置削弱迭代次数属调用方责任，非库本身漏洞。
