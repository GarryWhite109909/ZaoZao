## 编号分析（全文逐函数）

1. **第 1–14 行**：依赖引入。入口点包括 `fs`、`child_process`（sink 所在）、`guessEditor`（读取环境变量 EDITOR/VISUAL，属环境型第二入口）。

2. **第 16–31 行 `wrapErrorCallback`**：仅拼接字符串输出到控制台，无 sink，无注入风险。

3. **第 33–40 行 `isTerminalEditor`**：将编辑器归类为 vim/emacs/nano 等终端编辑器——这些编辑器会解析以 `-` 开头的参数为选项，是后文参数注入的前提条件之一。

4. **第 42–52 行 `parseFile`**：source 点。`file` 参数来自外部调用方（在 vite/create-react-app 场景中即 HTTP 请求路径）。行号列号由 `/:(\d+)(:(\d+))?$/` 提取，仅数字，安全；但 **fileName 本身未做任何字符校验**。

5. **第 58 行 `fs.existsSync(fileName)`**：要求文件真实存在，这是唯一的“防御”，但它不阻止文件名以 `-` 开头或含特殊语义字符。

6. **第 60–64 行**：`specifiedEditor` 若为函数则重排参数——类型混淆防护，无安全问题。

7. **第 66 行 `guessEditor(specifiedEditor)`**：editor 可来自调用方指定或进程环境变量（第二入口），非远程可控。

8. **第 68–75 行 WSL 分支**：仅做路径相对化转换，发生在 Windows 校验之前但平台限定为 linux，与 cmd.exe sink 不交叉。

9. **第 84–107 行 Windows 白名单校验**：`WINDOWS_CMD_SAFE_FILE_NAME_PATTERN` 拒绝 `& | ^ % ! "` 等 cmd 元字符，对 **win32 + cmd.exe 路径** 是有效防御（白名单而非黑名单）。**但该校验仅在 `process.platform === 'win32'` 时执行**。

10. **第 109–115 行参数拼装**：`args.push(fileName)` —— 在非 Windows 平台上，未经任何校验的 `fileName` 直接进入子进程参数数组。

11. **第 117–121 行**：杀掉旧终端编辑器进程，无注入面。

12. **第 123–131 行 sink**：
    - 第 124–127 行：Windows 下经 `cmd.exe /C` 执行，已被第 96 行白名单覆盖；
    - **第 129–131 行：非 Windows 下 `childProcess.spawn(editor, args)`，其中 `args` 含未校验的 `fileName`**。由于 spawn 无 shell，命令注入被阻断，但当 fileName 以 `-` 开头时构成 **参数注入（argument injection）**：结合第 33 行的终端编辑器列表，形如 `-c ...` 的文件名可被 vim 等解析为选项/命令参数，而非文件路径。

13. **第 133–147 行回调**：错误信息回传，无 sink。

**数据流结论**：source = 第 42/55 行外部传入的 `file` → 唯一有效防御是第 84–107 行且仅限 win32 → sink = 第 129–131 行非 Windows 的 `spawn(editor, args)`。POSIX/macOS 路径上 source→sink 数据流完全无校验，存在 CWE-88 参数注入；Windows 路径已有白名单缓解。
