# 全文逐函数安全分析

## 1. 文件结构与入口点枚举

本文件是 Moonraker 的 LDAP 认证组件，全文共 3 个函数 + 1 个工厂函数：

- **`__init__`（第 22–58 行）**：配置加载入口。source 为配置文件项 `ldap_host/ldap_port/ldap_secure/base_dn/group_dn/bind_dn/bind_password/user_filter`（第 24–33 行）。这些值来自 moonraker.conf，属于管理员可控的本地配置，非远程攻击者直接输入；但注意第 27、31 行使用 `config.gettemplate(...).render()`，模板可引用 Jinja 环境变量，仍属受信配置面。
- **`authenticate_ldap_user`（第 60–65 行）**：异步入口点。参数 `(username, password)` 由 Moonraker 的 Web 认证层传入——即 HTTP 请求中用户提交的登录凭据。这是**外部攻击者完全可控的 source**。
- **`_perform_ldap_auth`（第 67–101 行）**：同步 sink 所在函数，接收同一对凭据。
- **`_validate_group`（第 103–115 行）**：仅做组成员比对，无注入面。
- **`load_component`（第 118–119 行）**：工厂函数，无输入。

第二入口检查：除 `authenticate_ldap_user` 外无其他路由/回调/文件读取入口；`logging.debug`（第 71、109 行）中的 username 仅进日志，存在日志注入的理论可能但风险极低且非认证绕过。

## 2. source→sink 数据流逐条验证

**数据流 A：username → LDAP 过滤器（核心漏洞）**

- source：第 60 行 `authenticate_ldap_user(self, username, password)`，username 来自 HTTP 登录请求。
- 流转：第 64 行原样传入 `_perform_ldap_auth`。
- sink 1：第 78 行 `ldfilt = f"(&(objectClass=Person)({attr_name}={username}))"` —— **未做任何转义**直接拼接。
- sink 2：第 80–81 行 `ldfilt = self.user_filter.replace("USERNAME", username)` —— 同样是纯字符串替换，无 `ldap3.utils.conv.escape_filter_chars()` 调用。
- 防御验证：全文搜索确认不存在任何对 username 的过滤、白名单或 `escape_filter_chars` 调用；第 50–52 行仅校验 user_filter 模板含 "USERNAME" 字面量，与输入净化无关。**防御无效**。
- 可利用性：攻击者提交 `username = "*)(uid=*))(|(uid=*"` 即可构造恒真过滤器 `(&(objectClass=Person)(uid=*)(uid=*))(|(uid=*))`，绕过用户枚举限制；进一步可注入任意过滤器条件，实现：
  1. **认证绕过**：若配合 group_dn 校验逻辑缺陷——注意第 92–95 行：当 rebind 失败走新连接分支时，第 94 行 `if self._validate_group(username, user): return` 直接返回成功，而新连接本身能建立即说明密码绑定成功，此分支逻辑尚可；但在 rebind 成功路径（第 88–90 行），只要 rebind 成功即视为密码正确。注入恒真过滤器后，search 返回目录中第一个 Person 条目（第 84 行取 `conn.entries[0]`），随后用该条目 DN + 攻击者已知密码尝试 rebind——若攻击者知道任一有效账户密码即可冒充他人；更严重的是可注入 `objectClass=*` 类条件探测任意属性。
  2. **盲注信息泄露**：通过构造布尔化过滤器（如 `*)(memberOf=cn=admins...`）结合登录成败差异，逐字符提取 memberOf/DN 等敏感属性。
- 错误处理旁证：第 96–99 行将所有 LDAP 异常统一为固定消息，不泄露后端细节，但这不能阻止基于响应时序/成败的盲注。

**数据流 B：password → rebind/new connection**

- 第 87 行 `conn.rebind(user.entry_dn, password)` 与第 91–93 行作为连接凭据使用。password 作为简单绑定凭据由 ldap3 内部处理，不进入过滤器字符串，**无注入风险**；但会以明文经网络传输（第 74 行 `use_ssl=self.ldap_secure` 默认 False，第 26 行配置默认 False）——凭据明文传输属配置性弱点（CWE-319），依赖管理员开启 ldaps，非代码级强制。

**数据流 C：bind_dn/bind_password/base_dn（第 29–38 行）**

- 均来自配置文件，管理员可信输入，不构成远程攻击面；但 base_dn 若被模板渲染引入不可信变量则同样可注入，当前默认无可达路径，不计入结论。

**数据流 D：user.entry_dn → rebind（第 84→87 行）**

- entry_dn 来自服务器响应而非用户输入，不可被客户端直接伪造，无注入。

## 3. 第二入口与替代通道复核

- 无 REST 路由定义于本文件，唯一外部入口是认证调用链；
- `self.lock`（第 59、63 行）串行化认证，无并发绕过；
- 第 80 行 user_filter 替换通道与第 78 行 f-string 通道**均可达同一 sink**，两条通道都缺转义，修复需同时覆盖。

## 4. 结论

存在 **LDAP 注入（CWE-90）**：HTTP 提供的 username 未转义即拼入搜索过滤器（第 78、81 行），可致认证绕过与目录信息盲注。修复：使用 `from ldap3.utils.conv import escape_filter_chars` 对 username 转义后再替换/拼接。
