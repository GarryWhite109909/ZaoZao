## 编号分析

1. **第 20–28 行 `getTemplate`/`mustGetTemplate`**：模板名全部来自硬编码字符串（如 `"create_schema"`），embed.FS 只读，无外部输入，安全。

2. **第 44–52 行 `IngestRvtoolsQuery` / 第 54–62 行 `IngestSqliteQuery`**：`filePath` 参数直接放入 `ingestParams{FilePath: filePath}` 注入模板。**未经过任何转义**（对比其他字段都调用了 `escapeSQLString`）。若模板中形如 `read_xlsx('{{.FilePath}}')`，攻击者可通过含单引号的路径闭合字符串字面量实现 SQL 注入。这是全文唯一未经净化的外部字符串 sink。

3. **第 64–100 行 `VMQuery` 等**：所有 filter 字符串均经 `escapeSQLString` 处理；`NetworkColumns` 由固定循环第 68–71 行生成，无注入面。

4. **第 102–190 行各 Query 函数**：模式一致，`ClusterFilter`、`PowerStateFilter`、`VmIDFilter`、`Category` 均走 `escapeSQLString`；无参数遗漏。

5. **第 192–230 行 `generateOSCaseClauses` / `generateComplexityMatrixCaseClauses`**：数据来自编译期内置的 `complexity.OSDifficultyScores` 与 `ComplexityMatrix` 常量，非用户输入，仅拼接进 LIKE/CASE 子句，安全。

6. **第 236–258 行 `buildVMListFilter`**：对每个 vmID 执行 `strings.ReplaceAll(vmID, "'", "''")` 双写单引号后加引号包裹——这是标准且有效的字面量转义（非黑名单），在 DuckDB 中可阻断引号逃逸。`tableAlias` 仅由调用方传入硬编码 `"i"`、`"v"` 或空串，不可控。防御有效。

7. **第 260–272 行 `buildQuery`**：text/template 默认 HTML 转义不适用于 SQL，但此处参数均已在上游处理；模板内容来自 embed，静态可信。

8. **第二入口核查**：`Limit`/`Offset` 为 int 类型，无法携带 SQL 语法；无环境变量、回调或文件读取入口。唯一薄弱点即第 2 条的 `FilePath`。
