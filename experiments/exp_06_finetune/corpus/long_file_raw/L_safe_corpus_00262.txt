## 编号分析

**入口点枚举（全文）**
1. `SanitizeSQL(sql, args...)`（第 316 行附近）——唯一公开入口，source 为调用方传入的 SQL 模板与参数，sink 为返回的拼接后 SQL 字符串。
2. `NewQuery(sql)` / `Query.Sanitize(args)` —— 同一数据流的分步形式。
3. 无文件、环境变量、网络、回调等其他通道；`pool` 仅是内存复用。

**逐条数据流验证**

1. **占位符解析**：`rawState` 中 `$` 后跟数字进入 `placeholderState`；`placeholderState` 对超大数字做钳制（第 190 行附近注释），防止 int 溢出落到合法索引。`num` 最小为 0 时 `argIdx = -1`，`Sanitize` 第 44 行显式报错 `first sql argument must be > 0`。防御有效。
2. **参数不足/未使用**：第 47 行 `argIdx >= len(args)` 报错；末尾遍历 `argUse` 报错 unused argument，防止参数错位注入。有效。
3. **字符串参数转义**：`QuoteString` 将 `'` 翻倍为 `''`。在 `standard_conforming_strings = on`（PostgreSQL 默认）下这是完备的——反斜杠无特殊含义。函数文档（第 311 行附近）明确声明了该前提条件。注意：若部署环境把 `standard_conforming_strings` 关闭，或 SQL 模板用 `E'...'` 包裹占位符，则参数中的 `\` 可使后续 `'` 失效从而注入——但代码自身不控制服务器配置，且已文档化该限制，属已知前提而非可独立利用的漏洞。黑名单类过滤不存在，全部是状态机精确转义。
4. **字节串参数**：`QuoteBytes` 用 hex 编码 `'\x...'` 形式，hex 字符集内无引号/反斜杠，长度计算与写入一致（`requiredLen` 精确），无越界、无逃逸。有效。
5. **数值/布尔/时间**：`strconv.AppendInt/Float/Bool` 与 time 的固定格式串，均不可能产生引号。有效。
6. **SQL 模板中的引号上下文识别**：`singleQuoteState`/`doubleQuoteState`/`escapeStringState` 正确处理成对引号；`oneLineCommentState`、嵌套感知的 `multilineCommentState` 防止 GHSA-m7wr-2xf7-cm9p 类“注释吞占位符”攻击；占位符前后各写一个空格进一步阻断行注释拼接。有效。
7. **Dollar-quoted 字符串**：`scanDollarQuoteTag` 按 PostgreSQL 词法实现 tag 语法，`dollarQuoteState` 跳过整个 `$tag$...$tag$` 体，防止模板中字面量内的 `$1` 被误替换导致注入。有效。
8. **无效 UTF-8 截断**：各状态的 `RuneError && width != 3` 分支直接终止并截断剩余输入，避免多字节字符尾字节伪造引号（pgx #1380）。有效。
9. **对象池**：`bufPool`/`queryPool`/`sqlLexerPool` 均有 reset 且大小上限，无跨请求状态泄漏（`Query.init` 重置 parts，lexer 整体重置）。无并发漏洞。

**第二入口/替代通道检查**：`NewQuery` 与 `SanitizeSQL` 共享同一 lexer 与转义逻辑，无旁路；`Part` 类型由内部生成，外部无法直接构造非法 Part 进入 `Sanitize`（除非导出字段被滥用，属调用方责任）。

**结论**：在文档声明的前提（standard_conforming_strings 开启，PostgreSQL 默认）下，全文所有 source→sink 流均有有效防御，无可利用漏洞。唯一风险是部署方关闭该配置时的文档化限制。
