- 第 185–216 行：CLI 入口 `rclone serve restic`。

**逐条数据流验证**

1. **路径→文件操作**：第 232–239 行取路径，未做任何规范化或黑名单过滤即作为 remote 传给 `newObject/postObject/deleteObject/listObjects/createRepo`。但该值最终交给后端 Fs 的对象命名空间，跨仓库逃逸取决于后端实现；本文件内未见本地文件系统 sink 直接拼接，不能确证路径穿越。正则 `matchData`（第 362 行）仅用于重写，不构成安全防御。

2. **append-only 写保护（postObject）——确认漏洞**：第 405–414 行先以 `newObject` 检查文件是否存在，不存在才放行；随后第 416 行 `RcatSize` 执行真正写入。检查与写入之间存在明显 **TOCTOU 竞态窗口**：攻击者并发发起两个对同一 remote 的 POST，两个请求都可能通过第 407 行的存在性检查（均返回 not-found），随后第二个请求覆盖第一个已写入的快照数据。在 append-only 模式下这违反了不可篡改承诺，可破坏备份完整性（restic 的安全模型依赖历史数据不可变）。黑名单式“存在才拒绝”不是有效防御。

3. **append-only 删除检查（deleteObject）**：第 437 行用 `strings.Split(r.URL.Path, "/")` 判断倒数第二段是否为 `locks`，而实际操作的 remote 来自第 235 行的 `RoutePath`（可能为转义形式）。两者来源不一致：URL 编码（如 `%2f`）可使 `r.URL.Path` 与 `RoutePath` 呈现不同分段结构，存在绕过判定、删除非锁文件的可能；同时任何位于名为 `locks` 目录下的任意对象都可被合法删除，粒度过粗。此为第二入口/替代通道问题，与第 2 条同属 append-only 防线缺陷。

4. **私有仓库隔离（checkPrivate）**：第 258–260 行比较 URL 参数 `userID` 与认证用户名，逻辑本身一致；未发现绕过证据。

5. **createRepo/listObjects**：第 542 行校验 query 参数，第 491 行校验 Accept 头，均为功能性检查，无安全 sink。

**结论**：核心可证实漏洞为第 405–416 行 append-only 模式的 TOCTOU 覆写竞态，辅以第 437 行基于 `r.URL.Path` 分段判断的可绕过删除白名单。
