## 编号分析（全文逐函数）

1. **入口点枚举**：本文件是 cobra CLI 的 hooks 子命令模块，共 6 个用户入口：`add`（--source、--type）、`remove`（args[0]、--type）、`edit`（args[0]、--type、环境变量 UNIGET_EDITOR/EDITOR）、`list`（--type）、`run`（可变参数 args）、`test`（args[0] 为 hook 名，args[1:] 传给脚本）。另有被 install/uninstall 流程调用的 `runPreInstallHooks` 等四个包装函数（第 300-320 行附近）。

2. **addHooksCmd（约第 60-110 行）**：source→sink 数据流为 `hookSource`（用户本地文件）→ `myos.CopyFile` 复制到 `hooksDir/<type>/<basename>`。文件名取 `strings.Split(hookSource,"/")` 最后一段，无 `../` 注入可能（basename 不含路径分隔符）。hookType 经 switch 白名单校验，非法值时 hookFile 为空串会复制失败。这是用户把自己的脚本安装为钩子——设计意图即如此。

3. **removeHooksCmd / editHooksCmd**：args[0] 拼接路径后用 `filepath.Abs` + `strings.HasPrefix(hookFileAbs, hooksDir)` 做目录限制。该前缀检查确实偏弱（未加路径分隔符，`hooksDirFoo` 可绕过），且未做 Clean 后比较；但攻击者与执行者是同一本地用户（CLI 工具），删除/编辑自己 prefix 下邻近文件不构成提权或跨信任边界攻击。

4. **editHooksCmd 的 exec.Command(editor, hookFile)**（#nosec G204）：editor 来自 EDITOR 环境变量，属用户自身配置，注释已说明这是依赖 EDITOR 的固有模式；参数以切片传递不经 shell，无注入。

5. **runHook（文末）**：`exec.Command(hookFile, args...)` 直接执行钩子文件。钩子文件本身是用户通过 add 放入的脚本，执行它们是该工具的核心功能（uniget 的钩子机制），非漏洞。args 来自命令行，作为 argv 传参不经 shell。

6. **processHooks / 符号链接检查**：`os.Lstat` 错误判断逻辑写反了——Lstat 对普通文件也返回 nil，导致任何存在的钩子都会被误判为 symlink 而报错；正确应检查 `info.Mode()&os.ModeSymlink != 0`。这是一个功能性 bug（可能导致 list/run 异常），但方向是“过度拒绝”，不构成可利用的安全漏洞。

7. **testHookCmd**：hookName 拼接路径后直接 runHook，无前缀校验，理论上可用 `../../` 指向任意可执行文件——但仍是同一本地用户执行自己机器上的文件，无权限提升。

8. **信任边界结论**：所有 source（flags、args、env）到 sink（CopyFile、exec.Command、os.Remove）的数据流均发生在单用户本地 CLI 场景内，攻击者即操作者本人，“能执行任意脚本”是产品声明的设计能力（文档明确说明 hooks 用途）。不存在跨越信任边界的注入、提权或远程触发通道。
