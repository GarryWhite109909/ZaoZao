## 编号分析

1. **入口点枚举（全文）**：该 widget 的 AJAX 入口共 5 个：`onUpload()`（第 344 行起）、`onRemoveAttachment()`（第 246 行）、`onSortAttachments()`（第 256 行）、`onLoadAttachmentConfig()`（第 288 行）、`onSaveAttachmentConfig()`（第 305 行）。另有渲染路径 `render()/prepareVars()` 和配置表单 `getConfigFormWidget()`。所有入口均受后端认证保护（Backend 控制器），但仍需检查越权。

2. **`getFileRecord()`（第 152-170 行）**：source 为 `post('file_id')`。关键防御：查询通过 `$this->getRelationObject()->withDeferred($this->sessionKey)->find(...)`，将查找范围限定在当前 widget 所属关系的文件集合内，防止攻击者用任意 `file_id` 操作他人 `System\Models\File` 记录——这正是 GHSA-3277-h8g9-qj5f 的修复。`onRemoveAttachment` 与 `onLoadAttachmentConfig` 均经此函数，有效。

3. **`onSortAttachments()`（第 256-277 行）**：source 为 `post('sortOrder')` 数组。先用 `withDeferred` 取出合法 id 集合，再 `array_intersect_key` 过滤，保证只重排本关系内的文件；随后调用 `setSortableOrder($ids, $orders)`，orders 仅作为排序整数值写入，无 SQL 注入（ORM 参数化）。防御有效。

4. **`onSaveAttachmentConfig()`（第 305-325 行）**：通过内嵌 Form widget 保存，数据由 `fields.yaml` 定义的有限字段（title/description 等）过滤，且模型为第 2 步限定的记录，不存在任意字段写入或跨对象修改。

5. **`onUpload()`（第 344 行起）**：source 为 `Input::file('file_data')`。验证链：`isValid()`、可选 `extensions:` 规则、可选 `mimes:` 规则、max size。注意：
   - 若开发者未配置 `mimeTypes`，仅做扩展名校验——扩展名黑/白名单可被绕过（如双扩展、大小写），但 Winter 的 `System\Models\File` 存储时对文件名做了处理，且这是框架默认行为而非本代码缺陷；
   - 默认 image 模式允许 svg 上传，svg 可含脚本导致存储型 XSS——属于已知的设计权衡（后台管理员场景），非本次代码引入的可利用漏洞；
   - `Event::fire('backend.formwidgets.fileupload.onUpload', ..., true)` 允许插件接管验证，属正常扩展点。

6. **输出侧**：`decorateFileAttributes` 生成的 path/thumb URL 经 ORM 生成；模板中 prompt 文本经 `e()` 转义（第 216 行），CSS 尺寸来自开发者配置的整数。

7. **第二通道**：`getUploadMaxFilesize` 解析 ini 值无风险；`getAcceptedFileTypes` 仅影响前端 accept 属性与服务端扩展校验，不构成 sink。
