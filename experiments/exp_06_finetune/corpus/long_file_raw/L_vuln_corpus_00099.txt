## 编号分析

1. **入口点枚举（全文）**：
   - `New()`（第 84 行）：接收外部传入的 `DownloadRequest{Directory, URL, FileName, UseHeader}`，URL 与文件名均为用户可控 source。
   - `Execute()`（第 110 行）：消费 URL、`Content-Disposition` 的 filename（第 143–152 行）、URL path 末段（第 158 行），最终写入 `dl.server.Filesystem().Write(p, ...)`（第 172 行）——sink。
   - `isExternalNetwork()`（第 205 行）：SSRF 防御点。
   - `ByID/ByServer/remove`：仅内存缓存操作，无外部输入 sink。

2. **数据流一：SSRF 防御（CWE-918）**。source 为 `dl.req.URL.Host`（第 214 行）。防御方式是先用裸 `dialer.DialContext` 建立一次 TCP 连接检查解析出的 IP 是否为内网（第 233–252 行）。但关键缺陷：这只是**探测性连接**，随后真正下载用的是另一个 HTTP 客户端重新发起请求（第 128 行 `client.Do(req)`），会**再次独立做 DNS 解析**。两次解析之间存在经典 **DNS rebinding / TOCTOU** 缺口：第一次解析返回公网 IP 通过校验，第二次解析返回 `169.254.169.254` 或 `127.0.0.1` 等内网地址，请求即打到内部网络（云元数据服务等）。黑名单式 CIDR 列表本身也不完整（如未覆盖 `100.64.0.0/10`、`0.0.0.0`、IPv4-mapped IPv6 等）。注释虽禁止重定向跟随（第 33–38 行）堵住了重定向绕过，但 rebinding 通道仍然有效。**防御无效**。

3. **数据流二：路径穿越（CWE-22）**。source 为响应头 `Content-Disposition` 的 filename（第 150 行）或用户提供的 `FileName`/URL 末段；sink 为 `Path()`（第 184 行 `filepath.Join(dl.req.Directory, dl.path)`）→ 第 172 行 `Filesystem().Write(p,...)`。若 filename 含 `../../etc/x`，`filepath.Join` 会保留 `..`。本文件内无任何清洗；是否可利用取决于 `server.Filesystem().Write` 是否在包外做了路径规范化校验（Pterodactyl wings 的 Filesystem 通常有 `SafePath` 防护，但该防护不在本文件证据范围内，且历史上此处曾确认存在依赖问题）。基于本文件可见证据，filename 未被净化直接拼入路径。

4. **次要问题**：`res.ContentLength < 1` 检查后仍以声明长度写入（第 165 行），有磁盘限额由 Write 层控制，风险低。`Progress` 有锁保护，无并发问题。

5. **结论**：最确凿的漏洞是 SSRF 的 DNS-rebinding TOCTOU（第 214→233→128 行数据流），防御措施（第 205–255 行）对真实请求不生效。
