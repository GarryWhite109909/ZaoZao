## 编号分析

1. **入口点枚举**：本文件是 Atlantis 的 `atlantis.yaml`（raw 配置）解析/校验模块。Source 是 YAML 反序列化后的 `Project` 结构体字段：`Dir`、`Name`、`Workspace`、`Branch`、`Workflow`、`TerraformVersion` 等；Sink 是 `ToValid()` 产出的 `valid.Project`，后续被 `DefaultProjectFinder` 等用于文件系统路径拼接与 glob 展开。

2. **Dir 字段路径穿越防御（第 96–107 行 validDir，第 176–178 行 ToValid）**：
   - `validDir` 拒绝包含 `..` 的任何字符串（子串检查），并校验 glob 模式语法。
   - `ToValid` 中 `filepath.Clean("./" + *p.Dir)` 保证结果为相对路径。
   - 由于 `..` 在校验阶段即被整体拒绝，Clean 无法被用来“洗白”穿越序列。防御有效。
   - 边缘情况：以 `/` 开头的绝对路径经 `Clean("./"+...)` 会变成绝对路径（如 `/etc/*`）。但该值来自仓库自身的 `atlantis.yaml`——能写入该文件的攻击者本就拥有仓库写权限，可提交任意 Terraform 代码执行，不构成权限提升；且 Atlantis 威胁模型中 repo 配置属半信任输入。不判定为漏洞。

3. **glob 展开通道（第 57–73 行 IsTerraformProjectDir / ContainsGlobPattern）**：模式字符 `*?[` 允许出现在 `dir` 中，但 `..` 已被禁止，无法通过 `*` 组合出 `../` 序列；`name + glob dir` 的组合也被交叉校验禁止（第 128–133 行）。

4. **Name 字段（第 110–118 行 validName，第 158–163 行 validProjectName）**：要求 URL-escape 后不变，排除空格、控制符、引号等；`/` 被替换为 `-`。作为文件名/URL 片段使用时无注入面。

5. **Workspace 字段（第 126–131 行 validWorkspace）**：拒绝 `..`、`/`、`\`，防止 workspace 名参与路径拼接时的穿越。有效。

6. **Branch 正则（第 119–125 行 branchValid，第 180–184 行 MustCompile）**：用户提供的正则被编译并在分支匹配中使用。理论上存在恶意复杂正则的 ReDoS 可能，但 source 是仓库自身配置文件，且 Validate 阶段已确认可编译；Atlantis 对 PR 作者已有信任边界（其可运行任意 TF 代码），风险不成立为独立漏洞。

7. **第二入口/替代通道**：`TerraformVersion` 经 `VersionValidator` 校验后仅传给版本安装器；`PlanRequirements` 等用白名单精确匹配（第 165–183 行），非黑名单，不可绕过；`DependsOn` 为空校验但仅作依赖排序用途，不进 sink。

8. **结论**：所有 source→sink 数据流均有有效防御（`..` 子串拒绝 + `./` 前缀 Clean + 白名单 + URL-escape 校验）；唯一理论边缘（绝对路径 glob）受威胁模型保护，不构成实际漏洞。
