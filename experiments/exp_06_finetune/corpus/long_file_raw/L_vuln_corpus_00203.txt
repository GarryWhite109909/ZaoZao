## 编号分析

1. **第 44–45 行：正则定义**。`ESCAPE_REGEXP = /[&<>\u00A0]/g` 与 `ESCAPE_ATTR_REGEXP = /[&"<>\u00A0]/g` 都带有 **`g`（global）标志**。这是全文最关键的缺陷来源。

2. **第 47–65 行 `escape()`**：先执行 `ESCAPE_REGEXP.test(s)` 做快速路径判断，再 `replace`。带 `g` 标志的正则对象是有状态的——`.test()` 会推进并保留 `lastIndex`。当某次调用匹配成功后 `lastIndex > 0`，下一次对更短字符串调用 `.test()` 会从中间开始扫描，可能返回 `false`，于是走“无需转义”的快速路径直接返回原文，导致 `&`、`<`、`>` 未被转义。

3. **第 67–85 行 `escapeAttr()`**：同样模式，同样的有状态 `test()` 缺陷，属性值中的 `"`、`<`、`>` 可能漏转义，可造成属性上下文逃逸。

4. **第 87–101 行 `attrname()`**：命名空间前缀拼接，无用户可控注入面，正常。

5. **第 103–125 行 `escapeMatchingClosingTag()`**：用 `new RegExp(parentClosingTag, 'ig')` 动态构造正则；`parentTag` 来自 DOM 元素名，domino 的解析器会校验元素名，正则元字符注入实际不可达；且已修复 UTF-16 偏移问题。防御有效。

6. **第 127–140 行 `escapeClosingCommentTag()`**：`CLOSING_COMMENT_REGEXP = /--!?>/` 无 `g` 标志，`test()` 无状态污染；`replace(/(--\!?)>/g, ...)` 覆盖了 `-->` 与 `--!>`。防御有效。

7. **第 142–148 行 `escapeProcessingInstructionContent()`**：替换所有 `>`，PI 内容防逃逸有效；但第 152 行 `kid.target` 未做任何校验/转义即拼入输出——不过 domino 解析器对 PI target 有 Name 校验，程序化创建路径（如 `createProcessingInstruction`）也校验名称，故不可利用。

8. **第 150–190 行 `serializeOne()`**：
   - 第 156–162 行：标签名来自 DOM，受解析器约束；
   - 第 165–168 行：**属性值经 `escapeAttr()` 输出 —— 受第 2 条缺陷影响**；
   - 第 174 行：raw content 元素内文本不转义（符合规范），由 `escapeMatchingClosingTag` 兜底；
   - 第 182–186 行：文本节点经 `escape()` 输出 —— **受第 2 条缺陷影响**；
   - 第 188 行：注释内容经 `escapeClosingCommentTag`，安全；
   - 第 194–205 行：DOCTYPE 的 publicId/systemId 拼接被 `if (false)` 死代码屏蔽，不可达。

9. **数据流结论**：source 为任意进入 DOM 的文本节点/属性值（可含攻击者可控字符），sink 为第 168 行与第 186 行的序列化字符串拼接。由于 `escape`/`escapeAttr` 的有状态 `/g` 正则快速路径可在特定调用序列下误判“无需转义”，攻击载荷可原样进入序列化结果，下游若被当作 HTML 渲染即为 XSS。这是真实存在的逻辑漏洞（该类 bug 在多个库中出现过），但触发依赖跨调用的 `lastIndex` 状态，属于条件性绕过而非无条件注入，风险定为中等。
