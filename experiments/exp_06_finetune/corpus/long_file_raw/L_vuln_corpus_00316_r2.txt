## 三、source→sink 数据流验证

### 数据流 A：`properties[].id` → SQL 查询（第 88/101 → 第 62–64 行）

- Source：第 88 行或第 101 行的 `properties = data.pop("properties", [])`
- Sink：第 62–64 行：
```python
db.query(Property)
.filter(Property.id.in_([prop["id"] for prop in properties]))
```

防御验证：此处使用 SQLAlchemy 的 `in_()` 参数化查询构造器。SQLAlchemy 会将列表中的每个元素作为绑定参数处理，而非字符串拼接，因此即使 `prop["id"]` 含有恶意 SQL 片段（如 `'1) OR 1=1--'`），也只会被当作字面量比较值，无法逃逸出参数化上下文。**该 sink 不存在 SQL 注入**。

但需注意：若 `properties` 元素不是 dict（如传入字符串列表），第 63 行 `prop["id"]` 会抛出 TypeError——这是可用性问题而非安全漏洞；且上游 API 层通常有 Pydantic schema 校验。

### 数据流 B：`data` 整体 → `super().create/update`（第 89–91 / 102–103 行）

- Sink：第 90 行 `super().create(db=db, data=data, ...)` 与第 103 行 `super().update(db=db, data=data)`
- Base 类的 create/update 基于 pydantic schema 验证后映射到固定列（type/content/is_enabled），不存在动态列名拼接，无注入面。
- 潜在关注点：`content` 为 JSONB 列，模板内容含 Jinja 风格占位符（如第 26 行 `{{code}}`）。若管理员可自定义模板内容且渲染引擎使用服务端模板渲染（SSTI），理论上存在风险——但该文件本身不执行任何模板渲染，渲染发生在其他模块，且本文件范围内无证据表明可注入可执行表达式。基于“结论必须基于全文证据”的要求，不能在本文件内判定 SSTI 成立。

将查询结果赋给 relationship 属性，随后第 66 行 `save(db)`。对象均为 ORM 实体，无原始 SQL 拼接，无漏洞。
