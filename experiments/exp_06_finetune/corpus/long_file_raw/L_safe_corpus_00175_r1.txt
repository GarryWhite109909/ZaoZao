## 编号分析（全文逐函数）

**1. 入口点枚举**
- 唯一导出入口：`launchEditor(file, specifiedEditor, onErrorCallback)`（第 44 行）。`file` 来自调用方（通常是开发服务器在用户点击编辑器链接时传入的文件路径），是潜在 source。
- 无路由、无网络监听、无环境变量读取、无回调注入点；`onErrorCallback` 仅被调用（第 55、103、110 行），不被执行为代码。

**2. parseFile（第 32–41 行）**
- 用正则 `/:(\d+)(:(\d+))?$/` 剥离行号/列号，仅做字符串截取，无执行语义，不构成 sink。

**3. 文件存在性校验（第 47–49 行）**
- `fs.existsSync(fileName)` 要求路径真实存在，攻击者无法注入任意不存在的命令字符串作为文件名——这是对 source 的第一道有效约束。

**4. guessEditor / getArgumentsForPosition（第 57、66–70 行）**
- editor 来自本机环境探测或用户显式指定，非远程可控；extraArgs 由行号/列号拼接，正则保证其为纯数字。

**5. 非 Windows 分支（第 96–98 行）**
- 使用 `childProcess.spawn(editor, args, ...)`，数组形式传参，不经 shell 解析，文件名中的特殊字符不会被解释为命令，无注入面。

**6. Windows 分支（第 82–94 行）**
- sink 为 `childProcess.exec(launchCommand, { shell: true })`（第 92 行）。
- 防御链：`escapeCmdArgs`（第 76–78 行）转义 `& | < > , ; = ^`；`doubleQuoteIfNeeded`（第 81–90 行）对含 `^` 或空格的参数整体加引号。
- 结合第 47 行的存在性校验：能到达此处的 fileName 必须是磁盘上真实存在的文件路径。文件系统路径本身无法包含 CMD 元字符组合出可执行的额外命令（含 `&` 等字符的文件名虽可创建，但转义后仅作为字面量传给编辑器程序）。该设计正是注释中引用 CRA PR #4866/#5431 后针对元框架文件名需求所做的权衡方案。
- `_childProcess.kill('SIGKILL')`（第 73 行）与 exit/error 回调（第 99–111 行）只处理进程生命周期与错误信息展示，无二次 sink。

**7. 第二入口/替代通道核查**
- 全文无其他导出、无定时器、无 IPC、无对 `process.env` 的敏感使用；错误消息拼接（第 15、20、105–108 行）仅进入 console 输出，非 eval/exec 类 sink。

**结论**：source（file 参数）到 sink（exec）的数据流受「文件必须真实存在 + 字符转义 + 引号包裹」约束，且非 Windows 平台走 spawn 数组形式，未发现可利用的注入路径。
