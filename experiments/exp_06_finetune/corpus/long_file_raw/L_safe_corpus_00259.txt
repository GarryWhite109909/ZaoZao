## 编号分析

**入口点枚举（全文）**
1. `getData()`（第 21–54 行）：接收外部 `$filters/$sort/$dir/$offset/$limit`，内部调用 `getBaseQuery`。
2. `getColumns(?stdClass $configuration)`（第 56–78 行）：`$configuration` 来自上层控制器反序列化的请求参数，是直接的用户输入 source。
3. `buildQueryString()`（第 80–131 行）：把 `$config['sql']/'from']/'where']/'groupby']` 原样拼入 SQL。
4. `getBaseQuery()`（第 133–194 行）：处理 `$filters`，最终拼接执行。
5. `getAvailableOptions()`（第 196–219 行）：转发到 `getBaseQuery`。
6. `stripSqlCommentsForValidation()`（第 221–228 行）：唯一的“净化”函数。

**逐条数据流验证**

- **流 A：filters → getBaseQuery（第 141–173 行）**：所有 `$filter['property']` 经 `quoteIdentifier`，值经 `quote()`；日期走 `strtotime`。防御有效，无注入。
- **流 B：sort/dir/offset/limit（第 40–48 行）**：`$dir` 白名单化为 ASC/DESC；`$sort` 经 `quoteIdentifier`；`$offset/$limit` 为 int 类型声明。安全。
- **流 C：drillDownFilters（第 116–128 行）**：field 用 `quoteIdentifier`、value 用 `quote`。安全。
- **流 D：config 原始 SQL 片段（第 88、99、106、113 行）→ 黑名单校验（第 64–66、175–177 行）**：
  - 校验仅依赖正则黑名单 `(ALTER|CREATE|DROP|RENAME|TRUNCATE|UPDATE|DELETE)\s`，按题目要求黑名单视为可绕过；
  - 实际可绕过点明确存在：未列入黑名单的 `INSERT`、`SET`、`CALL`、`SELECT ... INTO OUTFILE/DUMPFILE`、`LOAD_FILE()` 等均可通过；例如 `getColumns` 中传入 `configuration.sql = SELECT ... INTO OUTFILE '/var/www/x.php'` 即写文件；
  - `stripSqlCommentsForValidation` 只处理 `/* */` 注释（第 223–224 行），不处理 `--` 与 `#` 行注释，且第 223 行会把 `/*!...*/` 内容还原保留，进一步削弱校验；
  - 第 85–87 行的 `SELECT` 前缀检查只看开头，无法阻止后续子句注入。
- **第二入口确认**：`getColumns` 的 `$configuration` 完全由请求构造（Pimcore 自定义报表控制器将请求 JSON 映射为 stdClass），即使报表定义本身受管理员控制，该入口允许低权限用户提交任意配置片段直达 `fetchAssociative`（第 69 行）sink。

**结论**：存在基于黑名单绕过的 SQL 注入（含任意文件写入风险）。
