## 编号分析（全文通读）

**入口点枚举**
1. `generate()` 第 118 行：外部 source 为 `$name` 与 `$parameters` 数组（通常来自用户请求参数）。
2. `doGenerate()` 第 145 行：接收上述参数、route 定义（tokens/requirements）、`RequestContext`（baseUrl/host/scheme，第 273–283 行）。
3. 静态方法 `getRelativePath()` 第 320 行：纯路径计算，无外部 sink。
4. 无文件操作、无 eval/include、无回调执行点；`array_walk_recursive` 的 caster（第 296 行）仅做类型转换。

**逐条数据流验证**

1. **路径变量**（第 178 行 `$url = $token[1].$mergedParams[$varName].$url`）：先经第 186 行正则校验（requirements），再在第 190 行整体 `rawurlencode` 后还原白名单字符。`/../`、`/.` 在第 192–197 行被显式编码。防御有效。
2. **查询串**（第 300–302 行）：`http_build_query(..., PHP_QUERY_RFC3986)` 全量编码，随后 `QUERY_FRAGMENT_DECODED` 仅还原 `/ ? @ : ! ; , *`，不还原 `%26`(&)、`%3D`(=)，无法注入新参数或截断。防御有效。
3. **fragment**（第 305–307 行）：`rawurlencode` 后同样只还原安全子集，无法注入 `#` 或换行。有效。
4. **Host 变量 token**（第 226–240 行）：这是全文唯一未做编码的 sink——变量值直接拼入 `$routeHost`（第 238 行），最终进入 `$schemeAuthority = $scheme.'://'.$host.$port`（第 283 行）。其唯一防线是第 230 行的 requirement 正则：
   - 正则使用 `'#^...$#i'` 且 **未加 `D` 修饰符**：PCRE 中 `$` 会匹配“结尾换行符之前”，即形如 `evil.com\n` 的值可通过宽松 requirement（如 `.+`）；
   - 当应用调用 `setStrictRequirements(null)` 时（第 110 行允许），第 230 行的校验被完全跳过，任意字符直接进入 authority；
   - 该值若被框架写入 `Location` 响应头，可造成 CRLF 头注入 / 开放重定向（CWE-113 / CWE-601）；`\r` 虽难通过多数 requirement，但 `\n` 因 `$` 语义可绕过。
5. **strictRequirements=false 分支**（第 235–240 行）：校验失败仅记日志并返回空字符串，不产生注入输出，本身安全；但与第 4 点组合时，null 模式是真实缺口。

**第二通道检查**：`_locale`（第 121–130 行）仅用于路由名拼接查找，不进入 URL 输出；`context->getBaseUrl()`（第 285 行）为服务端配置值，非用户可控；`getRelativePath()` 中冒号处理（第 355–357 行）已防 scheme 混淆。均无漏洞。

**结论**：核心缺陷集中在 host 变量 token 未编码 + 校验正则缺 `D` 修饰符 + 可被完全禁用这一条数据流上。
