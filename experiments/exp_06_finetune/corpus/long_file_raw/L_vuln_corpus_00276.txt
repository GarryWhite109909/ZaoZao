## 编号分析（全文逐函数）

**入口点枚举**
- E1：环境变量 `TRESTLE_BLOCK_PRIVATE_IPS`（第 33 行）→ 第 34 行读取，控制私有网段拦截开关。
- E2：`URLSecurityValidator.validate_url(url)`（第 76 行）——外部 URL 输入，SSRF 防线核心。
- E3：`PathSecurityValidator.validate_url_path_for_cache(url_path)`（第 193 行）——缓存路径的 URL path 分量。
- E4：`validate_cache_path`（第 220 行）、`validate_trestle_uri_path`（第 248 行）、`validate_local_path`（第 275 行）、`validate_local_file_path`（第 300 行）。

**数据流与防御验证**

1. **E2→IP 检查（第 76–110 行）**：解析 scheme 白名单（https/sftp，第 99 行）、元数据主机名黑名单（第 116 行）、域名白名单（第 128 行）、DNS 解析后逐一检查 IP（第 84–89 行）。防御结构合理，但存在以下绕过：

2. **IPv4-mapped IPv6 绕过 Tier-1 黑名单（关键漏洞）**：第 88 行 `_resolve_hostname` 用 `socket.getaddrinfo(hostname, None)`，AF_UNSPEC 下对 A 记录可能返回形如 `::ffff:127.0.0.1` 的映射地址。第 90 行 `ipaddress.ip_address()` 将其解析为 **IPv6Address**；第 105 行 `ip_addr in network` 对 IPv6 地址 vs IPv4 网络（如 `127.0.0.0/8`、`169.254.0.0/16`）返回 False 而非报错。因此 loopback/link-local/云元数据 IP 可通过 `::ffff:` 形式完全绕过 ALWAYS_BLOCKED_NETWORKS（第 46–51 行），构成 SSRF（CWE-918）。RFC1918 检查同理失效。

3. **元数据防护依赖主机名字符串黑名单（第 55–60 行 + 第 116 行）**：`100.100.100.200`（阿里云元数据）不在任何被封锁的 IP 网段内（非 link-local），仅靠字面量主机名匹配。攻击者使用解析到该 IP 的任意其他域名（或直接用数字 IP 变体写法经 DNS）即可访问阿里云元数据服务。黑名单式防御可绕过。

4. **DNS rebinding TOCTOU（CWE-367）**：第 70–72 行 docstring 自述“最小化 TOCTOU 窗口”，但验证时解析的 IP 与实际 fetch 时库重新解析的 IP 之间无绑定（未 pin IP），窗口依然存在——验证通过后 DNS 可切换到内网地址。

5. **默认允许私有网段（第 33–34 行 + 第 152 行）**：`TRESTLE_BLOCK_PRIVATE_IPS` 默认关闭，RFC1918 仅告警不阻断（第 178 行），内网 SSRF 默认可达——设计权衡但扩大攻击面。

6. **E3 `'..'` 子串检查（第 209 行）**：纯子串匹配属弱过滤——若上游传入未解码的 `%2e%2e%2f` 则漏检；同时误杀合法文件名（如 `data..v2.json`）。不过 E4 的 `resolve()+relative_to()`（第 237–240、288–291 行）是有效的规范化边界校验，构成纵深防御，故路径遍历实际风险被显著缓解。

7. **敏感文件清单为子串匹配黑名单（第 352–437 行）**：当 `allow_outside_workspace=True` 时仅靠该清单拦截，任意其他绝对路径（如 `/etc/cron.d/x`、`/home/u/.bashrc`）均可读——按设计放行任意文件读取，且 `/Library/` 这类宽匹配易误杀。

**结论**：存在真实可利用漏洞，最严重的是第 2 条（mapped-IPv6 绕过 Tier-1 封锁）与第 3 条（元数据 IP 非网段封锁），叠加第 4 条 rebinding。
