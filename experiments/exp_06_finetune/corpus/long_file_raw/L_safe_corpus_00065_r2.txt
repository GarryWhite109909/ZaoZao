2. **第 36–60 行 `RE_TAG_HTML` / 第 63–70 行 `RE_TAG_LINK_ATTR`**：入口点一——Markdown 渲染后的 HTML 文本中的 `<img src='...'>` 属性是攻击者可控的 source（文档内容）。正则只做解析，不做安全过滤。

3. **第 73–104 行 `repl_path`（核心 sink 所在）**：
   - source：`m.group('path')` 即 img 的 src 值；
   - 第 75–78 行：经 `util.parse_url`/`url2path` 转换；
   - 第 80–83 行：相对路径与 `base_path` 拼接后 `normpath`，绝对路径直接 `normpath`。`../` 目录穿越在此被规范化展开；
   - 第 84–92 行（关键防御）：当 `restrict_path=True` 时，用 `os.path.abspath(file_name)` 与 `root_path + os.sep` 做 `startswith` 前缀校验。由于拼接了 `os.sep`，兄弟目录前缀混淆（如 `/x/docs` vs `/x/docs_evil`）被正确阻止；穿越到根目录之外的路径（如 `../../etc/passwd` 规范化后）会被该检查拒绝并原样返回 link。**注意 `abspath` 不解析符号链接**——若攻击者能在 base_path 内放置指向外部的符号链接，可绕过此检查读取任意文件；但这要求对文件系统的额外控制能力，超出纯 Markdown 输入的威胁模型。
   - 第 93–101 行：sink 为 `open(file_name, "rb")`，但扩展名白名单（png/jpg/gif/svg）限制了内容类型，且文件内容仅作 base64 内嵌返回给渲染结果，无代码执行 sink。
   - 第 102–103 行：裸 `except Exception: pass` 吞掉所有异常——失败时安全降级为返回原始 link，不会跳过限制继续读文件。

4. **第 107–116 行 `repl`**：仅分发，`avoid` 分支跳过 script/style/注释，无新数据流。

5. **第 119–128 行 `B64Postprocessor.run`**：入口点二——配置项 `base_path`、`root_path`、`restrict_path` 来自扩展初始化配置。这些是部署方/开发者显式传入的可信配置，不是不可信用户输入；若部署方主动设置 `restrict_path=False` 或把 `base_path` 设为 `/`，属于配置决策而非代码漏洞。

6. **第 131–155 行 `B64Extension` / `makeExtension`**：默认 `restrict_path=True`，安全默认值正确注册 postprocessor，无其他入口点（无网络、无环境变量、无回调）。
