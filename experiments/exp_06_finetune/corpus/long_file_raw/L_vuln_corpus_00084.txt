## 编号分析

1. **入口点枚举（全文）**
   - 第 60 行 `onKernelRequest`：路由属性 `_live_component`、`_live_action` 来自请求路由配置；随后第 118–124 行处理 `_batch` 动作。
   - 第 129 行 `onKernelController`：校验动作是否被 `#[LiveAction]` 允许。
   - 第 176–216 行 `parseDataFor`：source 为 `$request->query` 的 `props/updated/children/propsFromParent`（GET）与 POST body 的 `data` 字段，产出 `args/actions/props` 等。
   - 第 219、257、276、299 行：View / Exception / Response 监听器，均以 `isLiveComponentRequest`（第 338 行）做门禁。
   - 第 371 行 `parseJsonFromQuery`：仅 JSON 解析，无注入 sink。

2. **source→sink 数据流验证**
   - **流 A**：`_live_action`（第 66 行）→ 第 126 行 `sprintf('%s::%s', $metadata->getServiceId(), $action)` 拼接控制器。类名来自容器服务 ID（非用户输入），方法名 `$action` 用户可控，但第 141 行 `AsLiveComponent::isActionAllowed` 白名单校验拦截——对普通动作有效防御。但注意：默认动作路径（第 84–90 行）设置 `_component_default_action = true`，跳过白名单，不过其方法名取自组件元数据 `default_action`，非用户输入，安全。
   - **流 B（关键）**：第 118 行 `_batch === $action` 时，设置 `_controller = 'ux.live_component.batch_action_controller'` 并标记 `_is_live_batch_action`（第 124 行）。回到第 133–135 行：`if ($request->attributes->get('_is_live_batch_action')) { return; }` —— **直接跳过 `isActionAllowed` 白名单检查**。batch 控制器随后对同一组件发起子请求执行 `actions` 数组中的任意方法名（来自 POST body `data.actions`，第 205 行），子请求中因存在 `_mounted_component` 走第 163–168 行分支覆盖控制器为 `[已挂载组件, 任意action]`，且该检查同样被跳过。即用户可控的方法名在未经验证的情况下作为 `$component->{$method}()` 形式调用（另见第 356 行 `preReRenderMethods` 仅限带属性的钩子，不构成此通道）。这是 source（POST body）→ sink（任意对象方法调用）的完整可利用链。
   - **流 C**：hydrate 数据（第 385–391 行）交给 `LiveComponentHydrator`，本文件内无 sink，依赖 hydrator 自身安全（有 dehydrator 属性白名单），不算本文件漏洞。
   - **流 D**：CSRF 防线在第 344–349 行：依赖 Accept 头 content-type + 同源策略，注释明示；属框架级缓解，但不能阻止上述已认证同源请求内的方法调用绕过。

3. **第二入口/替代通道**：GET query 的 `props` 等同样进入 hydrate，但最终 sink 相同且受 hydrator 约束；`_batch` 是唯一绕过动作白名单的替代通道。

4. **结论**：对应 Symfony UX 已知漏洞（CVE-2024-51736 类似问题）：batch 动作路径完全绕过 `LiveAction` 属性白名单，允许调用 Live 组件上任意公共方法（包括未暴露为动作的内部方法），可能导致信息泄露或状态篡改。
