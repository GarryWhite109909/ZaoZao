## 编号分析

**入口点枚举（全文通读）**
1. 第 20–60 行 `__init__`：所有输入来自 Moonraker 配置文件（`ldap_host`、`base_dn`、`group_dn`、`bind_dn`、`bind_password`、`user_filter` 等），属于管理员可控的静态配置，非外部用户输入。
2. 第 62–67 行 `authenticate_ldap_user(username, password)`：唯一运行时入口，username/password 来自上游认证 API 的请求参数（source）。
3. 第 69–103 行 `_perform_ldap_auth`：核心 sink 所在。
4. 第 105–117 行 `_validate_group`：仅做成员组比对。

**数据流逐一验证**

- **流 1：username → LDAP 搜索过滤器（第 78、80–82 行）**
  默认路径第 80 行使用 `escape_filter_chars(username)` 后再拼入过滤器——这是 ldap3 官方的过滤器转义函数，可中和 `*`( ) \ NUL 等注入字符，属有效防御。
  替代路径第 81–82 行：`self.user_filter.replace("USERNAME", escaped_user)` 同样先经过 `escape_filter_chars` 再替换，因此即使管理员自定义过滤器，插入的 username 也已转义。user_filter 本身是配置文件内容（管理员输入），不构成外部注入面。第 55–58 行还强制校验含 `USERNAME` token。
  结论：LDAP 过滤器注入被有效阻断。

- **流 2：password → 绑定操作（第 87 行 `conn.rebind(user.entry_dn, password)` 与第 94–96 行新连接）**
  密码只作为绑定凭据传给 ldap3 API 参数，从不拼入任何过滤器或 DN 字符串，无注入路径。

- **流 3：`user.entry_dn` → rebind 用户 DN（第 87、93 行）**
  entry_dn 来自 LDAP 服务器返回的条目，而非客户端输入；即便服务器被恶意控制，攻击者本就控制该目录，此非本组件可防御的边界。

- **流 4：错误信息回显（第 84 行 `f"LDAP User '{username}' Not Found"`）**
  原始未转义 username 进入错误消息/日志，理论上存在日志注入（伪造日志行）的次要风险，但不影响认证逻辑，且该消息以 401 返回给已发起请求的调用方，非存储型 XSS 面。属低危信息性问题而非可利用漏洞。

- **逻辑正确性检查**
  第 88–99 行：rebind 失败时新建连接验证凭据并校验组；两条分支中 `_validate_group` 返回 False 时都会落到第 101–102 行抛出 401，不存在绕过认证直接 return 的路径（return 仅在第 95 和 98 行组校验成功后触发）。第 66 行 asyncio.Lock 保证并发下连接参数字典 `conn_args`（第 72 行）不被交叉修改。

- **第二入口/替代通道检查**
  全文无其他路由、文件读取、环境变量或回调入口；配置模板 render 结果均为部署时管理员设定。

**结论**：核心 sink（LDAP 过滤器拼接）有 `escape_filter_chars` 有效防护，密码流安全，认证逻辑无绕过。仅有低危的日志/错误消息中原样回显 username 的信息性问题，不构成可利用安全漏洞。
