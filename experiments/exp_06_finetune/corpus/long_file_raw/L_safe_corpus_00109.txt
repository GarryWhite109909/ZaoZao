# 逐行分析

## 入口点枚举

本文件是 Jenkins 核心工具类 `hudson.util.CopyOnWriteList`（第 33 行），不是 Web 组件。全文无 HTTP 路由、无参数读取、无文件/环境变量访问。唯一的外部数据入口是 XStream 反序列化路径：`ConverterImpl.unmarshal`（第 191–221 行），其输入 XML 由 Jenkins 的 XStream 框架在加载持久化配置（如 config.xml）时传入。

## 数据流验证（source→sink）

**流 1：XML → readItem → items → CopyOnWriteList**
- source：`reader` 中的 XML 子节点（第 195 行 `while (reader.hasMoreChildren())`）。
- sink：`readItem(reader, context, items)`（第 198 行）——这是潜在的反序列化危险点，XStream 历史上可被用于任意对象构造。
- 防御分析：
  - 第 199–207 行：当 `elementType != null` 时做类型校验，非预期类型元素被拒绝并记录到 context，不加入列表。但注意第 176 行的单参构造器将 elementType 置为 null，此时跳过类型检查——不过这仅影响 CopyOnWriteList 自身元素的宽松度，真正的反序列化安全由 Jenkins 全局 XStream 配置（security framework / mapper 白名单）决定，不在此类职责内。
  - 第 209–213 行：捕获 `CriticalXStreamException` 直接抛出；其余 `XStreamException | LinkageError` 通过 `RobustReflectionConverter.addErrorInContext` 收集为错误而非中断——这是容错设计，不会吞掉安全问题导致对象被实例化后继续使用恶意逻辑（readItem 失败的项不会进入 items）。

**流 2：并发语义**
- `core` 为 volatile（第 34 行），写操作均 synchronized（add/remove/addAll），读操作基于不可变快照列表，iterator 持有快照引用（第 88 行）。`replaceBy(CopyOnWriteList)`（第 118 行）直接共享 core 引用，属轻微的共享可变状态风险，但调用方均为内部可信代码，非外部输入驱动，不构成漏洞。
