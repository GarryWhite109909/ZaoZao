# 编号分析

1. **第 1–30 行（类定义与属性）**：`LockTransaction` 是 Composer 依赖解析器的内部类，无 HTTP/CLI 入口点，无路由、无用户参数直接进入。

2. **第 38–46 行（构造函数）**：接收 `Pool`、`presentMap`、`unlockableMap`、`Decisions`，均为内部对象类型，非字符串输入源。

3. **第 48–66 行 `setResultPackages`**：遍历求解器决策结果，通过 `$pool->literalToPackage()` 取回包对象；调用 `ValidatingArrayLoader::validatePackage($package)` 做包元数据校验。数据流为对象→对象，无 sink（eval/exec/include/file write 等）。

4. **第 68–85 行 `setNonDevPackages`**：仅按包名做数组重排，纯内存操作。

5. **第 87–101 行 `getNewLockPackages`**：遍历结果包生成锁文件内容；`$updateMirrors` 为布尔参数。

6. **第 103–143 行 `updateMirrorAndUrls`**：唯一涉及 URL 的代码段。
   - 第 133 行正则 `{^https?://(?:(?:www\.)?bitbucket\.org|...)/}` 白名单限定 dist URL 必须来自 bitbucket/github/gitlab；
   - 第 134 行替换正则 `{(?<=/|sha=)[a-f0-9]{40}(?=/|$)}i` 仅匹配 40 位十六进制哈希并替换为 `$presentPackage->getDistReference()`——dist reference 来自已校验的包对象，且只写入锁文件数据结构，不触发任何下载/执行 sink。即使 URL 来自恶意仓库元数据，此处也不构成注入或 SSRF（不发起请求）。

7. **第 145–170 行 `getAliases`**：遍历别名数组做名称比较与排序，纯数据处理。

8. **第二入口/替代通道检查**：全文件无文件读写、无反序列化、无 shell 调用、无 SQL、无动态 include、无回调执行（`usort` 回调是静态闭包）。该类的输出最终由上层 LockStringWriter 序列化为 JSON 写入 composer.lock，序列化由 json_encode 处理，无注入面。
