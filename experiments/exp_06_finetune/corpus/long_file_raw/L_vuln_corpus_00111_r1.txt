# 全文逐函数安全分析

## 0. 文件定位与整体结构

本文件是 Symfony Monolog 桥接包中的 `ServerLogCommand`（`server:log` 命令），功能是启动一个 TCP 日志服务器，接收网络上传来的日志消息并实时显示。文件共约 130 行，包含以下主要函数/入口点，逐一分析：

1. `isEnabled()`（第 33–43 行）
2. `configure()`（第 45–66 行）
3. `execute()`（第 68–104 行）—— 核心入口
4. `getLogs()`（第 106–124 行）—— 网络数据源
5. `displayLog()`（第 126–135 行）

## 1. isEnabled()（第 33–43 行）

仅检查 `ConsoleFormatter::class` 与 `FormatterInterface` 是否存在，决定命令是否启用。无用户输入参与，无 source→sink 流。无漏洞。

## 2. configure()（第 45–66 行）

定义三个命令行选项：`--host`（默认 `0.0.0.0:9911`）、`--format`、`--date-format`、`--filter`。这些是**第一入口点：命令行参数（CLI operator input）**。此处只做注册，未消费。注意默认 host 绑定 `0.0.0.0`，意味着日志服务器默认监听所有网卡——这本身放大了后续漏洞的可达性（远程攻击者可直接连入 9911 端口）。无直接 sink。

## 3. execute()（第 68–104 行）—— 核心危险函数

### 3.1 第 69–76 行：filter 表达式
`$input->getOption('filter')` 被传入 `ExpressionLanguage::evaluate()`（第 92 行）。这是 CLI 操作者自己输入的表达式，属于受信任的运维人员输入；ExpressionLanguage 本身是沙箱化语言，且输入者即执行者，不构成跨信任边界注入。

### 3.2 第 79–86 行：format / date-format
`$input->getOption('format')` 与 `'date-format'` 直接进入 `ConsoleFormatter` 配置。同样是 CLI 本地操作者输入，输出到本地控制台，不跨越信任边界，风险可忽略。

### 3.3 第 88–91 行：socket 建立
```php
if (!str_contains($host = $input->getOption('host'), '://')) {
    $host = 'tcp://'.$host;
}
if (!$socket = stream_socket_server($host, ...))
```
CLI 输入直接作为传输器字符串。攻击面有限（本地操作者），但默认 `0.0.0.0:9911` 无任何认证，为下述漏洞提供了**远程可达的第二入口通道**。

### 3.4 第 93–101 行：★ 关键漏洞点 ★
```php
foreach ($this->getLogs($socket) as $clientId => $message) {
    $record = unserialize(base64_decode($message));   // 第 95 行
```

- **Source**：`getLogs()` 从网络 socket 读取的每一行 `$message`（见第 4 节分析）。任何能连接到该端口的人（默认 0.0.0.0，无认证、无 TLS、无来源校验）都可发送任意 base64 数据。
- **Sink**：第 95 行的 `unserialize()`。
- **防御验证**：source 与 sink 之间**没有任何过滤、白名单或 `allowed_classes` 限制**。唯一的“防御”是第 97–99 行对解码失败（返回 false）的 continue 处理——这只处理格式错误，完全不阻止成功反序列化的恶意对象图。base64_decode 只是编码转换，不是安全控制。
- **后果**：经典 PHP 反序列化漏洞（CWE-502 Deserialization of Untrusted Data）。若应用依赖链中存在 gadget chain（如 Symfony 自身历史 gadget、monolog handler 链等，phpggc 中有大量针对 symfony/monolog 的链），远程攻击者发送一条精心构造的 base64 日志行即可实现 RCE 或文件删除/SSRF 等。

## 4. getLogs()（第 106–124 行）

无限循环 + `stream_select` 多路复用：
- 第 112–114 行：accept 新连接并加入监听集合；
- 第 115–117 行：EOF 时清理连接；
- 第 118–119 行：`yield (int) $stream => fgets($stream);` —— **这就是网络数据的产生点（source）**。

确认：数据完全来自外部 TCP 连接，无认证握手、无大小限制、无内容校验。次要问题：`fgets` 无长度上限（潜在内存消耗 DoS），以及恶意客户端可通过大量半开连接耗尽 fd，但这些均从属于主漏洞。

## 5. displayLog()（第 126–135 行）

```php
$clientId = unpack('H*', $record['log_id'])[1];
$logBlock = sprintf('<bg=%s> </>', self::BG_COLOR[$clientId % 8]);
```
- 第 128 行：`$record['log_id']` 来自反序列化后的不可信数组。`unpack('H*')` 将其转为十六进制字符串，随后 `% 8` 取模索引固定白名单 `BG_COLOR`（第 12 行常量数组），最终写入本地终端。取模+白名单索引使此处无法越界，风险低。
- 第 133 行：`$this->handler->handle($record)` 将整条不可信 record 送入 ConsoleHandler 格式化输出。理论上存在终端转义序列注入（伪造日志内容欺骗运维人员，CWE-150 类），但相比 RCE 属次要问题，且 record 结构需匹配 handler 才会渲染。

## 6. 第二入口与替代通道核查

- **HTTP 入口**：无。本类仅为 Console 命令，不经 Web 请求触发。
- **第二入口确认**：真正的第二入口就是 **TCP 9911 端口本身**（第 89–90 行建立、第 106 行起消费），它使第 95 行的 `unserialize` 可被**远程匿名**触达——这正是 CVE-2019-10909 之后社区披露的同类问题（Symfony server:log 反序列化，对应 phpggc 的 `Symfony/RCE*` 相关利用场景）。
- **回调/环境入口**：无其他 include、eval、动态调用。

## 7. 结论

核心数据流：**网络 socket（getLogs 第 119 行 fgets）→ base64_decode → unserialize（第 95 行）→ 对象实例化/gadget 触发**。中间零防御，黑名单/正则也不存在（即便存在按规则亦视为无效）。这是一个真实存在的 CWE-502 远程代码执行漏洞（历史上 Symfony 已通过移除 unserialize / 改用 JSON 修复此类代码）。

修复建议：第 95 行改用 `json_decode($message, true)` 并配合发送端 `json_encode`；若必须保留兼容性，至少使用 `unserialize($message, ['allowed_classes' => false])`，并将默认监听地址改为 `127.0.0.1`。
