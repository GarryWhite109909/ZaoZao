## 编号分析

**入口点枚举（全文）**
1. `execute()`（第 152–163 行）：CLI `--mcp` 命令字符串与 `--mcp-env` 环境变量，是唯一外部 source。
2. `apply_to_agent_config()`（第 106–150 行）：第二入口，接受 str 或 dict 格式的 flag_value，dict 路径可携带 `command`、`env`、`timeout`。
3. 无文件读取、无网络输入、无环境变量直接读取、无回调注册。

**数据流验证**

- **流 A：command → shlex.split → basename 白名单 → MCP(command=…)**（第 66 行 → 第 82–88 行 → 第 133–138 行）
  - 防御：第 82 行取 `os.path.basename(cmd)` 后比对 `ALLOWED_MCP_COMMANDS`。白名单本身有效，但存在两个弱点：
    - 弱点 1：basename 校验不校验路径，`../evil/dir/npx` 或任意目录下名为 `npx` 的二进制可通过校验被执行（相对路径绕过）。
    - 弱点 2：白名单包含 `python`、`docker`、`node` 等，这些工具天然可执行任意代码（如 `python -c 'import os;os.system(...)'`），白名单无法阻止其参数层面的任意命令执行——这是设计使然。
  - 但关键上下文：第 12–14 行注释明确声明该 CLI 由开发者本人控制输入（'developers control their own inputs'），source 是本机用户自己的 CLI 参数，攻击者与受害者为同一信任域，故不构成跨信任边界的漏洞。

- **流 B：env_vars → split(',') → env dict → MCP(env=…)**（第 90–96 行 → 第 134 行）
  - 仅注入子进程环境变量，键值均来自用户自身输入，无路径遍历或注入 sink；MCP SDK 内部如何使用 env 不在本文件内，且同样处于同一信任域。

- **流 C：flag_value dict 路径**（第 113–119 行）
  - 与流 A/B 汇合于 `create_mcp_tools()`，防御相同；`timeout` 直接传入 MCP 构造器，无危险 sink。

- **流 D：config['tools'] 扩展**（第 141–146 行）
  - 将 MCP 工具对象加入 agent 配置，属内部对象传递，非序列化/反序列化或 eval 类 sink。

**替代通道检查**：文件内无其他 I/O 入口；`check_dependencies()`（第 44–55 行）仅做 import 探测。

**结论**：所有 source→sink 流的最终 sink 是受用户自身控制的本地进程启动，代码注释明确这是有意设计；basename 绕过（弱点 1）在威胁模型内不构成漏洞，但值得记录为加固建议。
