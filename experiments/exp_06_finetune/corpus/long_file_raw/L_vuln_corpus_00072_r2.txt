## 编号分析（逐函数、逐入口点）

**1. 全局变量与初始化（第 27-37 行）**
- 第 28 行 `oauth2Mgr` 为包级全局，第 30-36 行 `newOAuth2Manager(isShared int)` 根据 `isShared` 参数选择 DB 或内存实现。该参数来自外部配置（本文件未定义来源），仅影响存储后端选择，不构成攻击面。两个分支均无用户可控输入直接进入危险 sink。

**2. oauth2PendingAuth 结构（第 39-47 行）**
- 字段含 `State`、`ClientID`、`ClientSecret *kms.Secret`、`RedirectURL`。注意：这些字段带 json tag，意味着在 DB 模式下（第 96 行 `json.Unmarshal(val, &authReq)`）会从持久化数据反序列化。数据来源是服务器自己加密写入的 session，非直接用户输入，但仍是第二入口点，需验证。

**3. newOAuth2PendingAuth / state 生成（第 49-59 行）**
- 第 50 行 `state := sha256.Sum256(util.GenerateRandomBytes(32))`：state 由 CSPRNG 32 字节经 SHA-256 生成，熵充足，不可预测、不可枚举。这是 CSRF 防护的核心，此处实现正确。

**4. memoryOAuth2Manager.addPendingAuth（第 72-77 行）**
- 以 `pendingAuth.State` 为 map key 写入。key 为服务端生成的随机 hex，无碰撞/覆盖风险（除非攻击者能预测 state，已排除）。加锁正确。

**5. memoryOAuth2Manager.removePendingAuth（第 79-84 行）**
- 按 state 删除。state 为 256-bit 随机值，攻击者无法猜测他人 state 来删除其 pending auth；即使传入任意字符串也只是 delete 不存在的 key，无害。

**6. memoryOAuth2Manager.getPendingAuth（第 86-99 行）**
- 第 90 行按 state 查找；第 93-95 行校验时间差超过 `authStateValidity` 则拒绝。防御链完整：不可猜的 state + 时效校验。无绕过路径——不存在“先查后删”的 TOCTOU 窗口被利用的实际场景（删除与获取均持锁）。

**7. memoryOAuth2Manager.cleanup（第 101-112 行）**
- 遍历删除过期项，条件 `diff < 0 || diff > authStateValidity` 覆盖时钟回拨与过期两种情况。注意：cleanup 的调用点不在本文件内（由外部定时任务触发），若长期不调用，内存中会累积过期条目——但每条目仅在有效期内可被取回（getPendingAuth 有独立时效检查），故不构成安全漏洞，最多是轻微内存占用问题。

**8. dbOAuth2Manager.addPendingAuth（第 116-129 行）**
- 第 117 行先对 ClientSecret 加密；第 119-121 行失败时仅记日志并 return，**静默丢弃**（错误被吞掉），导致该次授权流程静默失败——这是健壮性问题而非漏洞。
- 第 123-128 行构造 Session 写入 dataprovider，Key 为随机 state，Data 含加密后的 secret。`Timestamp = IssuedAt + authStateValidity` 用于后续过期判断。secret 在落库前已加密，无明文泄露路径。

**9. dbOAuth2Manager.removePendingAuth（第 131-134 行）**
- 直接删 session，同上分析，state 不可猜，无越权删除风险。

**10. dbOAuth2Manager.getPendingAuth（第 136-147 行）**
- 第 137 行按 state 取 session；第 141-144 行用 `session.Timestamp < now` 判过期。与内存版等价的有效性校验。**第二入口验证**：session 数据虽来自数据库，但 Key 是 64 位十六进制随机串，攻击者无法枚举或伪造他人 session（除非攻破 DB 本身，超出威胁模型）。

**11. decodePendingAuthData（第 149-162 行）——关键反序列化点**
- 第 151 行类型断言为 `[]byte` 后第 153 行 `json.Unmarshal(val, &authReq)` 反序列化到含 `*kms.Secret` 的结构体。潜在风险是反序列化注入：若攻击者能控制落库的 JSON，可伪造 RedirectURL 或注入明文 secret 结构。但写入端（addPendingAuth）只写服务端构造的对象，且 secret 已加密；GetSharedSession 的 key 不可预测。因此 Unmarshal 的输入不可被攻击者直接影响，不构成可达的 source→sink 流。
- 第 157 行 `TryDecrypt()` 失败会返回错误并使整个请求失败，fail-closed，正确。

**12. 替代通道核查**
- 本文件无 HTTP handler、无路由注册、无环境变量读取、无文件 IO；所有外部交互经由 state（CSPRNG）和 dataprovider 抽象层。回调入口（OAuth2 redirect 处理）不在本文件，但即便上游将用户提供的 `state` 参数传入 `getPendingAuth`，本文件的查找+时效双重校验也能保证只能命中服务端自己签发的记录。
