## 编号分析（通读全文）

**入口点枚举（全文共 6 个公开方法 + 构造函数）：**

1. **第 24–44 行 `__construct()`**：唯一的全局防御是 `if ( ! is_cli()) exit(...)`（约第 27–29 行）。这确保所有方法只能通过命令行触发，HTTP 请求无法到达任何路由。这是有效防御，不是黑名单/正则，而是执行环境硬性判断。

2. **第 46–56 行 `install()`**：无用户输入，调用 `instance->migrate('fresh')` 和 `seed()`。source 为空，无数据流。

3. **第 58–80 行 `migrate(string $type = '')`**：source 是 CLI 参数 `$type`（来自 `php index.php console migrate <type>`），sink 是 `instance->migrate($type)`。攻击者需已具备服务器 shell 权限才能传入；且 CodeIgniter 的 CLI 路由仅将 argv 段映射为方法参数，无 Web 通道。属于受信运维操作，非远程可利用。

4. **第 82–92 行 `seed()`**：无输入。

5. **第 94–112 行 `backup()`**：source 是 `$GLOBALS['argv'][3]`（第 111 行），sink 是 `instance->backup(...)`。路径完全由 CLI 调用者控制——若 `instance::backup` 内部未校验，理论上可写任意目录（CWE-22 类风险）。但前提同样是本地 shell 访问权；拥有 shell 的攻击者本就可直接写文件，故不构成权限提升。

6. **第 114–135 行 `sync()`**：遍历数据库 providers，`filter_var(..., FILTER_VALIDATE_BOOLEAN)` 仅作业务开关判断（非安全过滤），随后 `Google::sync((string)$provider['id'])`。source 是数据库内数据（第二入口/存储型通道），但 id 为整数主键且 sink 是内部同步逻辑，无可利用的注入面；即便 DBA 注入恶意 settings 值，也只影响布尔分支。

7. **第 137–165 行 `help()`**：纯静态输出，`config('version')` 来自代码常量，无输入。

**第二入口/替代通道核查**：该文件定义于 CI 控制器目录，Web 路由理论上可寻址 `/console/install` 等，但构造函数第 27 行的 `is_cli()` 检查在 `parent::__construct()` 之前执行并直接 `exit`，封死了所有 HTTP 入口。未发现 AJAX/回调/环境变量等其他 source。
