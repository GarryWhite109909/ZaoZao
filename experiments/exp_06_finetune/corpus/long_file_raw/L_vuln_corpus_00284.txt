# 逐条分析

## 入口点枚举（全文）

1. **`ai_vision_analyze` 主入口**：`params` 中 `image_path`(L~200)、`image_url`、`prompt`、`provider`、`model`、`api_key`、`max_tokens`、`detail`。
2. **环境变量**：`os.getenv('OPENAI_API_KEY'/'ANTHROPIC_API_KEY')`（L~226）——读取凭据，非攻击面。
3. **文件系统**：`open(image_path, 'rb')`（L~243）。
4. **网络出站**：OpenAI/Anthropic 固定 URL POST；Anthropic 分支中 `session.get(image_url)`（L~345）下载任意 URL。

## 数据流验证

**流 A：`image_path` → `open()`**
- source: params 的 `image_path`；sink: L~243 `open(image_path, 'rb')`。
- 防御检查：仅有 `os.path.exists` 检查，**无路径规范化/白名单限制**。但该模块声明 `required_permissions=['filesystem.read']`，属于工作流引擎的受控模块，工作流作者本身可指定任意路径。若工作流参数来自不可信输入（如 Web 表单），则构成**任意文件读取**：读取 `/etc/passwd` 等后 base64 编码发送给外部 LLM API，数据外泄到第三方。mimetypes 仅决定 media_type，不拦截任何扩展名。**判定为真实漏洞（条件性）**：SSRF/任意文件读取决于平台是否允许不可信用户提交 params。作为开源 workflow 引擎模块，这是常见的高危模式。

**流 B：`image_url` → `session.get(image_url)`（仅 Anthropic 分支）**
- source: params 的 `image_url`；sink: L~345 GET 请求。
- 无任何 scheme/host 校验，无内网 IP 黑名单。**SSRF**：可访问 `http://169.254.169.254/latest/meta-data/`、内网服务，响应体被 base64 后进入 payload 并可能通过错误信息或分析结果回显（响应内容经 LLM 分析输出到 `analysis` 字段——间接回显通道）。OpenAI 分支虽不主动 fetch，但把 URL 交给 OpenAI 服务端 fetch，同样 SSRF（由 OpenAI 出口发起，风险较低）。

**流 C：`api_key` → headers**
- 凭据仅发送至固定官方域名，无泄漏面。

**流 D：`prompt`/`model`/`detail` → JSON payload**
- 经 aiohttp json 序列化，无注入面；`model` 可任意字符串但只影响 API 调用。`detail` 未校验取值，仅传给 API，无害。

**其他**：
- 错误处理将 API 响应 message 拼入异常，信息泄露轻微。
- `resp.json()` 对非 JSON 响应会抛异常，被 except ClientError 捕获不到（JSONDecodeError 不是 ClientError）——健壮性问题，非安全漏洞。
- 无重定向大小限制/超时设置于图片下载——DoS 面（次要）。

## 结论

主要漏洞：**SSRF（CWE-918）**，通过 `image_url` 参数在 Anthropic 分支直接请求任意 URL（含云元数据端点）；次要：**任意文件读取（CWE-22）**，`image_path` 无路径约束，文件内容外发至第三方 API。
