## 编号分析（全文逐函数）

**1. 第 14–27 行：TCP_HANDLERS 注册表**
四个处理器：`_ipp`、`_ipps`（TLS）、`_http`、`_https`（TLS）。注意 `_ipp` 与 `_ipps`、`_http` 与 `_https` 互为前缀包含关系，这为后面的匹配逻辑埋下隐患。

**2. 第 63–95 行：NewAcceptor —— 核心缺陷点**
第 82–90 行：
```go
for svcName, svcHandler := range TCP_HANDLERS {
    if strings.Contains(service, svcName) {
```
- Go 的 map 迭代顺序是**刻意随机化**的。对于服务名 `_ipps._tcp.local.`，`strings.Contains(service, "_ipp")` 与 `Contains(service, "_ipps")` **同时为真**；同理 `_https._tcp.local.` 同时命中 `_http` 与 `_https`。
- 命中哪个完全取决于随机迭代顺序：若先命中非 TLS 版本（`_ipp`/`_http`），则第 85–87 行不会设置 `acceptor.tlsConfig`，本应加密的服务将以**明文 TCP** 处理（TLS 剥离/降级）；且协议解析器也可能错配（如把 IPPS 流量交给按明文 IPP 解析的 handler）。
- 这是典型的“用子串包含做安全相关分发”缺陷（黑名单/模糊匹配式判断不可靠），且结果不确定——同一服务每次启动行为可能不同。

**3. 第 97–101 行：兜底 handler**
未匹配时使用通用 dump 处理器，本身无注入面（仅记录）。

**4. 第 103–140 行：startTCP**
- 第 107 行绑定 `0.0.0.0:%d`，监听所有网卡。该工具本质是局域网欺骗/仿真工具，暴露面是设计使然，但结合缺陷 2，攻击者可主动连上被错误地以明文处理的“应为 TLS”的端口。
- 第 122–135 行：每条连接无条件 `go a.handler.Handle(...)`，**无并发上限、无速率限制、无连接数上限**，远程攻击者可通过大量并发连接造成 goroutine/内存耗尽（CWE-770 资源分配无限制，DoS）。handler 内部逻辑不在本文件，但入口处的无限派生是本文件可证实的。

**5. 第 142–172 行：startUDP**
- 第 152 行固定 4096 字节缓冲读取，`Dump(buffer[0:n])` 仅用于日志输出；n 由 ReadFromUDP 保证 ≤4096，无越界。日志注入（伪造换行）属低危记录问题。

**6. 第 174–181 行：Start**
仅按 proto 分发，无新问题。

**7. 第 183–199 行：Stop**
`ctxCancel` 后等待 `context.Done()` 再 Close listener，关闭顺序正确，无 use-after-close 竞态窗口（Accept 错误由 running 标志抑制）。此函数未见漏洞。
