1. **入口点枚举（全文）**
   - `New()`（约第 130 行）：外部传入 `DownloadRequest{Directory, URL, FileName, UseHeader}`，URL 与 FileName 均为用户可控 source。
   - `Execute()`（约第 160 行起）：发起 HTTP 请求；`Content-Disposition` 头的 `filename` 参数（第 190 行附近）是第二入口（响应头注入的文件名）。

   - `Write(p, r, ...)`（第 225 行附近）：最终磁盘写入 sink。
   - 无其他环境变量/回调入口；`ByID/ByServer/remove` 仅是缓存查询。

2. **SSRF 数据流验证**
   - 防御一：自定义 `DialContext`（init 中），在真实连接建立后解析 `RemoteAddr`，阻断 loopback/link-local 及 `internalRanges`（10/8、172.16/12、192.168/16、169.254/16、::1、fe80::/10、fc00::/7）。该检查基于实际拨号 IP，天然免疫 DNS 重绑定（TOCTOU）——这是有效防御。
   - 防御二：`CheckRedirect` 返回 `ErrUseLastResponse`，完全不跟随重定向，杜绝重定向绕过——有效。
   - **缺口**：黑名单未包含 `0.0.0.0`（未指定地址）。在 Linux 上向 `0.0.0.0` 拨号等价于连接本机回环/本地服务；`0.0.0.0` 不属于 loopback、link-local，也不在 `internalRanges` 任何段内，检查全部放行。用户提交 `http://0.0.0.0:PORT/` 即可触达宿主机本地监听服务，构成 SSRF 绕过。此外也未覆盖广播/组播等其他特殊地址（如 `100.64.0.0/10` CGNAT、`::` 未指定地址），但 `0.0.0.0` 是最直接可利用项。

3. **路径穿越数据流验证（第二入口）**
   - `dl.path` 可来自：(a) 用户提供的 `FileName`；(b) 远端服务器完全控制的 `Content-Disposition: filename`（第 190 行附近）；(c) URL 末段。三者均未做任何 `..` 或分隔符清洗，随后进入 `filepath.Join(dl.req.Directory, dl.path)`。`Join` 只做词法清理不限制向上跳转，`filename=../../../etc/passwd` 形式的值可逃逸目标目录。最终依赖 `Filesystem().Write` 的内部校验（本文件不可见），若该层校验存在则风险被兜底，否则构成任意路径写入。就本文件证据而言，source→sink 链上无有效防御。

4. **其他通道**：重定向被禁用，故无法通过 302 使其访问内网；下载进度/取消逻辑无安全影响；缓存 map 有锁保护，无并发问题。
