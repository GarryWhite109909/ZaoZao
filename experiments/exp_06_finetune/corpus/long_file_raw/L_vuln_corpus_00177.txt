1. **入口点枚举**：
   - CLI 参数：`PATH`（第 96 行 `opts.path = args[0]`）、`--file`、`--output`、`--tag`、`--builder-image`、`--builder-image-pull`、`--btfgen`、`--btfhub-archive`（第 106–117 行）。
   - 文件输入：`build.yaml`（第 141/147 行读取），其中 `ebpfsource`、`wasm`、`metadata`、`cflags` 四个字段均为攻击者可控。

   - Docker daemon 交互：`buildInContainer` 全函数。

2. **source→sink 数据流逐一验证**：

   - **流 A：`conf.CFlags` → 本地 `exec.Command`**（第 233–237 行）。`exec.Command(cmd[0], cmd[1:]...)` 为数组形式，不经 shell，无法注入额外命令。但 `CFLAGS=` 作为单个 make 变量赋值传入，make 会展开其中的 `$(shell ...)`——不过这是构建工具对用户自己源码的固有行为（编译任意 C 源码本身就是代码执行），不构成越权漏洞。
   - **流 B：`conf.CFlags` + 环境 `CFLAGS` → 容器 Cmd**（第 421、442–444 行）。同样作为数组参数传入 Docker，无 shell 注入；容器内执行 make 属设计预期。
   - **流 C：`IG_SOURCE_PATH` 前缀校验**（第 417–420 行）：`strings.HasPrefix(cwd, inspektorGadetSrcPath)` 未加路径分隔符。若 `IG_SOURCE_PATH=/home/user/ig`，而当前目录为 `/home/user/ig-evil`，校验通过，随后 `gadgetRelativePath` 计算错误（TrimPrefix 得到 `-evil`），导致容器内挂载路径 `/work/-evil` 与 WorkingDir 不一致——是路径混淆缺陷，但仅影响构建正确性，且该环境变量由本机用户自行设置，无提权面。
   - **流 D：`opts.btfhubarchive` → bind mount Source**（第 455–459 行）：由本机用户指定，挂载到自己的构建容器，属预期功能。
   - **流 E：`builderImagePull` 白名单**（第 88–91 行）：`slices.Contains` 精确匹配三个合法值，有效防御。
   - **流 F：`SOURCE_DATE_EPOCH`**（第 268–273 行）：`strconv.ParseInt` 严格解析，失败即返回，无注入。
   - **流 G：helpers 文件写出**（第 216–228 行）：文件名来自 embed FS 常量，不可控。
   - **第二入口核查**：`os.Chdir(opts.path)` 后所有相对路径操作均在目标目录内；`filepath.Walk(goFolder,...)` 只读判断。无其他隐藏 sink。

3. **结论**：核心命令执行路径均使用数组式 exec / Docker API，无 shell 拼接；白名单与数值解析防御有效。唯一真实缺陷是第 418 行 `strings.HasPrefix` 缺少分隔符边界检查（路径前缀混淆），风险低。
