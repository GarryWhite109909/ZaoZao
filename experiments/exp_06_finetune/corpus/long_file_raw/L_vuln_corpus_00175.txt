## 编号分析

**入口点枚举（全文）**

1. 第 44 行 `launchEditor(file, ...)`：`file` 为外部传入的文件路径（source，通常来自 HTTP 请求中的 stack frame 文件名），是唯一外部数据 source。
2. 第 45 行 `parseFile(file)`：用第 34 行 `/:(\d+)(:(\d+))?$/` 剥离行号列号——行号列号被正则约束为纯数字（match[1]/match[3] 仅捕获 `\d+`），无注入面。
3. 第 46 行 `fs.existsSync(fileName)`：存在性检查，非安全防御但限制攻击面。
4. 第 57 行 `guessEditor(specifiedEditor)`：editor 来自参数或环境变量（VISUAL/EDITOR 等），属于第二入口（环境通道）。
5. 第 62–68 行：WSL 分支将绝对路径转为相对路径——发生在校验之前，转换后仍需通过后续白名单。
6. 第 78–96 行：Windows 白名单校验 `/^([A-Za-z]:[/\\])?[\p{L}0-9/.\-\\_+ \[\]]+$/u`。该白名单不含 `& | ^ % ! < > "` 等 cmd 元字符，也不含反引号；黑名单式绕过不适用，这是正向白名单且覆盖了 cmd.exe 的全部命令分隔符与变量展开符。注意第 80 行只对 `fileName.trim()` 校验，但首尾空白本身不是 cmd 元字符，不构成绕过。
7. 第 98–102 行：`getArgumentsForPosition` 接收的 lineNumber/columnNumber 已被正则限定为数字。
8. 第 113–116 行（sink）：win32 下 `childProcess.spawn('cmd.exe', ['/C', editor].concat(args))` —— args 中唯一外部可控项是 fileName，已被白名单拦截；lineNumber/columnNumber 为纯数字。
9. 第 118 行（sink）：非 Windows 下 `spawn(editor, args)` 不经 shell，数组形式传参，fileName 不被解释为命令，无注入。

**替代通道核查**
- `specifiedEditor`（第 43 行参数、第 50–53 行函数重载）：在 Windows 上会拼入 `cmd.exe /C`，若攻击者能控制 EDITOR 环境变量可执行任意命令——但这属于本机环境配置，威胁模型上等同开发者自选编辑器，非远程漏洞。
- 回调 `onErrorCallback` 仅做字符串拼接输出到 console（第 9–22 行），无 eval/sink。
- `_childProcess.kill`（第 105 行）：对象方法调用，无注入面。

**结论**：source（file）→ sink（spawn/cmd.exe）的数据流中，Windows 路径由正向白名单有效拦截所有 cmd 元字符；非 Windows 平台使用无 shell 的 spawn；行号列号受数字正则约束。未发现可利用的注入路径。
