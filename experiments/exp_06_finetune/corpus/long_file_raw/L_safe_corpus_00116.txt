## 编号分析（全文通读）

**入口点枚举**
1. `lookupByName(String key)`（第 76–88 行）：source 为 `kvClient.getValueAsString(key)`（第 81 行）——数据来自远程 Consul KV 存储，属于网络来源数据。
2. `lookupByNameAndType` / `findByTypeWithName` / `findByType`（第 90–150 行）：均最终调用 `lookupByName`，是同一 source 的替代通道；`findByType*` 还从 `kvClient.getKeys` 拿到攻击者可控的 key 再触发反序列化。
3. `put` / `remove`（第 152–210 行）：写入路径，`put` 中也调用 `lookupByName` 触发读路径。
4. 构造器 / Builder / setter（hostname、port、deserializationFilter）：配置入口。

**Source→Sink 数据流验证**

- **流 A**：Consul KV 值 → 第 82 行 `decodeBase64` → 第 83 行 `deserialize(postDecodedValue, deserializationFilter)` → 内部第 233 行 `in.readObject()`。这是典型的不可信数据 Java 反序列化 sink。唯一防御是 `ObjectInputFilter`。
- **防御有效性评估**：默认过滤器为第 47 行 `"java.**;org.apache.camel.**;!*"`。该白名单允许全部 `java.*` 包。已知存在纯 JDK 的过滤绕过链：`java.security.SignedObject`（属 `java.**`）其 `getObject()` 会执行一次**不带过滤器**的嵌套 `readObject()`，从而绕过本处设置的 ObjectInputFilter，再配合 classpath 上任意第三方 gadget 类（Camel 生态依赖庞大）可达成 RCE。因此该“白名单”在此威胁模型下不构成有效防御——且题目明确黑名单/宽松过滤视为可绕过。
- **前提条件**：攻击者需能向 Consul KV 写入恶意值（KV 未启用 ACL 或 ACL 泄露时成立），或中间人篡改（连接为明文 `http://`，第 57/66 行硬编码 http，无 TLS，也无任何响应校验/签名）。明文 HTTP 进一步降低了利用门槛。
- **流 B**：key 参数（`$`→`/` 替换，第 78 行）仅影响 KV 路径选择，无命令/SQL 等下游 sink，本身不构成注入。
- **流 C**：`deserializationFilter` 可被调用方通过 setter 放宽甚至置空（置空则完全无过滤，第 226 行判断后直接裸 `readObject`），属于危险的第二配置入口，但默认场景下主要风险仍是默认过滤器过宽。
- **其他检查**：Base64 编解码、锁逻辑、UUID session 名均无独立漏洞；`findByType*` 中对 key 的截取拼接只影响查询路径。

**结论**：存在真实漏洞——来自 Consul KV 的不可信数据在缺少有效反序列化防护的情况下被 `readObject()` 反序列化；默认过滤器允许整个 `java.**`（含 SignedObject 过滤器绕过原语），且传输为明文 HTTP，构成可利用的不安全反序列化（潜在 RCE）。
