# alpha05 缺陷 × alpha06 补样对账（基准 v2_23，2026-09-14）

> 问：从 alpha05 的测试成绩看它有什么缺陷，alpha06 数据集有没有把这些缺陷补好？
> 答：**9 类缺陷里 8 类有对应补样且入册率 73–100%（3394/3631 = 93.5%）；唯独测试里最致命的「类型归因塌缩」不但没补，还被构建脚本系统性强化。**

口径声明：
- alpha05 训据 = `data/final_train_chatml_alpha05.jsonl`（**7972 条**，正 3830 / 负 4142，79 个 CWE）——即 alpha05 实测时用的数据
- alpha06 最新 = `data/final_train_chatml_alpha06_v2_23_candidate_20260914.jsonl`（10000 条，104 个 CWE）
- alpha05 缺陷来源 = `results/弱点挖掘报告_alpha05_rolling_dev_20260824.md` §一~§四、§九、§十一、§十三
- 落地判据 = 代码指纹（剥注释 + 剥 docstring + 归一空白）精确匹配，非行数估算

## 四、唯一没补好的那一个，而且被治反了

### 实测：CWE-77 被构建脚本批量改写成 CWE-78

`scripts/build_alpha06_final_v2_2.py` **L51-52**：

```python
# 仅放行人工审核过的映射（同 v2.1，复用其复核结论）
ALLOWED_REWRITES = {("77", "78"), ("94", "917"), ("94", "1336"), ("1336", "78")}
```

构建时报"类型编号改写 **207** 条（白名单映射）"。

### 跨版本后果

| 版本 | CWE-77 | CWE-78 | 77:78 |
|---|---|---|---|
| **alpha05 训据**（出缺陷的那版） | 174 | 228 | **0.763** |
| alpha06（08-23） | 185 | 225 | 0.822 |
| **alpha06-v2_2（08-25）** | **1** | **437** | **0.002** ← 断崖 |
| v2_7 | 5 | 425 | 0.012 |
| v2_12 | 4 | 424 | 0.009 |
| v2_15 | 8 | 501 | 0.016 |
| v2_17_clean | 8 | 499 | 0.016 |
| v2_19 / v2_22 / **v2_23** | 9 | 511 | 0.018 |

- alpha05 的处方原话（§七）：「**CWE-78 塌缩 → 长尾类型样本配比 + 结论单类型约束强化**」。
- 实际动作：把近邻对的另一侧（77）从 185 条砍到 **1 条**，同时 78 从 6.0% 涨到 **10.7%**。
- 后果：**模型失去 77/78 的判别依据** → alpha05 里"57% 编成 78"的倾向，在新数据上从"倾向"变成"结构性必然"。

**要辩证的一点**：这个映射在**单条标签正确性**上可能站得住 —— 项目自己的笔记把 CWE-77 定义为"非 OS 命令语言注入"（sed/IMAP 等），CWE-78 才是 shell。如果那 185 条原本就该是 78，改判就是错标纠正。

**但即使每条都改对了，净效果仍然与缺陷处方相反** —— 塌缩是"配比"问题，不是"单条标签"问题。团队后来在 9/02 补了 `repair_wave/g26_command_language.jsonl`（真 CWE-77，按 MITRE Observed Examples 形态），这正说明事后意识到 77 被清空了；但只补到 **9 条**，量级上救不回来。

## 五、量级评估：补样能不能盖住结构性问题

| 维度 | alpha05 | v2_23 | 变化 |
|---|---|---|---|
| 总条数 | 7972 | 10000 | +25% |
| CWE 类数 | 79 | 104 | +25 类 ✅ |
| 78 占比 | 6.0% | **10.7%** | **+78% 🔴** |
| 77 条数 | 174 | **9** | **−95% 🔴** |
| 190（整数溢出） | 83 | **65** | −22% 🔴 |
| 441（工具全盲） | 51 | **37** | −27% 🔴 |
| 327（弱加密） | 32 | 67 | +109% ✅ |
| 863（授权） | 2 | 12 | +500% ✅ |
| 862（授权） | 90 | 112 | +24% ✅ |
| 611（XXE） | 112 | 180 | +61% ✅ |
| 1336（SSTI） | 92 | 145 | +58% ✅ |
| 918（SSRF） | 119 | 203 | +71% ✅ |

**读法**：
- 补样对**长尾/盲区类**缺陷有效（327/863/611/1336/918 都显著增长，CWE 类数 +25）。
- 对**配比类**缺陷（塌缩）无效甚至反向（78 +78%、77 −95%）。
- **190 与 441 两个被报告点名要补的，反而净减** —— 需要单独查回（190 是 W4"整数溢出"，441 是 W6"工具全盲 + 他明确要求定向补 30–50 条"）。

## 七、建议

1. **先决问题：77→78 的 207 条改写要复核。** 判据是项目自己的笔记（77 = 非 OS 命令语言注入）。抽样 20 条看原标签是否真错；若多数原本是 shell 注入，映射合法，那 77 就该从别的来源补，而不是回滚。
2. **77 必须补量。** 现状 9 条对 511 条，近邻辨析信息几乎为零。`g26_command_language` 是正确方向但只有 8 条，按 MITRE Observed Examples 再补 30–50 条（与 441 同一个量级要求）。
3. **190 与 441 需要查回**：报告点名要补，实测净减（83→65、51→37）。
4. **`supplement_alpha05_triage` 24 条查明为什么 0 入册**（全负样本，正好补 FP 侧，不该丢）。
5. 配比问题单独出方案：78 现占 10.7%，若要按"长尾再平衡"处理，涉及删/换标 ~300 行，**属破坏性操作，需先出清单再拍板**。
