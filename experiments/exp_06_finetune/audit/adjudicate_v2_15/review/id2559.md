## 教师分析

**分析过程**

1. 第34行 `@PostMapping("/profile/update")` 方法接收 `@ModelAttribute User user`。Spring 的 `@ModelAttribute` 会从 HTTP 请求参数中自动绑定所有与 User 类属性匹配的字段（如 username、email、admin、role），无需显式反序列化。
2. 第37-39行，代码意图是只更新 email 字段，先获取数据库中的 `existing` 对象，再显式复制 email。但 `user` 对象本身已被 HTTP 请求中的 `admin` 和 `role` 参数污染（例如攻击者提交 `admin=true&role=ADMIN`）。
3. 第40行 `saveToDB(existing)` 看似保存的是 `existing` 对象，但第39行仅复制了 email，`existing` 的 admin 和 role 仍是数据库中的安全值。然而，真正的漏洞在于第36行的 `existing = getCurrentUserFromDB(user.getUsername())` —— 如果攻击者同时修改 `username` 参数，就可能操作其他用户的数据（IDOR），但更直接的问题是：**由于 `@ModelAttribute` 直接绑定，攻击者可以通过 `admin` 和 `role` 参数影响 `user` 对象，而开发者在第37-39行误以为只更新了 email，但实际上 `user` 对象已被篡改**——不过这里 `existing` 是从 DB 取的，`user` 的污染并未写入 DB。
4. 关键漏洞点：第34行的 `@ModelAttribute` 自动绑定 + 第39行仅复制 email 的逻辑缺陷。如果开发者在第40行误写为 `saveToDB(user)`（而非 `existing`），则攻击者可直接提权。但当前代码中，真正的可利用点是：**攻击者提交 `username=adminUser&email=attacker@x.com&admin=true` 时，`user` 对象被绑定为 admin=true，而第39行复制 email 后，`existing` 的 admin 仍为 false，因此未直接提权**。
5. 实际漏洞：第34行 `@ModelAttribute` 绑定后，`user` 对象包含攻击者控制的 admin/role 字段，但代码未在服务端重新校验权限。若攻击者通过修改 `username` 参数（第36行 `user.getUsername()`）指向其他用户，则构成 IDOR + 属性注入（CWE-915 Improperly Controlled Modification of Dynamically-Determined Object Attributes
