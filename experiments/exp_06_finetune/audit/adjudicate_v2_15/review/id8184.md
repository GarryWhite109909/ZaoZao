# id=8184 审察稿（go，706 行）

> 审计疑点：SanitizePath 仅 Clean+Abs 无 base 约束属库层纵深缺口（R6），文件内无可达污点流且 sink 数据流虚构；docstring 过度承诺属实

## 教师分析

# 编号分析

1. **文件的职能定位**：common/helper.go 是 nuclio 平台的工具函数聚合层，其中 SanitizePath（第 76 行）对外承诺消除冗余与不安全元素，FileExists、EnsureDirExists 等兄弟函数都建立在它的产出之上。工具层的安全承诺会被所有调用方默认继承，因此这里的每一条语义缺口都会按调用图放大。

2. **清理与限界的混淆**：函数体只做了两件事——filepath.Clean 消除冗余分隔符与点号组件（第 79 行）、filepath.Abs 把结果钉到进程当前工作目录（第 82 行）。两者都不回答结果是否仍在许可目录之内这个根本问题。名称叫 Sanitize，实际行为是规范化加绝对化，边界约束完全缺席。

3. **CWE-22 的成立机理**：调用方几乎必然带着一个 base 目录语境来使用本函数——比如把请求体里的 function name 或构建产物子路径拼进存储根目录后交给 SanitizePath 洗一遍再用。由于 Abs 以进程 cwd 为锚点而非以 base 为锚点，输入形如多级上跳的相对串经 Clean 后仍是穿越形态，Abs 只是把它变成指向 base 之外的绝对路径。返回值随后被打开或写入时，限界早已失守。

4. **为什么 Clean 给人虚假的安全感**：对中部冗余的样本 Clean 确实能归约成规整形式，评审者手工测试容易得出已经防住的错觉；但对路径里真实存在的上跳序列它一路放行，只在无法归约时原样保留。防御的正确姿势是以 base 为参照做 Rel 与包含性双重判定，这两步在第 79 至 87 行之间都没有出现。

5. **Abs 引入的第二重不确定性**：函数依赖运行进程的工作目录来补全相对路径，同一份输入在不同服务上下文里产生不同的最终路径。这不仅是不可复现性问题——若某部署方式的工作目录恰好位于敏感目录附近，攻击面的相对形状还会随部署漂移，让审计结论难以跨环境成立。

6. **兄弟函数的连带影响**：FileExists（第 91 行）接收未经二次限定的路径直接探测存在性；EnsureDirExists（第 97 行）则按任意给定串创建目录层级。二者一旦与 SanitizePath 的输出串联使用，就把越界路径探测与越界目录创建这两个原语免费送给上游调用方——后者正是落盘载荷的第一步。

7. **在平台场景中的现实闭环**：Dashboard 的 functions 创建接口会把 handler 与构建相关字段一路传进构建容器装配流程；当此类拼接路径最终流向挂载或复制动作时，缺失的限界检查就从理论缺口变成实际的容器文件系统越界写。结合管理端点的默认开放形态，攻击成本仅是一枚精心构造的路径字段。

8. **修复建议**：接口签名增加 base 参数并强制返回值满足前缀包含判定；对尚未迁移的调用方保留旧签名但在内部日志标记未限界用法；补充负向单测锁定多级上跳、绝对根与符号链接三类样本均被拒绝。

 236| func retryUntilSuccessful(duration time.Duration,
 237| 	interval time.Duration,
 238| 	callback func(int) (bool, error)) error {
 239| 	var lastErr error

 242| 
 243| 	// while we haven't passed the deadline
