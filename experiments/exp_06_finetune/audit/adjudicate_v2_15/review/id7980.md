# MCPHandler 安全分析

## 一、文件结构与入口点枚举（全文通读）

本文件共约 150 行，定义单一类 `MCPHandler(FlagHandler)`，包含以下函数，逐一分析：

## 二、逐函数 source→sink 数据流验证

### 2.1 入口点一：`execute`（第 154-167 行）

- **Source**：参数 `command: str = None`、`env_vars: str = None`。该类是 CLI flag handler，`command` 直接来自用户命令行 `--mcp "..."` 参数（见模块 docstring 第 1-4 行的用法示例），属于**完全用户可控**的外部输入。
- **Sink**：第 166 行 `return self.create_mcp_tools(command, env_vars)`。
- **防御检查**：仅有第 160-161 行的空值判断 `if not command`，这是存在性校验而非安全过滤。**无任何白名单/黑名单/路径校验**。

### 2.2 入口点二：`apply_to_agent_config`（第 115-152 行）

- **Source**：`flag_value`（第 119 行），可为字符串或 dict（dict 的 `command`/`env`/`timeout` 键均来自外部配置）。
- **数据流**：
  - 字符串分支：第 124 行 `self.create_mcp_tools(flag_value)`；
  - dict 分支：第 126-130 行 `create_mcp_tools(flag_value.get('command',''), flag_value.get('env',''), ...)` —— dict 值未做任何类型或内容校验即传入。
- **防御检查**：无。dict 分支甚至允许 `command` 为任意字符串。
- **第二入口确认**：此函数绕过 `execute` 的空值检查逻辑（虽然也有 `if not flag_value` 判断），构成同一 sink 的替代通道。

### 2.3 核心解析：`parse_mcp_command`（第 50-77 行）

- 第 61 行 `parts = shlex.split(command)`：shlex.split 仅做**词法切分**，防止 shell 引号歧义，但**不限制可执行内容**——任意二进制路径、任意参数均可通过。
- 第 63-64 行：`cmd = parts[0]`、`args = parts[1:]`，直接取第一个 token 作为待执行程序名。
- 第 68-73 行环境变量解析：`KEY=value` 对直接写入 env dict，无键名合法性校验（如可注入 `LD_PRELOAD=...` 等危险变量）。
- **结论**：此函数是透传层，无有效防御。

### 2.4 核心 Sink：`create_mcp_tools`（第 79-113 行）

- 第 92 行：`cmd, args, env = self.parse_mcp_command(command, env_vars)`。
- 第 96-101 行：
  ```python
  mcp = MCP(
      command=cmd,
      args=args,
      env=env if env else None,
      ...
  )
  ```
  这是明确的 sink：MCP 客户端将以 `cmd + args + env` **启动子进程**（stdio transport 的标准行为，即 subprocess 执行）。
- **防御有效性评估**：
  - 第 85-86 行 `check_dependencies()`：功能可用性检查，非安全控制；
  - 第 94-95 行 `if not cmd`：空值检查，非安全控制；
  - 全函数**没有任何对 cmd 的白名单校验**（例如限定为已知 MCP server 包名）、没有禁止绝对路径/相对路径遍历、没有对 env 键的黑名单（如 LD_PRELOAD、PATH 劫持相关变量）。
  - 即使假设底层有 shlex 处理，本任务判定标准明确：黑名单/正则视为可绕过；此处连黑名单都没有。

### 2.5 攻击场景推演

由于该 handler 面向 CLI 终端用户，攻击面取决于调用上下文：

1. **本地 CLI 场景**：用户运行 `praisonai --mcp "rm -rf /"` 即可执行任意命令——但这本质上是“用户在自己机器上执行自己输入的命令”，与 shell 本身等价，通常不被计为独立漏洞（除非工具被用于代他人执行 prompt 的场景）。
2. **间接注入场景（真实风险）**：若 `--mcp` 值来自配置文件、远程同步的 agent 配置、或 LLM 生成的计划被回灌到 `apply_to_agent_config`（第 119 行 dict 分支支持从结构化配置注入），则任何能影响该配置的一方均可实现**任意代码执行**。docstring 中 `--mcp-env "BRAVE_API_KEY=xxx"` 表明 env 可携带敏感凭据，且第 68-73 行允许注入任意进程环境变量（如 `LD_PRELOAD` 指向恶意 .so），进一步扩大影响。
3. **错误信息泄露**：第 105 行 `print_status(f"Failed to connect: {e}")` 将异常细节打印，属低危信息泄露。

综合判断：source（用户/配置可控的 command 与 env）到 sink（第 97-101 行 MCP 子进程启动）之间不存在任何有效防御措施，构成 CWE-78（OS Command Injection）/ CWE-77 风格的任意命令执行链。考虑到 CLI 工具的设计意图本身包含执行用户提供的服务器命令，风险定级为中等偏高（在多租户/自动化/配置驱动场景下为高危）。

### 2.6 第二入口与替代通道核查结论

- 替代通道 1：`apply_to_agent_config` dict 分支（第 126-130 行）——确认可达同一 sink；
- 替代通道 2：`execute` → `create_mcp_tools`（第 166 行）——确认可达；
- 无其他隐藏入口（文件内无路由、无回调注册、无环境变量读取）。
