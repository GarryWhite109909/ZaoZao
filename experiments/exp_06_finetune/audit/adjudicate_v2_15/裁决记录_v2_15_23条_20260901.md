## 3. B 类改写要点（4 条，assistant 全文重写）

- **1108（502→safe）**：L34 `JSON.parse` 只构造纯数据对象（无类实例化/gadget 面），非 CWE-502 sink；L40-44 HMAC 校验存在；L53 特权分支（L55）与普通路径（L61）执行同一 `updatePassword(tokenData.userId, newPassword)`，特权分支仅多 `revokeAll(本人 token)`——"反序列化提权"不成立。保留签名覆盖缺口（sig 仅绑定 userId，未覆盖 role/forceReset）作为设计加固注记：在本文件内注入 role/forceReset 无提权收益。
- **8184（22→safe）**：SanitizePath（L76）仅 Clean+Abs、确无 base 包含性校验，但本文件为库层、文件内无攻击者可控 source；FileExists（L91）/EnsureDirExists（L97）分别为存在性探测/建目录，非内容读写型 sink；教师"Dashboard 构建接口路径拼接流向挂载"发生在文件外，按文件内污点流口径不可采信。记库级加固建议（base 参数+前缀包含断言）。
- **6347（false→CWE-798）**：L6 `app.secret_key = 'super_secret_key'` 为硬编码密钥字面量，违反系统判定规则 2。攻击者从公开源码取得密钥后可离线伪造任意 session cookie（含 csrf_token 字段），L11-12 `compare_digest` 读到的 expected 即伪造值——CSRF 防御被整体架空；compare_digest 本身是正确防御（保留说明），问题在密钥来源。sink 锚 L6（赋值即框架隐式 sink 生效点）。
- **2559（915→CWE-639）**：L36 `@ModelAttribute User user` 绑定含 admin/role，但 L39 仅复制 `user.getEmail()` 到 DB 加载的 existing、L42 `saveToDB(existing)`——提权字段被中和，mass assignment 为 near-miss（explanation 注记，不定级）。真实漏洞：L38 `getCurrentUserFromDB(user.getUsername())` 以请求参数定位目标记录且无所有权校验 → 攻击者传任意 username 可改写其邮箱（L39 写入、L42 持久化）→ CWE-639 水平越权，High。
