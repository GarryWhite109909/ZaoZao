## 四、learner_v3 的一处口径过宽（L15）—— 本轮实际踩到

**L15 原文**：
> 通道别只看 HTTP 参数——配置文件、环境变量、命令行参数、stdin、文件流、DB 回读、内部 API 传参都算，我以前漏报最多的就是这些

**teacher 追加层四 R2/R3**：
> R2. CLI 参数、环境变量：仅本机使用者/部署者可控，**本身不是攻击面**；仅当值被转发到其他攻击者可达上下文时才成立
> R3. 配置文件：同 R2；除非文件内可见"配置值来源于请求/上传"

**冲突点**：L15 把"通道"与"攻击者可控"混在一句里。它的意图是对的（**别漏非 HTTP 入口**，W5），但缺了第二层（**这个通道的值最终是谁控制的**）。教师拿到两种说法会在"CLI 参数算不算攻击面"上摇摆。

**本轮实际后果**：我按 L15 设计的 g27 首批，**16 条里 13 条的 source 是"函数参数 + 注释写'来自报表配置界面/运维面板'"**。按 R2/R3/R4，这 13 条会被判 safe 或降级——batch 作废。复审 agent 没抓到（它没对照 R2/R3/R4）。

**修法（已执行）**：把 13 条的 source 全部换成**文件内可见且属于 R1 的攻击者可达非 HTTP 通道**——上传的模板/配置文件、消息队列 payload、租户经 API 写入的 DB 记录回读、内部 API 请求体。这同时满足 W5（别漏非 HTTP 可控源）和 R2/R3（别把本机信任域当攻击面），而且**更真实**——真实世界的非 HTTP 污点源就是这么进来的。

**对 learner L15 的具体改法建议**：

```
现在：通道别只看 HTTP 参数——配置文件、环境变量、命令行参数、stdin、
     文件流、DB 回读、内部 API 传参都算，我以前漏报最多的就是这些

建议：通道别只看 HTTP 参数——上传的配置/模板文件、消息队列 payload、
     DB 回读的其他用户记录、上游服务响应体、stdin、内部 API 传参都算
     （我以前漏报最多的就是这些）。但每个非 HTTP 通道都要在代码内论证
     值最终来自攻击者可达的上下文；CLI 参数与环境变量若只由本机使用者
     提供，本身不是攻击面（那是我自己跑的），除非它们被转发到
     攻击者可达的上下文（如服务端代执行）。
```
