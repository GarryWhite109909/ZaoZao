# AcuityAds 适配器安全分析

## 一、入口点枚举（全文通读）

本文件为 Prebid Server 的 bidder 适配器，共包含以下函数与潜在入口：

1. **Builder**（第 21-29 行）：接收 `config.Endpoint`（来自服务端配置文件，非用户输入），解析为模板。
2. **getHeaders**（第 31-50 行）：从 `openrtb2.BidRequest` 提取 Device.UA / IPv6 / IP 写入出站请求头。
3. **MakeRequests**（第 52-83 行）：处理入站竞价请求，读取 `Imp[0].Ext`、构建 URL、序列化请求体。
4. **getImpressionExt**（第 85-101 行）：反序列化 imp.Ext 与 ext.bidder。
5. **buildEndpointURL**（第 103-110 行）：校验 Host 并做宏替换生成出站 URL。
6. **checkResponseStatusCodes**（第 112-134 行）：仅检查状态码，无数据流。
7. **MakeBids**（第 136-176 行）：解析 bidder 返回的响应体并转换为内部 bid。
8. **getMediaTypeForImp**（第 178-191 行）：按 ImpID 匹配媒体类型。

## 二、逐条 source→sink 数据流验证

### 流 1：`imp.Ext` → `acuityAdsExt.Host/AccountID` → 出站请求 URI（SSRF 候选路径）

- Source：外部竞价请求中攻击者可控的 `Imp[0].Ext`（第 61 行传入，第 85-100 行解析）。
- Sink：`MakeRequests` 第 68 行 `Uri: url`，即向该 URL 发起 HTTP POST。
- 防御：第 104-106 行调用 `urlutil.IsSafeHost(params.Host)`。这是 Prebid Server 框架级白名单校验（对照配置中的 host 列表，且拒绝 IP 字面量/内网地址），属于**白名单而非黑名单/正则**，是有效防御。宏模板本身由管理员配置（第 23 行），非用户可控。
- 结论：SSRF 被有效阻断。注意即使绕过 Host 校验，AccountID 仅插入模板占位符，模板由可信配置定义，注入面有限。

### 流 2：`Device.UA / IPv6 / IP` → 出站请求头（头注入候选路径）

- Source：第 37-46 行，攻击者可控的 UA/IP 字符串通过 `headers.Add` 写入 User-Agent 与 X-Forwarded-For。
- Sink：HTTP 客户端发送这些头。
- 分析：Go 的 `net/http` 在写入 header 时会拒绝含 CR/LF 的非法值（Header 值含换行会导致传输错误或被过滤），Go 标准库自 1.x 起 `http.Header.Write` 对值做了净化。因此经典 CRLF 头注入不可行。将 IP 写入 XFF 属于业务设计（透传真实 IP 给 bidder），非漏洞。
- 结论：无有效利用路径。

### 流 3：`responseBody` → `openrtb2.BidResponse` → 内部 bids（响应伪造/注入候选路径）

- Source：第 145 行 bidder 返回的原始 Body。
- Sink：第 147-149 行 `jsonutil.Unmarshal` 到强类型结构体；第 168-171 行逐 bid 构造 TypedBid。
- 分析：JSON 反序列化到固定 schema，无 eval/SQL/exec 类 sink；bid 内容后续由框架的 creative 渲染层另行处理（不在本文件）。未校验 `bid.ImpID` 是否存在于原请求（第 168 行 getMediaTypeForImp 匹配失败时默认返回 Banner，第 190 行），这可能导致媒体类型误判，但属于功能正确性问题，不构成可利用的安全漏洞。
- 结论：无 sink 可达的危险操作。

### 流 4：`config.Endpoint` → 模板 → URL

- Source 为服务器端配置文件，信任边界内；使用 `text/template` 但模板内容不含用户输入执行逻辑，仅 `macros.ResolveMacros` 替换 Host/AccountID 占位符（第 108-109 行）。
- 结论：无可控注入。

### 第二入口与替代通道检查

- 本适配器唯一对外入口是 MakeRequests/MakeBids，均经框架路由调用；无环境变量、文件读写、回调注册等其他通道。
- 第 63 行 `openRTBRequest.Imp[0]` 未检查 len(Imp)==0，空 Imp 数组会触发 panic（索引越界）。Prebid 框架在进入 adapter 前已保证至少一个 impression，故实际不可达；即便可达也仅为 DoS 自身请求处理，属健壮性缺陷而非安全漏洞。
- 第 96 行 `imp.Ext = nil` 修改了共享的入站对象——若框架并发复用该对象可能产生竞态，但 Prebid 中每个请求独立实例化，不构成漏洞。

## 三、结论

所有 source→sink 数据流均有有效防御或不可达 sink：Host 白名单阻断 SSRF，Go http 库阻断头注入，JSON 反序列化无危险 sink。未发现可利用的安全漏洞。
