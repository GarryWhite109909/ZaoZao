## 1. `Configure()`（第 32–35 行）

## 2. `SetCookie()` / `setCookie()`（第 38–79 行）

数据流：`val`（JWT，由上游认证流程生成，非直接用户输入）→ 构造 `http.Cookie{...}`（第 48–56 行）→ `http.SetCookie`。

关键点逐一验证：

- **Domain 来源**：第 44 行 `domains.Matches(r.Host)`——Host 头是攻击者可控的。若 `domains.Matches` 对未匹配域名返回空串或严格白名单匹配，则无 cookie 注入到任意域的风险；且 Go 标准库 `http.Cookie.String()` 会拒绝含非法字符的 Domain（含空格/逗号等会触发 sanitize 或忽略该字段）。此外第 45–47 行允许配置覆盖 domain，属管理员信任边界内。

结论：此函数 sink 无可被外部输入污染的注入路径。唯一理论弱点是若 `cfg.Cfg.Cookie.Domain` 配置过宽（如 `.example.com`）导致子域共享，但这是部署配置问题而非代码漏洞。

## 一、整体定位与入口点枚举

本文件是 OCI 运行时规范生成相关的辅助代码（典型来自 containerd/nerdctl 类项目），核心职责是：根据用户传入的 `username` 字符串（如 `--user 1000:1000` 或 `--user nobody`）在容器 rootfs 内解析出 UID/GID/补充组，并写入 spec。全文共 8 个函数/类型：`GetUser`、`ParseUIDGID`、`openUserFile`、`limitedReadCloser.Read`、`parseUID`、`WithUIDGID`、`setProcess`、`ensureAdditionalGids`。

**外部可控输入（source）清单：**
1. `GetUser(root, username)` 的 `root` 参数——容器 rootfs 路径，由调用方（镜像解包目录）决定；

3. `/etc/passwd` 与 `/etc/group` 文件内容——容器镜像内文件，属于半可信数据（镜像作者控制）；
4. `WithUIDGID(uid, gid, sgids)` 的三个参数——来自 `GetUser` 的返回值或调用方直接传入。

**sink 清单：**

- S2：`s.Process.User.UID/GID/AdditionalGids`（第 106-108 行）——OCI spec 写入，最终影响进程运行身份。

## 二、逐函数分析

### 1. GetUser（第 20-46 行）

- 第 21-25 行：`username == ""` 时置为 `"0"` 并标记 `isDefault`。空串是默认路径，无注入面。
- 第 27-29 行：先走 `ParseUIDGID` 快速路径。若形如 `uid:gid` 纯数字则直接返回，不触碰文件系统。
- 第 31-37 行：否则打开 rootfs 内的 `/etc/passwd` 与 `/etc/group`。注意第 32-35 行的写法：即使 `openUserFile` 失败，`passwdFile`/`groupFile` 保持 nil，随后传给 `user.GetExecUser`（moby/sys/user 库可容忍 nil reader）。这是健壮性处理而非安全问题。
- 第 39-44 行：解析失败时若 `isDefault` 则回退到 `0:0`；否则返回错误。错误直接上抛，未泄露敏感信息（仅含 moby/user 库的标准错误文案）。

**source→sink 验证：** `username` → `user.GetExecUser`。moby/sys/user 的 `GetExecUser` 对用户名做的是查表匹配 + 数字解析，不存在 shell 执行或 SQL 类 sink；即便 username 含特殊字符（如 `:`、换行），最坏结果是解析失败返回错误，不会逃逸出解析器。**无有效攻击路径。**

### 2. ParseUIDGID（第 49-63 行）

- 第 50-52 行：空串返回零值（注意这里返回 `(0,0,nil)` 即成功，与 GetUser 第 28 行配合：空串已被提前拦截不会走到这里，但独立调用时语义是“合法的 0:0”，属设计选择非漏洞）。
- 第 53 行：`strings.SplitN(str, ":", 2)` ——限制分割次数，防止多冒号字符串产生多余部分被忽略后误用；`uid:gid:extra` 中 `extra` 会被并入 parts[1] 导致 `parseUID("gid:extra")` 失败，行为安全（fail-closed）。
- 第 55-61 行：两段分别经 `parseUID` 校验，任一失败即整体失败。**纯数字白名单式解析（strconv.ParseUint），无绕过空间。**

### 3. openUserFile（第 66-89 行）—— 关键路径穿越审查点

这是本文件唯一涉及文件系统访问的函数，必须严格验证：

- **source**：`root`（容器 rootfs 根）、`p`（固定常量 `/etc/passwd` 或 `/etc/group`，见第 33、34 行调用点——均为硬编码字面量，非用户输入拼接）。
- **防御 1（第 68-71 行）**：`fs.RootPath(root, p)` 是 continuity 库的标准安全路径连接函数，其内部实现会清理 `..`、拒绝绝对路径逃逸、确保结果仍位于 `root` 之内。此处 `p` 本身就是固定的 `/etc/passwd`，不含任何用户可控成分，因此即使 `RootPath` 存在理论缺陷，也没有可注入的路径分量。**双重保障：p 是常量 + RootPath 防护。**
- **防御 2（第 77-81 行）**：`f.Stat()` 后强制 `info.Mode().IsRegular()` 检查——阻止将符号链接目标、FIFO、设备文件（如 `/dev/mem` 类）作为 passwd 读入。这防住了“镜像内 /etc/passwd 是指向宿主敏感文件的 symlink”这一经典 TOCTOU/链接攻击面。注意：symlink 若指向 rootfs **内部**的常规文件仍会被打开，但这正是预期语义（读取容器自己的 passwd），不构成越权。
- **残余风险讨论**：Stat 与后续 Read 之间存在理论上的 TOCTOU 窗口（文件在检查后被替换为非常规文件）。但该窗口要求攻击者已能在容器 rootfs 内并发修改文件——此时攻击者本就控制了镜像内容，权限边界未被跨越；且下游 `limitedReadCloser` 有大小上限兜底。**判定为不可利用。**

### 4. limitedReadCloser（第 92-107 行）

- 第 97-99 行：`io.LimitedReader{N: maxUserFileBytes + 1}`，即最多允许读 10MiB+1 字节。
- 第 102-106 行：每次 Read 后检查 `l.r.N == 0`，一旦耗尽配额立即返回错误 `%q exceeds %d bytes`。注意错误信息中包含 `l.name`（文件路径）——该路径由 `RootPath(root, 固定常量)` 得出，不含用户注入内容，日志注入面为零。
- **资源耗尽防护验证**：恶意镜像放置一个超大 `/etc/passwd`（如 10GB）会导致什么？LimitedReader 在读满 10MiB+1 后停止从磁盘读取并报错，`GetExecUser` 收到 error 终止。内存占用上限受限于 moby/user 解析器的缓冲策略，且 10MiB 上限显著收紧了原始无限制版本的风险。**有效防御，DoS 面已被封堵。**

### 5. parseUID（第 110-117 行）

- 第 111-112 行：`"root"` 特判映射为 0——语义正确（passwd 中 root 恒为 0），非黑名单绕过问题。
- 第 113-116 行：`strconv.ParseUint(str, 10, 32)`——十进制、32 位无符号白名单解析。拒绝负数、十六进制、超范围值。fail-closed，**无绕过**。

### 6. WithUIDGID（第 122-131 行）

- 接收 `GetUser` 输出的 uid/gid/sgids（均已是 uint32 强类型，类型系统保证了不可能携带任意字符串/路径等危险载荷）写入 spec。
- 第 124 行 `defer ensureAdditionalGids(s)` 保证主 GID 进入补充组列表——这是权限**收敛**方向的处理（确保进程组身份自洽），不是提权。
- **sink S2 验证**：写入 `s.Process.User.UID/GID` 的值要么来自数字解析，要么来自 passwd 表查询结果，不存在把任意攻击者字符串写入 spec 的通道。spec 后续由 runc 按最小权限原则执行 setuid/setgid，数值本身即最终身份，无二次解释风险。

### 7. setProcess（第 136-140 行）

- 仅做 nil 保护初始化空 Process 结构。空 `specs.Process{}` 不含任何预授权字段（无 capabilities、无 privileged 标志），不会意外放宽运行时约束。无安全影响。

### 8. ensureAdditionalGids（第 145-153 行）

- 第 147-149 行：`slices.Contains` 去重判断，避免重复添加主 GID。
- 第 150-152 行：头插主 GID。逻辑上只增不减，且添加的是刚被设置的 `s.Process.User.GID` 自身——不存在借补充组列表注入额外特权组的可能（sgids 来源仍是 GetUser 的表查询结果）。无漏洞。
