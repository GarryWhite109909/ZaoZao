**数据流验证**

- **流 A：payload 模板 → Twig 渲染（第 170、180 行）**
  `$view->renderString($webhook->payloadTemplate, ['event' => $e])` —— source 是管理员在 CP 配置的模板字符串，sink 是 Twig `renderString`。Craft 的 `renderString` 默认在受限的 Twig 环境中运行且仅限有 CP 权限的管理员配置，属受信配置而非外部输入；不构成可利用注入。

- **流 B：header 值 → HTTP 头（第 205–224 行）**
  header 值经 `App::parseEnv` + `renderString` 后，用 `preg_split('/[\r\n]+/')` 拆行并 trim（第 211 行），有效阻断了 CRLF 头注入；Guzzle 也禁止非法头。防御有效。

- **流 C：webhook URL → Guzzle 请求（SSRF）—— 关键问题**
  - source：第 235–238 行，`$url = App::parseEnv($webhook->url)` 后再经 `renderString($url, ['event' => $e])` 渲染；
  - 中转：第 247 行 `$this->request(...)` 将其写入 `{{%webhookrequests}}` 表；
  - sink：第 425 行附近 `sendRequest()` 中 `->request($data['method'], $data['url'], $options)`，method/url 均直接取自 DB（第 406 行），**无任何 scheme/host 白名单或黑名单校验**。
  - 防御评估：全文未发现对 URL 目标的任何校验（无内网 IP 过滤、无协议限制）。任何能访问 CP 且拥有 webhook 管理权限的用户（或能写入该表/篡改配置者）可将 URL 指向 `http://169.254.169.254/`、`http://localhost:xxxx/` 等内部服务，形成 **CWE-918 SSRF**。响应状态码、头与体还会被存入 activity 页面（第 438–443 行），造成内网信息回显泄露。

- **流 D：debounce 更新路径（第 315–330 行）**
  按 debounceKey 复用 pending 记录并更新 url/body，mutex 锁（`_lockRequest`）防并发竞态，逻辑上无注入（参数化查询）。

- **流 E：`toArray()`（第 466–495 行）**
  有深度限制和敏感字段 redaction，且输入来自事件对象而非请求参数，风险低。

**第二入口/替代通道**：`request()` 是 public 方法，其他插件代码可直接调用传入任意 url/method，最终同样汇入第 425 行的 Guzzle sink，进一步扩大流 C 的可达性。SQL 全程使用 Query/Db 助手参数化，未见注入。
