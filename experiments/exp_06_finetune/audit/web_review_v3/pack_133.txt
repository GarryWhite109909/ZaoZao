8. **框架定位带来的责任延伸**：作为通用 agent 框架，upsonic 无法约束每个模型宿主的诚实度；库层提供可信计量原语是唯一能让全生态同时受益的位置，正如 psd-tools 应在解码入口设尺寸哨兵的同构论证。

9. **修复验收口径**：负 tokens 输入抛 ValueError 且不落账；量级超过时间基线上限触发复核事件而非静默接受；三入口行为一致。三项样例入 CI 后，账本的完整性承诺才算落地。

10. **结语**：计费是平台与用户之间的信任契约；当契约的一侧被允许随口报价而另一侧无条件记账时，坏账只是时间问题。本文件把模型 SDK 的自报值当作免检事实，审查结论据此成立。

11. **会话存储的持久放大**：成本串落库后进入长期统计窗口，一次恶意会话的虚假低消费将永久拉低该用户的基线画像；修复不仅要在入口拦截，还需提供历史数据的重算工具，否则账本清洁无法恢复。

12. **与插件生态的组合面**：宿主进程内的第三方扩展同样能改写 usage 结构；把计量读取收敛到库层原语并把写入权限按调用栈分层，是比逐个审查插件更可持续的治理路径。

13. **行号索引**：15–21 计价工具导入；24–31 类自白 doc；34–50 主计算路径；53 行起两个变体签名。全部锚点经源文件核对。

14. **模型并发下的累积评估**：agent 场景里一次用户请求可能衍生数十次子调用，每条的虚报都会乘上并行度；账本误差因此随任务复杂度非线性放大，最终让配额体系在真实负载测算中彻底失去参考意义。

15. **修复原语的具体形态**：推荐提供 audited_cost 包装器——内部同时接受 usage 与 elapsed_ms 并执行三项检查后盖章返回；旧入口保留转发但标记 deprecated。迁移期两端并存可避免生态断裂。

16. **审查视角的元观察**：计费模块天然不进入安全扫描视野——它不做 IO、不执行命令、不解析用户输入；但当它的输出参与配额决策时它就是授权链的一环。把“数据被谁消费”而不是“数据是否危险”作为审计起点，是本篇方法论的核心收获。

17. **术语澄清**：这里的 CWE-807 指以未验证输入做授权相关判断；tokens 数值虽小，却直接决定资源闸门开合，属于与权限位同等地位的决策输入。命名带来的直觉偏差常使此类问题在评审中被归入正确性问题而非安全问题。

18. **上游协同的可能形态**：SDK 层若能提供带签名的 usage 回执，库层校验就有了密码学锚点；在此之前，本地三角基线是唯一现实选择。两种方案宜在 issue 中并行推进，分别对应长期架构与短期止血。

19. **多租户报表的连带义务**：修复后应提示运营方重算受影响时段的费用聚合，并对偏差最大的账户出具说明；透明处理能挽回部分信任，静默修正则会沉淀成社区对账本可靠性的长期质疑。

20. **结案**：全部证据沿三次函数签名展开且互相独立可验；缺陷根源于单侧信任而非实现失误，因此任何纯代码内的局部补丁都无法彻底解决——只有让计量原语拥有自己的验证逻辑，账本才重新值得托付。
