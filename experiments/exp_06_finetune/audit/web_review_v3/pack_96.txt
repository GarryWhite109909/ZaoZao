2. **key → 文件路径数据流**：所有含 key 的操作都先经过 `getCacheFileName`（第 100 行附近），key 被 `sha256 + hex.EncodeToString` 处理，输出仅为 `[0-9a-f]` 字符。因此 `../`、空字节、绝对路径等路径遍历 payload 均被彻底消除——这是规范化（哈希）而非黑名单，属有效防御。后续 `filepath.Join(cachePath, keySha256+suffix)` 中 key 部分不可注入。

3. **config → CachePath / FileSuffix 数据流**：`StartAndGC` 直接把配置中的 `CachePath` 用于 `os.MkdirAll`（第 91 行），`FileSuffix` 拼进最终文件名。若配置完全由攻击者控制，理论上可通过 `FileSuffix` 含 `../` 或恶意 `CachePath` 影响写入位置。但该配置是应用初始化时由开发者/运维提供的（如 beego 的 cache 配置项），不是运行时用户输入；框架文档明确其为管理员级配置。按威胁模型这属于受信任配置，不构成可达漏洞。

4. **替代通道检查**：
   - gob 反序列化（`GobDecode`）：若缓存目录可被攻击者写（如共享主机、目录权限 `os.ModePerm`=0777），可能注入恶意 gob 数据。但 gob 解码默认只实例化已注册类型，且前提是文件系统权限已被攻破，属于部署问题而非本代码可直接利用的漏洞。不过 `os.ModePerm` 创建文件/目录权限过宽（第 91、246 行）是一个值得注意的加固点（信息泄露/篡改风险的放大器）。
   - `fmt.Printf` 打印 cachePath（第 116 行）：轻微信息输出到 stdout，无实质危害。

## 一、文件定位与入口点枚举

本文件是 SFTPGo 的 HTTPD 模块中 OAuth2 状态管理器的实现（内存版 + 数据库共享会话版）。本文件本身**不注册任何 HTTP 路由、不直接解析任何用户输入参数**，它是一个被上层 `oauth2.go` / 路由处理器调用的库层组件。因此需要逐一分析每个函数，确认其输入来源与输出去向。

## 二、逐函数分析与数据流验证

### 1. 第 27-29 行：包级变量 `oauth2Mgr`

### 6. memoryOAuth2Manager 系列
#### 第 70-76 行：`addPendingAuth`
以随机 state 为 key 写入 map。state 服务端生成，map key 不可被攻击者碰撞（除非猜中 CSPRNG 输出）。

#### 第 78-83 行：`removePendingAuth(state string)`

#### 第 100-111 行：`cleanup()`
遍历清理过期项，条件 `diff < 0 || diff > authStateValidity` 覆盖时钟回拨与超期两种情况。无漏洞。
