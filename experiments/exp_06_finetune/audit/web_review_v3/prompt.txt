# 审查协议（每条按序，禁止跳步）

## 第 0 步 独立重解（仅基于分区 A 的 [CODE]）
1. **样本计数**：先数出本批实际有几个 "### id=" 块，记为 N。输出中必须出现 N 条记录。
2. **语言推导检查面**：根据 lang 标签和代码实际语言，推导该语言的危险 sink 和防御模式。禁止只套用 prompt 中出现过的漏洞名。
3. **枚举输入点**：从代码中找出所有可控输入点（argv、env、stdin、请求参数、header、文件读取等）。
4. **追踪污点流**：从每个输入点追踪到 sink，判断是否存在有效防御。
5. **无漏洞样本**：必须显式说明"未发现污点流"及原因（如：输入点不可控 / sink 处已过滤 / 常量传播）。
6. **输出**：has_vuln / CWE / source_line / sink_line / minimal_fix / confidence / tier(1-3)

## 第 1 步 结论比对（读取分区 B 后）
- 你 false 教师 true → 自查表面特征误导（拼接≠注入；绑定传值≠拼接；常量不可控；双引号变量展开不解析元字符），仍坚持 → false_positive
- 你 true 教师 false → 先自查你的结论是否依赖样本外假设（渲染层存在、调用方可控、框架自动行为、样本外函数语义）——这正是教师幻觉的同款模式，必须排除后才可信。自查后仍坚持 → false_negative（critical）
- 同 true 但 CWE/行号/成因不同 → wrong_cwe / line_number_error / reasoning_error
- 你 uncertain 教师笃定 → UNSURE
- 教师报了洞 A 而你独立发现未提及的洞 B/C → missed_vulnerability

## 第 2 步 事实断言核验（幻觉主战场）
- source/sink/fix 引用的变量、函数、文件名必须在 [CODE] 中真实存在 → hallucinated_identifier
- 教师说"line N 是 X"而第 N 行（按 "N|" 格式定位）实际是 Y → line_number_error（evidence 写"第 N 行实为 …"）
- 教师输出的代码片段/文件须存在于样本中 → hallucinated_artifact
- 教师断言依赖样本外代码行为（渲染层、调用方、上游框架、未包含的函数体）且未声明为假设 → hallucinated_behavior（major），evidence 指明该断言在 [CODE] 内不可验证
- 正文结论与 JSON 字段不一致 → analysis_json_mismatch
- API 存在性/参数含义/CWE 编号对应：没把握 → 写入 verify 数组（"待查证：&lt;具体断言&gt;"），禁止当事实放行也禁止凭空判错
- verify 断言的答案若可能改变本条 verdict（翻转有/无或主 CWE）→ 必须在 verdict_conditionals 写明翻转条件；该条视为条件裁决，下游解决 verify 后须机械复查

## 第 3 步 修复验证（以 [JSON] fix_suggestion 语义为准）
- 正确性：逻辑是否写反/写错（写反的修复比不修更有害）
- 完整性：堵的是漏洞类别还是只堵演示 payload → fix_half_measure
- 上下文可用：fix 依赖的模块/API 原代码是否已具备 → fix_context_broken
- 格式：单行、无代码块、行号真实存在；同一行重复相同建议 → duplicated_fix
- 教师 PoC/payload 有效性：按语义判断能否真触发（双引号内的 `;` 不会执行）→ poc_invalid

## 第 4 步 格式与一致性
- lang 标签 vs 代码实际语言 → language_label_mismatch
- 无漏洞时 explanation 不得含 CWE 编号
- vulnerability_type 命名语言混用 → vocabulary_inconsistency
- 教师对四步协议的遵循度 → protocol_noncompliance（minor）
- 核实 flags（bad_json / no_json / maybe_truncated / identity_leak / real_credential_pattern / field_order / safe_but_cwe_in_expl）

## 第 5 步 捷径审计（记录不改判定）
- 结论能否从表面特征直接读出——注释自我标注、变量名暗示、洞位置浅显固定 → label_leak_shortcut

# 官方 CWE 判别标准与原理（依据 MITRE CWE v4.20；归属判定前必须对照本区块。本区块已并入判别附录全部内容并以此为准，附录文件仅作历史参考）
## A. 注入主族：74 / 77 / 78 / 88（先问注入目标是什么）
- **CWE-78 OS 命令注入**：sink 是 OS 命令执行，**无论有无 shell 层**。官方两亚型：①输入拼命令串经 shell（system/os.system/execSync/bash -c/`subprocess shell=True`）；②无 shell 但"输入选择执行哪个程序"可控（`exec([COMMAND])`/`subprocess.run([user_cmd])`/`exec.Command(用户命令)`）。**不要因没有 shell=True 改判 77**。
- **CWE-77 命令注入泛化**：**专指非 OS shell 的命令语言**注入——sed 脚本、SNMP、IMAP/SMTP、MVG 图形语言、Fluentd/应用配置语言。注入目标是"某个解释器自己的命令语言"才是 77。
- **CWE-88 参数注入**：命令名硬编码固定、用户输入只落**参数位**且能注入开关/定界符（`git rebase --exec <x>`）。
- 原理：判定顺序 = "是否 OS 命令执行→78；非 OS 的命令语言→77；命令固定只注参数→88"。命令执行不看 shell 层，看 sink 是不是 OS 程序执行。
## B. 代码执行细分：94 / 95 / 917 / 1336 / 134 / 150
- **CWE-95 eval 一跳**：输入直接进 `eval()/exec()/Function()/vm.runInNewContext`/PHP `preg_replace /e`/`create_function`，收的是用户字符串。
- **CWE-94 拼代码再执行**：输入被拼进**生成的代码文本**再 compile+exec。
- **CWE-1336 SSTI**：模板引擎把输入当**模板源码**渲染。判据核心：外部输入必须进入了模板**源码字符串位**，如 `render_template_string(f"...{user}...")` 的 user 拼进模板串、`pug.compile(user)`、`Template(user_str)`、Thymeleaf 视图名拼接 `"...:: "+user`。**输入仅作变量值**（`render(name=user)`）不构成 SSTI。
- **CWE-134 格式串**：printf/`%`/format 的**格式串位**被外部控制（`fmt % CONFIG` 读密钥）。
- **CWE-150 终端转义注入**：输出到终端/TUI 的内容未净化 ANSI/OSC 等转义/控制序列（滚动区劫持、OSC 8 链接钓鱼）。
- **1336 vs 134 分界**：模板引擎 `{{}}` 语法被执行 → 1336；`%` 格式语义 → 134。**仅表层形似，别混淆**。
## C. 数据/查询注入：89 / 943 / 643 / 91 / 90
- sink 是 SQL → 89；MongoDB 操作符/NoSQL 查询 → 943；XPath 表达式查询 → 643（改 XML 结构是 91）；LDAP 过滤器 → 90。
## D. SSRF / 越权族判别
- **918 vs 441**：服务端替攻击者"取内容"（requests.get(user_url) 目的地未校验）→ 918；攻击者借产品"身份/网络位置"发请求（loopback 信任/directConnect）→ 441；骗浏览器跳转（Location/redirect）→ 601。
- **862/863/639/306**：先问"有没有查授权"→没查=862；"查了但做错"→863；"按用户可控 key 越权访问他人资源(IDOR)"→639；"关键功能连认证都没有"→306。
- **352 不是主洞终点**：若 advisory/上游标了别的 CWE（如 unserialize→502），主洞跟根因，CSRF 只是投递链。
## E. 三条判定纪律（从 web_review 实际歧义反推，必守）
1. **防御/净化代码识别**：先判断目标代码是不是"防御/校验/净化函数本身"（sanitizer、escape、白名单过滤、EscapeFilter 等）。若是，它不构成漏洞点——**除非其实现本身存在可绕过缺陷**（不完整转义、白名单漏项、清理方向写反），此时缺陷位置即漏洞位置。禁止把无缺陷的防御函数判成漏洞，也禁止以"这是防御代码"为由放过有缺陷的防御；真正的洞也可能在"防御缺失的可达路径"，与防御函数存在与否无关。
2. **硬编码凭证（CWE-798）按官方字面判存在性**：官方定义为"product contains hard-coded credentials"，**不含使用要求**。"定义未使用"仍构成 798，但影响有限——正确动作是 risk_miscalibrated（降 Low/Medium），禁止据此翻转 has_vulnerability 或 DELETE 样本。流向敏感操作（登录校验/加密/签名/鉴权）的硬编码凭证是标准形态，教师漏报此类 → false_negative；教师把未使用凭证报为漏洞与官方字面一致，**不算 false_positive**（若其判定源于自身规则书与官方的口径差，走权威层级第 4 条→framework_conflict）。
3. **模板源码注入判定**：判 1336 必须确认外部输入**进入了模板源码字符串**且被模板引擎执行，再谈 SSTI；否则按输出层（XSS=79）或其它实际 sink 定性。
## F. 归属纪律
CWE 归属判定前先对照本区块；拿不准（尤其 77/78/88、1336/134/95/94 近邻）→ 把归属断言写入 verify 数组待查证，禁止凭记忆硬判编号。

# 风险等级校准（偏离记 risk_miscalibrated）
Critical=可达 RCE/认证绕过/凭证直接泄露。认证门后即 RCE 的仍算 Critical——门槛属于可达性论证，不降等级
High=注入类/SSRF/XSS/越权读写（含特权会话中的反射 XSS）；无 gadget 演示的理论 RCE（原型污染、无调用方的反序列化链）记 High 不记 Critical
Medium=信息泄露/配置错误/有限 DoS/定义未使用的硬编码凭证
Low=影响极小

# 【verdict 判定政策——机械适用，禁止自行发明边界】
- **DELETE 仅限两种情形**：① 核心结论错误（有↔无翻转，或主 CWE 整体错标）且正确结论无法在原样本上局部改写（改写会翻转样本的教学身份，如"安全对照样本实际有洞"）；② truncated_output / 无 JSON，样本按原样不可用（亦可注明 unsure_reason=input_truncated 退回重投喂替代删除）。
- **FIX**：核心结论正确，但锚定/机制/修复/评级/格式存在任何 critical 或 major 错误——一律 FIX 并写明应改什么。结论可局部修复时**禁止 DELETE**（删除是最后手段）。
- **KEEP**：完全干净，或仅存在 minor 风格瑕疵。
- 方向偏好：假阳性倾向 DELETE（教错误事实），假阴性倾向 FIX（补充发现即可改好）。
- framework_conflict / 规则书冲突 → UNSURE + unsure_reason="genuine_ambiguity"，禁止自行裁决。
- independent.confidence ≠ high 时：DELETE 与翻转核心结论的 FIX 一律降级为 UNSURE。

# 输出格式（严格 JSONL，每条样本一行，批末一行汇总；不要外加散文）
{"id":…, "verdict":"DELETE|FIX|KEEP|UNSURE", "tier":1,
 "unsure_reason":"input_truncated|genuine_ambiguity"(仅 verdict=UNSURE 时输出，其余省略),
 "independent":{"has_vuln":…, "cwe":"…", "source_line":N或null, "sink_line":N或null, "confidence":"high|medium|uncertain"},
 "errors":[{"type":"…", "severity":"critical|major|minor", "evidence":"逐字引用+实际行号"}],
 "verify":["待查证断言，无则空数组"],
 "verdict_conditionals":["若<verify断言>答案为X则本verdict应翻转为Y——verify不影响verdict时省略本字段"],
 "note":"一句话"}

字段约定：无漏洞样本的 source_line/sink_line 固定输出 null（禁止 0）。tier 定义：1=干净或仅 minor 瑕疵、可直接蒸馏；2=存在 major 瑕疵、修复后可用；3=存在 critical 级错误或核心结论存疑。tier 描述样本状态，与 verdict 相互独立（DELETE 样本通常 tier3，tier3 不必然 DELETE）。

汇总行：{"batch":N, "counts":{…}, "top_errors":[…], "worst_ids":[…], "novel_error_count":N, "novel_errors":[…]}

error_type 闭合枚举（清单外用 other 并在 note 描述）：
false_positive / false_negative / wrong_cwe / missed_vulnerability / line_number_error / hallucinated_identifier / hallucinated_behavior / hallucinated_artifact / analysis_json_mismatch / poc_invalid / fix_invalid / fix_half_measure / fix_context_broken / fix_format_violation / fix_escape_pollution / duplicated_fix / truncated_output / language_label_mismatch / label_leak_shortcut / risk_miscalibrated / schema_limitation / framework_conflict / vocabulary_inconsistency / teacher_identity_leak / protocol_noncompliance / verbosity / other

严重度按对学生的后果：critical=习得错误事实认知（假阴性/幻觉标识符/行为断言错误/写反的修复）；major=结论对但推理·修复·锚定错误或系统性噪声；minor=风格

# 纪律
- evidence 逐字引用原文并附实际行号（按 "N|" 格式），禁止转述。
- 不确定 → UNSURE 并写明卡点，禁止硬判。
- novel_error_count：每批报告 prompt 未列举的新型错误数。若发现全部命中预置裁决与枚举、恒为 0，说明你在模式匹配而非审查——回炉重审本批最可疑的 3 条。novel 断言必须附逐字 evidence；无 evidence 的 novelty 不计入，禁止为凑数编造新型错误。
- 批间不携带上一批具体案例印象。
- 拿不准可以联网搜索有用信息

# 【输出前强制自检——静默执行，不展示过程】
