# Gitea TwoFactor 模型文件安全分析

## 一、文件定位与入口点枚举

本文件是 `models/auth` 包中的数据模型层代码，不含 HTTP 路由。其"入口点"是所有被上层（web 路由、API、CLI）调用的导出函数。逐一枚举：

1. **第 44-54 行**：`GenerateScratchToken()` — 生成恢复令牌，source 为 `util.CryptoRandomBytes(6)` 与 `util.CryptoRandomString(10)`；
2. **第 56-60 行**：`HashToken(token, salt)` — PBKDF2 哈希函数，参数为外部传入的 source；
3. **第 62-68 行**：`VerifyScratchToken(token)` — token 来自用户登录表单输入（第二入口：用户提交的 scratch code）；
4. **第 70-72 行**：`getEncryptionKey()` — 从 `setting.SecretKey` 派生 AES 密钥；

## 二、逐条 source→sink 数据流验证

### 数据流 1：scratch token 生成与存储（第 44-54 行 → 第 51 行 sink: DB 字段 ScratchSalt/ScratchHash）

- 第 46 行使用 `util.CryptoRandomBytes(6)`（CSPRNG），48 位熵 ≈ 2^48 空间；base32 编码后 10 字符。
- 第 50 行 salt 用 `CryptoRandomString(10)`，随机生成，非固定值。
- 第 52 行哈希后仅存 `ScratchHash`，明文 token 不落库——防御有效。PBKDF2-SHA256 10000 轮（第 58 行）虽轮数偏低但配合随机 salt 可接受。

### 数据流 2：VerifyScratchToken（第 62-68 行）

- source：用户提交的 token（HTTP 表单）；sink：`subtle.ConstantTimeCompare`（第 67 行）。
- 使用常数时间比较防时序侧信道，防御有效。无 SQL 注入面（纯内存比较）。
- 注意：无速率限制逻辑在本层，但暴力破解受 2^48 空间限制，且限速属上层职责，不构成本文件漏洞。

### 数据流 3：getEncryptionKey（第 70-72 行）— **发现漏洞点**



- source：`setting.SecretKey`（站点级长期密钥，来自 app.ini/环境变量）。
- sink：作为 AES 密钥传入 `secret.AesEncrypt/AesDecrypt`（第 77、88 行）。
- 问题：用 **MD5 截断为 128 位**派生 AES 密钥。MD5 已被证明不具抗原像性保证，且将任意长度 SecretKey 压缩到 16 字节，削弱密钥熵上限至 128 位；更重要的是这是非标准、弱化的 KDF（对比 PBKDF2/HKDF）。若 SecretKey 本身熵不足（如管理员设置短口令），MD5 快速哈希使离线爆破加密后的 TOTP secret 成为可行攻击路径：攻击者获取 DB dump（SQL 注入、备份泄露等第二通道）后可离线穷举 SecretKey 并解出所有用户的 TOTP 种子，从而完全绕过 2FA。
- 该模式在 Gitea 历史上确实被安全审计标记（后续版本改用 `secret.NewEncryptionKey()` 基于 SHA256 的正确 KDF），证实其为真实缺陷。

### 数据流 4：SetSecret / ValidateTOTP（第 74-93 行）

- SetSecret：AES 加密后 base64 存库，加密本身正确（依赖 secret.AesEncrypt 实现）。
- ValidateTOTP：解密失败返回错误而非 panic，passcode 直接交给 `totp.Validate`，无注入面。防御有效，但其安全性完全继承自数据流 3 的弱密钥派生。

### 数据流 5：DB 操作函数（第 95-145 行）

- 全部使用 xorm 参数化查询（`Where("uid=?", uid)`、`ID(id).Delete(...)`），无字符串拼接 SQL，无注入。
- `DeleteTwoFactorByID`（第 127-129 行）：删除条件同时绑定 `id` 和 `UID: userID`，防止越权删除他人记录（IDOR 防御有效）。
- `ErrTwoFactorNotEnrolled.Error()`（第 34 行）：UID 为 int64，`%d` 格式化，无格式化字符串注入。

## 三、第二入口与替代通道检查

- 替代通道 1：数据库备份/dump 泄露 → 配合第 71 行 MD5 弱 KDF 可离线破解 SecretKey 解密全部 TOTP secret（放大漏洞影响的关键路径）。
- 替代通道 2：scratch token 明文仅在生成响应中返回一次，库中只有加盐哈希，无泄露通道。
- WebAuthn 通道（第 137-145 行）仅做存在性检查，无数据流风险。

1. **第 1–30 行（包声明与错误类型）**：仅定义 `ErrTwoFactorNotEnrolled`，`Error()` 用 `%d` 格式化 int64，无格式化字符串注入面。

2. **第 38–48 行 `GenerateScratchToken`**：使用 `util.CryptoRandomBytes(6)`（CSPRNG）生成 8 字符 base32 恢复码，熵约 40 bit，对在线暴力破解足够；盐用 `CryptoRandomString(10)` 随机生成。无硬编码或可预测值。安全。

3. **第 51–54 行 `HashToken`**：PBKDF2-SHA256，10000 轮，50 字节输出，带随机盐。恢复码以哈希存储而非明文，防库泄露后直接使用。轮数偏低但可接受（Gitea 上游实现）。安全。

4. **第 57–62 行 `VerifyScratchToken`**：先做长度检查（非防御性黑名单，仅快速失败），比较使用 `subtle.ConstantTimeCompare`，消除时序侧信道。source 为用户输入 token，sink 为哈希比较——防御有效。安全。

5. **第 64–66 行 `getEncryptionKey`**：`md5.Sum(setting.SecretKey)` 派生 AES 密钥。MD5 作 KDF 是弱点（16 字节截断、无盐、无迭代），但这属于设计权衡而非本文件可利用漏洞：攻击前提是已获取数据库密文 + 已知 SECRET_KEY；SECRET_KEY 本身即根秘密，攻击者持有它时 MD5 不降低安全性。不构成独立可利用漏洞。

6. **第 69–76 行 `SetSecret` / 第 79–90 行 `validateTOTP`**：TOTP 种子经 AES 加密后 base64 存库，解密失败返回错误而非 panic/泄露。错误信息含底层错误但不包含敏感数据（不含 secret 明文）。安全。

7. **第 92–110 行 `ValidateAndConsumeTOTP`（重放防护）**：这是本文件核心逻辑。采用条件 UPDATE：`Where(IsNull OR Neq last_used_passcode)` 且 `Cols("last_used_passcode")`，仅当存储值不同才更新。并发请求下数据库行锁串行化，第二个相同 passcode 的 UPDATE 影响 0 行被拒绝，闭合了 read-validate-write TOCTOU 窗口。`Update(t)` 只写指定列，不会覆盖 Secret 等字段。逻辑正确。注意：该函数是注释声明的唯一消费入口，本文件内无其他绕过路径调用 `validateTOTP`（小写私有方法未对外导出）。

8. **第 113–124 行 `NewTwoFactor` / `UpdateTwoFactor`**：xorm 参数化查询，无 SQL 注入面。`AllCols().Update(t)` 由调用方控制结构体内容，本文件无用户输入直达此处。

9. **第 127–141 行 `GetTwoFactorByUID` / `HasTwoFactorByUID`**：`uid` 以占位符参数传入（`uid=?`），无拼接。安全。

10. **第 144–155 行 `DeleteTwoFactorByID`**：删除条件同时绑定 `id` 与 `UID: userID`（属主校验），防止越权删除他人 2FA 记录；影响行数不为 1 时报错。授权检查到位。安全。

11. **第 158–167 行 `HasTwoFactorOrWebAuthn`**：组合查询，均参数化。安全。

**入口点枚举结论**：本文件为 models/auth 层代码，无 HTTP 路由、无文件/环境变量读取、无回调注册；所有外部输入（token、passcode、uid、id）均来自上层调用方，且在本层内全部经过参数化查询、常量时间比较或原子条件更新处理。第二入口与替代通道核查：`validateTOTP` 为私有方法且仅被 `ValidateAndConsumeTOTP` 调用，无绕过重放防护的替代通道。
