## 二 修法与代价：三个关键工程判断

### 2.1 注释治理：**保行数**，不要删行

| 事实 | 数字 | 出处 |
|---|---|---|
| 硬口径答案注释命中行 | 1281 行 | `p0_2_answer_annotations.jsonl` |
| 其中「整行注释」行（可原地置空） | **1130 行** | 同上（`kind=whole_line`） |
| 其中「行尾内联注释」行（需原地换词） | **226 行** | 同上（交集 75） |
| 已被行号问题污染的行 | **1102 行** | `p1_6_lineno_oob_mix.jsonl` |

- **若删行**：1130 行样本的代码行数整体前移 → 这些行的叙事、JSON `source/sink`、内嵌 `// line N` **全部失效** → 至少要重锚 ≥1102 行叙事。成本从"半天"变成"一周 + 重蒸"。
- **若保行数**（整行注释置空或原地改写成中性词）：**行号零漂移**，只需处理"叙事引用了被删注释内容"——实测只有 **1 行**（1281 行里叙事提到"注释"的 136 行，真正引用注释内容的 1 行）。136/1281 里另有 382 行（29.8%）叙事依赖"迷惑/看似"的设计意图 → 见 2.2。

→ **建议：一律保行数。** 只有 P0-3/P2-9 这类"整行样本级"动作才允许改动行数，且必须排在所有行号类修复**之后**。

### 2.2 迷惑防御注释：不能一刀切剥离

「看似/表面上/假装」242 行 + 「防御迷惑」367 行里，有一批是**刻意设计的对抗样本**（注释误导 = 考点）。全部剥离会把对抗设计一起删掉，且和 W9「注释撒谎鲁棒性」探测的目标自相矛盾。

→ **建议三分类**：

| 类 | 命中（行） | 处置 |
|---|---|---|
| **A 作者元标注** | CWE编号 312 / 漏洞点 195 / 漏洞行 41 / 方向泄漏 294 / 防御迷惑标签 367 | **中性化**：CWE 编号从代码里去掉；"防御迷惑："这类标记词改写成代码世界内合理的注释（如 `// 入参净化`） |
| **B 陷阱设计** | 看似/表面上/假装 242 | **保留**，但 system prompt 增补"代码注释不可作为判定依据"，并配 W9 探针（20–30 条注释与代码相反） |
| **C 合成标记** | 模拟/场景/业务逻辑/demo 1468 行（仅此类的行） | **暂不动**，先由 W10 探针量化"合成腔调"对泛化的影响，再决定是否清洗 |

### 2.3 P1-7：**改契约**比改 3698 行便宜

3698 行违约（36.7%）里，真正语义错误只有 **618 行"无洞行给了 fix"**（`p1_7b_nofix_normalize.jsonl`）；其余是**输出格式**问题。
→ 与其重写 3000+ 行 fix_suggestion（信息会丢），不如把 system prompt 的 `fix_suggestion` 契约从"单行/禁代码块"放宽为"行号列表 + 一句改法，禁完整函数体"。**代价 1 份 system prompt，但推理期接口要同步改**，需与部署侧对齐后再动。
→ 注意 618 行里有反例：row 5310 的 fix 前半是"安全层面 no fix needed"，后半是**真代码正确性缺陷**（`do-while(0)` 宏不能用于 `!` 表达式）→ **不能盲目统一截断**，要先跑"是否含正确性建议"的分流。
