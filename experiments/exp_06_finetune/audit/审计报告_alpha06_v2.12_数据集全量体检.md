## 0. 总体结论

**这是一份"上半身很强、下半身漏风"的数据集。**

新增的 873 条针对性数据（taint_boundary / blindspot / crossfile / framework_safe / evidence_adjudication …）
质量**明显高于平均水平**——推理链完整、多数据流枚举、第二入口排查、防御有效性分级都对，
确实能教会模型对应能力。这部分我打 **B+**。

但占 90.3% 的基础库（8111 条）存在若干**会直接污染输出分布**的结构性缺陷，
且这些问题不是"少几条数据"，而是**在教模型做错的事**。这部分我打 **C-**。

按对 qwen3-8B 训练的危害程度排序，核心结论：

| 级别 | 问题 | 规模 | 危害 |
|------|------|------|------|
| **P0** | risk_level 大小写分裂 | 4553 条（50.7%） | 输出格式不可解析 |
| **P0** | 异种输出契约混入 | 24 条 | 输出 schema 漂移 |
| **P0** | 教师思维独白泄漏 | 13 条 | 教模型"边想边说"+元话语泄漏 |
| **P0** | 标签自相矛盾 | 5 条 | 直接反向监督 |
| **P0** | 空壳模板分析 | 290 条（124 条完全相同） | 教模型"安全样本不用分析" |
| **P1** | 行号-内容错配 | sink 约 12.5% | 行号指标天花板 |
| **P1** | 多余字段 cvss/fix_code | 731 条 | 违反 system prompt 示范 |
| **P1** | CWE 长尾 1-shot | 19 种 CWE 各 1 条 | 学不会，只会乱猜 |
| **P2** | 语言/框架覆盖断层 | TS 2 条、C# 2 条、ASP.NET 0 | 部署场景盲区 |

## 1. 格式合理性与一致性

### 1.1 骨架：干净

```
role 序列 (system, user, assistant)：8984/8984 = 100% 一致
messages 数量 = 3：100%
JSON 解析失败：0（行级）
字段顺序非规范：0
类型错误：0
user 全文指纹重复：0 组
user 代码块重复：0 组
```

这一层做得非常扎实，比大多数自建 SFT 集都好。**没问题。**

### 1.2 【P0-1】risk_level 大小写分裂 —— 4553 条

system prompt 明写：`risk_level: Critical/High/Medium/Low；无漏洞填 'None'`

实际分布：

| 取值 | 条数 | 判定 |
|------|------|------|
| `none`（小写） | **4553** | ❌ 违反规范 |
| `None`（规范） | 126 | ✅ |
| High / Critical / Medium / Low | 4299 | ✅ |
| `""`（空） | 24 | ❌ |

安全样本共 4679 条，其中 **4553/4679 = 97.3% 输出小写 `none`**。
大写 `None` 的 126 条全部集中在行号 8753-8880（即最后并入的新数据）。

**后果**：训后模型在"判安全"时约 97% 概率输出小写 `none`。
任何用 `risk_level == "None"` 或 `^(Critical|High|Medium|Low|None)$` 做校验的下游 parser
会大面积判为格式非法。这一项会让你的格式化输出合格率凭空掉 50 个百分点。

**修复**：一行正则的事，但对指标影响巨大。建议统一为 `None`（与 prompt 一致），
或反过来改 prompt 与评测脚本为 `none`——**两者必须对齐，不能两头分裂**。

### 1.3 【P0-2】异种输出契约混入 —— 24 条（行 8069-8092）

这 24 条用的是**另一套完整体系**：

| | 主契约（8960 条） | 异种契约（24 条） |
|---|---|---|
| system 长度 | 1982 字符 / 908 token | 771 字符 / 374 token |
| JSON 字段 | has_vulnerability, vulnerability_type, risk_level, source, sink, explanation, fix_suggestion | is_confirmed, vulnerability_type, reason, fix_suggestion |
| 任务前缀 | 「代码片段（语言: x）」 | 「【安全分析任务：裁决一个静态工具告警是否为真漏洞】」 |

**后果**：
1. 这 24 条**连续排在一起**（8069-8092），若 dataloader 保留顺序，会形成一个局部 batch
   全是异种契约，梯度冲击集中，容易在该区间产生格式坍塌。
2. 推理时你的线上 prompt 不可能是「【安全分析任务：裁决…】」这个前缀，
   所以这 24 条学到的行为**永远不会被触发**——纯占坑。
3. 它们同时贡献了"缺 5 个字段"的全部统计（has_vulnerability/risk_level/source/sink/explanation 各缺 24）。

**注意**：这 24 条的**判定逻辑本身是对的**（裁决工具告警真伪），任务也有价值。
**建议转写而不是删除**：把 `is_confirmed` 映射为 `has_vulnerability`，
`reason` 拆成 `source/sink/explanation`，即可无损并入主契约。

### 1.4 【P1】多余字段 —— 731 条

| 多余字段 | 条数 | 行号区间 | 问题 |
|---|---|---|---|
| cvss_vector + cvss_score | 661 | 6045-6705（连续） | 契约外字段，且 CVSS 值多为教师编造 |
| fix_code | 70 | 98-7021（分散） | **system prompt 明令禁止** |

`fix_code` 这条特别糟糕。system prompt 第 5 条白纸黑字写着
「只给应修改的具体行+改法即可……**禁止输出完整代码/补丁/代码块**」，
但有 70 条示范了完整代码。这是在教模型"禁令有时可以不遵守"。

661 条 cvss 连续排布同样会在该区间形成局部偏置，让模型在约 7.4% 的输入上多吐两个字段。

### 1.5 【P2】vulnerability_type 格式不统一 —— 18 条

规范要求 `'CWE-编号 漏洞名'`，违规样本：

```
CWE-184 / CWE-95 / CWE-200 / CWE-770 / CWE-532 / CWE-295 / CWE-209 / CWE-204 / CWE-88 / CWE-347×2   ← 纯编号，无漏洞名
CWE-170/CWE-22 路径前缀校验不严格                        ← 多 CWE 合并
CWE-282/862 授权默认放行叠加上下文状态直写                  ← 多 CWE 合并
CWE-15: 外部可控的系统配置（…）                           ← 冒号分隔
CWE-93: Improper Neutralization of CRLF Sequences (Email Header Injection)   ← 中英混排 + 超长
```

其中「CWE-170/CWE-22」「CWE-282/862」这种多 CWE 写法会破坏 `^CWE-\d+` 的解析。
建议统一为单 CWE + 中文漏洞名。

### 1.6 【P1】安全样本字段填充不一致 —— 96 处

| 违规 | 条数 | 样例 |
|---|---|---|
| fix_suggestion ≠ "no fix needed" | 76 | `line 7769: 在 find_handler 中增加 _host_allowed 白名单校验…` |
| sink ≠ "N/A" | 20 | `line 7463: subprocess.run()（但输入为常量，不可控）` |
| source ≠ "N/A" | 11 | `line 7769: 任意来源的 HTTP/WebSocket 请求…` |

**这里要替数据说句公道话**：7463-7470 这批「`line 7: subprocess.run()（但输入为常量，不可控）`」
的写法，信息量明显高于死板的 `N/A`——它明确告诉模型"我看到了这个 sink，只是输入不可控"。
这是**更好的教学信号**，是 system prompt 的规范定得太死。

**建议**：与其把这些改成 `N/A`，不如**放宽 prompt 规范**——
允许安全样本在 source/sink 给出"看到了但不可控"的锚定，全场统一到这个更富信息的写法。

## 2. 样本正确性

### 2.1 【P0-3】标签自相矛盾 —— 5 条（实为 6 处）

`has_vulnerability = true`，但 explanation / source / sink 全部自述"没漏洞"：

| 行号 | vt / risk | source | explanation |
|---|---|---|---|
| 608 | CWE-78 / Medium | `无实际注入点（所有输入均经白名单/格式校验）` | 所有命令执行均使用数组参数或双引号包裹，无用户可控拼接 |
| 1309 | CWE-798 / High | `无（Dockerfile 中未发现硬编码凭据）` | 未包含任何硬编码密码、API 密钥或令牌 |
| 1323 | CWE-798 / High | `无（Dockerfile中未发现硬编码凭据）` | 不存在该漏洞 |
| 1358 | CWE-798 / High | `未发现硬编码凭据的直接赋值` | CWE-798 漏洞不适用于此代码片段 |
| 1430 | CWE-798 / — | `未在提供的 Dockerfile 中找到硬编码凭据` | — |
| 1432 | CWE-798 / High | `无` | 未发现硬编码凭据…不构成 CWE-798 |

这是**教科书级的反向监督**：模型同时看到"解释说没有"和"结论说有（High）"，
唯一能学到的就是"explanation 和 has_vulnerability 可以不一致"。

形态上看，这是「教师被要求判 vuln、但代码确实是 safe」时的妥协产物——
和 v2.11 报告里剔除的 7 条毒样本（`#3573[F]: has_vulnerability 应为 true` 等）
是**同一批病灶，没清干净**。

**修复**：这 6 条全部应翻转为 `has_vulnerability=false`，或直接剔除。
同时建议把"Dockerfile + CWE-798"这个组合整族复查——6 条里 5 条是这个模式。

### 2.2 【P0-4】教师思维独白泄漏 —— 13 条

全部位于 `variant_crossfile_safe`（128 条中的 13 条，**占该类 10.2%**）：

```
line 8760, 8764, 8766, 8779, 8780, 8781, 8797, 8800, 8806, 8809, 8826, 8863, 8868
```

典型内容（原文节选）：

> "Actually I remember: Camel added `ClassFilters` / `ObjectInputFilter` in ...? Hmm."
>
> "**For this training data**, I don't need to replicate the exact upstream fix; I need a correct, non-bypassable whitelist defense..."
>
> "**The prompt asks to check** 替代通道/第二入口是否被同一防御覆盖..."
>
> "Since this is **a synthetic project**, I can add a helper in the security layer"

四重污染叠加：
1. **英文独白**（"Actually/Hmm/Let me/Wait/I'll"），与主库中文分析风格冲突；
2. **元话语泄漏**——把 prompt 工程的内部指令、数据生成过程写进了训练目标；
3. **长度爆炸**——这 13 条正是全库仅有的 13 条 >12288 token 样本（最长 35472 token）；
4. **JSON 失效**——其中 8797、8826 两条 JSON 解析失败，完全没有监督信号。

更麻烦的是：这 13 条**全部在 safe 侧**。
意味着 `corpus_00047/00065/00044/00046/00090/00049/00120/00117/00144/00148/00167/00213/00216`
这 13 个 task_key 的**跨文件安全对照，教学信号是废的**。

**附带好处**：删掉这 13 条，全库最长样本从 35472 token 降到约 8000，
长度问题一并解决（见第 5 节）。

### 2.3 【P0-5】空壳模板分析 —— 290 条，其中 124 条 assistant 完全相同

**组 1：72 条 assistant 逐字相同**

```
分析过程：
1. 污染源：检查用户可控输入点。
2. 危险 sink：N/A。
3. 数据流：追踪输入到 sink 的路径。
4. 防御检查：N/A。代码命中安全模式白名单，防御措施有效。
5. 结论：未发现漏洞，防御措施有效。

{"has_vulnerability": false, ..., "explanation": "N/A", "fix_suggestion": "no fix needed"}
```

**组 2：52 条 assistant 逐字相同**

```
分析过程：
1. 输入检查：识别代码中的用户输入点与处理逻辑。
2. sink 评估：N/A，需判断此处是否有有效防护。
3. 防御确认：N/A。
4. 综合判定：该防护措施有效，不存在可利用的安全漏洞。
5. 结论：代码安全，未发现漏洞。
```

三重问题：
1. **伪推理**——"检查用户可控输入点""追踪输入到 sink 的路径"是**步骤名**，不是结论。
   模型学到的是"输出 5 个不带结论的步骤名即可"。
2. **元信息泄漏**——"**代码命中安全模式白名单**"把数据生成流程的内部概念写进了答案。
3. **explanation = "N/A"** —— system prompt 只说 source/sink/fix 填 N/A，**没说 explanation 填 N/A**。

这批数据教的是：**遇到安全样本 → 套模板 → 不用真分析**。
这正是 1179 条安全样本 explanation=N/A 的源头，也是 FP/FN 边界模糊的成因之一。

### 2.4 安全样本 explanation = "N/A" —— 1179 条（13.1%）

全部集中在行 5807-8092（分段：5500 段 193、6000 段 500、6500 段 462、8000 段 24）。

占安全样本的 1179/4679 = **25.2%**。四分之一的"安全"示范没有给任何理由。

### 2.5 行号准确性 —— 这是行号指标上不去的根因

先看"越界"检测（宽松）：

```
JSON 行号越界：5 条 (0.12%)
分析行号越界：87 条 (2.05%)
```

看起来很好。**但"在范围内" ≠ "指对了行"**。做内容级校验后：

| 字段 | 可校验 | 精确行命中 | ±1 行 | ±2 行 | 完全对不上 |
|---|---|---|---|---|---|
| source | 3795 | **84.0%** | 90.0% | 92.3% | 7.7% |
| sink | 3457 | **79.7%** | 85.3% | 87.5% | **12.5%** |
| fix_suggestion | 3996 | 87.3% | 91.2% | 92.4% | 7.6% |

**注意：这个命中判定是宽松的**——只要描述中任一标识符出现在窗口内即算命中。
抽查"命中"样例可见误判：

```
line 1  @34: 描述='free(pkt->payload) 后未置 NULL'   实际='if (!pkt) return;'
line 5  @28: 描述='uint64_t total_pixels = ... 溢出'  实际='return false;'
line 6  @40: 描述='release_device(dev) 释放 config_buf' 实际='case 0x01:  // READ'
```

所以**真实精确行准确率低于 80%**，sink 尤甚。
错得最集中的是 **C/C++ 内存类**（UAF / 双重释放 / 溢出 / 空指针），
因为这类漏洞的 source 与 sink 概念上跨多行，行号本就难锚定。

**这直接解释了 strict_recall 的天花板**——不是模型不会判，是标注行号本身有 20% 在教它指错地方。

### 5.2 截断影响

**重要更正**：训练脚本在 `D:\code\yunduan\train_qlora_cloud.py`，

## 7. 蒸馏话语：啰嗦吗？专业吗？

### 7.1 不啰嗦 —— 这一项可以放心

填充词统计（全库 8984 条）：

```
套话开场（"作为…"/"这是一个…"）               0.00 次/样本
```

**这些数字很低。** 教师的输出是**密集**的，不是注水。
分析长度中位 610 字符（基础库）/ 783 字符（新数据），对 4-6 步推理来说是合理量级。

### 7.2 格式稳定性极好

```
分析步骤数分布：3 步 257 | 4 步 2117 | 5 步 5916 | 6 步 298 | 其他 396
```

**5 步占 65.9%**，4-5 步合计 89.4%。因为 system prompt 给了明确的
「1. 枚举输入点 / 2. 验证防御 / 3. 检查第二入口 / 4. 给 CWE」四步框架，
教师高度遵循。这对 8B 模型是好事——**结构稳定 = 更容易学会**。

### 7.3 专业性：新数据 >> 基础库

**基础库（8111 条）的问题**：
- 290 条空壳分析（2.4 节）；
- 1179 条 explanation = "N/A"；
- 20.2% 的样本分析中**完全没有行号引用**。

**新增 873 条的质量（抽样判读）**：

`taint_boundary_safe`（line 7872）片段：
> 1. 污点边界：本文件没有任何 request/input/environ 等显式 web 入口，但第 16~19 行
> `export_report` 是公开函数，其参数 `columns`、`agg`、`region_filter` 由上层 API 服务
> 透传用户筛选条件，**属于等效污点源**，必须按不可信数据处理。
> 2. 数据流一：`columns` → 第 26 行经 `_ALLOWED_COLUMNS` 白名单过滤…仅以 `?` 占位符形式拼入 SQL…
> 6. 第二入口检查：文件内无路由注册、无消息队列回调、无其他公开函数或间接调用路径…
> 结论：source→sink 全链路防御有效，不存在 CWE-89 注入。

`blindspot_vuln`（line 8969）片段：
> 3. 逐流防御验证：流1（第25→27行）`err.Error()` 零处理直传；流2（第25→31→32→34行）
> 全程唯一的变换是第 31 行 `filepath.Base`，它只约束文件名参与路径拼接（针对路径遍历），
> **对错误文本中的内部绝对路径与 OS 失败原因零过滤**——该防御的位置与覆盖面均与本类无关；
> 4. 第二入口检查：main 仅注册单一路由…但单入口内部有**四条相互独立的 sink 调用**，
> 且第 20-24 行的 `defer recover` 构成不依赖任何特定错误分支的**替代触发通道**。

这是**真正的高质量安全审计推理**：枚举数据流、逐流验证防御、区分防御类型
（白名单 vs 黑名单 vs 结构性替换）、排查替代通道、明确定性"该防御与本类无关"。
**这段推理链能教会模型"如何判断防御是否真的覆盖了该条数据流"——
这正是 8B 模型最缺的能力。**

**唯一的问题：太长了。**
`blindspot` 的 explanation 字段中位 442-518 字符，最长 949 字符，
基本是分析过程的完整复制。JSON 的 explanation 本应是**结论摘要**，
现在变成了 CoT 的第二份拷贝——翻倍 token 开销，且稀释了"最后一句是结论"的信号。
