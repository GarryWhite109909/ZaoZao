# wave2 的产出形式说明（2026-09-14 实测清点）

> 回答"wave2 是什么产出形式"。全部数字由 `wave2_宿舍工作包_20260913_v2.zip`（762 项）逐文件清点得出，可复算。

## 一、wave2 与 wave1 的结构差异

| | wave1（diffpair-corpus_*） | wave2（441 / 78-S / 95） |
|---|---|---|
| 来源 | 真实 CVE 的 pre-fix / post-fix 差分对，246 个 kit | **手写对**，46 对，按 `wave2_441_95_SPEC.md` 的形态清单逐条构造 |
| 配对单元 | `kits_learner/diffpair-corpus_xxxxx.txt` | `wave2_pairs/<pid>.txt`（自带 oracle 头） |
| 每对两侧 | 版本A（pre-fix）/ 版本B（post-fix），代码不同 | 版本A（vuln）/ 版本B（safe），**除防御行外逐字相同**（契约 6「成对同码」） |
| 编号口径 | 由 CVE 决定 | SPEC 目标 = CWE-441 / CWE-95（各 ≥15 对，8 vuln / 7 safe），78-S 为 safe 侧素材 |
| 蒸馏轮次 | 一轮（9/11 批）+ 复核 + 续投 | **两轮**：预审（task2）→ 正式（task4） |

`wave2_pairs/*.txt` 的头部自带机检断言，例如 `441-07`：

```
# wave2 pair 441-07 | CWE-918 | Python | 成对同码
# oracle_vuln（污点路径，行号自版本A围栏后起算）：
  - L8 `request\.args\.get\("url"` source：目的地 URL 用户可控
  - L13 `"X-Forwarded-Host": "avatar-svc\.internal"` 以产品内部身份出站（可被借用）
# anchor_vuln: 非 918 为主叙事的理由：…按 MITRE 441 的代理语义定位；若样本仅目的地未校验则应标 918。
```

## 三、v2_18 组装器实际只读"正式产出"

- 读：`WAVE/results/result.txt`（9_11批）、`KITS/result/result.txt`（续投批）、`kits_redistill_truth/result/result.txt`（复核批）、`wave2_formal_results_*.txt`（**仅这 5 个**）、`result_blocks.jsonl`（usable 标记）、`_wave2_preaudit_compare_20260913.json`（只取 `verdict ∈ {PASS, SIDE_B_HOLE}` 的 pid 名单）。

## 四、wave2 到底给 v2_18 贡献了多少

`增:wave2 = 27` 条，逐条核到来源对：

| 族 | 落库条数 | 写入 JSON 的 CWE 标签 |
|---|---|---|
| 441（441-07/08/13/14） | **4** | **CWE-918 SSRF** ← 注意：不是 441 |
| 78-S（11 对中的 10 对） | 10 | CWE-78 |
| 95（13 对） | 13 | CWE-95 |

即 31 个 PASS/SIDE_B_HOLE 里，27 个有正式 A 块 → 全部落库；剩 4 个（`441-09`、`441-10`、`78-S-09`、`78-S-09b`）无正式块，就是账本里的 `增跳:wave2缺块或码`。

**两个必须知道的结论：**

1. **CWE-441 的实际净增 = 0。** SPEC 目标是"441 定向补 30–50 条"，但 4 条落库的 441 族素材标签写成了 `CWE-918`（见 §一 的 oracle 头：首行 `CWE-918`，而 `anchor_vuln` 又论证"按 MITRE 441 的代理语义定位"）。全库 CWE-441 计数只从 36 → 37（+1，来自别处）。
2. **按这个口径，441/95 补弱根本没启动。** 95 拿到了 13 条真 CWE-95（计数 33→44），78 拿到 10 条；441 拿到 0 条。
