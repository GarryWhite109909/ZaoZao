# 官方口径测试集审查 + 易混淆 CWE 判别要点（2026-09-02）

**审查方法**：
1. 下载 MITRE 官方全量目录（cwe.mitre.org CSV 1000 视图，v4.20，2026-04-30 发布），本地持有全部 CWE 的官方定义/扩展描述/Observed Examples。
2. 导出三处测试集全部 157 段：`exp_04_hard_samples`（87）+ `rolling_dev`（50）+ `testset_cve_fix`（20）。
3. 对 rolling_dev / cve_fix 中全部 68 个真实 CVE 逐条调用 NVD 官方 API（services.nvd.nist.gov 2.0）比对官方 CWE 标签。
4. 对 NVD 未标注的条目，逐条抓取 GHSA 官方 advisory 页面核对 CWE 字段；拿不准的二次联网搜索。

---

## 一、总体结论

157 段中，**代码形态与标签语义匹配的约 147 段（94%）**；**确认错标 9 段**（rolling_dev 6 段 + exp04 复合标签问题 3 段）；另有一批**口径不一致 / 属性故事失真**问题需治理。

最重要的结构性发现：**rolling_dev 的错标集中在"按类配额填充"的样本上**——1336 三连（corpus_00003/04/05）全错、89 双连（corpus_00001/02）全错。这印证了用户判断："数据离真理较远"的根源不是蒸馏，而是**测试集采样时先定类配额、再找样本，样本找错也没复核**。

## 三、cve_fix 测试集：标签对、故事错

cve_fix_0009~0021 是 13 条手写样本，**代码与标签匹配（模型评的是代码，这部分没问题）**，但其中至少 8 条的 CVE 归属与 NVD 官方标签冲突（如 cve_fix_0010 标 89 声称 CVE-2020-9488，NVD 官方=295；cve_fix_0014 标 79 声称 CVE-2020-7981，NVD 官方=89；cve_fix_0018 标 798 声称 CVE-2018-1000544，NVD 官方=434;59）。风险：若未来做"对 NVD 自动重标"或论文声称"标签来自 NVD"，这 13 条会被误判/证伪。建议：desc 里把"Real pattern: CVE-XXXX"降级为"模式参考（非该 CVE 官方归因）"，或在 manifest 标注 `label_basis: code`。

其余 NVD 空标签条目（corpus_00056→502、00061→611、00075/00076→90）已对照 advisory 描述确认语义一致，**无需改**。cve_fix_0001 的 74→90 改标（2026-07-25 changelog）符合官方"精确子类优先"原则，**维持**。

### 样本质量备注（不急，可下轮处理）

- cve_fix_0004.py：`calculate()` 有字符白名单（无字母，无法 RCE）却 expected_present=True——严格说该函数形态接近 safe（仅剩 `9**9**9` 型 DoS）。建议改为移除白名单版或降级标注。
- typical_16（384 会话固定）：Flask 签名 cookie session 语义下会话固定攻击不典型，作为概念演示可保留，但蒸馏教师注意不要过度泛化到"所有登录后未 regenerate session 都是 384"。

## 四、易混淆组别差异与判别要点（官方口径）

以下每组的"官方依据"均出自 MITRE v4.20 官方定义/扩展描述/观测案例，"库内例证"为本次审查确认的测试集样本。

### 组 1：74 / 77 / 78 / 88 —— 注入主族（本库最高优先级）

| CWE | 官方定义核心 | 一句话判别 |
|---|---|---|
| 74 | 输出被**下游组件**解析，通用注入父类 | 下游解释器说不清是什么时才用；能用子类绝不停留在这 |
| 77 | **非 OS shell 的命令语言**注入（sed 脚本、SNMP、Fluentd/应用配置语言、IMAP/SMTP、表达式语言） | 注入目标是"某个解释器自己的命令语言"，但不是 OS shell |
| 78 | **OS 命令**注入，官方明确两个亚型：①命令串经 shell 解释；②无 shell 但**选择执行哪个程序**可控（`exec([COMMAND])`、`subprocess.run([user_cmd])`） | sink 是 OS 命令执行，无论有无 shell 层。无 shell 列表形式**仍是 78**，只是攻击者不能组合多命令 |
| 88 | **参数分隔符**注入：程序固定、命令名固定，只有**参数**可被注入（`git rebase --exec <x>`） | 什么时候用：程序名硬编码、用户输入落到参数位 |

- **库内例证**：corpus_00065（Fluentd 配置→77 ✓）、corpus_00066（Gogs `git rebase --exec` NVD=77，官方更精确是 88，**NVD 惯例：参数注入导致 RCE 常标 77**，模型在 rolling_dev 上应跟 NVD 口径）、corpus_00067/68（Glances `secure_popen`→78 ✓）。
- **关键锚**：老师/锚句已修正的口径正确——"无 shell 列表命令名可控 = 78 第二亚型"；**不要**因"没有 shell=True"改判 77。

### 组 2：94 / 95 / 917 / 1336 / 150 —— 代码执行细分区

| CWE | 官方定义核心 | 一句话判别 |
|---|---|---|
| 94 | 代码段整体或部分由外部输入构造（**生成/拼接代码**） | 代码是"拼出来的"：字符串拼接进源码、生成文件再执行 |
| 95 | 输入直接进入**动态求值调用**（eval/evalin 等一跳执行） | sink 就是 `eval()`/`exec()` 本身。官方 95 案例即 "Python compiler uses eval() to execute malicious strings" |
| 917 | **表达式语言**语句（SpEL、OGNL、JSP EL、log4j `${}`） | 框架表达式求值器在 sink。官方案例 log4shell |
| 1336 | **模板引擎**解析输入（Jinja2/Twig/Freemarker/Smarty/Velocity...） | 模板引擎把输入当模板语言渲染。SSTI 标准落点 |
| 150 | **转义/元/控制序列**（终端 ANSI/OSC） | 终端 TUI 渲染未净化控制字节。corpus_00003 应改这里 |

- 94↔95 边界：官方两者都收录 eval 形态案例（94 含 CVE-2023-29374 exec()），NVD 实践混用。**本项目统一口径建议：`eval()/exec()` 直接收字符串 → 95（与 NVD 对 Xinference 的官方标签一致）；拼接生成代码再执行 → 94。** exp04 typical_08（eval→94）建议随此口径改 95，与 cve_fix_0003/0004 对齐。
- 1336→94 链：SSTI 主洞标 1336，RCE 后果是链条，NVD 通常只标 1336。复合标签里加 94 可以，但**top-1 期望必须是 1336**。

### 组 3：89 / 943 / 643 / 91 —— 查询语言注入区

| CWE | 判别 |
|---|---|
| 89 | sink 是 **SQL**（含 ORM raw、拼接进 execute） |
| 943 | **非 SQL 的数据查询逻辑**（MongoDB 操作符注入 `$ne`、XML 数据查询之外的查询逻辑）。官方案例即 NoSQL/Mongoose |
| 643 | **XPath** 表达式注入（专类，比 943 精确） |
| 91 | **XML 文档结构**注入（改 XML 语法/内容，aka Blind XPath）——与 643 的区别：91 改 XML 本身，643 改 XPath 查询 |

- 库内：typical_25（MongoDB→943 ✓）、typical_26（XPath→643 ✓）。NoSQL 不要标 89；XPath 注入别标 91。

### 组 4：918 / 441 / 601 / 610 —— SSRF 与代理区

| CWE | 判别 |
|---|---|
| 918 | web 服务端**取回 URL 内容**且目的地未校验（典型 fetch/proxy sink：`requests.get(user_url)`、`urlopen(url)`） |
| 441 | 产品被当**代理/ intermediary**：请求看似来自产品（IP 信任、loopback 信任、directConnect 转发）。官方判据："request would appear to be coming from the product" |
| 601 | 浏览器侧**重定向**到外部站（响应头 Location / redirect()） |
| 610 | 外部可控引用指向另一信任域资源的**父类**，能用 918/611/22 就不呆在这 |

- 库内实证（NVD 官方标签同向）：corpus_00077/78（Lemur 取 URL→918 ✓）、corpus_00054/55（MagicMirror loopback 信任、appium directConnect→441 ✓）、cve_fix_0005/0006（9Router loopback 信任→441 ✓）。**判别口诀：服务端替攻击者"取内容"→918；攻击者借产品的身份/网络位置"发请求"→441；骗用户浏览器跳转→601。**

### 组 5：862 / 863 / 639 / 306 / 285 —— 认证授权区

| CWE | 判别 |
|---|---|
| 862 | **完全没做**授权检查（endpoint 裸奔、只认证不查权限） |
| 863 | **做了但做错**（规则写反、漏分支） |
| 639 | 资源定位 **key 用户可控**且未校验归属（改 URL 里 id 看别人订单）——IDOR 专类 |
| 306 | 关键功能**连认证都没有** |
| 285 | 授权问题泛父类，能用子类不停留 |

- 库内：typical_15（登录后不查 admin 角色→862 ✓）、hard_crossfile_03（user_id 未校验归属→639 ✓）、typical_13（无登录校验→306 ✓）。**判别口诀：先问"有没有查"，再问"查没查对"，最后问"是不是改 key"（639）；639 与 862 并存时 NVD 常两个都标，top-1 跟主缺失维度。**

### 组 6：327 / 328 / 329 / 330 / 338 / 347 / 295 —— 密码学区

| CWE | 判别 |
|---|---|
| 327 | 算法本身坏/险（MD5/SHA1 做安全用途、DES、ECB） |
| 329 | **CBC 模式 IV 可预测/复用**（硬编码 IV → 329，typical_18 ✓） |
| 330 | 随机性不足父类（安全语境用了不安全随机） |
| 338 | 具体到**密码学弱 PRNG**（random 模块出 token → 330/338 均见，top-1 建议跟 NVD 惯例 330，338 更精确可作次标） |
| 347 | **签名验证**缺失/错误（JWT alg=none、不验签） |
| 295 | **证书**校验缺失/错误（verify=False） |

- **库内口径分裂点**：JWT alg=none，rolling_dev corpus_00042 跟 NVD 标 327，exp04 hard_bypass_08 标 347。官方语义 347 更准（验证签名这一步没做），但 NVD 对 Parse Server 该 CVE 官方标的就是 327。**建议：锚句教"验签缺失→347；弱算法本身→327"，测试集维持各自来源现状并在 manifest 注明 dual-convention，避免教师两头挨骂。**

### 组 7：502 / 94 / 1336 —— 反序列化与执行链

- 502：`pickle.loads`/`yaml.load`/`ObjectInputStream`/Fastjson autoType/PHP `unserialize`，**主洞永远是 502**，RCE 是后果不是标签。corpus_00053 的教训：CSRF 只是触发链，GHSA 官方标 502。库内 typical_05/11/35、cve_fix_0007、corpus_00086（Keras pickle）、corpus_00057（Ray webdataset）均 ✓。

### 组 8：22 / 377 / 434 / 23 —— 路径与文件区

- 22：路径穿越读写（含 zip/tar entry 名穿越，cve_fix_0017、hard_cve_07 ✓）。
- 377：不安全临时文件（固定 /tmp 路径可预测，longfile_02/cve_03 补标 ✓，bandit B108 同口径）。
- 434：上传不限制类型（hard_owasp_01 434+22 复合 ✓）。
- 判别：**穿越→22；固定临时路径→377；上传类型不控→434；三者在归因解释中互相独立、可复合。**

### 组 9：798 / 760 / 208 / 209 / 117 —— 凭证与信息泄漏区

- 798：硬编码凭证/密钥（AWS key、DB 密码、JWT secret——corpus_00072 desc 自证 CWE-798 ✓）。
- 760：**可预测盐**（static salt 削弱 PBKDF2，longfile_01 补标 ✓）。
- 208：可观测时序差异（`==` 逐字节比较 token，bypass_06/longfile_01 ✓）。
- 209：错误消息含敏感信息（typical_28 ✓）。
- 117：日志注入（用户输入写 logger 可换行伪造，hard_cve_02 ✓；注意与 150 区分：117 是日志语义伪造，150 是转义/控制序列）。

### 组 10：915 / 1321 / 843 —— 对象属性与类型区

- 915：批量赋值/动态属性不控（typical_30 setattr ✓；Spring4Shell 数据绑定主官方标签是 94，915 只做伴生）。
- 1321：**原型链污染**（JS merge `__proto__`，typical_32 1321;915 ✓——JS 场景 915 是 1321 的父类，复合合理）。
- 843：类型混淆，**官方明确覆盖 PHP 类型杂耍/魔法哈希**（Observed Example CVE-2025-32352）。typical_33 843+798 ✓。

### 组 11：190 / 362 / 384 / 352 —— 杂数据点

- 190：整数溢出/回绕（Go uint16 回绕 corpus_00030/82、Java int 乘法 typical_29 ✓）。
- 362：竞态（check-then-act 无锁，typical_27 ✓；伴生锁未用注释是强证据）。
- 384：会话固定（见样本质量备注）。
- 352：CSRF（GET 改状态 corpus_00084、Referer 含字符串绕过 bypass_05 ✓；**注意 352 永远不是主洞根因链条的终点**——若 advisory 标了别的 CWE（如 502），跟 advisory）。
