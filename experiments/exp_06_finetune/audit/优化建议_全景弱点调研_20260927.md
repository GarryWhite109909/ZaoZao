## 1. 架构与门控层建议【架构】（零训练成本，先做）

### 1.1 预筛丢块修复 —— `_prescreen_chunks`（two_stage_scanner.py:2082）

**现状行为**：函数级切块 → 每块按词表打分（sink×3 + 源×2 + 入口×1，单模式封顶 5）→
`k = max(1, int(os.environ.get("VULN_SCANNER_PRESCREEN_TOPK", "3")))` 取 top-k；
**正分块不足 k 时不回填；全部零分时按原顺序取前 k 块保底**。

**证据样本**（rolling_dev50，两代同为漏报）：
- `corpus_00005.java`（CWE-862）：picked 三块 score 全 0（`ModelBridge.update` 100-104、120-139、155-160）——零分兜底取的是文件头部块，漏洞数据流大概率不在其中；
- `corpus_00080.py`（CWE-94）：picked 三块 score 全 0（`_RawRepr.__init__`、`__repr__`、`Constraints.validate_min_max_items`）；
- `corpus_00066.go`（CWE-77）：只凑出 1 个正分块（window_L151-300, score 2），**单块送复核**，其余文件内容 LLM 根本没看到。

**改法**（按优先级）：
1. 正分块 < k 时，用零分块**按行号均匀间隔回填**凑满 k（而不是顺序取头部）——保证覆盖面均匀；
2. 全零分文件改为**均匀行窗全文件覆盖**（150 行/窗、步长=窗长，切片总数超过 k 时按窗序等距抽 k），并在 `prescreen_info` 里记 `coverage="full"`；
3. 词表补盲（本次 3 例的真实形态）：Java 反射调用（`invoke`/`MethodHandles`）、Go `http.NewRequest*`/`Redirect`、PHP `unserialize(`/`eval(`、Python `__reduce__`/`secure_popen` 类自有包装 sink；
4. 观测：`prescreen_info` 增加 `picked_scores` 与 `zero_ratio`，接入 `_monitor_incr`（`recheck_prescreen_zero_cov`），零覆盖率成为常驻监控指标。

**回测要求**：87 集 safe 26 样本 + rolling_dev_safe 50 全部维持 TN（当前 α06 FPR 0.038 不得上升）；附录 A 的 00005/00066/00080 三例必须脱离「确定性漏报」状态（至少转 review）。

### 1.2 复核采信门分级放行 —— 全票门（:1149-1268）+ `_recheck_type_plausible`（:1926）

**现状行为**：无候选复核 N=3 投票，`votes_true==n` 且类型门通过 → 采信判真；
多数非全票 → `recheck_low_conf_review`；全票但类型门拦截 → `recheck_unverified_type_review`；
候选全否决后走兜底复核，同样非全票 → review。**类型门只校验注入型**（sink 存在 + 无标准防御），
缺失型（862/441/352 等）全票即采信、无形态校验。

**证据样本**（真票被浪费，rolling_dev50 附录 A B 类 7 例）：
- `corpus_00083.php`（CWE-89）：三个组态全部 T3/F0，仍转 review（α06 `recheck_unverified_type_review`）；
- `corpus_00070.php`（CWE-79）：α05/α06 均 T3/F0 → review；α06kp 才判真；
- `corpus_00031.js`（CWE-22）：α06kp T3/F0 → review。

**改法**：
1. 类型门返回值从 `(bool, str)` 扩为三态：`plausible / unverified / implausible`。`unverified`（缺失型/无编号）不再与 `low_conf` 同队——单独成「高优先级人工」队列，携带三票原文与 `true_types` 列表；**判真票不再丢弃**（现状 review 路径丢 `true_verdict`）；
2. 全票门保持 3/3 采信不变（FP 护栏），但 2/3 票真 + 1 票 invalid 的样本升入高优先级队列（当前与 1/2 票真混在一起）；
3. 记录并导出每例 `votes` 明细到 review 工单（现在只有计数），让人工裁决可以一键反哺训据。

**回测要求**：safe 侧全绿不变；预期收益 rolling_dev recall +6~8pp（7 例 review 中至少 4 例为一致真票）。

### 1.3 工具类型→CWE 归一映射（新增，候选生成处）

**证据**：
- α05 `typical_14/15/16` 判 "Secret Keyword"——**该串无 CWE 编号**，`_model_cwes_exp07` 提取为空，
  实例全部按 0.5 分计（GT 639/862/384 全丢）；
- S4 统计：错型/无号候选占候选总数 27~50 个/运行（87 集 134 个候选中 50 个非对型）。

**改法**：候选入裁决 prompt 前统一过 `normalize_cwe_label` + 兜底表
（`Secret Keyword→CWE-798`、`SSRF→CWE-918`、`LDAP→CWE-90` 等，已在调研中验证 normalizer 覆盖率）；
prompt 中对通用规则（detect-secrets/bandit/prefilter）的候选加注「类型仅供参考，需独立归因」。
**0927 复核补**：类型门对**无 CWE 编号**的候选直接放行不校验（two_stage_scanner.py:1954-1956）
——无号候选现在既丢分（typical_14/15/16 按 0.5 分计）又整体绕过形态门；归一化补号后
两条路同时堵上，收益比初稿估计更大。
**验收**：`model_cwes` 空号率 → 0；typical_14/15/16 至少从「方向分」变「命中分」。

### 1.4 跨文件 FP 守卫补全（crossfile_01 方向）

**现状**：判假侧已有 `_has_param_driven_sink` / `_has_external_sink_call` 双守卫（:1278-1296，
crossfile_02_input 由此转 review）；但**判真侧** `hard_crossfile_01_input`（expected safe，
sink 在另一文件）在 α05 被复核判真 943 直接采信（T1/F2）。
**改法**：判真侧加对称守卫——「本文件既无标准 sink 特征也无对外部函数的调用（`_has_cross_file_call`
复用类型门 ① 的逻辑）→ 判真降级 review」，复用 `_RECHECK_SINK_RE`，不针对样本拟合。
**回测**：hard_crossfile_02_sink（真漏洞、sink 在外）必须仍能走 `has_sink=外部调用` 通道采信。

逐 CWE 实例召回 × 训据存量（三集合并，官方口径）：

| CWE | 测试实例 | α05 命中 | α06 命中 | v2_26 漏侧行 | 结论 |
|---|---|---|---|---|---|
| 862 | 5 | 0 | 0 | 112 | 有量无效 |

| 77 | 3 | 0 | 0 | 25（α05 集 174） | 有量无效 |
| 306/434/384/843/329 | 1~2 | 0 | 0 | 18~65 | 有量无效 |
| 760/377/150 | 2~3 | 0 | 0 | 0/0/1 | 真空白 |
| 78/89/79/22 | 17~19 | 7~10 | 6~9 | 272~512 | 量大仍低（卡检测段） |

**结论修正**：这些族语言分布已均衡（862: py44/java26/php19/js16/go7），缺的不是量、不是语言
覆盖，是**形态**——训据是蒸馏「教科书形态」，测试是真实 CVE 代码。
**改法**（0927 复核修正，修污染风险）：不再对以上族新增合成样本；**三集 FN 清单
（附录 A，~30 例）只做形态规格（spec），本身不进训据**——按清单给出的 CWE×形态，
另挖**实例不相交**的其他 CVE（取对应修复 commit 的修复前代码）造近邻对（同一蒸馏管道、
过防御反证门）。
> 修正理由：初稿「从三集 FN 清单 + 对应 CVE 修复前代码直接造近邻对」会把考卷同源代码
> 带进训据——cvefix 的源 CVE 就是样本本身，87 集是招牌指标集，rolling_dev 是
> held-out 新鲜度纪律集（至今零训后复测消耗）；训据一经混入，α07 与 α05/α06 不可比，
> rolling_dev 一次性报废。
**入册门**：新批次过簇审计——对 87/cvefix/rolling_dev 三集做词集 Jaccard / n-gram
查重（9967 泄漏簇同款检测手法，阈值沿用簇审计现行口径），**零重叠才入册**。
补样来源 = 形态规格清单（FN 逐例的 CWE×语言×sink 形态）+ §5.3-2 的框架习语形态
（Next.js/middleware）与 N2 真实防御形态谱；补样过程中三集样本只读不训。

### 3.3 裁决任务监督从 0.9% 规模化 + 升级为原生多候选 schema

**证据链**（修正 0927 初稿"零监督"的说法）：
- α05 训据（08-07 冻结）：裁决形态 **0 行**——α05 时代的「切片裁决 4/5 推翻污点链」
  （0824 弱点挖掘报告 §十）完全没有数据侧修复，靠的是 prompt 侧 ②a 证据消费条款
  （`build_triage_prompt` 逐段核验，已落地）硬顶；
- v2_26：有 **96 行**单候选验证形态（含 0824 报告蒸馏的 37 条证据消费演示及其后波次，
  157 行含"逐段核验"CoT 风格），但 schema 已转为主扫描 `has_vulnerability`，
  **原生多候选 `is_confirmed` 为 0 行**；占比 0.96%；
- 评测结果：v2_26 带着这 96 行训练的 α06，对型候选确认率反而比 0 行监督的 α05
