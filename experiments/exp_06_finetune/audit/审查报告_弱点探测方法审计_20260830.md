## 一、逐项核查结论

### 1. 探测对象：✅ 明确是已 SFT 的 alpha05，⚠️ 缺 base 对照

- 证据：报告头部口径"evaluate.py 单条贪心解码、system=alpha05 训练原版、
  无工具层参与；Qwen3-8B NF4 + adapter_alpha05_stage2"——探测对象明确为
  SFT 后模型（alpha05），弱点集就是"当前可改进模型"的弱点，方向正确。
- **缺口**：base（Qwen3-8B 原始权重）从未用同口径探过。后果：FPR 0.595、
  CWE-78 塌缩 57% 这类退化无法区分"基座固有"还是"SFT 教出来的"——
  这决定修法（基座固有 → 补知识数据；SFT 退化 → 改配比/改教学方向）。
  两者的数据修法完全不同，混着修就是浪费切片。

### 2. 语言分布：✅ 模型层不偏科，⚠️ 两个登记缺口

- 模型层探测语言条数（本次独立复核 manifest）：
  rolling_dev 50 = **JS 7 / Python 13 / Go 14 / PHP 8 / Java 8**；
  real_safe 47 = JS 7 / Python 13 / Go 11 / PHP 8 / Java 8。
  五语言均衡，且 §13.1 补了分语言指标（Java recall 2/8、JS 2/7 最弱，
  PHP FPR 6/8 最高）——偏科检查该做的都做了。
- 缺口一：**工具层探测暴露真偏科**（train_pool 291：PHP 覆盖 4%、Go 5%、
  Python 33%，Go+PHP 占语料一半）——模型层/工具层两本账，工具层的语言
  偏科已列为补丁驱动挖掘的输入，无新动作。
- 缺口二：**C/C++ 全流程无探测格子**（训练语料、87 段、rolling_dev 均无）。
  若部署声明范围限五语言则不算缺陷，但须在探测矩阵登记为"范围外格子"，
  论文写明范围声明，防止答辩被问"为什么不测 C"。

### 3. 假阳性率：✅ 已测，全流程最强环节

- real_safe 47 条（离线补丁重建）、FPR 0.595 [0.452, 0.738]（bootstrap CI）、
  FP 25/25 逐条人工复核（0 条口径问题）、第一根因=防御未识别 11/25、
  与翻转失败 16/20 同源确认——方法论上无懈可击。
- 缺口：训后无复测（见第 7 项闭环）；FP 探测的安全形态只有"修复版 CVE"
  一种（real_safe 的 safe 定义=修复了原 CVE），"天然无洞的普通代码"形态
  未独立成层——优先级低，real_safe 的配对设计已部分覆盖。

### 4. 过度拒答：❌ 完全没测

- `analyze_mining_run.classify()` 只有 parse_fail_truncated / parse_fail_format /
  FN_cwe_mismatch / FN_wrong_direction 四类；evaluate.py / compute_mining_stats
  全文无 refusal/拒答逻辑。模型 raw_output 里的"无法确定…"字样存在但从未聚合。
- 现实风险评估：当前任务是代码审计判断（非攻击载荷生成），qwen3-8B 系拒答
  概率低；但**"弃权式保守"**（"信息不足无法判定"）是另一个真实风险形态，
  两阶段管线里 review 率 32% 已经是它的管线层表现，模型层从未单独量化。

### 5. 多漏洞 / 非模板鲁棒性：❌ 探测侧零覆盖（训练侧已有响应）

- 多漏洞：rolling_dev manifest 50 条**全部单一 expected_cwe（本次复核=0）**，
  "只报第一个就停"这一弱点在模型层从未探测。训练侧反而有响应切片
  （v2_14 g14_priority / g17_priority_authz + 教师"按危害可达性取主类型"
  通用规则）——**切片跑在探测前面**，训后无法验证切片是否起效。
- 非模板问法：mining 用单一固定组态（system=alpha05 原版 + 固定 user 模板）；
  13 个 system variant 消融全部是 08-12~16 alpha05 时代旧集合产物；
  无 paraphrase/格式扰动/误导注释鲁棒性测试。§8.7 的双组态对比
  （bypass_03 票型翻转）是"扰动敏感性真实存在"的证据点，但那是 2 个组态的
  事后对比，不是系统探测。

### 6. Held-out 探针：⚠️ 半齐——L1 级合格，L2 级未建

- 合格部分：rolling_dev 50（2026 真实 CVE、冻结、0 重叠）+ real_safe 47
  是合格 held-out；泄漏门在跑（v2 冻结 31 剔除）；train_pool 按 CVE 哈希
  留出 20% 有明文纪律。**至今零训后复测消耗——held-out 的"新鲜度"还在**。
- ❌ L2 手写探针（框架习语 / 跨文件 / 无污点硬安全 / minimal pair——恰是
  L1 固有测不到的盲区）明确"尚未手写"（考卷簇制度 20260828 §六原文）；
  `tool_blindspot_hint` 只是规划中的验收通道名，无实体。
- ⚠️ 风险：`corpus/blindspot_teaching_wave.jsonl`（104 条）是**训练教材**
  （SFT 用），无 held-out 标记——若训后把它当探针复测即自欺
  （教材即考卷）。
- L3 时间盲测：制度有、实体无（未到时间点，不算缺口）。

## 四、闭环断点判定

```
弱点 → 切片 → 训练 → 复测
 ✅     ⚠️      ❌      ❌
```

- **弱点→切片**：大体齐（19 组 repair_wave + 五轮冻结），但**账本未核销**
  （G7）：映射停在 08-25 的行动映射，v2_13→v2_14 的组没有回写；N1/N2 两处
  真断（G6）。
- **切片→训练**：❌ **断在这里**——alpha06 从未开训（最新权重仍是
  adapter_alpha05_stage2；训练脚本与 12288 断言就绪，"随时可训"）。这是
  执行未到，不是方法论缺陷；但 A1/A2/A8 三件训前必做的事没做就开训，
  会把 G2/N1 带进"训后无法验证"的状态。
- **训练→复测**：❌ 未建——复测的**验收线已定**（审查与执行记录 §五：
  loose recall 不回退、FPR ≤0.12、strict ≥0.87、专项 3×temp 稳定命中），
  但**执行条件不具备**：L2 探针不存在（G2）、拒答字段不存在（G4）、
  复测脚本未预置（A6）。现在的状态是"考试标准写好了，考卷还没出"。

**一句话结论**：探测与切片两环质量高（FPR 测量与 FP 逐条复核是同类工作里
少见做得这么实的），真正的断点在"训练未执行"与"复测未备卷"——开训之前
必须补上 A1/A2/A8，否则训后那一刻就会发现：最大的两个根因（N1 sink 词表、
N2 防御识别）没有切片可验，L1 盲区没有考卷可测。
