## 二、对账报告的 4 处事实修正（实测）

### 2.1 「CWE-77 被治反了」——机制反了，结论要改

**报告说**：`ALLOWED_REWRITES` 把 77 批量改成 78 → 77:78 从 0.763 崩到 0.002，是"把缺陷治反了"。

**实测（脚本 `_plan_diag4` / `_plan_diag8`）**：

| 项 | 实测值 |
|---|---|
| alpha05 的 CWE-77 | 174 条，**174 条代码指纹全部唯一**（无重复冗余） |
| 这批代码在 v2_23 的存活 | 151 条（87%），**其中 147 条被标为 CWE-78**、2 条 neg、1 条 22、1 条 918 |
| 另 23 条 | 确实不在 v2_23（在 v2_2 重建期未进池） |
| **147 条的 sink 形态机判** | **131 条（89%）纯 OS-shell**（`eval` / `sh -c` / `bash -c` / `shell=True` / `execSync(shell:true)` / `exec()` / `system()` / `Runtime.exec` / `ProcessBuilder`） / 16 条混合待人工 / **0 条判为非 OS 命令语言** |

**抽样 12 条逐条读码**（v2_23 idx 237/252/254/258/259/262/264/265/268/270/286/287）：sink 全部落在 shell 路径，仅 idx 252 的 `tar -czf` 属参数注入边缘。

**结论（与报告相反）**：
1. `ALLOWED_REWRITES` 的 77→78 **是做对了的错标纠正**，不是编码破坏。alpha05 的"77"里 75%（131/174）本来就是 shell 注入。
2. 真正的事实是：**alpha05 的 77 从来不是有效的近邻对**。模型在 alpha05 上"TP 57% 编成 78"，机制不是"塌缩"，而是**训练数据把 77 和 78 教成了同一个东西**。
3. 所以**回改 147 条是错的方向**——会把已经改对的标签又改错。77 的量只能靠**新造真 77**（形态：sed 脚本 / IMAP·SMTP 命令 / SNMP / MVG 图形语言 / ffmpeg 滤镜图 / LDAP Filter / XPath / 应用配置语言）。

### 2.1b 「双重 buff」的定量论证（Garry 2026-09-14 提出，已量化）

> Garry：*"坍缩到某个类型大概率是**数据质量不够**和**配比过于极端**的双重 buff"* —— 实测确认，**两面都是必要条件**。

| 面 | 实测 | 缺了它会怎样 |
|---|---|---|
| **质量面** | 77 侧 9 条里 7 条是 g26 合成、2 条 alpha05 遗留；**238 个 kit 里没有一个真 77**（标称的 5 个实测全是 OS shell） | 即使配比拉到 1:1，模型看到的 77 与 78 在 sink 形态上**不可分** → 学出 77≈78 → 仍答 78 |

⇒ **治配比的手段是抬冷门侧，不是砍热门侧**。见 §五 S6/S7。
