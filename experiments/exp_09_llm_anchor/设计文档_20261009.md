# exp_09：LLM 补锚实验——设计文档（2026-10-09）

> 研究问题：**工具召回天花板（rolling_dev50 有锚 13/50）能否用 LLM 全文件复核兜底？**
> 这是"工具层 + 裁决层"两阶段架构的边界实验：当 stage1 零候选时，stage2 的
> no-candidate full_recheck 通道到底能救回多少、代价是多少 FPR。
> 对照基线：semgrep 官方规则本集 recall **0.060**（台账 2026-09-07 条目）。

## 1. 协议

- **对象**：rolling_dev50 中 37 个零锚文件（50 − 有锚 13；清单由
  `exp_02_baseline_tools` 口径的 stage1 扫描结果生成，冻结清单入本目录）。
- **召回模式**：no-candidate full_recheck——全文件等距分块（§1.1 修复后的
  `_prescreen_chunks` 覆盖语义）送裁决层，N=3、T=0.7、ctx16384、full_recheck，
  trust_llm_recheck 开（含 §1.2 分级放行：unverified+T3/F0 autopass 串联守卫）。
- **权重（协议钉死，二选一后不得换）**：
  - 主选：`alpha05-stage2-merged-Q4_K_M`（adapter 合模 + GGUF，转换脚本与哈希入库，
    见《α07 数据配方与验收设计》§8——Ollama 跑不了 LoRA，NF4 不支持 CPU，合模是
    本机 CPU 路线的唯一通路）；
  - 若走 GPU 机组态则用原装 transformers NF4 + adapter，并注明"组态=wave8 同款"。
  - **不得用 v9max 顶替**（发布形态与裁决权重不同代，混用会污染结论归属）。
- **判分双口径**（诚实性设计）：
  - TP：复核全票判真且采信（含 autopass）；
  - 脱离确定性漏报：转 review（任何 review 决策）即计——单独成列，不与 TP 混算。

## 2. FPR 守护（本实验最容易被漏的一半）

无候选全文件复核是 FPR 高危模式（0824 real_safe 47 条离线补丁重建 FPR 0.595 的教训；
§1.1 修复前 safe 侧也有同类风险）。因此 **safe 侧 47 文件必须同组态同步跑**：
- 指标：safe 侧误报数与 FPR；§1.2 自动采信路径（`recheck_unverified_autopass`）在
  safe 侧的开火次数单独列出——**任何一次 safe 侧 autopass 即红线**（T3/F0 全票 +
  sink 守卫仍判真安全文件 = 双护栏同时失效，须停机归因）。
- real_safe 47 条（0824 补丁重建集）若可在本机重建，一并跑——这是"评测 FPR 0.038
  vs 真实分布 FPR"落差的第二个数据点，论文第 4 章诚实性素材。

## 4. 执行步骤（CPU 过夜量级）

1. **前置**：合模 + GGUF 转换（一次性 ~1-2h）→ Ollama 装载 → 1 例冒烟计时
   （预估 ~20-40 min/文件 ×3 票；若 tok/s < 5 则改走 GPU 机，协议组态行相应更新）；
2. 冻结 37 文件清单 + safe 47 清单（本目录 `manifest_*.json`）；
3. 跑 batch（--resume 语义：按文件落盘单文件 JSON，断点续跑）；
4. 汇总 → `results/exp09_*.json` + 本目录结果报告；数字入台账新条目。

## 5. 与其他批次的关系

- **先于 α07 训练**：其结论（补锚收益与 FPR 代价）决定 §1.2 分级放行的阈值是否需要
  收紧，直接影响 α07 评测组态的信任层参数；
- 工具规则流水线（Go/PHP 新规则）若已入库，重跑 stage1 有锚统计——有锚数上升会
  缩小 37 文件清单，实验对象随之更新（清单以当次扫描为准，冻结后不变）。
